File Handling and Modules

A card-by-card walkthrough to lock in reading and writing files, file modes, the with statement, try/except, CSV handling, and importing modules.

🔮 predict before revealing💬 debrief🤖 AI moment✅ takeaway

What this post-read covers

Why programs need files; open() and file modes (r, w, a); the with context manager; reading line by line; writing and appending; try/except; the csv module; creating and importing your own modules; standard library modules; and a cumulative log-analyzer mini project.

01 · the idea

Everything a program knows disappears when it ends

Every program we've written so far has had the same problem: the moment it ends, everything it knew disappears. If we build a to-do list app and store tasks in a Python list, closing the program throws every task away.

tasks = ["Buy milk", "Finish homework", "Walk the dog"]
print(tasks)
🔮 Before you reveal: if we wanted this list of tasks to still be there tomorrow, what would we need to do differently?

We'd need to save it somewhere outside the program's memory — in a file on disk. Python gives us a built-in function, open(), that lets a program talk to a file: read what's already there, or write new content into it.

✅ TakeawayTo keep data around between runs of a program, save it to a file — memory alone disappears when the program ends.
02 · reading files

open() and .read()

open() takes a filename and gives us back a file object we can read from. Calling .read() on it pulls in the entire contents as one big string.

🔮 Predict what this prints — assume notes.txt already contains "Buy milk" and "Walk the dog" 
file = open("notes.txt")
contents = file.read()
print(contents)
file.close()

Buy milk
Walk the dog
📌 NoteEvery file we open needs to be closed when we're done, or the program can leave it locked or lose unsaved changes. Forgetting to close a file is such a common bug that Python gives us a cleaner way to handle it — next card.
03 · file modes

r, w, a — getting this wrong destroys data

Mode Behavior
"r" Read — file must already exist, starts at the beginning.
"w" Write — creates the file if missing, erases existing contents first.
"a" Append — creates the file if missing, adds new content to the end.
🔮 notes.txt currently contains "Buy milk" and "Walk the dog." Predict what it contains after this runs. 
file = open("notes.txt", "w")
file.write("Finish homework")
file.close()

notes.txt now contains only:

Finish homework

"w" mode doesn't add to the file — it erases everything that was there first, then writes fresh. "Buy milk" and "Walk the dog" are both gone.

✅ TakeawayIf the goal is to add a new entry without losing the old ones, use "a" (append), not "w" — this mix-up is one of the most common ways beginners accidentally destroy their own data.
04 · the context manager — with

Closing files automatically

Manually calling .close() works, but it's fragile — if an error happens between open() and close(), the close line never runs. Python's with statement fixes this: it opens the file, runs the code inside, and guarantees the file gets closed afterward, even if something goes wrong inside.

🔮 Predict what this prints, and whether we need a separate file.close() line anywhere 
with open("notes.txt", "r") as file:
    contents = file.read()
    print(contents)

print("Is the file closed now?", file.closed)

Finish homework
Is the file closed now? True

There's no file.close() anywhere in this code, yet file.closed reports True once we've left the with block — the context manager closed it automatically the moment the indented block finished.

✅ TakeawayFrom here on, always use with to open files — it's the standard, professional way to do it in Python, not just a nice-to-have.
05 · reading line by line

A file object is directly loop-able

Reading an entire file as one string is fine for small files, but often we want to process it one line at a time — like checking every line of a log file.

🔮 notes.txt contains three lines: "Buy milk", "Walk the dog", "Finish homework." Predict exactly what this prints, including any blank-looking gaps. 
with open("notes.txt", "r") as file:
    for line in file:
        print(line)

Buy milk

Walk the dog

Finish homework

Each line read from a file keeps its trailing newline character (\n) — and print() adds its own newline on top of that, which is why we get an extra blank line after each one.

📌 NoteThe usual fix is line.strip(), which removes that trailing newline (and any stray whitespace) before printing or storing the line.
06 · writing and appending

Same method, different starting point

We've already seen .write() with "w" mode. The same method works with "a" mode — the only difference is where Python starts writing from.

🔮 notes.txt currently contains "Buy milk", "Walk the dog", "Finish homework." Predict what it contains after this runs. 
with open("notes.txt", "a") as file:
    file.write("Call the vet\n")

notes.txt now contains:

Buy milk
Walk the dog
Finish homework
Call the vet

"a" mode added the new line onto the end without touching what was already there — unlike "w" mode, which would have erased everything first.

📌 NoteNotice the \n at the end of the string we wrote — write() doesn't add line breaks automatically the way print() does, so if you want each write() call to land on its own line, you have to include \n yourself.
07 · try/except

Catching an error instead of crashing

So far, whenever something has gone wrong — a missing file, bad input — Python has just crashed with a red error message and stopped. try/except lets us catch that error ourselves and decide what the program should do instead.

🔮 missing.txt does not exist. Predict what happens when this runs. 
try:
    with open("missing.txt", "r") as file:
        print(file.read())
except FileNotFoundError:
    print("That file doesn't exist yet — creating it now.")

That file doesn't exist yet — creating it now.

Without the try/except, this program would have crashed with FileNotFoundError and stopped completely. With it, the program noticed the specific problem and kept running with a sensible fallback.

✅ Takeawayexcept FileNotFoundError only catches that one specific kind of error — a bare except: would catch anything, including bugs you'd actually want to see, so naming the specific exception is the safer habit.
08 · handling errors gracefully

Different responses for different problems

A try/except block can have more than one except clause, so we can respond differently depending on exactly what went wrong.

🔮 Predict which except block runs for each of the two calls below 
def read_notes(filename):
    try:
        with open(filename, "r") as file:
            return file.read()
    except FileNotFoundError:
        return "Error: file not found."
    except PermissionError:
        return "Error: not allowed to read this file."

print(read_notes("notes.txt"))
print(read_notes("secret_diary.txt"))

Buy milk
Walk the dog
Finish homework
Call the vet

Error: file not found.

notes.txt exists, so the function returns its contents normally. secret_diary.txt doesn't exist, so Python raises FileNotFoundError, and our except catches it and returns a friendly message instead of crashing.

📌 NoteOrder matters when you have multiple except clauses for related exception types — Python checks them top to bottom and uses the first one that matches, so put more specific exceptions before more general ones.
🤖 AI momentOnce read_notes() works, ask an AI assistant: "I'm opening and reading a text file in Python. Besides FileNotFoundError and PermissionError, what other exceptions might realistically happen here, and should I catch all of them or let some crash the program?" Then independently verify: deliberately trigger one of the exceptions it mentions (e.g. try opening a folder name instead of a file) and confirm it isn't silently caught by your existing except clauses. Catching an exception you don't have a real response to often just hides a bug.
09 · csv file handling

Reading structured data properly

A lot of real-world data — spreadsheets, exported reports, database dumps — comes as CSV: comma-separated values, one row per line. We could split each line on commas ourselves, but that breaks the moment a value contains a comma. Python's csv module handles those edge cases for us.

🔮 students.csv contains: "name,grade" then "Rex,A" then "Priya,B" then "Rahul,A". Predict what this prints. 
import csv

with open("students.csv", "r") as file:
    reader = csv.reader(file)
    for row in reader:
        print(row)

['name', 'grade']
['Rex', 'A']
['Priya', 'B']
['Rahul', 'A']

csv.reader() gives us each row as a plain list of strings, split on commas automatically — including the header row, which this code hasn't treated specially yet.

📌 Notecsv.DictReader() is often more convenient — it uses the first row as column names and gives you each row as a dictionary, like {'name': 'Rex', 'grade': 'A'}, so you can access row['grade'] instead of remembering which index the grade is at.
🔮 Predict what scores.csv will contain after this program runs 
import csv

rows = [["name", "score"], ["Rex", 92], ["Priya", 88]]

with open("scores.csv", "w", newline="") as file:
    writer = csv.writer(file)
    writer.writerows(rows)

scores.csv now contains:

name,score
Rex,92
Priya,88

csv.writer().writerows() takes a list of rows and writes each one as a properly comma-separated, newline-terminated line — including converting the number 92 to the text "92" automatically.

📌 Notenewline="" in the open() call is a small but important detail on some systems — without it, csv can end up writing an extra blank line between every row. Always include it when writing CSVs.
10 · creating your own module

Every .py file is already a module

We just haven't been reusing them from other files yet. Say we have helper functions we want to use across several scripts, instead of copy-pasting them into each one. Imagine a file called greetings.py:

# greetings.py

def say_hello(name):
    return f"Hello, {name}!"

def say_goodbye(name):
    return f"Goodbye, {name}!"
📌 NoteThere's nothing special about this file syntactically — it's ordinary Python. What makes it a module is simply that another file is going to import it by name.
11 · importing modules

Pulling functions in with import

🔮 Predict what this prints, assuming greetings.py is in the same folder 
import greetings

print(greetings.say_hello("Rex"))

Hello, Rex!

Notice we had to write greetings.say_hello(...), not just say_hello(...) — a plain import keeps everything inside its own namespace, named after the module, so it's clear where a function came from.

from greetings import say_hello        # bring in just one function directly
print(say_hello("Fido"))               # no "greetings." prefix needed now

import greetings as g                  # give the whole module a shorter nickname
print(g.say_goodbye("Fido"))

from greetings import *                # bring in everything — generally discouraged
📌 Notefrom module import * grabs every public name from the module directly into your file, which is convenient but risky — if two modules define a function with the same name, one silently overwrites the other with no warning. Prefer import module or from module import specific_name in real code.

13 · mini project

Log File Analyzer

Combine every idea from this class: read a CSV of website visit records, handle a missing file with try/except, count error requests (status code 400+), and write a summary out to a new file.

🔮 visits.csv contains: "page,status_code" then "/home,200", "/login,200", "/admin,403", "/checkout,500". Predict all printed lines and what summary.txt will contain. 
import csv

def analyze_visits(filename):
    try:
        with open(filename, "r") as file:
            reader = csv.DictReader(file)
            rows = list(reader)
    except FileNotFoundError:
        print(f"Error: {filename} not found.")
        return

    total = len(rows)
    errors = [r for r in rows if int(r["status_code"]) >= 400]

    print(f"Total requests: {total}")
    print(f"Errors: {len(errors)}")

    with open("summary.txt", "w") as file:
        file.write(f"Total requests: {total}\n")
        file.write(f"Errors: {len(errors)}\n")

analyze_visits("visits.csv")

Total requests: 4
Errors: 1

summary.txt now contains:

Total requests: 4
Errors: 1

Only /admin,403 and /checkout,500 count as errors, since 403 and 500 are both greater than or equal to 400 — while /home,200 and /login,200 don't.

✅ TakeawayThis program uses every core idea from the class: try/except around the risky file-open, with as the context manager for both reading and writing, csv.DictReader() to read structured data by column name, and writing a plain text summary with the correct mode.
14 · final recap

The one idea to leave with

open(filename, mode) r / w / a │ ↓ with ... as file: (auto-closes, even on error) │ ┌────┴────┐ ↓ ↓ READ WRITE .read() .write() csv.reader csv.writer loop │ ↓ try / except (catch, don't crash)

Files let a program's data survive after the program itself ends. open() takes a mode — "r" to read, "w" to overwrite, "a" to append — and getting the mode wrong is one of the easiest ways to accidentally lose data. The with statement is the standard way to open a file, because it closes the file automatically, even if something goes wrong inside the block. try/except lets a program catch a specific problem, like a missing file, and respond sensibly instead of crashing. The csv module handles comma-separated data properly, including edge cases plain string splitting would get wrong. And any .py file is already a module — import lets us reuse functions across files, and Python's standard library means an enormous amount of functionality is already sitting there, ready to import.
