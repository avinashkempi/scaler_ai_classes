Tableau 5 · Operations on dataset

Bringing multiple data sources together in Tableau

Real business data almost never lives in one table — sales sits in one system, returns in another, employees in a third. This article walks through the four ways Tableau lets you combine them: Joins, Relationships, Unions, and Data Blending, plus the special case of Cross‑Database Joins — and, most importantly, how to choose the right one.

Join — adds columns Relationship — keeps tables separate Union — adds rows Blend — combines sources in a view Cross‑database join
Sheet · Overview
Foundations

Five ways to combine data

Every combination method answers a different question: are the tables in the same place, do they share a structure, and do you need row‑level detail or just a quick comparison? Tap a card below to see what each method actually does before diving into the details.

Each method trades off differently between flexibility, row‑level detail, and how tightly the underlying data needs to be connected. The rest of this article works through each one, with the reasoning and pitfalls that matter when you're deciding which to reach for.

Sheet · Join
Method 1

Join

The data you want to analyze is often a collection of tables related by specific fields. Joining combines the related data on those common fields — and the result is typically a table extended horizontally, by adding columns.

Analogy Think of two paper registers at a school. One has student names and roll numbers; the other has roll numbers and exam scores. To get a single report of names alongside scores, you'd look up each roll number and write the data side by side — that's exactly what a join does. The roll number is the common field, and the combined register is the joined table. If a student appears in the first register but never sat the exam, their score is missing: an inner join would drop that student entirely, while a left join would keep the student with a blank score.

Reach for a join when…
  • Both tables are in the same data source and you need one flat combined table.
  • You need explicit control over the join type (inner, left, right, full outer).
  • You're working with custom SQL.
Avoid a join when…
  • Tables have very different granularity (one row per customer joined with many rows per order) — this causes row duplication.
  • You'd rather Tableau manage the join logic automatically — use a Relationship instead.

Worked example: CO₂ emissions by country

Business problem: find CO₂ (kt) and CO₂ per capita for each country, filtered to the top 10 countries by CO₂ (kt), using World_Bank_CO2.xlsx. The information the business needs — country name, CO₂ (kt), and CO₂ per capita — is split across two tables that both share Country Name, so they're joined on that common field before building the view.

The pitfall: row duplication

When tables are joined at different levels of granularity — say, one row per order joined against a returns table where some orders were returned more than once — the join produces one output row per match. If an order matches three return entries, that order's row (and its Sales value) appears three times.

Always verify row counts and key metrics after a join; an unexpected increase usually means a one‑to‑many or many‑to‑many match. This is exactly the problem Relationships were introduced to solve.

Working with Join · maps

Geographic data type & maps

Depending on the map you want to build, fields need the right data type, data role, and geographic role. Latitude and longitude fields should typically be a decimal number, a measure, with the Latitude / Longitude geographic roles assigned. Every other geographic field — country, state, postal code — should be a string, a dimension, with the matching geographic role.

When a field has the correct geographic role, Tableau matches its values against its built‑in geocoding database to plot them on a map — that's how it knows where each location belongs. A globe icon on a column means a role is already assigned; otherwise it can be assigned manually from the field's data‑type menu.

Try it: fix a broken postal code field

Tableau sometimes assigns a Postal Code column a Number (whole) data type. That breaks map views — leading zeros in postal codes get silently dropped, and no geographic role can be attached to a numeric field.

Keep in mind when building a map
  • Latitude/longitude fields: numeric (decimal) data type, measure role.
  • Country, city, state fields: string data type, dimension role.
  • Tableau auto‑assigns geographic roles based on field name and values where it can.
  • No latitude/longitude in the source? Maps can still be built from geographic fields like country or state alone.

Importance of maps

Location data enhances the insight you can pull from a dataset and presents it more intuitively than most other chart types — useful for spatial questions like state‑wise sales, which states have the highest profit, or where a particular product sells best.

Method · Cross‑database join

Cross‑database join

A cross‑database join joins two or more tables that live in different databases using a common field, producing a single table in Tableau that visualizations can be built from. It requires a multi‑connection data source — a separate connection to each database, created before the tables are joined.

Worked example: highest and lowest‑selling sub‑categories

Business problem: identify the sub‑categories with the highest and lowest sales, using Retail_store_order_details.xlsx (Excel) and Retail_store_product_details.csv (CSV). Sales lives in one file, product/sub‑category information in the other — different file formats, but joinable because they share Product ID.

Recipe
  1. Load both files as separate connections in one data source, then inner‑join order_details and product_details on Product ID.
  2. Sub‑Category is a dimension being grouped, so it goes on Columns; Sales is a measure being aggregated (SUM), so it goes on Rows.

Sheet · Relationship
Method 2

Relationship

Joins combine two tables into one flat table at the physical level — powerful, but when tables sit at different levels of granularity (an Orders table with one row per order, a Returns table with fewer rows), the result can duplicate data and inflate metrics, as seen above. Relationships solve this: they connect tables logically without forcing them into one flat table, and Tableau joins them on the fly, only when a visualization actually needs it.

  • A dynamic, flexible way to combine data from multiple tables for analysis.
  • No join type to define — there's no Venn diagram, because tables aren't merged.
  • Describes how two tables relate based on common fields, without merging them.
  • Each table keeps its own level of detail and domain.
Analogy A company has two departments: Sales keeps a detailed transaction log; HR keeps a list of employees with department and salary. Physically merging these into one spreadsheet would repeat each employee's salary on every one of their transaction rows — wasted space and confusion. Instead, keep both registers separate but connected by Employee ID, and look up the relevant information only when a question needs both. That's what a Relationship does: the data stays in separate tables, and Tableau fetches what it needs only when the visualization requires it.
Reach for a relationship when…
  • It's your default — Tableau's recommended approach for combining tables since version 2020.2.
  • Tables sit at different levels of granularity and you want to avoid row duplication.
  • You want Tableau to determine the correct join type automatically, at query time.
Avoid a relationship when…
  • You need custom SQL.
  • You require a specific join type that Tableau's automatic logic won't produce.
  • You're working with a legacy workbook that relies on explicit join behavior.

Sheet · Union
Method 3

Union

Though it isn't a type of join, a union is another way to combine two or more tables — by appending rows from one table after another, extending the data vertically.

Analogy Think of a diary of daily expenses, with a new page for each month — January, February, March — all sharing the same columns: Date, Item, Amount. To see a full year of spending, you don't match rows between pages; you simply stack all twelve pages together. That's a union.

For a union to work cleanly, the tables need the same number of fields, the same field names, and fields of the same data type.

Join vs. Union

JoinUnion
Combines related tables using a common fieldAppends rows from two or more tables
Extends data horizontally — adds columnsExtends data vertically — adds rows
Requires a common field between tablesTables must have the same fields, in the same number and order
Types: inner, left, right, full outerAppends data vertically; does not match rows
Best when combining related data and seeing more detail in the same rowBest when combining similar data from different periods or sources
Reach for a union when…
  • Tables share the same (or a very similar) structure and represent different subsets of the same data — time periods, regions, or categories.
  • You need to append rows vertically into one continuous dataset.
Avoid a union when…
  • Tables have different structures or represent different entities — don't union an Orders table with a Customers table.
  • You need to combine tables horizontally — use a Join or Relationship instead.
Sheet · Blend
Method 4

Blend

Joins, Relationships, and Unions all combine data within the same Tableau data source — even one with multiple connections, as in a cross‑database join. Data Blending is different: it links data from completely separate Tableau data sources at the visualization level, without physically combining the underlying data. It brings in additional information from a secondary source and displays it alongside the primary source, directly in the view.

Analogy Planning a trip: flight information lives in one airline's app, hotel booking in a different app, the local tour schedule on a travel website — three systems with no connection to each other. But mentally, you link them by date: on April 10th, the flight lands at 2 PM, hotel check‑in is at 3 PM, the city tour starts at 5 PM. That's blending — combining separate sources using a shared field, here the date, without ever merging the underlying systems.

A LEFT JOIN is created between the primary and secondary source, based on common dimensions (the linking field). All records from the primary source are retained; matching data from the secondary source is added, and unmatched values return as null.

Worked example: Olympic medals vs. CO₂ per capita

Business problem: for each country, find the total Olympic medals won and CO₂ per capita emissions through 2008 — using Modified Summer Olympic Medallists 1896‑2008.xlsx and World_Bank_CO2.xlsx, two entirely separate workbooks. Since these datasets are meant to stay separate and only need to be compared within one view, a join isn't the right tool here — this is a blending problem, linked on Country Name.

Brazil has no matching row in the secondary source, so its medal count returns null — the primary source's fields still define the level of detail. Country names can also differ across sources (for example, "United States" vs. "USA"); when that happens, Tableau flags the linking field and an alias can be set on the mismatched value so the two sources line up correctly.

Reach for blending when…
  • Data lives in completely separate Tableau data sources that can't be connected within one multi‑connection source.
  • You need a quick comparison between two sources without restructuring your data model.
Avoid blending when…
  • Both datasets could be brought into the same data source — use a Join or Relationship instead.
  • You need row‑level detail from the secondary source (blending always aggregates it).
  • Performance is critical — blending can be slow on large datasets.

Sheet · Summary
Recap

Quick summary

There are several ways to combine data, each with its own strengths and trade‑offs.

Join

Combines tables side by side using a common field — more columns, established before analysis begins. Can duplicate or drop rows when granularity differs.

Adds columns

Relationship

The default and most flexible method. Adapts to each sheet's analysis, works across tables at different levels of detail, without duplicating rows.

Keeps tables separate

Union

Stacks tables with identical structure on top of each other — more rows, for data split across time periods, regions, or categories.

Adds rows

Blend

Queries each data source independently, aggregates the results, then presents them together in one view. Handles different levels of detail and separate sources, including published data sources.

Combines sources in a view

In professional practice: prefer a Relationship as your default. Reach for a Join only when you need explicit control over join type or custom SQL. Use a Union when tables share a structure and you're stacking rows. Fall back to Blending only when the data truly can't live in the same source.
