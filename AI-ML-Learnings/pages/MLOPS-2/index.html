00 Introduction

The debt this session pays

The previous session closed on six MLOps principles, with "version everything" holding up the other five — and nothing implemented. This session pays that debt. Everything is worked at the command line, in real repositories, broken on purpose and repaired.

It starts from what version control is and why copying files does not work, assumes no prior Git experience, and builds up to something you can reason about rather than a save button you press and hope. The last third covers what changes when a repository holds an ML project rather than an application, and it ends by measuring the thing that makes this an MLOps problem: datasets and model binaries cannot live in Git, and pretending otherwise is how teams end up with a repository nobody can clone.

THE OPEN QUESTION

Which exact data and which exact code produced this exact number?

Today answers the code half of that question, precisely. The data half — why it needs a different tool entirely — gets measured, not just asserted, in the closing sections.

01 Why version control exists

The folder everyone has produced

You have a folder with a training script and a notebook. You try something, it works, you keep going. Two weeks later the folder looks like this:

folder listing
analysis.ipynb
analysis_v2.ipynb
analysis_final.ipynb
analysis_final_FIXED.ipynb
analysis_final_use_this_one.ipynb
train.py
train_old.py
train_backup.py

The trouble is not that it's ugly. The trouble is the questions it can't answer, all of which you will genuinely need answered:

Which file is the source?

Which file produced the accuracy number you put in the slide deck?

What actually changed?

What changed between final and final_FIXED, and why?

Whose version wins?

Your teammate edited analysis_final.ipynb at the same time as you.

When did it break?

Something worked Monday and is broken today. What happened in between?

A copy records the state of a file and nothing about the change — not when, not who, not why, not what it looked like before. All four questions are questions about change, which is why no amount of careful file naming will ever answer them. A version control system records the change. You keep one analysis.ipynb, and the history of every edit lives alongside it.

What Git actually is

Git is a program you run on your own machine. Point it at a folder and it records snapshots of that folder on request. Three things about that sentence surprise most people:

Whole-folder, not per-file

The unit of work is your project. There's no such thing as the history of one file in isolation.

Only records on request

Git is not an autosave. You decide when the project is worth remembering, and you say so.

Entirely local

Everything Git knows sits in a hidden .git folder. Delete it and you have an ordinary folder again.

No account required

Git is usually introduced through GitHub, but you can use Git for years, alone, with no account anywhere.

Git is not GitHub

What it is
GitA version control program that runs on your machine.
GitHubA website that hosts copies of Git repositories.

Git is the tool. GitHub is one of several places (GitLab, Bitbucket, Azure Repos) where a team keeps a shared copy, so everyone has an agreed destination for their work and an agreed source for everyone else's. The practical consequence: most of what follows in "What Git stores" and "The everyday workflow" needs no account, no network, and no login. GitHub becomes relevant the moment a second person is involved.

02 What Git stores

The picture that makes the commands obvious

Almost all beginner pain with Git comes from carrying an inaccurate picture of what the commands operate on. The commands themselves are short — they're also unforgiving about that picture, and give unhelpful errors when it's wrong. Four claims, in order, and the everyday commands become consequences rather than incantations.

A repository is your folder, plus .git

A repository is a project folder that Git is tracking, together with its history. git init turns an ordinary folder into one — and creates exactly one thing, the .git folder, leaving your project files untouched beside it.

-b main names the first branch main. A branch is a line of commits with a name attached, and main is the conventional name for the line holding a project's accepted work. git status is the command you'll run more than any other — read it as the answer to "where am I, and what have I got?"

A commit is a snapshot, not a diff

People describe Git as storing changes. It does not. A commit stores a complete listing of your project at one moment, plus a pointer to the commit before it, plus who made it and why. Git shows you diffs by comparing two snapshots — what it keeps is the snapshots.

The name of a commit is a SHA-1 hash of all of that content, which is why commit IDs look like a3f9c21. Change one byte of a file, the message, or the parent, and you get a different name — the reason a commit SHA works as a name for "the code that produced this model."

WRITING A COMMIT MESSAGE

Write it in the imperative — "add baseline training script," not "added." Git quotes messages back inside sentences it generates itself, like Revert "Add baseline training script", and the imperative is the form that reads correctly there. Spend the words on why, since the diff already records what changed. A feat(train):-style prefix is optional and cheap, and it makes a long log skimmable.

first commit, and the object Git wrote
mkdir -p src
printf 'print("baseline model")\n' > src/train.py
git add src/train.py
git commit -q -m "feat(train): add baseline training script"

git cat-file -p HEAD
tree a1b2c3d author MLOps Student <student@example.com> 1699999999 +0000 committer MLOps Student <student@example.com> 1699999999 +0000 feat(train): add baseline training script

The commit points at a tree — a directory listing, not a diff. It carries an author, a committer, a message. No parent line yet, because nothing came before it. A second commit adds that line, and it's what makes history a chain: git log is just a walk backwards from HEAD, nothing cleverer. src/train.py itself is stored as a blob named by a hash of its bytes — two files with identical content anywhere in history share a single blob. Git is a content-addressed store, and that one design choice is the source of both its strengths and its unsuitability for data, measured later in this reading.

A change lives in one of three places

Here's where the confusion actually lives. Between your editor and your history there are three separate stores. Explore what each command moves below.

Working directory
files you're editing
Staging area
the next commit, being built
Repository (.git)
committed history, permanent
Remote (GitHub)
the shared copy
Click a command to see which trees it moves data between.

git status reports on all three local trees at once, which is why its output has a three-block shape:

  • Changes to be committed — staging area against the last commit.
  • Changes not staged for commit — working directory against staging.
  • Untracked files — everything Git has never been told about; invisible until added.

The two forms of diff split the same way: git diff shows what you have not staged; git diff --cached shows what you have. If git diff prints nothing while git status insists you have changes, everything is staged.

A branch is a pointer, not a copy

A branch is physically a 41-byte file containing a SHA. Creating one copies nothing — it writes a new pointer at your current commit, which is why branching in Git is instant. HEAD points at a branch, which points at a commit. Checking out a specific commit directly (rather than a branch name) puts you in a detached HEAD — not an error, just standing on a commit rather than a branch. A commit made there is still reachable even with no branch name pointing at it, which matters later when recovery comes up.

The loop, now that you know what it moves

Everything above assembles into one short cycle. A change moves left to right through four places:

StepCommandMoves
1git add <files>Working directory → staging area
2git commit -m "why"Staging area → local repository
3git pushLocal repository → remote (GitHub)
4git pullRemote → local repository → working directory
03 The everyday workflow

Staging with intent, undoing safely, merging

This is the loop you'll run hundreds of times a week: change something, look at what changed, stage a coherent piece of it, commit with a message that explains why, eventually share it.

Staging and committing with intent

git add . is a habit to break early. Stage selectively and git log becomes a readable account of the project. Stage everything and it becomes a diary of your interruptions.

ONE COMMIT, ONE IDEA

This is what the staging area is for: you edit six files and choose which three belong together. If a commit message needs the word "and," you probably wanted two commits.

Undoing things safely

Four commands do four different jobs, and choosing the wrong one is how people lose work. Learn them as a set — the dividing line is whether anyone else has seen the commit.

CommandWhat it does
git restore <file>Throws away working-directory changes.
git reset --soft HEAD~1Undoes the commit, keeps changes staged.
git reset --mixed HEAD~1Undoes the commit, keeps changes unstaged.
git revert <sha>Adds a new commit that reverses an old one.

reset rewrites history and belongs to commits you haven't shared. revert adds history and is correct for anything already pushed, because it doesn't lie about what happened — it records that you changed your mind. There's also git reset --hard, the one Git command that can genuinely destroy uncommitted work.

Branching and merging

Merges come in two shapes, and telling them apart from a graph is a useful reflex. Toggle between them below.

main has not moved since the branch was cut — Git slides the main pointer forward. No merge commit, history stays a straight line.

A merge conflict, on purpose

Far better to meet conflict markers here than at 6pm on a Friday. Conflicts are normal — not a sign you did something wrong, or that Git is broken. A merge conflict is Git declining to guess between two changes to the same lines. The only real failure mode is resolving one carelessly.

RUNNING.md — during a conflict
Run:
<<<<<<< HEAD
python src/train.py --config configs/train.yaml
=======
python src/train.py --n-estimators 100 --max-depth 4
>>>>>>> docs/run-with-flags
<<<<<<< HEADEverything below this, down to the divider, is the version already on the branch you're standing on.
=======The divider between the two competing versions.
>>>>>>> docs/run-with-flagsEverything above this, up to the divider, is the version coming in from the branch being merged.

git status --short reports UU RUNNING.md — U on both sides means unmerged from both, because each branch modified this file. In real projects the answer is very often "both changes are valid." Resolving is not picking a winner; it's writing the version the team actually wants, then deleting the markers, git add-ing the file, and committing.

Try it yourself — Checkpoint 5.1
  1. Initialise a repository, make three commits, then produce a git log --oneline --graph you'd be happy to show a reviewer. Make a fourth commit with the message wip and undo it with reset --soft, keeping the work. Why it matters: reset --soft is what lets you commit early and often without leaving a mess behind.
  2. Create two branches from main that edit the same line of the same file. Merge one, then the other, and resolve the conflict so the final file keeps both intentions. Why it matters: the first conflict you resolve shouldn't be one that matters.
  3. Run git status at four points: clean, after an edit, after git add, and after git commit. Predict each output before you look. Why it matters: if you can predict git status, you have the three trees; if not, memorising commands won't help.
04 GitHub: the shared copy

One copy everybody agrees on

Everything so far ran on one machine, no account, no network — that's genuinely how Git works, and also not how anyone ships. The moment a second person is involved, the team needs one copy everybody agrees on.

What a remote is

A remote is another repository yours knows how to exchange commits with — a name and a URL, nothing more. By convention the shared one is called origin. A clone is a full local copy of a remote, history included. Because every clone holds the entire history, git log, git diff, git branch, and committing all work with no network — Git is distributed. GitHub is a convention for agreeing which copy counts, plus what a website can do that a version control program can't: review, permissions, a link you can share.

authenticate once per machine, over SSH
ssh-keygen -t ed25519 -C "you@example.com"
eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519
cat ~/.ssh/id_ed25519.pub   # paste into GitHub → Settings → SSH keys
ssh -T git@github.com

The private key never leaves your machine — only the public half goes to GitHub. Do this once, and a new empty repository accepts your history cleanly:

push an existing local project
git remote add origin git@github.com:your-username/your-repo.git
git push -u origin main

git remote add records the name and URL in .git/config. git push -u origin main sends your commits and sets origin/main as what your main tracks — what lets Git later tell you that you're two commits ahead or one behind. After the first push, a bare git push is enough.

fetch, merge, pull

These three get conflated constantly, and the confusion is expensive — it decides whether you can look before you leap.

git fetch

Downloads new commits and moves origin/main. Your own branches don't move; nothing in your working directory changes.

git merge origin/main

Merges the downloaded commits into the branch you're on.

git pull

Is those two, in that order. pull = fetch + merge.

Careful default

git fetch then git status -sb then git diff main origin/main before you merge — costs five seconds, occasionally saves an afternoon.

git pull is the right default on a branch only you're working on. On a busy shared branch, fetch and look first.

Pull requests and review

You have write access to your own repository, so nothing above required a pull request. Teams add one anyway, because the point of a pull request is not the merge — it's the conversation and the checks attached to it.

opening a PR from the terminal
git switch -c feat/new-branch
# edit src/train.py
git add src/train.py
git commit -m "feat(train): weight classes by inverse frequency"
git push -u origin feat/new-branch

Notice what has not happened: main hasn't moved, on your machine or the server. The branch exists in both places now, and that's all. GitHub spots the new branch and offers to open a pull request for it. A PR description for ML work repays being written properly — three headings cover most cases: what changed, how to reproduce it, what happened to the metric. If a reviewer can't re-run your result from the description, the review is a spell-check.

What a reviewer of ML work should check

  • No data files or model binaries in the diff.
  • No credentials in the diff.
  • Enough in the description to reproduce the reported number.

After it merges, the merge happened on the server, so your local repository still knows nothing about it:

closing the loop
git switch main
git pull                              # the merge commit comes down
git branch -d feat/class-weighting    # delete the branch you're done with

git branch -d refuses if the branch holds commits that never reached main — exactly the check you want. -D forces it, and is how work gets quietly lost.

Protected branches

Everything above is a preference until the server enforces it. Branch protection rules on main can refuse direct pushes, require an approving review, and require a named check to pass before merge. "We use pull requests" describes a habit. A protected branch describes a guarantee — and the difference shows up on the afternoon somebody is in a hurry.

05 Reshaping and moving work

Stash, rebase, cherry-pick

Up to now you've been a passenger in your own history — commits happen and stay as they happened. This section is where you take the controls: three tools, in increasing order of how much damage they can do, plus one safety net.

git stash — setting work aside

It exists for interruptions: a teammate needs you to look at main right now, you started editing the wrong branch, or you need to pull and Git refuses because your working directory is dirty. Prefer git stash apply while learning — if applying goes wrong you still have the stash; with pop you have an unexpected working directory and nothing to go back to.

This is the part that specifically bites ML work — three tiers of what a stash actually captures:

tracked, edited

Plain git stash

Only tidies away edits to files Git already tracks. A brand-new config file is left sitting in the working directory, untouched.

+ untracked

git stash push -u

Also captures new, untracked files — the script you just wrote, the fresh config. Fixes the trap above.

gitignored

Still won't touch .gitignored paths

In an ML repo, data/, models/, artifacts/ are ignored — no form of stash touches them, ever.

This matters more than it looks: switch branches with stale artifacts in models/ and your workspace now holds a model produced by different code. Nothing errors. Nothing warns you. That's the code/data mismatch in miniature — the problem the "Why Git fails for data" section is entirely about.

THE HONEST WARNING ABOUT STASHES

A stash is local, invisible to your teammates, unnamed unless you write a message, and easy to forget. It is never pushed. If your laptop dies, the stash dies with it. A stash is a five-minute tool and not storage. A stash older than a day should have been a branch — git stash branch <name> is how you fix that after the fact.

git rebase — replaying commits onto a new base

The diagram is the entire lesson, so it comes before any command. Suppose you branched from main at commit B, made X and Y, and meanwhile someone added C to main.

The feature branch (X, Y) diverges from main after commit B.

Merge joins two histories and records that they were joined. Rebase replays your commits one at a time on top of the new base, producing brand-new commits — X' carries the same change as X but has a different SHA, because its parent is different and the parent is part of the hash. Every other property of rebase is a consequence of that one idea.

The conflict loop

A rebase replays commits one at a time, and each replay can conflict. The loop is: resolve, git add, git rebase --continue — once per conflicting commit. Know all three exits before you start one:

ExitEffect
git rebase --continueCarry on, once you've resolved and staged.
git rebase --skipDrop the commit being replayed.
git rebase --abortReturn to exactly where you were before the rebase.

--abort is safe and complete — costs you nothing beyond the resolution you just did. A rebase can hit the same file conflict commit after commit; that's not you doing it wrong. Each commit touched the file, so each replay reconciles against the new base separately. Squashing a messy branch first avoids most of it.

Interactive rebase — cleaning a branch before review

git rebase -i HEAD~n opens an editor with one line per commit, letting you rewrite the last n commits:

Keep the commit exactly as it is — the default for every line.

Keep the change, but stop to edit the commit message.

Merge this commit into the previous one, combining both messages into one you then edit.

Like squash, but silently discards this commit's message — useful for "oops, typo" follow-ups.

Delete the commit entirely.

Stop the replay here so you can amend the commit's contents before continuing.

The realistic case: a branch containing wip, fix, actually fix, which needs to become one reviewable commit before the pull request goes out. Changing pick to squash on the second and third lines replays all three as one, then reopens the editor with all three messages stacked up for you to replace with the real one. Three commits become one, the content is unchanged, and the message says what the branch does — what a reviewer should receive.

The golden rule, and --force-with-lease

Never rebase commits that anyone else has pulled.

Rebasing rewrites commits. If a teammate holds your old commits and you replace them with new SHAs, their branch and yours now disagree about history, and every one of them has to perform a recovery you'll have to explain. Rebase your own unshared branches as much as you like — leave shared history alone.

Once you've rebased a branch you already pushed, the remote rejects an ordinary push, because its history is no longer an ancestor of yours. The wrong fix is --force — "overwrite whatever is there." The right one:

the safe force-push
git push --force-with-lease origin my-branch

The lease means "overwrite it only if it's still exactly what I last saw." If a teammate pushed while you were rebasing, Git refuses with [rejected] (stale info) — nothing was destroyed. With plain --force, their commit would now be gone from the remote, recoverable only from their local reflog, if they still have it. --force-with-lease costs eleven characters over --force and is the cheapest safety net in Git.

Merge or rebase? Decide it as a team

RebaseMerge
HistoryLinear, easy to read and to bisect.Records what happened, including the mess.
SafetyRewrites SHAs — unsafe on shared branches.Never rewrites anything.

Both are defensible. A common and sane convention: rebase your own feature branch to keep it current, then merge it into main through a pull request. What matters less is which one you pick than that the team picks one and writes it down — an undocumented convention is not a convention.

git reflog — the safety net

Learn this the same day you learn rebase, because it's what makes rewriting history survivable. Git records every move of HEAD locally, and commits no branch points at aren't deleted immediately — by default they survive around 90 days. A "lost" commit after a bad rebase or a reset --hard is usually still sitting there, unnamed, reachable as e.g. feat/messy2@{1} — the position a branch pointed to before the rebase finished.

recovering from a botched rebase
git reflog show feat/messy2
git reset --hard "feat/messy2@{1}"

A botched rebase is almost never fatal — locally. The reflog lives in your own .git directory. It cannot help a teammate whose commits you overwrote on the remote, and it cannot help you on a fresh clone. One more reason not to rewrite what you've already shared.

git cherry-pick — moving one commit

Specific situations: a hotfix landed on main and needs to go onto a release branch too, or one genuinely useful commit sits on an experiment branch you're otherwise abandoning. Everything follows from one fact: cherry-pick copies the change, not the commit. The new commit has a different SHA, so the same work now exists twice in the repository under two identities. -x appends (cherry picked from commit ...) to the message — free provenance, so use it.

The consequence shows up later: cherry-pick a commit off main, then merge that branch back into main, and the same change can appear twice under two SHAs. Often Git merges it silently because it recognizes the change was already applied; in less lucky cases you get a conflict that looks baffling because you're reconciling a change with itself. The one routine, legitimate use in ML work is moving a single config change onto another experiment branch. Otherwise, cherry-pick is a targeted tool for exceptional situations — reaching for it routinely usually means branches were cut from the wrong place.

The rest of the Git surface (not covered here)

git submodule and git worktree for managing multiple checkouts and nested repositories, git bisect for finding the commit that broke something by binary search, and git filter-repo for rewriting history at scale — the answer to "I committed a 500 MB file," which the data section below measures the cost of.

Try it yourself — Checkpoint 7.1
  1. Edit a tracked file and create a new untracked file. Run plain git stash, then ls. Confirm which file went away and which didn't, then redo it with -u. Why it matters: this is the most common way ML students lose track of a new script or config.
  2. Create a branch with four commits named wip, wip2, fix, fix again. Squash them into one properly-messaged commit with git rebase -i HEAD~4. Why it matters: this is the difference between a reviewable pull request and one your reviewer skims out of politeness.
  3. Start a rebase that conflicts. Before resolving anything, read git status and identify which branch you're on, which commit is being replayed, and the three ways out. Then --abort. Then redo it and resolve with --continue. Why it matters: being stuck in a rebase is a reading-comprehension problem, and this is the reading.
  4. After that exercise, run git reflog and find the SHA your branch pointed at before the rebase. Reset to it, confirm the old commits are back, then reset forward again. Why it matters: once you've recovered from a rebase, you stop being afraid of them.
06 Git for ML projects specifically

Where an ML repository behaves differently

Everything so far applies to any codebase. This section is about the parts of an ML repository that behave differently from application code.

A sane repository structure

There's no universal layout, but there's a widely-used convention (the Cookiecutter Data Science layout is the usual reference) — the logic behind it repays understanding rather than copying. Click a row to see why it's there.

├──src/
├──notebooks/
├──configs/
├──data/ gitignored
├──models/ gitignored
├──tests/
└──requirements.txt · README.md · .gitignore

The important line is the boundary between src/ and notebooks/. A notebook is a fine place to look at data and a bad place to keep the code that produces a model, because it has no callable interface, no test surface, and an execution order that depends on what you clicked. The discipline: explore in a notebook, then move the code that worked into src/.

A real ML .gitignore

Write this on the first day of a project, not the day after you accidentally commit a 300 MB parquet file. History is immutable, which is the whole problem.

.gitignore
# Python
__pycache__/
*.pyc

# Environments and secrets
.venv/
venv/
.env

# Notebook cruft
.ipynb_checkpoints/

# Data and artifacts — these do not belong in Git
data/
models/
artifacts/
*.pkl
*.joblib
*.h5

Secrets

Never commit credentials. When you do, three things are true at once:

  • Removing the file with git rm does not remove it from history — the old commit still contains it, readable with git show.
  • Rewriting history to excise it (git filter-repo) is possible but invasive: every SHA after the offending commit changes, invalidating every clone.
  • Therefore the only correct first response is to rotate the credential. Assume it's compromised, because it is. Cleaning the repository afterwards is hygiene, not remediation.

The minimum practice is unglamorous and sufficient: keep secrets in a gitignored .env file, read them from the environment in code, and commit a .env.example listing the variable names with no values.

=== what Git is actually tracking === .env.example .gitignore README.md requirements.txt === and .env is correctly ignored === .gitignore:8:.env .env

git ls-files shows .env.example and no .env. Run that command on your own repositories occasionally — it's the fastest way to find out what you've been committing without noticing.

Notebooks in Git are a real problem

A structural mismatch rather than an inconvenience, for three reasons:

It's JSON

A one-line code change shows up as a diff in a nested structure, with execution_count and metadata churn around it.

Outputs live in the file

A plot is a base64 PNG, sometimes megabytes of it, changing every run. Diffs become unreadable and the repository grows for no reason.

Metadata churns on every run

Two people editing one notebook conflict almost every time — in JSON rather than code. Rebase makes it worse, since it replays each commit.

The fix is upfront

Squash notebook-heavy branches before rebasing them, and adopt a standard tool (below) from day one.

Installs a Git filter that removes outputs and execution counts automatically as files are staged. Minimal change to your workflow: keep working in .ipynb, and Git only ever sees the clean version.

pip install nbstripout
nbstripout --install   # run once, inside the repository

Pairs each notebook with a plain-text representation (usually .py with light markers) and keeps the two in sync. You commit the text file, which diffs and merges like code. A bigger change to how you work, and a better answer for notebooks that hold real logic.

Whichever you pick, the underlying rule is the same: commit notebooks without outputs.

Tags, and the callback to last session

A tag is a human-readable name for a commit. a3f9c21 is precise and forgettable; v1.2-fraud-baseline is both. Tag the commit that produced a model you deployed, or the state of the repository at a milestone.

THE TWO-LINE HABIT

Record the commit SHA in your run metadata. Two lines in your training script:

python
import subprocess
sha = subprocess.run(["git", "rev-parse", "HEAD"], capture_output=True, text=True).stdout.strip()

Write that into your metrics file, your log line, your model card. It's the link that makes "which code produced this model" answerable at all, and it costs two lines. The other half — which data produced it — needs the tool covered next.

07 Why Git fails for data

Measured, not asserted

This claim gets asserted constantly and demonstrated almost never — which is why students end up half-believing it and committing a CSV "just this once." A commit stores a snapshot; content is stored as compressed blobs identified by hash. For text that's efficient: Git can store one version as a delta against another, and source files are small. For data, two things go wrong at once — the files are large, and successive versions aren't similar in the way Git's compression needs.

The experiment: a modest 14 MB CSV, refreshed four times the way a real dataset gets refreshed — same schema, new snapshot of underlying reality. Commit each version, measure .git after each one.

.git size CSV file size
commit 1commit 2commit 3commit 4
after git gc --aggressive: 26 MB → 24 MB — barely a dent

Read the numbers: the working file never grows past its ~15 MB, but .git grows by roughly the compressed size of the dataset with every commit, because every version is stored in full. Four refreshes of a 14 MB file cost the repository several times the size of the data you actually care about. To be fair to Git, it does try: git gc --aggressive repacks and hunts for deltas between similar objects — and barely helps, because delta compression works when two versions share long runs of identical bytes. A refreshed dataset, a re-sampled split, a re-encoded feature, a shuffled export — every byte moves, and there's no delta to find. In ML work, that's the normal case.

The mechanics, stated plainly

  • Every version of every dataset is stored in full, forever, in every clone. A new teammate pays for your entire data history before they can run anything.
  • History is immutable. A 500 MB file committed once is in history permanently. Deleting it in a later commit doesn't shrink the repository — only rewriting history does, and that invalidates every existing clone.
  • GitHub enforces limits regardless of your opinions: warnings above 50 MB per file, a hard block at 100 MB, and a recommendation to keep repositories well under a few gigabytes.

What about Git LFS?

Git LFS (Large File Storage) replaces large files with text pointers and stores the bytes on a separate server — structurally the idea every data-versioning tool uses. A genuine improvement for a team versioning a handful of large binaries alongside application code. Its limits for ML work specifically:

Billed quotas

Bandwidth and storage quotas on GitHub, easy to exhaust with datasets.

No deduplication

No awareness across similar files, or of which version of the data produced which result beyond the pointer.

No pipeline concept

LFS knows the file changed, not that the change invalidates your training stage.

Co-located

Still hosted with your Git provider, so data lives where code lives — often not where your compute is.

THE ACTUAL REQUIREMENT

Version the data like code, but store the bytes somewhere built for bytes.

A small text pointer goes under version control, so data versions move with branches, commits, and merges exactly like source files. The actual gigabytes live in object storage — S3, GCS, Azure, or a network mount. What matters today is that you can say precisely why "just commit it" fails, because you've watched a repository reach 26 MB over four refreshes of a 14 MB file and seen aggressive garbage collection give back only 2 MB of it.

Try it yourself — Checkpoint 9.1
  1. Write one of your own projects a .gitignore from scratch, without looking at the one it already has. Then run git ls-files and read the whole list. Why it matters: git ls-files is the fastest audit of what a repository actually contains, and almost nobody runs it.
  2. Commit a file holding a fake credential, remove it with git rm, and commit again. Now retrieve it with git log -p and git show <sha>:<path>. Why it matters: until you've pulled a "deleted" secret back out of your own history, rotating the key instead of just deleting the file won't feel mandatory.
  3. Run the bloat experiment against a dataset of your own, at whatever size it really is, and write down .git before and after. Why it matters: a measurement from your own project wins the "this doesn't belong in the repository" argument in a way an opinion doesn't.
08 Common failures and how to debug them

Not exhaustive — but these will actually happen to you

Roughly in order of how often. Click any one to expand.

stuck

Stuck in a rebase

git status says interactive rebase in progress and you don't know whether to commit, continue, or abort. Read the status output — it names the commit being replayed and lists your three exits. Resolve the files and git add them, then git rebase --continue. Or git rebase --abort and you're exactly where you started. Never git commit mid-rebase — it isn't one of the exits.

force-push

Force-push clobbered a teammate

You rebased a shared branch and forced. Their commits are gone from the remote. Recovery: they find the pre-push SHA in their local reflog and push it back. Prevention: --force-with-lease, which refuses when the remote has moved.

stash

The lost stash

You stashed, changed context for two days, stashed twice more, and stash@{0} isn't what you think. git stash list and git stash show -p stash@{1} before you pop anything, and always use -m.

stash

Untracked files not stashed

The one that bites ML students hardest. git stash ignores untracked files; use -u. Gitignored artifacts are never stashed at all.

duplicate

Duplicated commits after cherry-pick

You cherry-picked a fix, then merged the branch it came from — the change exists twice. Sometimes silent, sometimes a conflict that looks like nonsense because you're reconciling a change with itself. Prefer merging the whole branch when you can.

rebase

A rebase conflicting again and again

Each of your commits touched the file, so each replay conflicts separately. Expected, not a bug. Squash first if the branch is messy.

bloat

You committed a 500 MB file

It's in history permanently. Deleting it in a new commit doesn't shrink anything. Options: rewrite history with git filter-repo and force everyone to re-clone, or start a fresh repository. Both are unpleasant — which is why .gitignore comes before the first git add.

notebook

A merge conflict inside a notebook

The conflict is in JSON — in execution_count and output blobs rather than your code. Take one side wholesale, re-run the notebook, and commit that. Then install nbstripout so it stops happening.

branch

A branch that will not delete

git branch -d refuses because the branch holds commits that never reached main. That refusal is correct — check git log main..the-branch before reaching for -D.

09 The MLOps perspective

Where this sits on the maturity model

Three levels exist above this: manual, pipeline automation, and CI/CD automation. Nothing in this reading automates anything, and that's fine — you cannot automate a process you cannot reproduce. A versioned repository with a reviewable history is the floor the other two levels stand on.

Review is the cheapest quality gate you have. A pull request that changes how a feature is computed shows up as a diff somebody reads, instead of surfacing three weeks later as a metric nobody can explain. Every argument for code review applies with more force to ML code, because the failures are quieter.

Pitfalls seen in industry, all of them common

  • Treating main as a personal scratchpad — no branch protection, no review, and the deployed model comes from whatever was pushed last.
  • Versioning code religiously and data not at all — the most common half-measure by a wide margin, and it leaves you exactly as unable to reproduce a result as versioning nothing.
  • Committing notebooks with outputs, then being puzzled that every merge conflicts.
  • Committing a credential and then "removing" it in a later commit, without rotating it.
  • A repository nobody has ever cloned from scratch — if a fresh clone plus a README can't get a new teammate running, the history is a diary rather than a project.
ONE THING TO CARRY OUT OF THE ROOM

Your repository is your project's memory. Not your laptop, not your notebook outputs, not the Slack thread where you posted a screenshot of a ROC curve. A project you cannot reconstruct from its repository is a project you do not own — you are borrowing it from your own filesystem.

10 Class summary

What we opened with a debt for, and what we now have

"Version everything" was a principle with no implementation. Here's what's now in place.

Git, understood rather than memorised

A commit is a snapshot plus a parent, named by a hash of its content. Three trees — working directory, staging area, repository — with every command moving things between them. Branches are pointers, so branching is free. HEAD is where you're standing; detached HEAD is a place, not an error.

The everyday workflow

Including the conflict created on purpose. Merge conflicts are Git declining to guess, and resolving one is a normal Tuesday.

GitHub as the shared copy

A remote is a name and a URL, origin by convention. SSH keys once per machine. fetch moves origin/main and touches nothing of yours; merge brings it in; pull is the two in order. Pull requests carry the review; branch protection turns a habit into a guarantee.

Reshaping work

stash for interruptions, with -u for untracked files. rebase as replaying commits onto a new base, with the conflict loop, the three exits, and interactive rebase for turning messy commits into one reviewable one. The golden rule: don't rewrite what others have pulled. --force-with-lease when you must, reflog as the net that makes it survivable. cherry-pick for the exceptional case, with the duplication it creates.

Why Git fails for data

Measured, not asserted: four refreshes of a 14 MB CSV grew the repository several times over, and aggressive GC barely helped, because refreshed data shares no deltas. Plus GitHub's hard limits and the permanence of history.

Git for ML work specifically

A layout separating src/ from notebooks/, a .gitignore written before the first git add, secrets that live in .env and never in history, notebooks committed without outputs, and a tag on the commit that produced a model — plus the two-line habit of writing the commit SHA into your metrics file.

The question that opened this reading was: which exact data and which exact code produced this exact number? Half of it is now precisely answerable — given a metric, you can name the commit, and given the commit you can recover the code, the config, and the environment file that produced it. The data half is next, and you now know exactly why it needs different machinery.

12 What's next

The gap this reading measured

You can now version code, collaborate on it without losing work, and point at the commit that produced a model. The gap is the one measured in "Why Git fails for data."

Next up is data versioning: a pointer file under Git, the bytes in S3, and the pair of commands that restore a past state of a project completely rather than halfway. That's where the opening question gets its full answer, and where you meet the failure that makes it matter — a checkout that brings back old code beside new data and reports a plausible, wrong number without warning you.

BEFORE THEN

Use what you have on something real. Take one of your own projects, give it a .gitignore before anything else, put exploratory work in notebooks/ and the code that matters in src/, and make its history something you'd be willing to show a reviewer. Git is the half of this problem that is genuinely solved. Being fluent in it is not the interesting part of MLOps — and everything interesting rests on it.
