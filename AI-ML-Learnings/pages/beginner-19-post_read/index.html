§ 1

Why Prompt Management Matters in Real Teams

⏱ 10 min

One person, one chat window, no problem. The moment a second person touches the same prompt, everything below becomes necessary.

🧑‍🍳
The Analogy

Amberlight already has a system for this — just not for prompts yet. Every candle scent has a batch card: who formulated it, which version number, what changed since the last one, and the QC panel's notes before it ships. Nobody at Amberlight would let three people quietly re-mix the signature scent in the same jar with no batch card. A prompt that answers real customers is exactly that jar.

✗ What a chat-window prompt gives you

Whoever edited last wins, silently. No record of who owns it, what changed, or why. No way to tell if the newest version is actually better — only different. When it breaks, nobody can point to the moment it broke.

✓ What a managed prompt gives you

One named owner accountable for it. A version number for every real change. Saved test cases you can re-run. A changelog explaining why v2 exists. When it breaks, you can point at the exact version and the exact line.

🎙 Instructor Says

"Say this back to yourself, because it's the whole section: this is code review, for prompts. Nobody would let four engineers push straight to production with no version control, no tests, and no changelog — yet that's exactly what happened to Amberlight's return-reply prompt. The prompt didn't get worse because Devraj is careless. It got worse because there was no process that would have caught it."

Q1. Why doesn't scrolling through the chat window's edit order tell you which version of a prompt is actually live?
AIt always does — the last message in the thread is always the live prompt, no exceptions.
BChat order isn't the same as edit time, and nothing labels which message is "the one currently in production" — you have to compare timestamps by hand, and even then there's no changelog explaining why any of it changed.
CIt doesn't matter which version is live, since Claude and Gemini always produce identical output for the same prompt.
Correct answer: B. A shared chat thread has no built-in concept of "current version" — that's precisely the gap a version and a changelog exist to close.
§ 2

The Prompt as a Product

⏱ 12 min

Four fields turn a scratch note into something a team can actually trust. None of them are optional if more than one person depends on the output.

Prompt as a Product

Any prompt that (a) more than one person touches, or (b) makes a decision with real consequences, deserves four things: an owner (one accountable name, not "whoever's around"), a version (a number that goes up every time the wording changes), test cases (a small fixed set of inputs you always check it against), and a changelog (one line per version explaining what changed and why). Miss any one of the four and you're back to a chat-window guessing game.

FieldWhat it actually answersWhat breaks without it
OwnerWho signs off before a change ships?Anyone can edit; nobody's accountable — Devraj's Tuesday edit.
VersionWhich exact wording produced this output?No way to say "it broke between v2 and v3."
Test casesDoes it still handle the cases that matter?"Looks fine" replaces actually checking — Sana's screenshots.
ChangelogWhy does this version exist?"Warmed it up" gets lost; nobody can undo it on purpose.
🎙 Instructor Says

"None of these four fields require a special tool. A spreadsheet can hold all four — that's literally Build 1, coming up next. The tool matters later, for scale. Right now, the habit is what matters, and the habit costs nothing but four extra minutes per change."

The trap worth naming: people hear "version" and think "only for big rewrites." Devraj's one-line tone tweak is exactly the kind of change that should have gotten a version bump and a changelog line — it's small edits that quietly break things, not big obvious rewrites. Size of change has nothing to do with whether it needs tracking.

§ 6

Prompt Regression Testing

⏱ 15 min

Not "did the output change" — every edit changes the output. The real question is: did it get worse, and at exactly which version?

Regression Testing (for prompts)

Running a small, fixed set of test cases — the same inputs, every time — against a new prompt version, and checking the outputs against a rubric you set in advance. A regression is a version that fails a test case a previous version passed. Without saved test cases, "worse" is just a feeling someone eventually notices, days later, from screenshots.

🎙 Instructor Says

"Here's the exact moment Amberlight's incident became preventable: three fixed test cases — cracked jar, wrong scent, shipping question — run against every version before it ships. v1 passes all three. v3, Devraj's version, fails the one that matters most. That's not hindsight. That test case existed the whole time; it just never got run."

Q4. A teammate says "v3's output is just different from v2's, not worse — different isn't automatically bad." How do you actually settle that, instead of arguing about it?
AWhoever has seniority decides which version sounds better.
BRun the saved test cases against both versions and compare against the rubric — a regression is a version that fails a test case a previous version passed, which is checkable, not a matter of opinion.
CAssume the newest version is always the better one, since it's the most recent.
Correct answer: B. Test cases turn "feels different" into "provably fails a case it used to pass" — that's the entire point of keeping them instead of relying on impressions.

§ 8

The Differentiator — Power User vs. AI Ops

⏱ 10 min

Writing a great prompt for yourself and owning a versioned, tested prompt system other people depend on are different skills. Only one of them is a role.

LayerWhat it actually is
Power userPersonally good at getting strong single outputs — iterates well, phrases things precisely, gets more out of a chat window than most people.
AI tools specialist / AI OpsOwns prompts as shared infrastructure across a team or across tools — versioning, test cases, regression checks, changelogs, on behalf of people who never see the prompt itself.
🎙 Instructor Says

"This is the honest answer to 'is this a real job.' Being great at prompting one chat window is a personal skill — genuinely valuable, but it caps out at making you faster. The moment you're the person other people trust to own a prompt's version history, its test cases, and its changelog — across support, ads, and product — that's a different job description. Today built the muscle for exactly that second thing."

03

Catch a regression on something you already wrote

›
Mission

Write one sentence explaining how you know.

Key Takeaways

1. A prompt with more than one editor is infrastructure, not a chat message. Owner, version, test cases, changelog — miss one and you're back to guessing.

2. "Different" and "worse" are not the same claim. Only saved test cases, run before and after, can actually tell them apart.

3. A spreadsheet is the floor, not the ceiling. Four columns get you real discipline for free; a dedicated tool like PromptLayer automates the same discipline at scale.

4. The differentiator isn't prompting skill — it's ownership. Being good at prompting makes you faster. Owning a team's prompt lifecycle is a different, billable role.

Four people, one chat window, zero record — that's how Amberlight's return-reply prompt broke. Now it has an owner, a version, three test cases, and a name on every line of its changelog.
