§ 1

Build 1 — Three Nodes, One Working Automation

⏱ 16 min

The smallest thing that is genuinely useful. Someone fills in a form; an AI node reads it and writes a two-line summary; that summary lands in your inbox. Three nodes, no branches, no conditions. Everyone gets this running before we add anything.

01
Form → AI → Email
3 NODES · EVERYONE RUNS THIS TODAY

The Whole Workflow

Three nodes, named exactly as they appear in n8n's node picker.

⚡ n8n Form Trigger→ 🧠 Basic LLM Chain→ ✉️ Gmail

Every automation has these three roles — and Class 10's framework was exactly this: something starts it, something happens in the middle, something comes out. Build 1 is that sentence with nothing added. Every node you learn after today slots into one of those three roles.

How Build 1 Comes Together — Three Steps

Step 1 · n8n Form Trigger. Add it, set the form title to Wanderline — Trek Inquiry, and add three fields: Name (text), Email (email), Your message (textarea). Copy the test form URL and open it in a second browser tab — leave that tab open for the rest of the build.

Step 2 · Basic LLM Chain. Add it and connect it after the form. Notice the dangling connector underneath the node — that's not decoration, it's where the model goes. Attach a chat model sub-node there and pick your model. Then the prompt:

// Basic LLM Chain — prompt field
Summarise this travel inquiry in two short lines
for our team inbox.

Name: {{ $json.Name }}
Message: {{ $json['Your message'] }}

Those double curly braces are an expression — "put the live value here." $json means the data arriving from the node just before this one. That's the entire idea, and it's the only expression syntax you need for Build 1.

Why $json['Your message'] has brackets but $json.Name doesn't: n8n uses your form's field label as the key. A label with a space in it can't use dot notation, so it needs bracket-and-quote form. This one detail costs beginners fifteen minutes on their first build — name it now and it costs them nothing.

Step 3 · Gmail. Operation Send a message. To: your own email address, typed in plain. Subject: New inquiry from {{ $json.Name }} — wait. Try it, and watch it fail to resolve. This is a deliberate teaching moment: the Gmail node's input is the LLM node's output, and the LLM node only outputs its generated text. The name is gone. For now use a plain subject line and put the summary in the body with {{ $json.text }}. Build 2 solves the missing-name problem properly — leave it broken and move on.

Now press Test workflow, submit the form in your other tab, and watch three nodes turn green.

+ IF · + Google Sheets
5 NODES · THE SAME WORKFLOW, GROWN

What's New — And What Isn't

⚡ n8n Form Trigger→ 🧠 Basic LLM Chain→ ❓ IFNEW→ ✉️ Gmail→ 📊 Google SheetsNEW

IF node

A node with two outputs instead of one — a true door and a false door. It looks at the data arriving, checks one condition you write, and sends the item out of whichever door matches. It changes nothing about the data; it only chooses the path.

🚪
The One Analogy

Everything so far has been a corridor — data walks in one end and out the other, and there's nowhere else to go. An IF node is the first doorway with two doors. Same corridor, same walker; the only new thing is that something now looks at them and decides which door they go through.

How Build 2 Comes Together — Two Additions

First, teach the AI node to label things. Open your existing Basic LLM Chain and add one line to the prompt — you're not adding a node, you're improving one you already have:

// Basic LLM Chain — prompt field (add the last line)
Summarise this travel inquiry in two short lines
for our team inbox.

Name: {{ $json.Name }}
Message: {{ $json['Your message'] }}

Then on a new final line, write exactly one word:
BOOKING if they want to book, GENERAL if it is a
question, or SPAM if it is junk.

Add the IF node after the LLM node. Condition: {{ $json.text }} — String — contains — BOOKING. Two output handles appear on its right edge: true on top, false underneath.

Rewire Gmail onto the true output. It's already configured from Build 1 — just drag the connection. Only booking inquiries now generate an email.

Add Google Sheets (Append row) and connect both the Gmail node and the IF node's false output into it. Yes, two connections into one node — that's allowed, and it's exactly what you want here: every inquiry gets logged, whichever door it went through. Only the booking ones also got an email on the way.

Now the missing-name problem from Build 1. The Sheets node needs the guest's name and email — but its input is the Gmail node's output, which contains neither. This is the moment for the second and last expression form you'll learn today: 
// reach back to any earlier node, by name
{{ $('n8n Form Trigger').item.json.Name }}
{{ $('n8n Form Trigger').item.json.Email }}

$json = the node right before me. $('Node Name') = any node, anywhere upstream, by name. That's the whole expression system. Build 1's broken subject line gets fixed with it too.

🔍 SIM 2 · Follow The Data

n8n's most important panel, and the one beginners never open. Click each node to see what went in and what came out — then click any output field to get the exact expression that pulls it downstream.

EXPRESSION
Click any field in the OUTPUT panel above.
Beginner Note: the two panels are the whole game. A node can only use data that appears in its own INPUT panel. If a field isn't there, no expression will conjure it — reach back to the node that has it.
Intermediate Note: watch the guest's name and email disappear as you click along the chain. Each node replaces the item with its own output. That's not a bug to work around — it's why $('Node Name') exists, and why you never need to bolt extra nodes onto a canvas just to carry fields forward.
Advanced Note: reach-back stores the node's name as text. Rename "Basic LLM Chain" to "Classify Inquiry" and every expression pointing at the old name breaks — at runtime, not at save time. n8n warns you when you rename; read the warning.
The honest limitation: checking whether the AI's text contains the word BOOKING works, and it's how most people start. It's also fragile: the model might write "this is not a booking question" and the IF would match on that. The robust fix is a Structured Output Parser that forces real JSON back, which is a later class. Naming the weakness now is what separates teaching a tool from teaching the craft.

Quiz 2 · The Google Sheets node at the end needs the guest's email address. Its INPUT panel shows only the Gmail node's output, which doesn't include it. What's the correct fix?

AMove the Sheets node before the Gmail node, so it gets better input
BUse a reach-back expression — {{ $('n8n Form Trigger').item.json.Email }} — to pull it from the node that actually has it
CAdd a second Form Trigger before the Sheets node so the email is available again
DIt's impossible — once data passes through a node that drops a field, that field is gone for the rest of the workflow
Why B? Any node's output stays addressable by name for the whole execution. A works by luck and breaks the next time you reorder — it also treats a data problem as a layout problem. C would make the workflow start twice. D is the belief that causes people to bolt extra nodes everywhere carrying fields "just in case."

How Build 3 Comes Together — The Parts That Are Actually New

Node 1 · Schedule Trigger. Weeks → every 1 week → Monday → 08:00. Then go straight to Workflow Settings → Timezone and set Asia/Kolkata. Do this immediately: the trigger fires in the workflow's timezone, and a fresh instance often defaults to UTC. Leave it, and Farah's 8am digest arrives at 1:30pm.

Node 2 · HTTP Request. Method GET, and no credential of any kind:

// HTTP Request node — no API key, no account, no signup
GET https://api.open-meteo.com/v1/forecast

// Query Parameters — use the fields, not a pasted URL;
// n8n encodes them properly for you
latitude   34.16          // Leh
longitude  77.58
current    temperature_2m
daily      temperature_2m_max,precipitation_sum
timezone   Asia/Kolkata

Run just this node and open its output panel. The response is somebody else's JSON, nested — the temperature sits at {{ $json.current.temperature_2m }}, not at the top level. This is SIM 2's skill applied to data nobody designed for you.

Node 3 · Google Sheets — operation Get row(s), pointed at the sheet Build 2 has been filling. Run it and look at the item count in the node's corner: 12 items, not 1. That number is the whole next idea.

Node 4 · Aggregate — All Item Data (into a single list). Twelve items go in, one comes out, carrying all twelve inside it. Skip this node and twelve emails get sent instead of one; SIM 3 makes that concrete before it happens for real.

Nodes 5–6 · LLM Chain and Gmail, both already familiar. And the weather? The LLM node reaches back for it, using the exact skill from Build 2 — no new node needed:

// Basic LLM Chain — prompt field
Write Farah a short Monday digest of last week's
travel inquiries.

Leads: {{ $json.data }}
Leh temperature: {{ $('HTTP Request').item.json.current.temperature_2m }}°C
Notice what just happened: two different sources of data needed to combine in one node, and that skill was already there. That's the growth curve working — Build 3 introduces three new nodes, but the thing that joins them together is a skill learned in Build 2.

A node is a worker at a conveyor belt, not a manager reading a report. Quiz 3 · A Google Sheets node returns 30 rows. Directly after it sits a Gmail node, with no Aggregate anywhere. Kabir presses Test workflow. What happens?

AOne email is sent, containing all 30 rows in the body
B30 separate emails are sent — one run of the Gmail node per item

When It Breaks — Visual Debugging

⏱ 13 min

All three builds work. In four days, one of them won't — and the person who can open the executions list and find out why in ninety seconds is the person who gets handed the automation work. Four real failures, diagnosed one at a time.

Where To Look, In Order

A fixed routine, every time. Never start by guessing which node is wrong.

#Where you lookWhat it tells you
1The Executions tab (left sidebar)Did it run at all? A workflow with zero executions has a trigger problem, not a node problem — and that changes everything you do next
2The failed execution's canvasWhich node has the red border. Everything to its right never ran; everything to its left ran fine
3The red node's error messageThe literal reason, usually from the outside service — a status code, a missing field, a permission
4That node's INPUT panelWhat it was actually handed. Nine times out of ten the node is fine and the data arriving is wrong
5The previous node's OUTPUT panelWhere the wrong data was born. This is usually where the real fix goes
The rule that saves the most time: the red node is where it stopped, not always where it broke. A Gmail node failing on a missing address is a symptom; the bug is usually upstream, where the address was never carried forward.

D is the last thing to check, not the first.
§ 5

Error Handling & Retry Basics

⏱ 9 min

Debugging is what you do after someone tells you it broke. Error handling is how you find out before they do — and how a workflow survives problems that were never your fault.

Three Settings, One Safety Net

All three live in a node's Settings tab, which most people never open. The fourth lives in Workflow Settings.

SettingWhat it doesTurn it on when
Retry On FailRe-attempts the node up to Max Tries, waiting Wait Between Tries ms each timeThe node calls an outside service. Networks blip; APIs rate-limit. Most "failures" succeed on attempt two
On Error → Continue (using error output)Adds a second, red output; failed items go down it instead of killing the runOne bad item shouldn't stop the other eleven from being processed
Always Output DataEmits an empty item instead of nothing, so downstream nodes still runA lookup legitimately finds nothing and you still want the "found nothing" path to do something
Error Workflow (workflow settings)A separate workflow, started by an Error Trigger, that runs whenever this one diesAlways, on anything running unattended. This is what makes failure visible
Build the error workflow once, reuse it forever. It's two nodes: an Error Trigger and a Gmail send to yourself — genuinely the smallest useful workflow there is, and a nice echo of Build 1. The Error Trigger hands you the failed workflow's name, the node that broke and the error message, so the alert can say "Monday Digest failed at Google Sheets: 503" rather than "something went wrong." Point every workflow at that same one.

🛡 SIM 6 · The Retry Lab

Farah imports the weekend's 12 unprocessed inquiries and re-runs Build 2's router over them — so 12 rows get written to Sheets. Row 4 hits a transient 503 Service Unavailable, gone a second later. Configure the node, run it, and see what Farah actually experiences.

Advanced Note: retry is for transient failures — timeouts, 429s, 503s. Retrying a 401 Unauthorized three times just fails three times more slowly, and retrying a send that actually succeeded before timing out can double-send. Retry things that are safe to repeat; be careful with anything that charges money or messages a customer.

First Look — The n8n AI Agent Node

⏱ 9 min

No building here — this is a first look only. A preview of the tier above everything in today's three builds, so that when it's met later, what it is — and, more importantly, when it's the wrong choice — is already known.

💬
Tsering (Solitude Peaks) → KabirThursday, 11:04 PM

"Third guest tonight asking what time checkout is and whether the Khardung La road is open tomorrow. It's in their booking email and on the weather site. Can your thing handle that, or does it only do new inquiries?"

Why Today's Builds Can't Do This

Every workflow built today runs the same nodes in the same order, every time. That's a strength — it's predictable and easy to debug. But look at what Tsering's guests actually ask:

Guest asksWhat answering it requires
"What time is checkout?"Look up this specific guest's booking row
"Is the Khardung La road open tomorrow?"Call a live external source — no booking involved
"Can I get a late refund?"Neither. A human, immediately — this is money
"Checkout time, and will it be cold?"Both lookups, then one combined answer

Four questions, four different sequences — and there's no way to know in advance which arrives. An IF could be drawn for each, but that stops scaling at about three. That's the situation the AI Agent node exists for: hand it tools and a goal, and it picks the order itself, per message.

🛎
The One Analogy

A Basic LLM Chain — the node used all through today's builds — is a scripted phone menu. It does what it was built to do, in the order it was built to do it. An AI Agent is a concierge with a desk: a guest book, a phone, and a manager's extension. Ask anything, and they decide which to reach for, in what order, and how many times — then answer once.

What It Looks Like On A Canvas

The visual surprise: the AI Agent isn't wide, it's deep. Connectors hang off its underside, and each takes a sub-node.

🧠 Chat Model 💭 Simple Memory 🔧 Google Sheets Tool 🔧 HTTP Request Tool 🔧 Gmail Tool — "escalate"

Four of those five are already familiar. A "tool" is just a node already used today — Sheets, HTTP, Gmail — handed to the agent to call whenever it judges it useful, instead of being wired into a fixed position. That's the entire conceptual jump, and it's smaller than it looks from outside.

Quiz 5 · A guest messages: "Hi — I was told on the phone I'd get 20% off for the delayed check-in. Can you apply that?" The agent has all three tools available. What should it do?

ALook up the booking, confirm the delayed check-in, and apply the 20% — the record backs the guest up
BEscalate immediately and tell the guest a team member will confirm — it's money, so it isn't the agent's decision to make
CReply that Wanderline doesn't offer discounts, since no discount tool exists
DAsk the guest to forward proof of the phone call, then decide based on what they send
Why B? The question is never "does it have enough information" — it's "is this a decision the business will accept being made unattended." A discount is a binding financial commitment, and a promise made on an unrecorded call is exactly the ambiguity a human resolves. A is Air Canada from Class 10, precisely: a plausible claim, a confident automated agreement, a company bound by it. C invents a policy the business never stated — the same failure pointed the other way, and it annoys a guest who may well be right. D has the agent running an evidence review, which is the judgment call it should never make.

Exporting & Sharing Workflows Safely

⏱ 7 min

Three workflows exist. They live in one browser, in one account. Getting them out — into version control, into a teammate's instance — takes ten seconds, and there is exactly one way to do it badly.

How It Works

ActionHowWorth knowing

Mission

Key Takeaways

Start with three nodes. Trigger, one thing in the middle, one output. Get it running, then grow it. Nobody designs a twelve-node workflow and builds it — that canvas is the end of a process, never the start.

Two expressions cover almost everything. $json.field is the node right before me. $('Node Name') is any node, anywhere upstream. That's the whole system.

An IF node is just a doorway. It changes nothing about the data — it only chooses the path. Adding decisions to a workflow is one node, not a rebuild.

Nodes pass lists of items, and run once per item. Aggregate when you want one of something. This is the mistake everyone makes exactly once.

The HTTP Request node is the escape hatch. Every pre-built integration is one of these underneath. Once you're comfortable with it, "n8n doesn't support that" stops being a sentence you say.

Test workflow is not Activate. Testing proves it works; only the Active toggle makes it real. Two of today's four failures were this.

Green does not mean correct. A successful execution only means nothing threw an error. Reading the output is still your job.

Unattended means it needs to be able to shout. Retry for blips, error output so one bad item doesn't stop the batch, and an error workflow so a failure reaches a human.
