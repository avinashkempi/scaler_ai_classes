Class 7 Pre-read

Finding answers across the data

About 5 minutes to read. Nothing to install or submit before class.

The case that disappeared

Meridian has two support cases. One has a recorded review. The other does not. A colleague connects the case list to the review list and gets back only one row.

Nothing was deleted. The second case disappeared because there was no matching review to attach to it. The result may still look tidy, but it no longer represents every case Meridian started with.

When two sources are connected, should records without a match disappear or remain visible?

Class 6 ended at this exact problem. The issue table knew what happened. The review table knew what a person did. The rule table knew why a case was routed. Each source held one part of the answer. Class 7 begins by connecting those parts while deciding, deliberately, what must remain in the result.

The count that became larger

Now imagine one support case was reviewed twice. When the case is connected to its review history, it appears twice: once for each review. A count of the resulting rows would report two, even though Meridian still has only one case.

After combining data, are you counting cases, review events, or rows created by the connection?

All three counts can be useful, but they answer different questions. The difficulty is that the wrong number often looks believable. Before reporting any total, we need to finish the sentence: I am counting what?

The filter that removed the missing cases

A teammate tries to keep every support case and attach only a particular kind of review. The connection initially preserves the full case list. A later filter then removes every case that had no matching review, quietly undoing the original intention.

This is the sort of mistake that can survive a quick check. The query runs, the columns look correct, and the number may seem reasonable. The only way to catch it is to compare the result with the business question and ask which records were allowed to vanish.

If a result is smaller than expected, which condition removed the missing records?

The answer lives in more than one place

Meridian wants to know which issue types reached human review and which rule caused the route. The issue type, review record, and rule description live in different tables. A dependable answer must connect them through shared identifiers and keep reviews that do not name a rule visible.

The same principle applies to history. If a case was reviewed more than once, Meridian may need its latest decision or the change between reviews. The newest row in the whole table cannot answer what is latest for every case.

What should stay separate when we read the history of thousands of cases at once?

What will Class 7 do

In this working session, you will:

  • Connect related tables while choosing whether unmatched records should remain visible.
  • Count cases and review events correctly after records have been connected.
  • Find cases with no review and build larger answers in smaller, checkable steps.
  • Save a reusable question and read the latest change within each case history.

What to bring to class

You do not need to memorise query syntax before the session. Bring these three questions with you:

  1. One. When two datasets are connected, which records are we willing to lose if there is no match?
  2. Two. If one case has several reviews, how will we stop it from being counted as several cases?
  3. Three. If the answer needs facts from three tables, which identifiers connect the evidence?
