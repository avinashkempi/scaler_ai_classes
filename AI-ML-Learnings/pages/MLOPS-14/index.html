AWS SageMaker · Feature Store · Part 2 · The Online Store

From a customer ID to a live prediction

Part 1 kept every version of each customer's history for training. This part gives the checkout a fast way to read the latest version, and checks that the model sees the same numbers live as it did in training.

9 msmedian single read from the online store
11,565customer rows loaded before 1 July 2026
2,986orders replayed, July to September
0 of 2,986orders that saw training's row when written first

In the previous part, the customer's history got a home. A feature group kept every version of every customer's counts in its offline store, and a point-in-time join built training data that did not cheat. The honest model trained on it scored an AUC of 0.721.

That model still cannot help at checkout. When an order comes in, the checkout knows the customer's ID and the order, and nothing else. Something has to fetch the customer's history in a few milliseconds, lay it out the way the model learned it, and send it to the endpoint. The offline store is too slow for that: it answers SQL queries in seconds, and it runs minutes behind the writes. This part adds the other half of the feature store, the online store, and builds that live path.

What you will be able to do
  • Explain what the online store keeps, how it differs from the offline store, and why serving needs it.
  • Put the previous part's honest model on a real-time endpoint.
  • Create a feature group with both an online and an offline store.
  • Write a customer's row, read it back straight away, and load every customer.
  • Read customers one at a time and in batches, and measure how long it takes.
  • Score one order through the live path, from a customer ID to a prediction.
  • Replay three months of orders and show whether the live path feeds the model the rows training used.
  • Recognise the online store's quiet failures, and clean up everything that bills.

01Why an online store

In simple words, an online store is a table that keeps only the latest row for each customer, and answers a lookup by customer ID in a few milliseconds. This section shows why the checkout needs one.

1.1What the model needs

The model from the previous part takes 18 numbers for every order.

PartColumnsWhere they come from at checkout
The order, 5 numbersprice, discount_pct, delivery_days, is_gift, seller_ratingThe order itself
Category and payment, 9 numbersOne-hot columns for the 5 categories and the 4 payment methodsThe order itself
The customer, 4 numbersorders_so_far, returns_so_far, return_rate, tenure_daysNowhere yet

The checkout has the order, so the first 14 numbers are easy. The customer's 4 numbers are the problem. They come from the customer's whole history of orders and returns. Working them out from the raw orders on every request would be slow, and it would copy features.py into a second place. Two pieces of code working out the same thing is how training and serving drift apart, as Part 1 showed.

1.2Two stores for one feature group

A feature group can keep its rows in two stores at once.

Offline storeOnline store
What it keepsEvery version of every customerOnly the latest row of each customer
Who reads itTraining, with SQL in AthenaThe checkout, by customer ID
How fastSeconds, and minutes behind the writesMilliseconds, straight after the write

Think of a bank. The offline store is the statement, with every transaction and its date. The online store is the balance on the app's home screen.

One put_record call writes to both. The online store replaces the customer's row with the new one, and the offline store adds the new row to its files. So training and the checkout read numbers that came from the same write.

1.3The plan

Select any step to see what it does. The offline store is greyed out, because the previous part covered it.

1.4The question this read answers

The model learned from rows built by a point-in-time join. Every order got the customer's row from strictly before the order, so the row never counted the order being scored. At checkout, the online store hands over whatever row it holds at that moment. Is that the same row? It depends on what happens first.

Score first, then write

The shop scores the order and only then writes it into the store. The store still holds the row from before, so the two match.

Write first, then score

The shop writes the order first and scores it after. The store already counts it. That is the <= mistake from Part 1, happening live.

The core question

Section 8 replays three months of orders both ways and measures the difference. To try any of this, the platform has to come back first.

07The live path

At checkout, three things turn an order into a prediction.

  1. Read the customer's four features from the online store, with get.
  2. Lay out all 18 numbers in the order the model learned them, with model_row.
  3. Send them to the endpoint, with invoke_endpoint.

7.1rows.py, the layout

model_row(order, features) lays out one row exactly as the previous part's training files did. Both the training code and the serving code should call this one function, so that the two cannot lay a row out differently.

When features is empty, because the store has no row for the customer, model_row fills in what training filled in for a customer with no history: 0 orders, 0 returns, a return rate of 0.2, and the tenure from the sign up date.

08Does the live path see what training saw?

Section 1.4 asked whether the row the checkout reads is the row training used. This section answers it, first for one order, then for three months of orders.

8.1One order, two rows

The snapshot in section 7.3 showed two rows for C-00001 around the order. The 27 June row is from before the order. The 10 August row already counts it. Score the same order with each one.

Notebook cell · same order, two rowsinvoke_endpoint twice
Output

With the 27 June row, the chance of a return is 0.570. With the 10 August row, it falls to 0.531. That row already counts the order being scored, so orders_so_far is one higher and return_rate drops from 0.625 to 0.5882. Whether this order comes back cannot be known yet, so the extra order makes the customer look a little less likely to return things. For this order both scores are still above 0.5. Over three months of orders, the same small push adds up.

8.2Replay three months, both ways

Now do the same for every order from July to September 2026. The replay walks through the days in order, the way the shop lived them, and does three things each day.

  1. Score the day's orders with predict. The store holds only rows from before today. This is score first.
  2. Write the day's new customer rows with put.
  3. Score the same orders again. The store now counts today's orders too. This is write first, what a shop that updates the customer before scoring would see.

The cell keeps both probabilities and both sets of features for every order. Run the replay only once. After one replay the store holds every customer's rows up to the end of September, and a second replay would read those instead. Section 9.2 shows why.

Score first gives an AUC of 0.721, the same number the training job reported in Part 1. Write first gives 0.719. The other numbers tell a different story. With score first, 608 orders would get the message, and 371 of them did come back. With write first, only 502 would get it, and 314 came back. The shop would miss 57 customers who went on to return their order.

Why? Counting the order being scored raises orders_so_far, but its return cannot be known yet. So return_rate falls, and the customer looks less likely to send things back, exactly as for C-00001 in section 8.1. Fewer orders cross 0.5.

With score first, every one of the 2,986 orders got exactly the row training used. With write first, not one did. That is the <= mistake from Part 1, and no error said so. In a real shop, this mistake comes from an order system that updates the customer's counts the moment an order is placed, with the scoring call a moment later. 09Failure modes

The replay showed that the store keeps what it is given, in the order it is given. The online store also has rules of its own, and three of them fail quietly. The tests below use customer IDs that start with C-TEST, so they cannot be mistaken for real ones.

9.1A customer the store has never seen

Notebook cell · an unknown customerC-99999
Output

get_record for a customer the store has never seen does not raise an error. Its answer simply has no Record, so get returns an empty dict. Section 6.2 showed the batch call doing the same, leaving such customers out without an error.

When "no history" is the wrong answer

An empty dict reaches model_row, which fills in the defaults for a customer with no history. That is the right answer for a brand new customer. It is the wrong answer when the customer is not new at all, for example when an ID has a typo or an extra space. The model then scores a regular customer as a stranger, and nothing complains. Empty lookups are worth counting and watching.

9.2A row older than the one stored

Write a row for C-TEST-1 from 1 September with 5 orders. Then write one from 1 August with 3 orders.

Notebook cell · an older event timetwo writes
Output

The store still says 5 orders. The second write, with an older event time, was accepted without an error and then ignored. The online store keeps the row with the newest event time, whatever order the writes arrive in. That protects the store from a slow job writing old rows over new ones. But a correction stamped with an older time never reaches the online store. If a row was wrong and you fix it by writing it again with its original event time, the checkout keeps reading the value you meant to fix.

Why the replay runs only once

After one replay, the store holds every customer's row from late September. Loading the rows from before July again changes nothing, because they are older. A second replay's daily writes are older too, and they are ignored. So every order would read the customer's September row, which often already counts the order's own return. No error appears, and the AUC rises well above 0.721.

10When an online store is more than you need

The online store earned its place here for two reasons. A checkout needs one customer's latest row in milliseconds. And the same put_record call that feeds it also feeds the offline store that training reads. Take either reason away and it may not be worth it.

Batch scoring needs no online store

If the shop scored yesterday's orders overnight instead of at checkout, the batch transform from the lesson before last would do, fed by the point-in-time join from Part 1. Nothing would need an answer in milliseconds.

A plain key-value table can also answer fast

A team that never trains from the offline store could write the latest row to any fast database and read it by customer ID. What the feature group adds is that one write lands in both stores, so the training rows and the serving rows come from the same code. Without the offline half, that benefit is gone, and the feature group is one more service to pay for and look after.

There is more than one kind of online store

This part used the standard tier, the default. It bills for the data it stores, by the month, and for each read and write. Feature Store also has an in-memory tier, run on Amazon ElastiCache, for very high read rates. It works only for groups with no offline store, and it bills for storage by the hour, with a minimum size, so it costs money for as long as it exists. At the speed section 6 measured, the standard tier is fast enough for a checkout. Check the pricing page linked below before you choose.

12Summary

Part 1 built the offline store and an honest model from it. This part gave that model a live path. A feature group with both stores took the customer rows through one put_record call. The online store kept only the latest row of each customer and answered a lookup in about 9 milliseconds, where an Athena query takes seconds. The live path read the customer's row with get, laid out the 18 numbers with model_row in the training layout, and called the endpoint.

  1. The core question was whether the live path feeds the model what training used. The replay scored every order from July to September 2026 twice, once before that day's writes and once after. Scoring first, all 2,986 orders got exactly the row training used, and the AUC was 0.721, the training job's own number. Writing first, not one order did. Yet the AUC barely moved, to 0.719, while 57 of the orders that came back would no longer have been flagged. Compare inputs, not only scores.
  2. Unknown customers vanish quietly. An unknown customer comes back as an empty answer, alone or in a batch, and turns into a new customer.
  3. Older writes are ignored. A write with an older event time is accepted and ignored, which is also why a replay cannot be run twice.
  4. A time to live counts from the event time. An old row with a short time to live is gone before anyone reads it. And the offline store runs minutes behind, so its files can keep arriving after the group is deleted, which is why the cleanup looks twice.
  5. Know when to skip it. The online store is worth having when a request needs one customer's latest features in milliseconds, and when the same writes also build the training data. For batch scoring, it is more than you need.

Where this goes

The endpoint here serves one model file, copied into the bucket by hand. Teams keep many versions of a model, and need to know which one is serving and how it was trained. Keeping track of that is the job of a model registry, which comes next in the course.
