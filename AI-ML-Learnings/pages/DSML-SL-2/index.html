Let scikit-learn do the heavy lifting

Writing kNN by hand was great for understanding it. In production, we use a tested, optimised library implementation instead. scikit-learn’s KNeighborsClassifier does the distance, sorting and voting for us.

  • .fit() stores the training data. Unlike Logistic Regression, it does not learn weights.
  • .predict() and .score() handle distance, sorting and voting.
  • n_neighbors is our k, and metric is the distance measure. Both are choices we make.

Because .fit() only stores data, you should not expect it to take noticeably longer as the training set grows. The cost chapter shows why.

What k really controls

We picked k = 5 in Class 1 without justifying it. Let us understand what k actually controls.

A thought experiment

Suppose our training data has 30 “Moderate” stores and 1 mislabelled “High” store sitting right in the middle of them, purely due to a data entry error.

  • With k = 1, a new store near that mislabelled point is predicted “High”, purely because of one bad data point.
  • With k = 29 (almost the whole neighbourhood), that one bad point barely matters. The vote is dominated by the correctly labelled “Moderate” stores.

If k equals the entire training set, kNN always predicts the overall majority class, no matter where the query point is.

Overfitting and underfitting

The two extremes have names. A model that fits every quirk and outlier extremely closely, and changes a lot if the training data changes slightly, has high variance and low bias. That is overfitting, and a very small k pushes kNN in this direction. A model that is too smooth to capture real patterns has high bias and low variance. That is underfitting, and a very large k pushes kNN there.

Choosing k with a validation curve

k is a hyperparameter. Training data is used to fit the model, test data is opened only once at the end, and validation data is exactly what we use to compare hyperparameter choices such as k.

The plan: loop over k from 1 to 50, record training and validation accuracy for each, and plot both. The k with the highest validation accuracy is best_k.

Code: plot accuracy against k

A second way to pick k: the elbow method

Looking for the single highest point on the validation curve works, but it can be noisy: the very top point is sometimes just a lucky value of k, not a genuinely better one. A more robust habit is the elbow method. Plot the error rate (1 − accuracy) against k and look for the point where the curve stops dropping sharply and flattens out, like a bent elbow. Past that point, a larger k mostly adds smoothing (and eventual underfitting) rather than real improvement.

Code: the elbow plot

Reading the curves

Training accuracy is highest for very small k. Why does it fall as k grows?

With a very small k, the model follows every training store closely, so it does well on the data it has stored. As k grows, each vote averages over more stores, so the model fits individual training points less closely and training accuracy falls.

Validation accuracy rises, peaks, then falls. What does the peak represent?

The peak is the best balance between the two extremes: k is large enough to ignore noisy points and small enough to keep real patterns. To its left the model overfits, and to its right it underfits.

Where is the elbow, and does it agree with best_k?

On the error-rate plot, the elbow is where the curve stops dropping sharply. It should roughly agree with best_k. If they differ slightly, remember that the single highest point can be a lucky value, which is why the elbow is the more robust habit.

Where does overfitting happen, and where does underfitting start?

Overfitting happens at small k, where training accuracy is high but validation accuracy is lower. Underfitting starts at large k, where validation accuracy has fallen away from its peak because the vote is too smooth to reflect the data.

Is kNN actually fast enough?

The worry about scale is real. Let us work out exactly what kNN costs, in time and memory, so we can answer it properly. Say we have n training stores and d features.

Training time

.fit() does no real computation. It just stores the data. The cost is constant: it does not grow at all, no matter how many stores we have.

Space

We keep every training point, with every feature. Memory grows in proportion to n × d.

Prediction time, one new store

Distances to all n points, each using d features: proportional to n × d. Sorting those n distances grows a little faster than n (roughly n times its own logarithm). Taking the top k is negligible.

Training barely costs anything, but every single prediction gets more expensive as the store count grows.

So per prediction, cost grows in proportion to n × d, plus a bit more for the sorting step. That answers the ticket’s scaling question directly: with 10x the stores, each prediction does roughly 10x the distance work.

When the data is not clean

Real-world data is messy: fields go missing, and some fields are not numbers at all. kNN needs a real number for every feature, for every store, to compute a distance. Suppose a new field, City_Type, arrives with values like “Metro”, “Tier-2” and “Tier-3”. It cannot go into knn.fit() as it is.

Categorical features need numbers

The curse of dimensionality

Here is the problem with piling on dimensions carelessly. As the number of features grows very large, distances between points start to lose their meaning. Points that should look “close” and “far” start to look almost equally far from each other. The demo below measures this on random data: one query point, 500 random points, and the ratio (farthest − nearest) / farthest.

In low dimensions, the nearest and farthest points are clearly different distances away. As dimensions grow, that ratio shrinks, so every point looks about equally “close” or “far”, and the whole idea of a “nearest neighbour” starts to break down.

Code: measure the distance spread

Take-away. One-Hot Encoding a field with many categories can push us into this territory. That is one reason Target Encoding, which keeps one column per feature and uses the average target value per category, is often preferred for high-cardinality categorical features in distance-based models.

Missing values

Real store records sometimes arrive with a missing value, for example a missing Detergents_Paper figure. We cannot compute a distance using a missing number. Filling in a single global average is the simplest option, but kNN itself offers a better one, built later in this class.

Choosing the right distance metric

So far we have always used Euclidean distance. It is not the only option, and the right choice depends on the data. Take two points, A(1, 1, 3) and B(1, 3, 5).

Manhattan distance sums the absolute difference along each feature: |1−1| + |1−3| + |3−5| = 0 + 2 + 2 = 4. Euclidean distance takes the straight line: √(0 + 4 + 4) = √8 ≈ 2.828.

Euclidean and Manhattan are two ends of the same family

( ∑j=1d |xj(1) − xj(2)|p )1/p
  • p = 1 gives Manhattan distance (also called L1 distance): useful when movement happens along a grid, like city blocks on a map.
  • p = 2 gives Euclidean distance (also called L2 distance): the straight-line distance we have used so far.
  • This general form is the Minkowski distance, and p is itself a hyperparameter.

Cosine similarity: when direction matters more than distance

After One-Hot Encoding, our data can become sparse (mostly zeros) and high-dimensional. Manhattan and Euclidean distance treat every feature equally, including the many irrelevant zeros. Cosine similarity instead looks at the angle between two feature vectors, which tends to ignore those irrelevant zero features better.

cosine similarity = x(1) · x(2)‖x(1)‖ ‖x(2)‖

Which metric to use

MetricBest suited for
EuclideanLow-dimensional, dense numeric data (most common default)
ManhattanGrid-like or map-like data
Cosine similarityHigh-dimensional, sparse data (for example, after heavy One-Hot Encoding)
MinkowskiWhen you want a custom p between Manhattan and Euclidean

All of these are simply hyperparameters of kNN, chosen and compared using the validation set, exactly like k.

Making search fast: Locality Sensitive Hashing

Two worries remain: speed at scale, and one more useful trick, using kNN itself to fill in missing values. Start with speed.

We already worked out that prediction cost grows in proportion to n × d (plus a bit more for sorting) per query, comparing against every single stored point. Real systems, including large-scale image and product search, rarely do this literally. Instead, they use Locality Sensitive Hashing (LSH) to avoid comparing against everyone.

The idea: a hash table of neighbourhoods

The core idea is the same as a hash table, or a dictionary:

KeyValue
'Metro-HighFresh'[Store A, Store B, Store C]
'Tier2-LowFresh'[Store D, Store E]

LSH builds a hashing function so that similar stores tend to land in the same bucket. Then, for a new store, instead of comparing against every stored store, we only compare it against the (much smaller) bucket it hashes into.

A simplified LSH implementation

One simple way to build such a hash: project each point onto a few random directions, and use the sign of each projection as one bit of the hash. Points that end up with the same hash string are the ones LSH considers “probably close”.

Bonus: using kNN to fill in missing values

Earlier we asked how to handle missing fields. One neat answer is kNN itself. To impute a missing value for feature f in store x:

  1. Ignore feature f temporarily.
  2. Find the nearest neighbours of x, using the remaining features.
  3. Fill in the missing value using the mean of feature f among those neighbours.

Key takeaways

  1. scikit-learn’s KNeighborsClassifier replaces our from-scratch version: .fit() stores the data, and .predict() and .score() handle distance, sorting and voting.
  2. A very small k tends to overfit (high variance, low bias). A very large k tends to underfit (high bias, low variance). A validation accuracy-versus-k curve is how we choose k properly.
  3. Training is constant, since kNN just stores data. Prediction is expensive, in proportion to n × d + n log n per query, since it compares against every stored point.
  4. Categorical features must be converted to numbers, for example with One-Hot Encoding, but this can blow up the number of features.
  5. In very high dimensions, distances lose meaning. This is the curse of dimensionality, and it is one reason Target Encoding is often preferred for high-cardinality features.
  6. The choice of distance metric is itself a hyperparameter: Euclidean for dense low-dimensional data, Manhattan for grid-like data, Cosine similarity for sparse high-dimensional data.
  7. Locality Sensitive Hashing groups similar points into buckets, so real systems compare a query against a small bucket instead of the entire dataset.
  8. kNN can also impute missing values, by averaging a feature over the nearest neighbours that do have it.
