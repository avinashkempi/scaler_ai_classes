    Experiment tracking with MLflow · Part 2

    Packaging the training run, and the model it produces

    So a teammate can rerun the one, and load the other, without reading your code first.

    Adds: MLflow Projects & MLflow Models Library: MLflow 3.16.1 Read time: ~20 min

    The last session gave the campaign model a memory. Running python -m campaign.track trains it and records its parameters, its holdout metrics, its commit, and the fitted pipeline — every run searchable afterward. That answers how the model was created. It doesn't answer two other questions.

    A teammate who wants to extend the tuning search can see the commit history, but not which command to run, which arguments it takes, or which environment it needs. A developer who wants to use the trained model still needs to know, by hand, how the pipeline is shaped, what its inputs look like, and how to read what it returns.

    MLflow answers both with two small conventions. An MLflow Project names the commands a repository offers, so anyone can run training the same way — locally, or straight from GitHub — with mlflow run. An MLflow Model packages a fitted model with instructions for loading it, so a tool can load and serve it without any custom code. This session builds both, and along the way finally connects the tuning search to the tracking store.

    00

    What a teammate still cannot do

    The quickest way to see the gap is to record a run the ordinary way, then read it back as a stranger would — using only what the tracking store itself can say.

    Search for that run and its tags say LOCAL: a script, started by hand. The run knows its source file and its commit. It holds no tag at all about how it was launched. So a teammate who wants to rerun it has to work several things out for themselves: that the file runs as python -m campaign.track, not python campaign/track.py; that it has to run from the repository root; which Python environment it needs; and which of several commands in the README comes first. If they want more tuning trials, they also have to discover that tuning is a separate command with its own --trials flag.

    None of this is hard

    It's all written in the README — and a README is prose for people. It goes stale without anybody noticing. An MLflow Project puts the same facts in a file a program reads and runs, so a wrong line fails loudly the first time somebody actually uses it.

    01

    A project is a folder with a manifest

    An MLflow Project isn't a new kind of code. It's a repository plus one file at its root, MLproject, naming the commands the project offers — plus, optionally, a file describing the environment those commands need. mlflow run reads both, prepares the environment, opens a run in the tracking store, and starts the command.

    Plenty of teams never write one. They wrap training in a container instead and start it from a scheduler. What MLproject writes down still carries over: named commands, declared parameters, an environment built from a file, a pinned commit — it's simply the smallest way to get all four, and it plugs straight into a tracking store you already have.

    The manifest

    MLprojectrepository root
    # What `mlflow run` reads. Each entry point is a command the project
# offers, with the parameters it accepts. The experiment is not named
# here, because that's the caller's choice:
#     mlflow run . -e train --experiment-name term-deposit
#     mlflow run . -e tune -P trials=10 --experiment-name term-deposit

name: term-deposit

python_env: python_env.yaml

entry_points:
  # Continue the stored Optuna study. One parent run, one child per trial.
  tune:
    parameters:
      trials: {type: int, default: 10}
    command: "python -m campaign.track_tune --trials {trials}"

  # Fit the study's best configuration. No parameters — train.py reads
  # its choices from the study rather than the command line.
  train:
    command: "python -m campaign.track"

    The file must be named exactly MLproject, no extension. name is a label; python_env points at the environment file. entry_points is what matters — each one a command the project offers, with a name, its parameters, and a command template that mlflow run fills in before running it from the project's folder. There are two entry points because the project already has two jobs with different costs: train wraps last session's training and takes nothing, because it reads its choices from the study; tune continues that study, and its one parameter is how many trials to add.

    A parameter has a type and a default. The documented types are string, float, path and uri — MLflow accepts any name you give it, such as the int used here. What that type actually enforces turns out to be less than it looks; section 03 checks.

    The comment at the top says the experiment isn't named in the file. That's deliberate, and it's about to cost something.

    The first run — and its intended failure

    terminalrepository root
    mlflow run . -e train --env-manager local

    Training runs to completion — and then the run fails, on the line that opens it inside track.py. The order of events explains most of what mlflow run does. It opens a run before the command starts; with no experiment given, it opens one in Default. It then starts the command with three environment variables set — the run id, the experiment id, the tracking store — so when track.py calls mlflow.start_run, MLflow sees that run id and joins it rather than creating a new one. But track.py had just called set_experiment("term-deposit"), and a run can't belong to two experiments at once. MLflow refuses.

    A run that fails late fails expensively

    The run isn't lost — a failed run now sits in Default, and training has already rewritten the files on disk. Nothing about this was wasted quietly.

    The experiment is the caller's choice, so it belongs on the command line:

    terminalrepository root
    mlflow run . -e train --env-manager local --experiment-name term-deposit

    This time it succeeds, named campaign-train because track.py names it. Set beside the run started by hand in the previous section, the tags that describe where each came from tell the whole story:

    Same command, two ways of starting it
    TagStarted by handStarted by mlflow run
    mlflow.source.typeLOCALPROJECT
    mlflow.source.nametrack.pythe project folder itself
    mlflow.project.entryPoint—train
    mlflow.project.backend—local

    The project run holds the full instruction for rerunning it: entry point train, of that project, at the commit it also records. The failed attempt sits in Default, with its entry point recorded too — nothing about a project run vanishes just because it failed.

    02

    Entry points, parameters, and the search

    The tune entry point is where parameters earn their place, because tuning is the job people rerun with a different budget. It's also where the last session's loose end gets tied off — the Optuna study the tracking store couldn't see.

    Every trial becomes a run

    campaign/track_tune.py runs the same search campaign.tune always ran, on the same stored study, and records it as one parent run with a child run per trial. The search script itself is never edited, for the same reason the training script wasn't edited last session.

    campaign/track_tune.py
    def tracked(objective):
    """Wrap an objective so every call is a child run of the open parent."""
    def run_trial(trial):
        with mlflow.start_run(run_name=f"trial-{trial.number:03d}", nested=True):
            value = objective(trial)
            mlflow.log_params(trial.params)
            mlflow.log_metric("cv_roc_auc", value)
            mlflow.set_tag("stage", "trial")
        return value
    return run_trial

    nested=True is what makes a run a child — it tells MLflow to attach it to whatever run is already open instead of refusing to open a second one. The child opens before the objective runs, not after it succeeds, so a trial that raises still leaves a FAILED child behind, and a crashing corner of the search space shows up instead of disappearing.

    Ten trials, one parent — a search of any size stays one line in the runs table until you expand it.

    The parent, main(), opens a run named campaign-tune, hands the wrapped objective to study.optimize, and records how large the study was before, how many trials were requested, and the best score and family the whole study has found so far. artifacts/study.db stays the source of truth for the search — the sampler still reads it to decide what to try next — while the tracked runs become the searchable record of what was tried.

    Passing ten more trials grows the study from 60 to 70. The best score is still 0.8013, unchanged since it was first found — none of the ten beat it, which is ordinary once a study has converged, and it's also why the model train logs doesn't change either.

    Optuna ships its own MLflow callback that does much the same job, in the optuna-integration package — but it logs a trial only after it finishes, so a trial that crashes leaves no run behind. The wrapper here is a dozen lines, all readable, and opens the child first specifically so a crash still gets recorded.

    Who actually checks a parameter

    The manifest declares trials as an int. Passing something that isn't one, and then passing a name that doesn't exist, both fail — but not for the reason you'd expect, and not in the same way.

    Which layer actually catches the mistake?

    Neither message comes from MLflow. Both come from argparse, inside track_tune.py itself. For ten, MLflow put the text into the command exactly as given, and the parser rejected it. For the misspelled trails, MLflow doesn't know the manifest never declared it — it's added to the command anyway, while --trials quietly keeps its default of 10. parse_args happens to fail on an unknown flag; a more forgiving parse_known_args would have ignored it outright, and the search would have run with defaults and nobody would have noticed.

    The type in MLproject is documentation, except for path and uri, which MLflow does act on. The real check is your own argument parser, exactly as strict as you wrote it. Both mistakes still leave a run behind — two failed runs with random names, since the command died before the parent could be named. They hold no metrics, so unlike an ordinary failed run they can't climb a leaderboard; filtering on status keeps them out of any search that matters.

    Letting MLflow log the fit by itself

    mlflow.sklearn.autolog() patches scikit-learn so every fit logs a run with no logging code at all. Run once, on one pipeline fit, it's worth judging against the runs this session writes by hand.

    autolog() vs. the project's own logging
    mlflow.sklearn.autolog()campaign/track.py
    Parameters logged59 — every pipeline setting, chosen or defaultonly the ones actually decided
    Metrics loggedtraining rows only (0.9065 accuracy — a model that says no to everyone already scores 0.8873 on those same rows)the holdout metrics the service reports
    Model formatcloudpickle, chosen quietlyskops, chosen and trusted deliberately

    Autolog earns its keep early in a problem, trying things in a notebook where nothing should go unrecorded. A command whose runs other people will compare should log the holdout metrics it was built to report, and save the model in the format you actually decided on — which is exactly why the project's own commands log by hand instead.

    03

    Where the code runs

    Every run so far used --env-manager local — the environment you're already sitting in. That's fast, and it's exactly the “works on my machine” setup a project is meant to get away from.

    An environment built from the file

    --env-manager uv tells MLflow to build a fresh environment from python_env.yaml before running the command, using uv — the same installer that built the project's own .venv.

    MLflow keeps the environment under ~/.mlflow/envs/, named by a hash of the environment file, and reuses it unchanged.

    The two managers suit different jobs. local suits your own laptop while you work — fast, and it uses what you already have. uv suits a run somebody else has to trust, because it proves the project works from its own files rather than from whatever you happened to install last month. (virtualenv and conda are the older ways of doing the same thing.)

    Be honest about how far this goes: the environment is only as fixed as requirements.txt. This project pins scikit-learn and mlflow exactly, and gives only lower bounds for the rest — enough to protect the two libraries that would change the model or the store, not enough to reproduce a run years later. That would call for a full lock file, which is more ceremony than this project needs yet.

    Running a commit straight from GitHub

    So far . has meant “the project in this folder.” mlflow run also accepts a Git URL, with --version naming the commit — the full hash, since MLflow asks GitHub for exactly the name it's given, and GitHub only knows full hashes, branches, and tags.

    terminalrepository root
    COMMIT=$(git rev-parse HEAD)
mlflow run https://github.com/pulkit-scaler/mlops-mlflow-projects-2 \
  -e tune -P trials=2 --version $COMMIT \
  --env-manager local --experiment-name term-deposit

    MLflow clones the project into a temporary folder, checks out that exact commit, and runs it there — nothing in the working copy is touched. Read the trial count this run starts from: 60, the study as it was committed at that hash, even though the local folder had already grown to 70 and beyond. That's the whole promise of a project — anybody with the URL and the hash gets the same code and the same starting files you had, whatever state your own laptop is in.

    The run still lands in the local store, the one the browser UI is already showing. That needed one small change to track.py this stage: mlflow run passes the caller's store to the command as MLFLOW_TRACKING_URI, and the training script now reads that variable instead of always writing to mlflow.db next to itself. Without the fix, a temporary clone would see an empty database and fail outright with “Run with id=… not found.”

    One warning about --version

    Use it with a URL, never with .. For a local folder MLflow doesn't clone — it checks the commit out inside the folder you gave it, which moves your own working copy onto that commit and leaves it there.

    04

    What log_model wrote

    The project makes training repeatable. The rest of this session is about what training leaves behind. track.py now ends with mlflow.sklearn.log_model, and every training run since has logged a model alongside it.

    The FastAPI service loads artifacts/model.joblib directly with joblib.load — which works only because the service was written by the same people who trained the model. It knows the file is a scikit-learn pipeline, which version pickled it, and that a “yes” probability sits in column 1 of predict_proba. Take that shared knowledge away, and every model needs its own loading code: a PyTorch model one way, a booster from another library a third way entirely.

    Every model MLflow saves gets a pyfunc flavor, whatever library trained it — one door, whatever's behind it.

    The folder

    Looking a model up follows last session's advice — filtering on the tag and entry point of the command that logs models, and on FINISHED, rather than trusting the best number in the experiment.

    model.skopsthe fitted pipeline itself, in the format chosen and trusted last session
    requirements.txtthe environment it was saved in, for pip
    python_env.yamlthe same environment, for MLflow's own tools
    conda.yamlthe same environment again, for conda-based tools
    input_example.jsonthe example rows track.py passed in
    serving_input_example.jsonthe same rows, already wrapped the way a model server expects a request
    registered_model_metaa placeholder — the model registry writes here, later in the course
    MLmodelthe file that ties all of the above together

    The MLmodel file

    What matters most in it is the list of flavors — a flavor being simply one way of loading the same saved model.

    Two flavors, the same model folder
    FlavorForGives back
    sklearncode that already knows it's dealing with scikit-learnthe actual Pipeline object, every attribute intact
    python_function (pyfunc)code that knows nothing about the training libraryone method, .predict(data) — here returning probabilities, because track.py passed predict_fn: predict_proba

    Every model MLflow saves gets a pyfunc flavor, whatever library trained it, so every one can be loaded by the same call and asked the same question. It doesn't remove the need for the library — loading still needs scikit-learn installed — but the calling code no longer has to know which library that is.

    One model, two ways to load it

    Loaded through each flavor, the same saved model comes back as two different objects: through sklearn it's the Pipeline, with its preprocess and model steps — the object you'd inspect or refit. Through pyfunc it's a PyFuncModel, offering little beyond predict. Its answer is a NumPy array with two columns per row, the probability of no and of yes. Over all 10,297 test rows, it matches model.joblib to the last digit — it's the same model, reached two ways.

    runs:/<run id>/model is one address for it. Since MLflow 3 a logged model also gets an id of its own, so models:/<model id> loads the same folder — though the run id is the one you'll usually have to hand.

    05

    What the signature checks

    A signature is the part of MLmodel the last section skipped. It lists every input column with a type, and describes the output. track.py never wrote it by hand — infer_signature read the three example rows and wrote down what it saw. From then on, pyfunc checks every input against it before the model ever sees the data.

    The model refuses its own training data

    The signature says age is a double — a float. In the training frame, age is an integer. MLflow won't silently convert a 64-bit integer to a float, because very large integers lose precision that way, so it refuses the whole frame — the model rejects the very rows it learned from.

    The cause is one line in track.py: every numeric column of the example rows was cast to float before the signature was inferred from them, because pdays is missing for most customers and an integer column can't hold a missing value. A fair choice — but it means every Python caller now has to cast too. A signature is inferred from whatever you show it; the example rows are a decision about the model's contract, not a formality.

    What it refuses, and what it quietly lets through

    Eight inputs, each one real caller mistake, each changing exactly one thing from a correctly typed row. Choose one to see what the signature actually does with it.

    Click an input to see the signature's verdict

    The first three are refused, each with a message naming the exact problem — that's what a signature is for. Without it, a renamed-but-correctly-ordered frame could be scored with nobody noticing. The next two are accepted, reasonably: an extra column is dropped (here it's duration, the leakage column from the earlier end-to-end session, thrown away before the model ever sees it), and column order never matters because columns are matched by name.

    The last three are the ones worth remembering. A job the bank has never heard of, a month typed in capitals, and a negative age are all scored and handed back a probability — no error, no warning. The model isn't wrong, exactly; it's quietly answering a different question than the one the caller meant to ask.

    A signature is a contract about names and types

    Never about values. That gap is exactly what app/schemas.py fills in the FastAPI service — where job is a fixed list of the values the encoder actually saw, month is one of ten lower-case strings, and age must be at least 17.

    06

    Serving the logged model

    MLflow can put a logged model behind HTTP with one command and no code. The earlier end-to-end session built a service by hand for the same model. This section runs both, side by side, and sends them the same requests.

    terminalrepository root
    mlflow models serve -m runs:/$RUN_ID/model --env-manager local --port 5001
    Easy to point at the wrong run

    The autologged run from section 02 has a model too — but its predict returns a bare 0 or 1, not a pair of probabilities. Picking a run by hand in the UI is easy to get wrong; the lookup above filters on the tag and entry point that only the real training command sets.

    One line in what it prints is worth reading: exec uvicorn … mlflow.pyfunc.scoring_server.app:app. mlflow models serve is uvicorn, running in front of an application MLflow ships. /ping answers 200 once the model is loaded — what a load balancer would check. /invocations takes a JSON body, runs it through the same signature check from the last section, calls predict, and returns one pair of probabilities per row. One command, and it's a working prediction service.

    The same prospect, two services

    The FastAPI service takes a request shaped like a person, and builds the rest itself. The MLflow server takes exactly the model's twenty columns — so for that request, the caller has to build those columns using the project's own code.

    Send one prospect to both servers

    Which one to put in front of callers

    mlflow models serve is right when the caller already speaks in model columns — another team's batch job over the same feature table, a quick check of a new model before anyone writes a service, or a platform serving many models the same way. No code, works for any flavor, always in step with the model because the signature comes straight from it — and it's the form most hosting platforms expect.

    The FastAPI service is right when the caller is a product — here, a campaign console and a person on the phone who shouldn't need to know what pdays is. It carries the decisions the model itself doesn't contain: the threshold, the allowed values, the economic context, the version to report.

    They're not rivals, and they could meet in the middle — the service could load its model from the tracking store by address instead of from model.joblib, keeping its own contract in front. That swap needs a way to say which of all the logged models is the approved one. That's the registry's job, later in the course.

    07

    Where this stops

    This session made training something anyone can run and the model something anyone can load. Four things were left out on purpose — they mark the edges of what Projects and Models do.

    Not recorded — which model is approved

    The store holds several logged models, all loadable by address, and nothing says which one is the approved one. A name, versions, and an alias such as champion is the model registry's job, later in the course — registered_model_meta is where it will write.

    The environment is only Python

    python_env.yaml rebuilds Python packages. It can't install a system library, pin the operating system, or guarantee the same machine. MLproject also accepts a docker_env that runs an entry point inside a container — the next session builds that image.

    The store is still a file on your laptop

    Projects run straight from GitHub still wrote their runs into your own mlflow.db. A team points MLFLOW_TRACKING_URI at one shared server instead — track.py already reads that variable, so no code changes when that happens.

    The service still loads model.joblib

    Section 06 showed the logged model can be served, and why the product's contract still belongs in front of it. Moving the service onto a model it fetches from the store waits for the registry too.

    An honest word on cost

    For one person training one model from one laptop, a README and --env-manager local would do. MLproject earns its keep the first time somebody else — or a scheduler — has to run your training without asking you, and the same goes for rerunning a commit you've already moved past. This project has reached that point. The signature and pyfunc earn theirs the moment a model leaves the code that trained it.

    08

    Summary

    A tracked run knows what happened. By itself, it doesn't tell anybody how to make it happen again, or how to use what it left behind.

    An MLflow Project fixes the first half: the repository plus an MLproject file naming entry points — each a command with typed parameters — and an environment file pointing at one requirements.txt. mlflow run opens a run, starts the command with that run's id and store in its environment, and records the entry point and source. A command shouldn't pick its own experiment unless the caller agrees, and it should read the store it's handed rather than choosing one.

    The search is now part of the record: each Optuna trial is a child run of one campaign-tune parent, named by its trial number, while the study itself stays the source of truth for the sampler. Autolog would record every fit with no code at all — but with training-only metrics, dozens of unchosen parameters, and a pickled model, which suits exploring more than a command other people will compare. --env-manager uv builds the environment from the file and reuses it; a Git URL with a full --version hash runs that exact commit in a clean checkout, and still logs to your store.

    An MLflow Model fixes the second half: log_model writes a folder holding the saved model, its environment, example rows, a signature, and an MLmodel file listing its flavors. The sklearn flavor gives back the pipeline; the pyfunc flavor gives any caller .predict, returning probabilities here because of predict_fn. mlflow models serve puts the same thing behind HTTP with one command.

    The quiet failures worth remembering
    The parameter type in MLproject isn't checked.Your argument parser is the real check — a typo only fails if the parser is strict.
    The signature follows the example rows.A cast in the example decides what every caller must send, down to rejecting the training frame.
    The signature checks names and types, never values.An astronaut gets a probability. The value contract belongs in front of the model — the service already has one.
