Thinking in Tensors · Part 1

Shape, Dtype, Device, and Grad

Every PyTorch model — from a two-line linear regression to a production LLM — is built out of tensors that carry four pieces of information. Get any one of them wrong, and the model either crashes loudly or, worse, keeps running and quietly learns the wrong thing. This is the practice of interrogating a tensor before trusting it.

By the end of this read, you'll be able to

  1. Predict tensor shapes through a forward pass, using batch-first conventions for tabular, image, and token data.
  2. Implement a linear layer and reductions with tensor operations, choosing the reduction axis correctly.
  3. Explain broadcasting and catch silent shape bugs before they corrupt a training run.
  4. Choose numeric types deliberately and estimate a model's memory footprint.
  5. Explain autograd — the computation graph, gradient accumulation, and when to turn tracking off — and verify a gradient independently.

Core idea

The most expensive bugs in deep learning are not the ones that crash. They're the ones that run to completion, print a plausible number, and are wrong. Everything in this read builds toward recognizing that difference.

Four Failure Signatures

Four short PyTorch snippets, four different error messages — each one a real failure you will meet in the first month of working with tensors. Expand each to see the code, the error, and which passport it's checking.

1Multiplying two mismatched matrices›
a = torch.randn(32, 10) # batch of 32 samples, 10 features b = torch.randn(8, 4) # wrong shape for a weight matrix a @ b
RuntimeError: mat1 and mat2 shapes cannot be multiplied (32x10 and 8x4)

The inner dimensions — 10 and 8 — don't match for matrix multiplication. In practice, a is a batch of features coming out of a dataloader, and b is a weight matrix defined with the wrong size.

Shape
2Averaging integer class labels›
labels = torch.tensor([1, 2, 3, 4]) # class labels, loaded as-is torch.mean(labels) # "let's just check the average label"
RuntimeError: mean(): could not infer output dtype. Input dtype must be either a floating point or complex dtype. Got: Long

torch.mean refuses to guess an output type for integer tensors — it needs floats. It's tempting to assume PyTorch "just works" the way Python's sum()/len() does, but PyTorch is deliberately stricter about numeric types, because silent int-to-float coercion has caused real bugs in production pipelines.

Dtype
3Moving a tensor to a device that isn't there›
x = torch.tensor([1.0, 2.0]).to('cuda')
AssertionError: Torch not compiled with CUDA enabled

On a machine that does have a GPU, the more common version of this failure looks different but is the same passport breaking:

RuntimeError: Expected all tensors to be on the same device, but found at least two devices, cuda:0 and cpu!

Both are the same failure: the tensor isn't where the computation expects it to be.

Device
4Calling backward() on an untracked tensor›
x = torch.tensor([1.0, 2.0, 3.0]) # requires_grad=False by default y = (x * 2).sum() y.backward()
RuntimeError: element 0 of tensors does not require grad and does not have a grad_fn

x was never told to track gradients, so there's no computation graph to walk backward through.

Grad
Worth remembering

All four of these errors stopped the program. That's the friendly case. The most dangerous version of a tensor bug is the one that changes what a model learns — and never raises a single error. That's the subject of the broadcasting section below.

Tensors & Shape Conventions

A tensor is just a multi-dimensional array — but the meaning of each dimension depends on what's being modeled. Getting the convention right is half the battle, and one convention is universal enough to memorize on its own: the batch dimension, B, always comes first.

Tabular / structured
(B, F)
32 customers × 10 features → (32, 10)
Images
(B, C, H, W)
16 RGB images, 64×64 → (16, 3, 64, 64)
Sequences / text
(B, T, D) or (B, T)
8 sentences, 20 tokens each → (8, 20)

From scalar to batch

Four tensors, four different ranks — torch.tensor() wraps data that already exists, while torch.rand/randn/zeros/ones generate data of a shape you specify.

scalar = torch.tensor(7) # a single value, e.g. one brightness reading vector = torch.tensor([2, 4, 6, 8]) # a 1D list, e.g. 4 days of temperature matrix = torch.tensor([[1, 0, 3], [4, 5, 6]])# 2 samples x 3 features batch_images = torch.rand(16, 3, 64, 64) # (B, C, H, W): 16 RGB images, 64x64
scalar shape=() ndim=0 numel= 1 dtype=torch.int64 vector shape=(4,) ndim=1 numel= 4 dtype=torch.int64 matrix shape=(2, 3) ndim=2 numel= 6 dtype=torch.int64 batch_images shape=(16, 3, 64, 64) ndim=4 numel=196608 dtype=torch.float32
Common misconception

"It's just a tensor — it should behave the same no matter how I made it." Not true. torch.from_numpy() creates a view that shares memory with the original NumPy array; torch.tensor() makes a full copy. Mutate the original array after converting it, and the from_numpy version silently changes too, while the tensor() copy stays put. One way to hold onto the distinction: from_numpy is like handing someone a key to your apartment; torch.tensor() is like giving them a photo of it.

after mutating np_arr[0] = 999: torch.from_numpy tensor: tensor([999, 2, 3]) <- changed! torch.tensor copy : tensor([1, 2, 3]) <- unaffected

Inserting a batch dimension

Models expect a batch — even a batch of one. unsqueeze(0) inserts a size-1 dimension at position 0, and it's the one-line fix every inference endpoint needs: a model trained on batches of 32 still expects a leading batch dimension when a single user request arrives.

image(3, 224, 224)
→ unsqueeze(0) →
batched(1, 3, 224, 224)
sentence(5,)
→ unsqueeze(0) →
batched(1, 5)
In practice

If logits has shape (5,) — five class scores for one sample — and a loss function expects (B, 5), the fix is logits.unsqueeze(0), one line, every time this pattern appears.

Tensor Ops Are Neural-Network Math

A network doesn't just store tensors, it transforms them. * is element-wise multiplication; @ is matrix multiplication. Confusing the two is one of the most common early bugs, because * on mismatched shapes will often silently broadcast into something unintended.

a = torch.tensor([[1., 2.], [3., 4.]]) b = torch.tensor([[5., 6.], [7., 8.]]) a * b # element-wise: [[1*5, 2*6], [3*7, 4*8]] a @ b # real matrix multiplication
element-wise a * b: tensor([[ 5., 12.], [21., 32.]]) matrix mult a @ b: tensor([[19., 22.], [43., 50.]])

A linear layer, by hand

Straight from the formula y = xWᵀ + b:

X = torch.randn(32, 10) # batch of 32 samples, 10 features each (B, F_in) W = torch.randn(4, 10) # 4 output neurons, each reading 10 features (F_out, F_in) b = torch.randn(4) # one bias per output neuron out = X @ W.T + b # (32,10) @ (10,4) + (4,) -> (32, 4)
X: (32, 10) W: (4, 10) -> out: (32, 4)

This is nn.Linear(10, 4) — literally the same computation that PyTorch's built-in layer performs. Knowing what it does under the hood is exactly what interviewers tend to probe for.

Reductions and the reduction axis

The reduction axis argument tells PyTorch which axis collapses — and the intuition runs backwards from what feels natural at first. Toggle between the two below to see the difference.

Collapsing an axis of [[10, 20, 30], [40, 50, 60]]
dim=0 collapses the sample axis — mean per feature, averaging down each column.
In practice

Normalizing a feature (subtracting the column mean) needs dim=0. Averaging a sentence's token embeddings into one vector needs dim=1 (or whichever axis is the token axis). Getting this backwards silently computes the wrong statistic — no error, just wrong numbers.

argmax on classifier logits

logits = torch.tensor([[2.1, 0.3, -1.2], # sample 0's scores for 3 classes [0.1, 3.4, 0.2]]) # sample 1's scores preds = torch.argmax(logits, dim=1) # collapse the CLASS axis -> one prediction per sample
predicted class per sample: tensor([0, 1])
Interview question: calling torch.argmax(logits) with no dim returns one number instead of a batch of predictions. What happened?
Weak answer: "It's broken, I'd just add .item()."
Strong answer: Without dim, argmax flattens the whole tensor and returns one global index — it doesn't know dim=0 is the batch axis. dim=1 is needed to get one prediction per sample, collapsing the class axis.
Check your understanding

A batch of 64 product-review embeddings, each 300-dimensional, passes through a linear layer with 5 output neurons. What is the shape of the weight matrix W, and the output?

nn.Linear-style weight matrices are shaped (F_out, F_in) — 5 output neurons, each reading all 300 input features — because the layer computes X @ Wᵀ + b, and Wᵀ needs shape (300, 5) to multiply against X's (64, 300). The output keeps the batch dimension first: (64, 5).

The Bug That Doesn't Crash

Every operation so far had shapes that matched exactly. PyTorch doesn't always demand that — a feature called broadcasting quietly stretches mismatched shapes so an operation can run anyway. Usually that's convenient. Sometimes it's a trap.

Broadcasting rule of thumb

Compare shapes from the right. Two dimensions are compatible if they're equal, or if one of them is 1 — a size-1 dimension gets stretched to match.

row = torch.tensor([1., 2., 3.]) # shape (3,) col = torch.tensor([[10.], [20.]]) # shape (2, 1) row + col # (3,) and (2,1) broadcast to (2,3)
row + col: tensor([[11., 12., 13.], [21., 22., 23.]]) result shape: torch.Size([2, 3])

The scenario: predicting delivery time

Picture a model predicting delivery ETA in minutes. In the training loop, predictions easily come out shaped (N, 1) — maybe from a linear layer with one output neuron — while the true labels are shaped (N,). Computing MSE loss the "obvious" way:

loss = ((pred - target) ** 2).mean()

No error. A number comes out. Training "works." Here's what that number is actually rewarding — comparing a model that predicts exactly right against one that ignores the input and always predicts the average:

Broadcasted diff shape inside the buggy loss: (200, 200) model BUGGY loss CORRECT loss perfect predictions 120.522 0.000 always-predict-mean 60.261 60.261
The surprise

The model that predicts every value exactly right scores worse than the model that just guesses the average every time, no matter the input.

What the buggy loss is actually averaging

A smaller, six-sample version makes the mechanism visible. pred.unsqueeze(1) - target doesn't produce six differences — it broadcasts (6,1) against (6,) into a full (6,6) grid, comparing every prediction against every target:

(predi − targetj)² for 6 samples
The .mean() call averages all 36 cells — only the 6 diagonal cells (i = j) are the pairs actually meant to be compared.
target index j →
↑ prediction index i (reading top to bottom)

The diagonal — where i = j — is all near-zero, because those are the pairs that actually match. But .mean() averages all 36 cells, and the 30 off-diagonal cells compare a prediction to a completely unrelated target. Those large, meaningless errors dominate the average. A model that predicts the same constant everywhere never suffers this problem, because being "wrong" against a random target is no worse than being "wrong" against the right one — so the buggy loss can't tell the two models apart properly, and ends up preferring the lazy one.

Deeper understanding

"No error" does not mean "correct." Shape mismatches that broadcast are the most dangerous bugs in deep learning precisely because they run.

The fix

Assert that shapes match before computing a loss — a real engineering habit, not paranoia:

def safe_mse(pred, target): assert pred.shape == target.shape, f"shape mismatch: pred {tuple(pred.shape)} vs target {tuple(target.shape)}" return ((pred - target) ** 2).mean()
Caught before it could silently corrupt training: shape mismatch: pred (8, 1) vs target (8,) fixed loss: 1.516536831855774

PyTorch's own built-in loss function actually warns about this exact bug:

UserWarning: Using a target size (torch.Size([8])) that is different to the input size (torch.Size([8, 1])). This will likely lead to incorrect results due to broadcasting. Please ensure they have the same size. loss value (still computed, still wrong): 2.3656139373779297
In practice

This exact bug has shipped to production at real companies — a ranking model that mysteriously preferred "safe," generic predictions over accurate ones, traced weeks later to an (N,1) vs (N,) mismatch in the loss. The model wasn't "bad at learning" — it was learning the wrong objective perfectly.

Interview question: a model trains without errors, the loss goes down, but predictions all converge to nearly the same value regardless of input. First hypothesis?
Strong answer: Before touching hyperparameters, print the shapes going into the loss function — a broadcast-induced loss is a classic cause of a model that appears to train but learns to ignore its input.
Check your understanding

loss = ((pred - target) ** 2).mean() where pred has shape (16, 1) and target has shape (16,). What does this actually compute?

Broadcasting aligns shapes from the right: (16, 1) and (16,) become (16, 16) after the size-1 dimension stretches to 16, and PyTorch compares every prediction against every target before averaging. These shapes broadcast without error — that's exactly what makes the bug dangerous.

Dtype & Memory

Shape decides whether an operation runs at all. But even with perfect shapes, the number type stored in a tensor decides both correctness and cost.

int_tensor = torch.tensor([1, 2, 3]) float_tensor = torch.tensor([1.5, 2.5, 3.5]) (int_tensor + float_tensor).dtype # auto-promotion
int tensor dtype : torch.int64 float tensor dtype: torch.float32 int + float dtype (auto-promotion): torch.float32
Worth noting

PyTorch auto-promotes mixed dtypes in arithmetic (int + float → float), which feels convenient — but it will not auto-promote in stricter operations like torch.mean(), or in loss functions expecting long labels. That's exactly the error from the second failure signature above.

Memory is parameter count × bytes per parameter

This shows up in every "why can't we fit this model on our GPU" conversation. For a 7-billion-parameter model — a common "small" open LLM size:

GB required for weights at 7B parameters, by precision
Dashed line marks a 24 GB GPU (e.g. a single RTX 4090 or L4).
In practice

This arithmetic — not a benchmark, not a paper, just parameters × bytes — is the first question in almost every "can we deploy this model" conversation. fp32 doesn't fit on a 24 GB card; bf16 fits comfortably with room for activations; int8 and int4 shrink further but cost accuracy.

Interview question: serving a 7B model on a single 24 GB GPU, keeping as much accuracy as possible. Which precision, and why not quantize further to be safe?
Strong answer: bf16 — it already fits in 13 GB, leaving headroom for activations and KV-cache, and it preserves noticeably more accuracy than int8. Quantizing further only makes sense if memory-constrained even at bf16, or higher throughput is needed.
Check your understanding

A model has 3 billion parameters. In float32 it needs about 11.2 GB for weights. Roughly how much memory in int8?

Memory scales directly with bytes-per-parameter: float32 uses 4 bytes, int8 uses 1 byte — a 4× reduction, so 11.2 GB becomes roughly 2.8 GB. (float16/bfloat16, at 2 bytes, would be the "half of float32" answer — that's not what int8 is.)

Autograd: How PyTorch Learns

Storing data correctly, shaping it correctly, and typing it correctly isn't learning. Nobody hand-derives the chain rule for a network with a million weights — so who does it, and how do you know it isn't lying to you?

Three ways to check one gradient

Setup: loss(w) = (w·x − y)², with x = 4, y = 10, starting w = 2. By the chain rule, d(loss)/dw = 2·x·(w·x − y).

Three independent methods, one answer
Hand-derived
−16.0000
Autograd
−16.0000
Finite-difference
−16.0000

All three methods agree. This is worth sitting with: autograd isn't magic — it's the same chain rule done by hand, applied automatically to a graph of operations. loss.backward() walks that graph backward and fills in .grad for every tensor with requires_grad=True.

Common misconception

"Autograd computes symbolic derivatives, like a computer algebra system." It doesn't — it's numeric, recording the exact sequence of operations that ran (the graph), not manipulating an equation symbolically.

Gradients accumulate by default

Calling .backward() doesn't overwrite .grad — it adds to it. Three calls in a row on the same w, with no reset in between:

w.grad after each call
−16
call 1
−32
call 2 (no reset)
−48
call 3 (no reset)
−16
after zero_grad()

Each backward() call adds −16 to whatever was already stored, so it climbs −16 → −32 → −48. This is by design, not a bug — it's what enables accumulating gradients across several small batches to simulate one large batch, which is how teams train big models on GPUs too small to fit a large batch at once.

Interview question: why does PyTorch accumulate gradients instead of resetting them automatically before every backward()?
Strong answer: It's a deliberate design choice that enables gradient accumulation — summing gradients over several smaller batches before one optimizer step — simulating a large effective batch size on a GPU that can't fit it in memory at once. The cost: remembering to call zero_grad() when accumulation isn't wanted.

no_grad() vs. detach()

Sometimes a computation should happen without building a graph at all — for inference, or for a manual parameter update that shouldn't itself be tracked.

with torch.no_grad(): w_updated = w - 0.1 * torch.tensor(4.0) # w_updated.requires_grad -> False y = w * 3 y_detached = y.detach() # y.requires_grad -> True | y_detached.requires_grad -> False

no_grad() is a context — it turns off tracking for everything inside it. detach() operates on a specific tensor — it cuts that one tensor loose while everything else keeps tracking. Both exist because building a graph costs memory; for inference, where .backward() is never called, tracking is pure waste. (torch.inference_mode() is a newer, slightly stricter, slightly faster version of no_grad() for pure inference code.)

In practice

Forgetting no_grad()/inference_mode() during inference is a classic cause of a production service that mysteriously uses far more GPU memory than the model size would suggest — every forward pass silently builds a graph nobody will ever call .backward() on.

Check your understanding

loss.backward() is called twice in a row on the same computation graph, without zero_grad() and without recreating loss. What happens on the second call?

By default, PyTorch frees the graph's saved intermediate tensors after backward() runs, to save memory — calling backward() again on the same graph without retain_graph=True raises a RuntimeError. This differs from calling backward() on a new loss computed from the same w (the accumulation case above), which builds a fresh graph each time.

Recap: The Four Passports

PassportQuestion it answersWhat breaks if it's wrong
ShapeDoes it fit?Crash, or worse — silently wrong math
DtypeIs it the right number type?Crash, or silent precision loss
DeviceIs it in the right place?Crash, or silent slowdown
GradIs it being tracked for learning?Model doesn't learn, or memory blows up
  • "No error" is not "correct." The broadcasting bug computed a confident, wrong number with no error at all — the single most expensive category of bug in this read.
  • The batch dimension always comes first. Internalizing (B, …) prevents a huge share of shape confusion before it starts.
  • Memory is just arithmetic. Parameter count × bytes per parameter decides whether a model fits on the hardware available.
  • Gradients accumulate by default. zero_grad() is a habit, not a formality.
  • Autograd is numeric, not symbolic — and it's always verifiable against a hand derivation or a finite-difference check.
