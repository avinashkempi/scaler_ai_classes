Preface

From a model that scores well to a project that can be called

A model that runs cleanly inside a notebook is not yet a project. Nothing about it can be called by another system, run by somebody else, or explained three months from now. A repository with a history says which version of a script produced a result. A search that tunes hyperparameters finds a good configuration instead of a guess. An app that puts a model in front of a person is useful. None of those three, on their own, is a project.

This read builds one. A program that turns a raw table into a versioned artifact whenever a single command runs. A second that loads that artifact and answers over HTTP, so anything on the network can ask it a question. A third — the console — that holds no model at all and asks the service the same way everybody else does.

FastAPI is the framework doing the serving, and it earns its place through one idea: a function's type annotations become the parser, the validator, and the published documentation all at once, so the contract between caller and service has nowhere to quietly go stale.

What this walkthrough covers

  • What an API promises, how an HTTP request and response are actually shaped, and how GET and POST differ.
  • What uvicorn and ASGI each do, and what's left for application code to do.
  • Laying out training, serving, and the interface as three programs that share one artifact — and what that boundary buys.
  • Producing a training entry point that writes a versioned artifact carrying its threshold, its category vocabulary, and the commit that built it.
  • Reading a metadata file as a contract, and naming the fields a service could never work out on its own.
  • Expressing a model's input contract as a schema that keeps a raw file's quirks out of the public interface.
  • Measuring what a batch endpoint is worth, and what it costs to offer one.
  • Building a console as a client of a service rather than as a second copy of it.
  • Five ways a service fails silently — and how each one shows up as nothing more alarming than a 200.
  • Choosing between promoting a model and promoting the training code, and between a service and a dependency.

Prerequisites. Comfort with Python, pandas, and enough scikit-learn to fit a classifier and read a metric. No prior web development — HTTP, APIs, and the framework are built up from first principles.

Chapter 01

The problem, and what has to exist at the end

A model that scores well and a model that can be used are not the same thing.

A Portuguese bank sells term deposits by phone from a call list. Historical campaign data covers 41,188 calls across 20 features, and roughly 1 call in 9 converts.

No subscription
88.73%
Subscribed
11.27%

Predicting who is likely to subscribe is a familiar exercise. Getting those scores in front of the people who need them is the hard part. A batch process, a real-time dialler, and a campaign manager's console all need a score — and none of them can execute a notebook cell.

Take a notebook model that scores well and runs without errors, and ask three questions of it.

Who can call it?

Only the person who wrote it. It lives in a kernel or an app started by hand. The dialler can't reach it, and neither can a nightly job.

What does it expect?

The author knows, because they wrote it. That knowledge lives in their head and in the order of some cells — not anywhere a caller can read it.

Which version answered?

If a campaign goes badly in six weeks and somebody asks which model produced the list, the honest answer is usually a shrug.

None of those are modelling problems, and a better score fixes none of them. They're fixed by one move: stop treating the model as the last thing produced, and start treating it as a file other programs load.

That single move decides everything that follows. A program that turns a raw table into a file whenever one command runs. A second program that loads that file and answers over HTTP, so anything on the network can ask. A third, for the campaign manager, that holds no model at all and asks the service like everybody else.

Chapter 02

The project: three programs, one artifact

The shape of the whole design, before any of the code.

Three programs and the file that passes between them make up the entire architecture. The pieces share files, not code imports — the serving application never imports the training package, and the console imports neither. Select each piece below.

Turns the raw table into a fitted pipeline. Runs offline, on its own schedule, and never touches a network socket. Its only output is the artifact to its right.

model.joblib and model_meta.json: a simple pair of files that can be copied, versioned, or rolled back at any time. Every feature assumption made during training has to be written down here, in the open, for serving to read — which is the whole benefit of not sharing code imports.

Loads the artifact once and answers single requests over HTTP. Handles one prospect at a time, online, while an agent or a dialler waits for the answer.

Holds no model, no threshold, and no category vocabulary. It's a client of the service, exactly like the dialler, and reads everything it displays from the service's own /model endpoint.

This decoupling buys three things. Programs run on independent schedules — training chews through the whole dataset offline, while serving answers one request at a time online. The artifact becomes a simple file that can be copied, versioned, or rolled back. And because there's no shared code to lean on, every assumption made during training has to be written down somewhere serving can read it — which is what actually catches bugs early.

The repository layout

The rest of this project runs against this structure. File order is forced by dependency: campaign/data.py decides what a row is, so everything else has to agree with it first.

Chapter 03

What an API promises, and how HTTP carries it

Four ideas, and none of them belong to Python.

An API is a promise about messages

API stands for application programming interface, and the word doing the work is interface — the part of a program other programs are allowed to touch, together with a promise that it keeps behaving the way it was described. pipeline.predict_proba(frame) is one such promise, with no network anywhere near it: scikit-learn promised a name, an argument, and a return value, and calling code leans on that promise rather than on how the library works inside.

A web API is the same promise with a network in the middle, and the network removes everything that used to be implicit. The two programs no longer share a process, so they can't hand each other objects. They no longer share a language, so a Python dictionary means nothing on the other side. They no longer share a machine, so either one can restart mid-exchange. Four things have to be agreed in advance instead: where to send a message, what to send in a format both sides can read, what comes back and what each field in it means, and what happens when it goes wrong — a status code the caller can act on, because an exception can't cross a network.

HTTP is two messages

HTTP is plainer than its reputation. A request carries a method, a path, some headers, and sometimes a body. A response carries a status code, some headers, and usually a body. Everything else in HTTP is detail layered on those two shapes. Below is a real exchange with this project's own service, captured line by line as it actually crossed the socket — select any line for what it means.

REQUEST — sent by the client RESPONSE — sent back by the service
What this line means

The entire request line: a method, the path being asked for, and the protocol version. Nothing else about the request is on this line.

A header — a name/value pair describing the request rather than being the request. Host says which name was used to reach this machine.

Identifies the program that sent the request — here, the curl command line tool.

What the client is willing to receive back. */* means "anything."

Not spacing — this blank line is the separator between headers and body. A GET has nothing to send, so the body is empty.

The status line: protocol version, then 200, the number a caller actually branches its logic on.

Tells the client how to read the bytes that follow — the header that matters most to a program parsing the answer.

The size of the body in bytes, so the client knows exactly when to stop reading.

Names the program that wrote these bytes — the ASGI server this project runs on, introduced in the next chapter.

The body itself: a small JSON object reporting whether the model loaded and which commit built it.

HTTPS is exactly this, inside an encrypted connection. The request and response don't change shape — the whole exchange simply travels inside TLS, so nobody in between can read or alter it. A service usually keeps speaking plain HTTP on a port only a proxy can reach, and the proxy holds the certificate.

GET and POST

The method is the verb of the request, and two of them cover nearly everything a model-serving project needs.

VerbCarriesChanges the server?Used here for
GETNothing — everything needed goes in the URLNo, by convention/health, /model, /docs
POSTA bodyMay, and callers can't assume it's safe to retry/predict, /predict/batch

A prediction changes nothing on the server, so by that rule it ought to be a GET. It's a POST here because of the body, not the verb — a prospect is fourteen fields, and putting fourteen fields in a URL means encoding each one, meeting length limits nobody agrees on, and watching every value land in an access log. Scoring data belongs in a body, which makes it a POST.

Two ways a caller gets it wrong

Real responses from this service
RequestResultWhat it means
GET /predict — right path, wrong verb405The path exists and refuses this method. The response names what it would accept: allow: POST.
POST /predictions — good verb, wrong path404No such path exists, whatever verb is used.

A caller reporting the API is "down" and showing a 404 has a typo. A caller showing a 405 read something and then did something else. Neither is an outage, and telling them apart saves an afternoon of debugging.

Postman, and the document that fills it in

Most teams keep the same requests saved in Postman, a desktop app that sends HTTP and lays out what came back. Nothing about the request changes — Postman is a form over the same four things above.

None of it gets typed by hand, though. This service already publishes a machine-readable description of itself at /openapi.json — a 6 KB document listing all 4 endpoints and pre-filling the 14 fields of a POST /predict body. Postman (or anything else that reads OpenAPI) imports that file and builds the entire collection from it. The interactive /docs page in a browser is built from the same document, so the page, the collection, and the service can never quietly drift apart from one another.

Chapter 04

FastAPI: the annotation is the interface

One idea, applied over and over.

A web server owns the socket — it listens on a port, accepts connections, reads bytes in, writes bytes out, and knows nothing about prospects. An application is the Python being written — handed an already-parsed request, and returning a response for somebody else to send. Between the two there has to be an agreement about how work is handed over, or every server would only work with one framework. In Python, that agreement is ASGI (the Asynchronous Server Gateway Interface). uvicorn is the server. A FastAPI app is the application. ASGI is the plug between them — which is why either side can be swapped without touching the other.

What FastAPI adds is one idea, applied repeatedly: the function signature is the interface. The parameters declared, and the types they're annotated with, are read at import time and turned into a parser, a validator, an error formatter, and a machine-readable description — all four derived from a signature nobody had to write twice.

Why none of this needs async

FastAPI is built on an asynchronous framework, yet every handler in this project is a plain def. A handler declared async def runs on the event loop, sharing a thread with every other request — the right shape when a handler spends its time waiting on something else. It's the wrong shape when a handler computes: predict_proba calls into compiled code and never awaits, so writing it async def would block the loop for every other caller. Written as plain def, FastAPI runs it in a worker thread instead and the loop stays free. The rule: waiting on the network, async def; doing arithmetic, def.

Five short scripts show the mechanics in isolation. Each tab below pairs the code with real requests sent to it and the real responses that came back.

snippets/01_hello.py

from fastapi import FastAPI

app = FastAPI()

@app.get("/ping")
def ping():
    return {"pong": True}

One file, one function, one decorator. GET /ping → {"pong":true} [200]. Nobody wrote /openapi.json or /docs either — FastAPI generates both from this function, and both answered 200 too. The documentation page is built from the same annotations that do the parsing, so it's the one kind of API documentation that can't go out of date.

This is the setting the prediction endpoint uses later: a model service tends to accumulate internal numbers, and the response is the one place an internal number quietly becomes somebody else's dependency.

Chapter 05

Training the artifact, in four files

Everything in campaign/ exists to produce one file.

5.1 · data.py — where the data decisions live

Every other file has to agree with this one about what a row is. Three decisions here are invisible in a describe() and decide whether this is a real project or a demo.

Drop duration

Call duration is, by far, the strongest single predictor — mean 258.3 seconds, median 180, and a max over 4,900 seconds. It's also completely unusable: at prediction time, before the call happens, duration doesn't exist yet. A feature only belongs in a model if its value is actually available the moment a prediction is needed.

Split pdays into a flag and a count
999 (never contacted) · 96.3%
real value · 3.7%

96.3% of rows carry the sentinel value 999, meaning "never previously contacted." Genuine values run only from 0 to 27 days. Left as-is, a model reads that sentinel as "contacted 999 days ago" for almost every row. The fix is a boolean previously_contacted flag plus a pdays column that's only meaningful when the flag is true — and the service applies the identical rule at request time.

emp.var.rate, cons.price.idx, cons.conf.idx, euribor3m, and nr.employed describe the Portuguese economy on the day of the call, not the prospect. A dialler knows a prospect's age or job; it has no way to know the quarterly Euribor rate. These five values have to be supplied by the serving side, not sent by the caller.

Leave "unknown" categories alone

A missing answer carries its own predictive signal, distinct from a negative one — so the encoder gets a dedicated unknown column instead of an imputed guess.

5.2 · pipeline.py — one estimator, not four steps

A fitted Pipeline is the one object that carries training-time transformations along with it — which categories an encoder saw, what a scaler's medians and ranges were. None of that lives in source code. At serving time there's one prospect and no training set, so nothing can be refit; a pipeline pickles as one object and carries its learned state with it.

Numeric branch

Median imputation, then standard scaling. Fills the pdays gaps left by the earlier split.

Categorical branch

One-hot encoding with handle_unknown="ignore" — a value the encoder never saw becomes a row of zeros rather than an error.

Two arguments here look like training details and are really serving decisions. handle_unknown="ignore" decides what happens when a category the encoder never saw arrives; remainder="drop" decides what happens to a column nobody asked for. Both are sensible library defaults, and both are ways of not telling anybody something went wrong. That's exactly what the request schema in Chapter 6 exists to police instead.

5.3 · tune.py — letting the search choose the model

Optuna searches over the model family and its parameters together, because the parameter space only exists once a family is picked — no grid can express that. The search's own history is stored in a SQLite file rather than kept in memory, so a run can be interrupted, resumed by a different process, or inspected next week. This project shipped with 60 stored trials; running five more from a separate process brought the total to 65 without losing anything already found.

5.4 · train.py — the artifact, and what it has to carry

Training replays the winning trial's own search logic rather than hand-translating parameter names — a trial records hgb_l2, but the estimator expects l2_regularization, and any manual mapping is a second place that translation can go wrong. The command also records git provenance: which commit built the artifact, and whether the working tree was clean at the time — the cheapest useful answer to "which code produced this."

The interesting output of a training run isn't the model file — it's the JSON beside it. model_meta.json is a contract, and it's worth reading field by field.

"decision_threshold": 0.22

A number derived from data — scikit-learn will not pickle it. Without it, the service has to guess, and the guess is 0.5.

"feature_order": [ …20 columns… ]

The exact column order the pipeline was fitted with, so the service can build its frame from metadata rather than from a list somebody typed into the serving file by hand.

"categories": {
  "poutcome": ["failure","nonexistent","success"], …
}

What the fitted encoder actually saw, column by column. The most useful — and most often omitted — field in the file, because it's exactly the vocabulary the request schema needs to enforce.

"git": {"commit": "5692338…", "dirty": true}

Which code produced this artifact, and whether the tree had uncommitted changes at the time. Somebody holding only a prediction can read the model version, ask /health for the commit, and land on the exact source that built it.

"sklearn_version": "1.9.1"

Answers whether the artifact will even unpickle correctly. requirements.txt pins this exactly, while everything else only sets a floor.

5.5 · The threshold is a serving decision

predict() calls a positive anything at or above probability 0.5 — a convention, not a result. It's the right cut only when a false positive and a false negative cost the same, and here they plainly don't: a false positive is a wasted phone call, a false negative is a customer who would have said yes. It's also the wrong cut for a rare event — with roughly 1 subscriber in 9, a rule that only calls when the model is more than half sure will hardly call anybody. The threshold is a business choice, and a serving one: it can change without retraining, which means serving code has no way to work it out for itself and it has to travel with the model.

Scored on the same 10,297-row holdout, 1,160 of whom actually subscribed

People called4261,474

The stored threshold reaches more than twice as many subscribers as the library default, but by calling a lot more people — precision drops as recall rises. Neither number is universally correct; deciding which trade to accept needs a business view of what a call costs against what a deposit is worth, and the model alone can't make that call. What matters here is that this cutoff defines the model's behaviour just as much as its internal parameters do — and a serving layer that quietly falls back to predict() will miss hundreds of real subscribers without raising anything. Chapter 10 measures exactly that.

Chapter 06

The contract: app/schemas.py

A schema is the way a service says no.

Whatever a schema doesn't reject, it accepts — and then the model has to have an opinion about it. The real question when writing one isn't what a valid request looks like. It's what's the worst request you're willing to score.

The Customer model uses Literal types wherever the encoder learned a fixed vocabulary, so a field like month doesn't accept a string — it accepts one of ten specific strings, the same ten the encoder saw. extra="forbid" turns an unrecognised field into a 422 instead of a silent drop, because a caller sending day_of_the_week instead of day_of_week has a bug worth surfacing immediately rather than three weeks later in a campaign report.

Chapter 07

The service: app/main.py

Four decisions turn a request into an answer.

uvicorn app.main:app — and the module that command names. Each decision below has a lazier version that works fine on a laptop and causes real trouble later.

Where the model is loaded

@asynccontextmanager
async def lifespan(app: FastAPI):
    try:
        app.state.bundle = load_bundle()
    except Exception:
        app.state.bundle = None
        raise
    yield

lifespan runs once, before the first request, and the loaded bundle lives on app.state. The lazy alternative loads inside the handler, so every single caller pays for the file read and the unpickle. Notice what happens if the artifact is missing: nothing catches the error, so the process refuses to start. That's deliberate — a service that starts without a model looks healthy to whatever is watching it, and returns errors to real traffic. Failing at deploy time is far cheaper than failing quietly in production.

Where a request becomes a row

def to_row(customer: Customer, bundle) -> dict:
    row = customer.model_dump()
    row.update(contact_features(row.pop("days_since_last_contact")))
    row.update(bundle["context"])
    return row

Three sources meet in four lines: the fourteen fields the caller sent, the two contact columns derived by a shared rule, and the five economic values the service holds. contact_features is the single function imported across the boundary between campaign/ and app/ — the one exception to these programs talking only through files. The reason: anything fitted travels inside the pickled artifact; anything merely decided, like treating an uncontacted customer as having no contact date, is ordinary Python a pickle can't carry. Retyping those two lines here would have created a second copy of the same rule to keep in sync forever.

Where the decision comes from

def score(frame, bundle) -> list[Prediction]:
    threshold = bundle["meta"]["decision_threshold"]
    proba = bundle["pipeline"].predict_proba(frame)[:, 1]
    return [Prediction(subscribe_probability=round(float(p), 4),
                       call=bool(p >= threshold), threshold=threshold, …)
            for p in proba]

predict_proba, compared against the metadata's threshold — never predict(), because predict() means 0.5, and 0.5 isn't this model's number. The caller gets back the probability, the decision, the threshold that produced it, and the model version — nothing else, because the endpoint declares response_model=Prediction.

What an endpoint actually is

@app.post("/predict", response_model=Prediction)
def predict(customer: Customer, request: Request):
    bundle = get_bundle(request)
    return score(to_frame([customer], bundle), bundle)[0]

Three lines, two of them the functions above. The decorator says which method and path; the annotation customer: Customer is what makes FastAPI parse, validate, and answer the caller itself if the body doesn't fit. Everything difficult has already happened by the time the first line of the body runs.

/health reports on the model, not the web server — it names the commit that built the artifact, so somebody debugging a strange call list can read that without opening the repository. /model publishes the threshold, the metrics, and the full category vocabulary, so a client never has to hardcode a value that might change the next time somebody retrains.

7.1 · What a batch endpoint is worth

An overnight job doesn't want one prospect — it wants tomorrow's whole call list. There are two ways to give it one: call /predict in a loop, or call /predict/batch once.

200× in a loop
984 ms
One batch call
5.2 ms

≈191× faster. Almost none of that gap is the model. A single call spends its time on connection handling, JSON parsing, and a predict_proba call on a one-row frame — about as inefficient as scikit-learn gets. The batch call pays for the round trip once and hands the pipeline a 200-row frame, the shape it was written for. The trade: the batch endpoint caps at 1,000 prospects per call, and it rejects the whole batch if a single prospect is malformed — a defensible, deliberate choice rather than an accident.

No model loaded (never seen here)503Running, but not ready — the code a load balancer understands as "send traffic elsewhere"

Nothing on that list needed a try block or a hand-written error body.

Chapter 08

The console: dashboard/app.py, a client of the service

A campaign manager wants to try a prospect and see a number.

There are two ways to build the console the manager uses, and the choice is the interesting part.

Load model.joblib directly. One import, and it's what a demo app usually does. It also means the threshold gets applied in two places, the feature frame gets built in two places, and the economic context gets injected in two places — every one of those is a rule that now exists twice, which is exactly the drift this whole project exists to prevent, just moved to a new address.

Be a client, like the dialler. The console posts to /predict the same way any other caller does, so there's exactly one place in the entire system where a prospect becomes a probability. It's also the only version that answers the question this project started with, because software can't call a Streamlit app — the nightly job can't post to it, and neither can the dialler.

@st.cache_data(ttl=60, show_spinner=False)
def fetch_model_card(api):
    response = requests.get(f"{api}/model", timeout=TIMEOUT)
    return response.json()

Every dropdown, the threshold, and the metrics shown come from this one cached call to /model. Nothing about the model is written down in the console, so a retrain that adds a category reaches the interface without anybody editing it. The cache isn't an optimisation flourish — a Streamlit script reruns top to bottom on every interaction, so without it this would be one HTTP call per keystroke.

Driven headlessly (the way its own tests would), the console holds up exactly as expected:

Cold prospect

Warm prospect

41.1%

The batch tab reports plainly: "1 of 3 clear the service's threshold of 0.22." No exceptions anywhere. And because the console and the service are now genuinely dependent on each other, it has to have an opinion when the service is down — pointed at a port with nothing behind it, the console shows a plain sentence rather than a stack trace:

"No answer from http://127.0.0.1:9. Start the service with uvicorn app.main:app."

A sentence and a next step, rather than a traceback — the difference between a page a campaign manager can act on and a page they forward to somebody else.

Chapter 09

Tests: what proves the seam holds

Four files that don't check whether the model is any good.

They check that the parts still agree with each other — because that's what breaks, and it breaks without ever moving a score.

........................ 24 passed in 0.75s

test_data.py

Pins the data decisions — including an assertion that duration is still in the raw file, so the day the dataset changes, the leakage lesson fails loudly instead of quietly becoming untrue.

test_features.py

Checks that training's frame-wide rule and serving's single-value rule for pdays agree on real rows — the exact setup that produces skew if the two implementations drift.

test_contract.py

Asserts the sentinel never leaks into the public interface: pdays and previously_contacted are absent from Customer; days_since_last_contact is present.

test_api.py

The skew test, and the one worth copying into any project — detailed below.

def test_the_service_agrees_with_the_pipeline_it_serves(client, prospect):
    served = client.post("/predict", json=prospect).json()
    frame = to_frame([Customer(**prospect)], bundle)
    direct = bundle["pipeline"].predict_proba(frame)[0, 1]
    assert served["subscribe_probability"] == pytest.approx(direct, abs=5e-5)

Score the same prospect twice: once through HTTP, with JSON parsing, schema validation, and frame-building in between; once by calling the pipeline directly, the way training does. Require the two numbers to match within 5×10⁻⁵. A serving layer that reorders a column, derives the contact features differently, or forgets the economic context passes every other test in the file — because the others only check that the response has the right shape. This six-line test is the only one that can catch training and serving quietly drifting apart.

Chapter 10

Five things that break quietly

Every one of them returns 200.

A service that returns 500 gets noticed within the hour. A service that returns 200 and a slightly wrong number gets noticed when somebody audits a campaign — if ever. Silence, not severity, is the criterion below.

The category the encoder never saw

An upstream system starts capitalising its values — "cellular" becomes "Cellular". Nobody deployed anything; a client library was upgraded elsewhere.

One column corrupted
2.2%
All ten corrupted
4.1%

Asked directly, handle_unknown="ignore" turns the unrecognised value into a row of zeros — the model reads it as a prospect with no contact channel and scores it anyway, indistinguishable from a valid input. Hundreds of bad recommendations pass through silently. Routed through the API service instead, the same corrupted request is rejected outright:

422 
{"detail":[{"type":"literal_error","loc":["body","contact"],
 "msg":"Input should be 'cellular' or 'telephone'","input":"Cellular"}]}

The caller's integration tests fail, the string gets corrected, and no bad recommendation ever reaches production. Typing the field with Literal is what stops the bad input before it reaches the encoder at all.

The threshold nobody carried across

This one needs no bad data at all — somebody writes the obvious version:

# Not in this project — the version written by accident
recommendation = pipeline.predict(frame)[0]   # looks right, means 0.5
predict(), means 0.5

399 subscribers — 34% of everybody who would have said yes — never called. No error, no bad input, no exception. Every request succeeds, the response shape is correct, and a dashboard stays green. The only symptom is a call list that's shorter than it should be, with nothing to compare it against.

The context that went stale

The service supplies five economic values from market_context.json, written once at training time. Nothing updates them — a deliberate, documented shortcut with a real cost.

Honest context
11.2%
Drifted context
19.3%

17.9% of decisions change — 1,841 of 10,297 — from a shift in two numbers nobody in the calling system has ever heard of. No error, no warning, no field anywhere saying how old the context is.

Holding the last known values is a reasonable first implementation — it beats making the dialler send them. The shortcut isn't wrong; it's invisible. A cheap fix — recording the date the context was captured, returning its age in the response, and marking /health degraded past some agreed number of days — wouldn't remove the staleness, only stop it being silent.

The artifact reloaded on every request

Loaded once (lifespan)
0.39 ms
Reloaded per request
5.30 ms

The gap is the cost of the file read and the unpickle, paid once per request by the lazy version. A small logistic regression from earlier in a course might cost half a millisecond to reload — a rounding error. A larger ensemble is a different object, and nothing in the handler changes to warn anybody. There's a second cost a mean hides entirely: under concurrency, every request in flight holds its own copy of the model, so a service comfortable at one request at a time can fall over at fifty for reasons that look exactly like a memory leak.

The health check that only proves the port is open

The most common health endpoint in production is {"status": "ok"}. It answers a question nobody asked — an orchestrator wants to know whether to send this process traffic, and a process can be listening while its artifact is missing, corrupt, or unpickled under a scikit-learn that quietly renamed an attribute.

That's why the trained version is written into the metadata rather than left for a deployment to get right by luck.

Chapter 11

Ways to ship this

Three decisions every project like this one meets.

11.1 · Promote the model, or promote the code

Train wherever's convenient, then move the artifact itself to production and let the service load it. What travels between environments is a file. Production never trains, and the model being served is byte-for-byte the one that was tested. Suits a model retrained a few times a year with somebody signing off each time — rolling back is copying the previous file back.

Move the training code to production and let it train there, on production data, on a schedule. What travels is a commit, not a large binary. The only option when production data legally can't leave production — ordinary in banks and hospitals — and far less work than shipping a new file every night if retraining happens nightly.

11.2 · Where the artifact lives

This project commits its artifacts to git — not the usual advice, but reasonable for a few hundred kilobytes that change only when somebody retrains: a clone can serve predictions immediately, with nothing to download. Past a few megabytes, or with a nightly retrain, that stops being true, and the artifact wants a store of its own with the repository holding only a pointer.

Committed to git

Fine at a few hundred KB, changing rarely. History bloats past a few MB.

A dedicated store

The repository holds a pointer; the artifact lives elsewhere. Scales to frequent retrains.

Baked into the image

What ships is one unit — no question which model a running process loaded. A new model means a new image.

11.3 · A service, or a dependency

The console chose to be a client rather than load the model itself — a choice with names in architecture documents.

Model-as-ServiceModel-as-Dependency
ShapeBehind its own API, reached over HTTPShips as a library, loaded inside the caller
CostsA network hop, a deployment to runNothing — no process that can be down
BuysOne place a prospect becomes a probability; a caller that need not be PythonSuits one application that owns its model outright
This projectchosen — the dialler is written by another team 

A dependency isn't the amateur option — it's right for a model inside a mobile app, where the network isn't always there. It stops being reasonable the moment a second caller needs the same answer, because the scoring logic then exists in two places. Batch scoring is a third, easy-to-forget option: if the only caller is a nightly job, a scheduled script that writes tomorrow's list into a table is simpler than a service and never wakes anybody at 3 a.m. The question worth asking before any of the others: is anything actually waiting for the answer?

11.4 · Running it the way a deployment runs it

Every command so far has been the development one. --reload watches files and restarts on change — useful while writing, with no place on a server. --host 0.0.0.0 replaces 127.0.0.1 once other machines need to reach the port. --workers N starts N independent processes behind one port — the way a Python service uses more than one core, since Python runs one thread of bytecode at a time. Each worker is a separate process with its own copy of the model in memory.

Capacity planning for a model service is a multiplication, not a division — each worker's memory is the model plus pandas plus scikit-learn, not a share of one copy. A large artifact costs more than the disk it sits on.

Chapter 12

What's still missing

Naming it accurately is more useful than a diagram.

No memory of past runs

The metadata names the commit and the ROC AUC this artifact reached, and nothing about what last month's model reached. If tomorrow's retrain is worse, there's no way to compare — only one of the two runs still exists. Tying a run to its inputs, code, and result is experiment tracking.

The environment is still yours

The service runs because pinned requirements were installed by hand. Making the environment part of what ships is containerisation — the groundwork is already done: dependencies are pinned, entry points take no arguments, and configuration is read from files.

Nothing watches the predictions

The holdout was scored once, the day it was split. A model can go wrong without anybody changing anything. Every response already carries a model version — the hook monitoring needs — and nothing consumes it yet.

What changed is smaller than the file count suggests. Three programs now agree through files, and everything they must agree about is written in those files rather than remembered. Every silent failure in Chapter 10 was something true about the model that was never written down — a vocabulary, a threshold, an economy, a library version. The pattern isn't that FastAPI is good. It's that a boundary forces assumptions to be named, and named assumptions are the only kind that can be tested.

Chapter 13

Class summary

A model that scores well is one file. A project is several programs that agree about that file.

The split is campaign/ producing an artifact, app/ serving it, and dashboard/ consuming the service — one function crosses that boundary, and the rule for what's worth keeping shared is simple: anything fitted travels inside the pickle; anything merely decided has to be shared as code, or it gets written twice and eventually differently.

Training was kept short on purpose, and it left three things behind that serving could never have worked out alone: the decision threshold, a business choice rather than a modelling result; the category vocabulary the encoder actually saw; and the commit that built the artifact, flagged for whether the tree was clean. All three live in a five-kilobyte JSON file next to the model, and each one turns up again as a failure mode the moment it's missing.

An API is a promise about messages, and HTTP is the shape those messages take — a method, a path, headers, sometimes a body going out; a status code, headers, and usually a body coming back. FastAPI earns its place through one idea: the function signature is the interface, so the same annotation that documents a field also parses it, validates it, and rejects what doesn't fit.

The five failures, in one line each

An unseen category changes a decision and raises nothing. A serving layer that calls predict() silently uses 0.5. A frozen economic context goes stale invisibly. A reloaded artifact costs latency that grows without anyone deciding it should. A health check that proves the port is open proves nothing about the model.

The shipping decisions

Whether the model travels or the training code does. Where the artifact lives — repository, store, or baked into an image. Whether the caller even wants a service, or would have been happy with a file written overnight.

The console holds no model, no threshold, and no vocabulary — it asks the service for all three, because a client that loads the artifact itself is a second copy of the scoring logic to keep in step forever. A service isn't an alternative to a console. It's the thing a console is a view of, and the only one of the two that other software can actually call.
