      Classification metrics & imbalanced data

      Handling Imbalanced Data

      Post Read

      A model can be 99.5% accurate and still be useless for the one job it was built to do. This is the story of how a wildfire-detection system learns that lesson — and the tools that fix it.

      The setting

      Nimbus County Fire Watch

      Nimbus County has spent the last year wiring its forests with roughly 4,000 low-cost sensors. Every few minutes, each one reports temperature, smoke density, and humidity back to a control room, where a classification model looks at each reading and predicts one of two things:

      • Class 1 — Fire: this reading looks like the start of a wildfire
      • Class 0 — No Fire: this reading looks like a normal day in the forest

      The county owns exactly six fire trucks. Every "Fire" prediction sends one out to investigate — so every alert has a real cost, and every missed fire has a much bigger one.

      The team's first test ran on a small pilot region where fire and no-fire readings were, by design, roughly balanced — enough of both to sanity-check the model quickly. That pilot is where this story begins, and it's also where the trouble starts, because the real county doesn't look anything like the pilot.

      Beyond accuracy

      Sensitivity and specificity

      Once the pilot model is trained, the control room asks one question: if we deploy this, how often will it actually catch a real fire, and how often will it send a truck out for nothing? Accuracy can't answer that — it treats "correctly ignoring a normal day" and "correctly catching a fire" as equally important, and for Nimbus County they clearly aren't.

      Sensitivity (Recall)

      Of all the readings that were actually fires, what fraction did the model correctly flag?

      Sensitivity = TPTP + FN

      Specificity

      The mirror question: of all the readings that were actually normal, what fraction did the model correctly leave alone?

      Specificity = TNTN + FP

      The confusion matrix, in Nimbus County terms

      Every prediction lands in one of four boxes. Two of them are correct; two are costly in very different ways.

      Predicted: Fire
      Predicted: No Fire
      Actual: Fire
      TPReal fire, truck dispatched — the system did its job.
      FNA real fire, missed entirely. It keeps growing unchecked.
      Actual: No Fire
      FPNormal day, truck sent anyway — a wasted run.
      TNNormal day, correctly left alone.

      For Nimbus County, a false negative is a fire that grows unchecked — sensitivity is what keeps the county safe. A false positive is a wasted truck run — specificity is what keeps the budget sane. Every decision about where to set the alarm threshold is really a decision about how much of one you're willing to trade for the other.

      Check yourself

      The fire chief says: "I don't care how many false alarms we get, I never want to miss a real fire." Which metric should the team prioritise when choosing a threshold?

      The chief's priority is entirely about false negatives — real fires the model fails to catch. Sensitivity is exactly the fraction of actual fires the model catches, so it directly reflects that priority. Specificity still matters as a secondary constraint (there are only six trucks), but no metric is "always" the most important one — it depends on the relative cost of each error type.

      Sweeping the threshold

      The ROC curve

      The model doesn't output "Fire" or "No Fire" directly — it outputs a probability, and Nimbus County chooses where to draw the line. Lower the threshold and the system flags more readings (sensitivity rises, but so do false alarms); raise it and the opposite happens.

      The ROC curve is what you get by sweeping the threshold from 1 down to 0 and, at every value, plotting the false positive rate against the true positive rate:

      x-axis
      False Positive Rate = FP / (FP + TN) = 1 − Specificity
      y-axis
      True Positive Rate = TP / (TP + FN) = Sensitivity

      At threshold 1, the model flags almost nothing (bottom-left corner). At threshold 0, it flags everything (top-right corner). A model no better than a coin flip traces the diagonal; a genuinely useful model bows up toward the top-left, where you get high sensitivity without paying much in false alarms.

      Think it through

      A false alarm costs Nimbus County about $50 in truck fuel. A missed fire is estimated to cost $2 million in damage. Given that gap, where on the curve above would you set the operating threshold — closer to the bottom-left or the top-right — and why?

      One number for the whole curve

      AUC — area under the ROC curve

      The ROC curve is a full picture of every trade-off, but the county still wants a single number to compare models before picking a threshold at all. AUC is exactly that: the area under the ROC curve, integrated over the false positive rate from 0 to 1.

      An AUC of 1.0 means a perfect ranking — every real fire scores higher than every normal reading. An AUC of 0.5 means the model is no better than random. Put in words: AUC is the probability that, given one random fire reading and one random normal reading, the model scores the fire reading higher.

      Where AUC falls short

      AUC treats every threshold — including the ones nobody would ever use — as equally important. A model can post an excellent AUC by ranking things well overall, while still being mediocre at the one threshold the county will actually operate at. AUC also gets harder to interpret once one class is much rarer than the other, because the false positive rate's denominator (FP + TN) gets dominated by the huge number of normal readings — a problem this post comes back to shortly.

      Check yourself

      Model A has AUC = 0.92. Model B has AUC = 0.90, but at the specific threshold the county actually plans to operate at, Model B has noticeably higher sensitivity than Model A. Which model should the county deploy?

      AUC summarises performance across every possible threshold, but Nimbus County will only ever operate at one of them. A model with a slightly lower AUC can still be the better real-world choice if it performs better specifically at the threshold that matters — that's exactly AUC's limitation: great for comparing overall ranking ability, but it can hide the one number you actually care about.

      A companion view

      The precision-recall curve

      Sensitivity tells the county what fraction of real fires get caught, but says nothing about how many of the alerts turn out to be real. That's precision:

      Precision = TPTP + FP

      The precision-recall curve plots precision against recall (recall here is just another name for sensitivity) as the threshold sweeps from one extreme to the other — the same underlying sweep as the ROC curve, viewed from a different angle.

      Illustrative precision-recall curve

      Precision starts high and only falls once the threshold is lowered enough to push recall up.

      Check yourself

      Why might the precision-recall curve become more informative than the ROC curve once fires are very rare compared to normal readings?

      FPR's denominator is FP + TN. When normal readings vastly outnumber fires, TN becomes huge, and FPR can look artificially small even with a lot of false alarms relative to how few real fires exist. Precision's denominator, TP + FP, never involves TN — so it stays sensitive to exactly the over-alerting that matters most once positives are rare.

      From pilot to full county

      What is imbalanced data?

      The pilot went well — but it was chosen specifically because it had a reasonable number of past fires to learn from. When the team rolls the model out across the full 4,000-sensor network, they discover something the pilot never warned them about: on any given day, roughly 1 in every 200 readings is a real fire. The other 199 are just a normal day in the forest.

      The model hasn't changed. The metrics above haven't changed. But the ground truth it's learning from looks completely different, and that changes everything about how the model behaves.

      Full county network — every square is one reading; one square is a fire

      Imbalanced data is simply a dataset where one class occurs far more often than the other. Nimbus County's full network is a textbook example, but this pattern shows up constantly outside forests: fraudulent transactions among millions of legitimate ones, defective parts on a factory line, rare diseases in a screened population.

      The core problem: a model trained on imbalanced data can achieve very high accuracy simply by leaning toward the majority class, without ever learning to recognise the minority class at all. If 199 out of 200 readings are "No Fire," a model that predicts "No Fire" every single time is already 99.5% accurate — and completely useless to Nimbus County.

      Think it through

      Fraud, rare-disease screening, and manufacturing defects all share this shape: a rare, costly positive buried in routine negatives. What other domains fit the same pattern?

      A subtler symptom

      Imbalance, logistic regression, and model confidence

      Training the same kind of logistic regression model on the full county's true 1-in-200 fire rate produces a model whose accuracy looks excellent — and that may be catching very few, or even none, of the actual fires. This is imbalance quietly breaking the model in exactly the way described above.

      There's a second, subtler symptom worth naming: model confidence. Logistic regression outputs a predicted probability for each reading — how "confident" it is that a reading is a fire. When training data is this skewed, the model learns that predicting a low fire-probability is almost always correct, so it becomes systematically under-confident about the minority class. Even genuine fires often get scored with a low probability — not because the signal in the sensor readings is weak, but because the model was trained in a world where "probably not a fire" was the safe bet 199 times out of 200.

      Check yourself

      A colleague looks at the full-county model above and says: "Accuracy is over 99%, this model is great." What's the strongest response?

      With roughly 1 in 200 readings being a real fire, a model that predicts "No Fire" for almost everything is guaranteed very high accuracy without doing the job Nimbus County actually needs. This is exactly why sensitivity, precision, and the ROC/PR curves matter so much more than accuracy once the classes are imbalanced.

      Fixing it

      Handling imbalanced data

      Nimbus County's engineers have three standard strategies on the table, and each one changes a different part of the training process.

      The simplest fix doesn't touch the data at all — it changes how much each training example is allowed to influence learning. Every minority-class (fire) example gets a larger weight, so getting it wrong is penalised more heavily.

      wi = nsamplesnclasses × nsamples,i

      Because the fire class is small, its weight comes out large — every fire example effectively "counts more" during training.

      Gains
      Sensitivity typically improves a lot — the model becomes willing to raise more alarms in exchange for catching more real fires.
      Costs
      Overall accuracy often drops a little. That's expected, not a bug: it's the trade Nimbus County usually wants to make.

      Change the training data itself: keep every minority-class (fire) example, but randomly drop some majority-class (normal) examples so the two classes are closer to balanced when training begins.

      Gains
      Fast, simple, and directly rebalances the classes the model sees.
      Costs
      Nimbus County throws away the vast majority of its normal-day readings — data that might have held useful patterns about what a genuinely normal day looks like across different weather conditions. With only 20,000 readings in this example (and far more in reality), that's a lot of signal discarded.

      Go the other direction: instead of discarding majority-class data, duplicate minority-class (fire) examples until the classes are closer to balanced.

      Gains
      Keeps every original reading — no data is thrown away.
      Costs
      Because it's just copying existing fire examples rather than creating new information, the model can start to memorise those exact few fires rather than learning the general pattern of what a fire looks like — a classic overfitting risk.

      A smarter kind of oversampling

      SMOTE — Synthetic Minority Oversampling Technique

      SMOTE addresses oversampling's weakness directly: instead of duplicating existing fire examples, it generates new, synthetic ones. For each real fire example, SMOTE looks at its nearest fire-example neighbours in the sensor-reading feature space, and creates a new synthetic point somewhere along the line segment between the original point and one of those neighbours.

      xnew = xi + λ × (xneighbour − xi)
      x_i
      an existing minority-class (fire) example
      x_neighbour
      one of its nearest minority-class neighbours
      λ
      a random number between 0 and 1
      x_new
      the new synthetic fire example, somewhere between the two

      Drag λ to place the synthetic point

      The two violet points are real fire examples that are near neighbours in feature space. The magenta point is the synthetic example SMOTE generates between them.

      x_new = x_i + 0.50 × (x_neighbour − x_i)

      The result is a set of new fire examples that are plausible variations rather than exact duplicates — giving the model more to learn from without literally repeating the same handful of past fires.

      Check yourself

      What is the key difference between naive random oversampling and SMOTE?

      Naive random oversampling literally copies existing minority-class rows, so the model can see the exact same fire examples multiple times, increasing overfitting risk. SMOTE instead constructs new, synthetic minority-class points along the line between real examples and their nearest neighbours — giving the model more varied information rather than repeating the same points.

      Beyond Nimbus County

      Where this shows up in production systems

      Everything in this post generalises far beyond wildfire sensors.

      In production ML systems

      Fraud detection teams, medical-screening pipelines, and manufacturing quality-control systems all face the same shape of problem: a rare, high-cost positive class buried in a sea of routine negatives. None of these teams pick a threshold, or a class-weighting scheme, by intuition alone — they plot the same ROC and precision-recall curves covered here, weigh the real-world cost of a false negative against a false positive, and choose the operating point that fits their situation.

      Fraud detection

      Genuine fraud is a tiny fraction of all transactions, but missing one is far costlier than reviewing a false alarm.

      Medical screening

      A rare disease in a screened population — sensitivity to catch true cases matters more than raw accuracy.

      Quality control

      Defective parts are rare on a healthy production line, but a missed defect can be expensive downstream.

      In modern AI evaluation

      The same problem shows up when evaluating AI systems themselves. Safety classifiers and content-moderation "guardrail" models — the systems deciding whether a piece of text or an AI-generated response should be flagged — are trained on data where genuinely harmful content is a small minority, much like Nimbus County's fires. Teams building these guardrails track precision and recall rather than raw accuracy, reason about ROC/PR trade-offs when picking a flagging threshold, and apply the same class-weighting or resampling techniques used here when fine-tuning a classifier on skewed data.

      Think it through

      If harmful examples make up less than 1% of a safety classifier's training data, which technique from this post — class weights, undersampling, oversampling, or SMOTE — would you reach for first, and why?

      Summary

      Wrap-up

      • 1Sensitivity and specificity describe two different kinds of correctness — which one matters more depends entirely on the cost of each error type.
      • 2The ROC curve shows every threshold's sensitivity/specificity trade-off at once; AUC summarises it into one number, but can hide performance at the one threshold you'll actually use.
      • 3The precision-recall curve becomes more informative than the ROC curve once the positive class is rare, because precision is never diluted by a large number of true negatives.
      • 4Imbalanced data is any dataset where one class heavily outnumbers the other — it can make accuracy look excellent while the model quietly fails at the one job that matters.
      • 5Under imbalance, a model's predicted probabilities skew toward the majority class, even for genuine minority-class examples.
      • 6Class weights, undersampling, oversampling, and SMOTE each correct for imbalance differently, trading off information loss, overfitting risk, and how much they shift model behaviour.
      • 7These exact techniques and trade-offs show up directly in production ML systems and in how modern AI safety and guardrail classifiers are built and evaluated.
