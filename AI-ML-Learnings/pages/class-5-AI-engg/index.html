00SETUP
Before any agent code

Connect VS Code to your AWS account

The agent code you'll write today contains no keys, no login, no endpoint. So how does it reach your AWS account? Understanding this once saves you every "AccessDenied" afternoon later.

Here's the core idea. The Strands SDK talks to Amazon Bedrock through boto3, the official AWS SDK for Python. And boto3 never looks inside your script for credentials — it looks at your machine's environment. So "connecting to AWS" is something you do to your laptop once, before running, and every script afterwards simply inherits it.

The three gates — all must be open

People hit errors here because they treat this as one thing ("auth"). It's actually three independent gates, and any one of them can block you with a similar-looking error:

How boto3 finds your identity: the credential chain

When your script runs, boto3 searches a fixed list of places in order and uses the first credentials it finds. This is why the same three-line agent "just works" in SageMaker Studio (it silently hits step ⑤, the environment's IAM role) but does nothing on a fresh laptop (steps ①–④ are all empty until you fill one):

Think of it like UPI on a new phone The payment app (your script) has no money inside it. It works because the phone was linked to your bank account once. New phone (new laptop) → link again. Same app code, zero changes.

Setup, step by step (~15 min, once per laptop)

  1. Install Python packages & the AWS CLI

    You need Python 3.10+, the Strands SDK, and the AWS CLI (the tool that writes your credential files).

    $ terminalinstall
    $ python --version          # must be 3.10 or higher
$ pip install strands-agents strands-agents-tools boto3
$ aws --version              # if missing → install from aws.amazon.com/cli

  2. Create an IAM identity with Bedrock permissions (gates ① + ②)

    In the AWS Console → IAM → Users → Create user (e.g. agent-dev). Attach a policy that allows invoking Bedrock models — this minimal one covers today's session:

    IAMminimal-bedrock-policy.json
    {
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": [
      "bedrock:InvokeModel",
      "bedrock:InvokeModelWithResponseStream"
    ],
    "Resource": "*"
  }]
}

    Then create an access key for this user: IAM → your user → Security credentials → Create access key → choose Command Line Interface (CLI). Copy both values — the secret is shown only once.

    Company laptop? If your org uses IAM Identity Center (SSO), skip access keys: run aws configure sso once, then aws sso login each day. Short-lived credentials, same end result — boto3 finds them at step ④ of the chain.

  3. Link your laptop: aws configure (fills chain step ③)

    $ terminalone-time link
    $ aws configure
AWS Access Key ID [None]:     AKIA••••••••••••
AWS Secret Access Key [None]: ••••••••••••••••••••
Default region name [None]:   us-west-2
Default output format [None]: json
    what this wrote
    ~/.aws/credentials   ← your key pair        (chain step ③)
~/.aws/config        ← region = us-west-2   (used by every call)
    Region is part of the address Bedrock model access is enabled per region. If you configure us-west-2 here but enabled models in ap-south-1 (Mumbai), you'll get access errors that look like IAM problems but aren't. Pick one region and use it everywhere today.

  4. Enable model access in Bedrock (gate ③ — the console step)

    AWS Console → set the region (top-right) to the same region you configured → Amazon Bedrock → Model access → Modify model access → enable Anthropic Claude and/or Amazon Nova → Submit. Approval is usually near-instant.

    This is an account-level opt-in per model per region. It is not an IAM policy — perfect credentials + IAM still fail if this box isn't ticked.

  5. Verify each gate before writing agent code

    $ terminalverify gates ①–③
    # Gate ① — do credentials resolve? (identity check, needs no extra perms)
$ aws sts get-caller-identity
{ "Account": "123456789012", "Arn": "arn:aws:iam::123456789012:user/agent-dev" }

# Gates ② + ③ — can THIS identity see Bedrock models in THIS region?
$ aws bedrock list-foundation-models --region us-west-2 \
      --query "modelSummaries[?contains(modelId,'claude')].modelId"
    healthy output
    [ "anthropic.claude-sonnet-4-20250514-v1:0", ... ]   ← you're ready ✓
    Checkpoint ✋ — don't continue past this line until…

    get-caller-identity returns your account number, and the model list is non-empty. If both are true, every notebook below will run. If not, jump to the troubleshooting table.

01BRAIN
Understanding AI agents on AWS

What an agent really is — and where it lives on AWS

"Agent" gets used loosely. Before writing one, let's pin down precisely what changes as we climb from a plain LLM to an agent — because each rung of that ladder maps to a segment of today's session.

The ladder: from LLM to multi-agent

You've already built the first two rungs with LangChain. Watch what each rung adds:

  • Rung 1 — LLM. Text in, text out. Brilliant reasoning, but frozen knowledge and no ability to touch the world. Ask it "is our staging server up?" and it can only guess.
  • Rung 2 — + RAG. Grounds answers in your documents. Fixes "it doesn't know our data" — but it's still read-only. It can quote your runbook; it cannot restart the server.
  • Rung 3 — + Tools ⇒ an agent. This is the real jump. The model gains the ability to act: call functions, hit APIs, query databases — and, crucially, to decide for itself which action to take and when. That decision-making loop is what makes it an agent rather than a chatbot with plugins. (Segment 02.)
  • Rung 4 — + Memory. The agent retains context and preferences across sessions, becoming a continuing assistant instead of a stranger every time. (Segment 03.)
  • Rung 5 — Multi-agent. Specialist agents collaborate on tasks too big for one — coordinated by patterns like supervisor-worker, and talking over protocols like MCP (agent ↔ tools) and A2A (agent ↔ agent). (Sessions 2+; today just know the ladder goes higher.)

What actually makes it an agent: goals, not steps

Here's the sharpest way to state the difference. With ordinary code — or even a LangChain chain — you write the steps: fetch, then parse, then summarize, then send. With an agent, you write the goal and describe the available actions; the model plans the steps itself, at run time, adapting as results come back.

Concretely, an agent runs a repeating cycle:

  1. Reason — the model reads the goal plus everything learned so far and thinks: what's the next best move?
  2. Act — if a tool is needed, the agent executes it (call an API, query a table, run a calculation).
  3. Observe — the tool's result is fed back into the model's context.
  4. Repeat — until the model judges the goal is met, then it composes the final answer.

That loop is why agents handle messy, multi-step requests you never explicitly programmed — and also why they need guardrails (an autonomous loop with real permissions can do real damage; that's Session 4's topic).

Cab vs self-drive A chain is Google Maps navigation with you driving — it suggests, you execute every turn. An agent is the cab: you give the destination, the driver picks the route, reroutes around traffic, and tells you when you've arrived. Same city, very different division of labour.

Where it lives on AWS: the stack, and the one decision that matters

To build the ladder on AWS, you assemble four layers. From top to bottom: an IDE where you develop (VS Code, SageMaker Studio, Kiro), a framework that expresses agent logic (Strands SDK or LangChain/LangGraph), a reasoning engine — the model that does the thinking — and the tools + memory that ground it in the real world.

The only real decision at this stage is where the reasoning engine comes from, and AWS gives you two doors:

  • Amazon Bedrock — a fully managed, API-first service. You call foundation models (Claude, Nova, and others) with one API; AWS runs the infrastructure. Default choice, and what we use throughout this session.
  • Amazon SageMaker AI — for when you must customize the brain: fine-tune or train a model, deploy it to endpoints you control, and manage cost/latency/infra yourself. Complementary, not competing — a SageMaker-tuned model can even serve as the brain behind a Bedrock-style agent.

Strands SDK: the loop, packaged

Strands is AWS's lightweight agent framework, and its design philosophy is exactly the theory above: an agent is just model + tools + prompt, wrapped in the reason–act–observe loop. You declare the three ingredients; Strands runs the cycle. It's the same loop you've seen in LangGraph's ReAct agents, with far less ceremony — and it defaults to Bedrock as the brain.

Hello-World agent — with the connection made visible

Now the code. We could write bare Agent() and rely on defaults — but defaults hide the model and the region, the two things you just set up. So we'll pin both explicitly. Notice there are still no credentials in the code: boto3 pulls them from ~/.aws/, exactly as in Fig 0b.

In [1]:hello_world.py · VS Code
import boto3
from strands import Agent
from strands.models import BedrockModel

# The brain: which model, in which region (match your setup region!)
model = BedrockModel(
    model_id="us.anthropic.claude-sonnet-4-20250514-v1:0",
    boto_session=boto3.Session(region_name="us-west-2"),
)
# ↑ credentials come from the chain (~/.aws/credentials) — never from code

agent = Agent(model=model)

response = agent("Explain Amazon Bedrock Agents in two sentences.")
print(response)
output
Amazon Bedrock Agents let you build AI applications that reason, call
tools, and complete multi-step tasks using foundation models — without
managing any model infrastructure yourself.
Why not bare Agent()? It works — Strands falls back to a default Bedrock model and your default region — but "works by invisible defaults" is exactly how region-mismatch bugs are born. In teaching and in production: pin the model, pin the region. (In a SageMaker Studio setup, bare Agent() is fine because the Studio environment supplies everything.)

Mapping back to the ladder: what you just ran is rung 1–2 territory — a model that talks but can't act. Next segment we climb to rung 3 and make it an actual agent.

02TOOLS
Building agents with tools

Giving agents hands

Our Hello-World agent can talk but can't do. Without tools, even the smartest model is just a very expensive chatbot. Tools are how an agent checks a server, queries a database, or sends an email — this is the rung where a model becomes an agent.

Think Zomato A model without tools is a friend who knows every restaurant in town but can't place the order. Tools are the "order now", "track", and "pay" buttons — they turn advice into action.

Anatomy of a tool: one function, three ingredients

In Strands, a tool is a normal Python function. You make it agent-callable by adding three things — and each one is a message to the model:

  • @tool decorator → "expose this function to the agent."
  • Type hints → "here's exactly what arguments to pass, and of what type."
  • Docstring → "here's what I do — use me when a request needs this." The model literally reads this to decide when to call you.
In [2]:first_tool.py
from strands import Agent, tool
import requests

@tool                                                # ① decorator
def check_server_status(server_url: str) -> str:      # ② type hints
    """Check if a server is responding by making an HTTP request.
    Args:  server_url: The URL of the server to check       # ③ docstring
    Returns: A message saying whether the server is up or down"""
    try:
        r = requests.get(server_url, timeout=5)
        return f"Server is up. Status code: {r.status_code}"
    except requests.exceptions.RequestException:
        return "Server is down or unreachable"

# Hand the tool to an agent — now it can actually check servers
agent = Agent(model=model, tools=[check_server_status])
agent("Is the staging server at https://staging.myapp.com running?")

That's the entire pattern. Add @tool, give the function to your Agent, and the reason–act loop can now include it whenever a request calls for it.

Many tools, one agent — the agent plans the order

The magic shows up with multiple tools. Imagine a sales assistant: "pull last quarter's sales and email a summary to the team." That's three jobs — get data, analyze, email. You write three small, single-purpose tools and hand them over. You never write the sequence. The agent plans it — that's "goals, not steps" in action.

In [3]:sales_assistant.py
from strands import Agent, tool

@tool
def get_sales_data(quarter: str) -> dict:
    """Retrieve sales data for a specific quarter."""
    return {"revenue": 1250000, "deals": 47, "quarter": quarter}

@tool
def analyze_sales(revenue: int, deals: int, quarter: str) -> str:
    """Calculate key metrics from sales data."""
    avg = revenue / deals
    return f"{quarter}: ${revenue:,} revenue, {deals} deals, ${avg:,.0f} avg deal"

@tool
def send_email(to: str, subject: str, body: str) -> str:
    """Send an email message."""
    return f"Email sent to {to}"

agent = Agent(model=model, tools=[get_sales_data, analyze_sales, send_email])
agent("Pull last quarter's sales data and email a summary to the team")
Build focused, single-purpose tools Resist the mega-tool that does everything. Small tools are easier to maintain, easier for the agent to reason about, and reusable — the same analyze_sales works no matter where the data came from.

Hands-on: a tip-splitter agent

Let's build something you'd actually use at dinner. Bill arrives, you need the tip and the split. Three steps — tool, agent, question.

In [4]:tip_splitter.py
from strands import Agent, tool

# Step 1 — a tool is just a @tool-decorated function
@tool
def calculate_tip(bill_amount: float, tip_percentage: float,
                  num_people: int = 1) -> dict:
    """Calculate tip and split the bill among people.
    Args:
        bill_amount:    Total bill in dollars
        tip_percentage: Tip percent, e.g. 15, 18, 20
        num_people:     People splitting the bill (default 1)"""
    tip = bill_amount * (tip_percentage / 100)
    total = bill_amount + tip
    return {
        "tip": round(tip, 2),
        "total": round(total, 2),
        "per_person": round(total / num_people, 2),
    }

# Step 2 — give the tool to an agent
agent = Agent(model=model, tools=[calculate_tip])

# Step 3 — ask a plain-English question
response = agent("The bill is $85. What's a 20% tip, and how much "
                 "does each person pay if we split it 4 ways?")
print(response.message['content'][0]['text'])
output
For an $85 bill with a 20% tip:
  • Tip: $17.00   • Total: $102.00
  • Each of the 4 people pays $25.50

Trace the loop through this run: the model reasoned that the request needs math → acted by calling calculate_tip(85, 20, 4) with arguments it extracted from your English → observed the returned dict → judged the goal met and phrased the answer. You wrote maths once; the agent handled language both ways.

Pre-built tools & talking to AWS

You don't have to write every tool. The strands-agents-tools package (installed in Setup step 1) ships dozens ready to import.

use_aws — reach S3, DynamoDB, Lambda & more.

The one that unlocks real enterprise work is use_aws. Your data lives in S3, DynamoDB, and RDS; your logic runs in Lambda. use_aws lets the agent reach all of it — it translates plain English into AWS CLI calls using the same credentials from your setup. No boto3 code, no hand-written API calls.

In [6]:aws_agent.py
from strands import Agent
from strands_tools import use_aws, calculator

agent = Agent(
    model=model,
    tools=[use_aws, calculator],
    system_prompt="You are an AWS assistant that manages cloud resources.",
)

# The agent picks the right AWS operations for each request:
agent("List all S3 buckets in my account")
agent("Read sales-2024.csv from the 'my-bucket' S3 bucket, "
      "calculate total revenue, and save a summary back to S3")
agent("Invoke the Lambda function 'order-processor' with order ID 67890")
More power ⇒ more IAM use_aws runs real commands as your identity. For today's S3 examples, add s3:ListAllMyBuckets, s3:GetObject, s3:PutObject to your user's policy (and lambda:InvokeFunction for the Lambda example). Scope it tight — least privilege. If an S3 call throws AccessDenied, that's gate ② again, just for a new service.

03MEMORY
Agent memory

Making agents remember

Our agent can act — but it forgets everything the moment a session ends. Memory is rung 4 of the ladder: it turns a one-off responder into an assistant that feels like a continuing relationship.

Why memory matters

Picture a travel chat. You ask, "good places to visit in NYC?" and it says "Times Square." Then you ask, "what's the best time to visit it?" A memoryless agent has no idea what "it" means. With memory, it knows "it" = Times Square and answers smoothly. Memory is simply the agent's ability to write useful information and read it back later.

FeatureWithout memoryWith memory
Contextresets when a session endscarried forward across sessions
Personalizationgeneric repliestailored to the user's history
Efficiencyuser repeats themselvesbuilds on what it already knows
Experiencetalking to a stranger each timea continuous assistant

Two kinds of memory

Just like people, agents have short-term and long-term memory — and the split maps onto AWS services cleanly.

short Short-term (working)

The current conversation — what was said a few turns ago. Keeps a single chat coherent. Bounded, and trimmed as it grows.

long Long-term (persistent)

Preferences and facts that survive across sessions — "I'm vegetarian", "keep replies under 100 words". Grows over time.

Hands-on: a personalized agent with Mem0

Mem0 is an open-source memory layer that plugs into Strands as a tool. The agent extracts a user's preferences from what they say, stores them, and recalls them later. The key discipline: scope memory per-user so one person's data never leaks into another's answers.

In [7]:personalized_agent.py · setup
import warnings; warnings.filterwarnings("ignore")
from strands import Agent, tool
from strands_tools import mem0_memory, use_llm
from ddgs import DDGS          # pip install ddgs — web search library

# Per-user guardrail: this agent only ever sees ONE user's memories
SYSTEM_PROMPT = """You are a personal assistant for {user_name}.
Never access any other person's information. If asked about someone
else, politely refuse. Learn {user_name}'s preferences from what they
say and remember them, always tagged with their user name."""

@tool
def websearch(keywords: str, region: str = "us-en",
              max_results: int = 5) -> str:
    """Search the web for fresh information."""
    return DDGS().text(keywords, region=region, max_results=max_results) \
           or "No results found."

# Helper: build an agent bound to one named user
def create_agent(user_name: str) -> Agent:
    return Agent(
        model=model,
        system_prompt=SYSTEM_PROMPT.format(user_name=user_name),
        tools=[mem0_memory, websearch, use_llm],
    )
In [8]:personalized_agent.py · teach it about a user
agent = create_agent("Priya")

# The agent extracts and stores each preference as a memory
for note in [
    "I am a veggie lover.",
    "I need low-sodium food and decaf drinks only.",
    "I prefer full-service restaurants.",
]:
    agent(note)

# Later — it answers using what it remembered about Priya
agent("Suggest a place for dinner near me tonight.")
output
Based on your preferences (vegetarian, low-sodium, decaf, full-service),
here are a few sit-down vegetarian spots with lighter menus nearby...
Memory is a superpower and a responsibility Storing user preferences means storing personal data. Scope it per-user in the system prompt (as above), and be deliberate about what you keep. "Remembers everything" is a feature and a privacy surface.

Managed memory: AgentCore Memory

Mem0 is great for learning the concept. For production on AWS, Amazon Bedrock AgentCore Memory is the managed option — it handles short-term and long-term memory for you. A common pattern uses it as a checkpointer behind LangGraph: LangGraph orchestrates the reasoning, and AgentCore Memory persistently saves the agent's state so a conversation survives restarts. (This needs bedrock-agentcore:* permissions on your identity — gate ② grows with your ambitions.)

In [9]:agentcore_with_langgraph.py
from langchain.chat_models import init_chat_model
from langgraph.prebuilt import create_react_agent
# AgentCoreMemorySaver bridges LangGraph state → Bedrock AgentCore Memory
from ... import AgentCoreMemorySaver   # exact import path depends on your library version

memory = client.create_memory(name="math-agent-memory")

# A checkpointer that persists graph state to AgentCore Memory
checkpointer = AgentCoreMemorySaver(memory_id, region_name=region)

agent = create_react_agent(
    model=init_chat_model("us.anthropic.claude-sonnet-4-20250514-v1:0"),
    tools=[...],
    checkpointer=checkpointer,   # state survives across runs
)
The mental model Mem0 / AgentCore Memory = the notebook the agent writes preferences into. The checkpointer = a save-game file for a whole conversation's state. Same goal — survive across time — at two different granularities.
