What XGBoost changes

XGBoost (Extreme Gradient Boosting) still builds trees stage by stage, each one correcting the ensemble so far, exactly as before. What changes is the objective each tree is built to optimise and how quickly splits can be found.

1. A regularised, second-order objective

In plain Gradient Boosting, each new tree is fitted to the pseudo-residuals, the negative gradient of the loss. XGBoost instead defines an explicit objective for each new tree fm, with a penalty on the tree's complexity built in:

L(m) = Σi l( yi, ŷi(m−1) + fm(xi) ) + Ω(fm)
Ω(f) = γT + ½ λ Σj=1T wj2

Here T is the number of leaves, wj is the prediction (weight) of leaf j, γ penalises each extra leaf, and λ penalises large leaf weights.

XGBoost then approximates the loss with a second-order Taylor expansion, using both the gradient gi and the curvature (Hessian) hi of the loss at each point. For a fixed tree structure, let Gj and Hj be the sums of g and h over the points in leaf j. Then the best weight for each leaf has a closed form, and so does the gain from a split:

wj* = − Gj / ( Hj + λ )
Gain = ½ [ GL2/(HL+λ) + GR2/(HR+λ) − (GL+GR)2/(HL+HR+λ) ] − γ

A split is only worth making if this gain is positive, so γ acts as a minimum-improvement bar and λ shrinks every leaf's weight. Regularization is part of how each tree is grown, not something bolted on afterwards.

G and H are the summed gradient and Hessian of the points that fall in each child. The numbers here are made up to show how the formula behaves; they are not from the Pay Band data.

2. Faster split finding

  • Parallel split evaluation. The boosting stages still happen one after another, but within a single stage XGBoost evaluates candidate splits across features in parallel on multiple CPU cores.
  • Approximate threshold search. The earlier threshold search tested every unique value of a numerical feature. XGBoost can instead propose candidate thresholds from quantiles (or histogram bins) of the feature, so it compares far fewer candidates while still landing on a very good split.

Keeping XGBoost from overfitting

XGBoost inherits every overfitting risk of plain Gradient Boosting: too many stages and too much depth. The objective gives more precise levers.

  • max_depth, n_estimators, learning_rate, subsample: exactly as before.
  • colsample_bytree: each tree sees only a random subset of features, adding randomness in the spirit of Random Forest.
  • min_child_weight: a split is rejected unless each child carries at least this much total Hessian weight (Hj). Higher values force leaves to rest on more evidence, blocking splits that only isolate a few noisy points.
  • reg_lambda (λ): a larger value shrinks leaf weights, damping each tree's influence.
  • gamma (γ): a split must improve the objective by at least this much, or it isn't made.

Try the calculator above: the "noisy points" preset is rejected by min_child_weight, and the "large γ" preset by gamma.

LightGBM: speeding things up further

LightGBM keeps the boosting framework but adds several speed-ups. Two headline ideas are GOSS and EFB. It also relies, more quietly, on histogram-based split finding and leaf-wise tree growth.

Four ideas behind LightGBM's speed

Which of these are active in the demo?

TechniqueStatus in the Pay Band demo
GOSSOff. It is opt-in: it needs data_sample_strategy='goss' (LightGBM 4.x) or boosting_type='goss' (older versions), and the tuning run uses the default 'gbdt'.
EFBOn by default, but it only helps with sparse, mutually exclusive features. The EMG data has 8 dense channels, so there is nothing to bundle. It would matter for one-hot encoded columns or sparse text counts.
Row subsamplingTakes effect in LightGBM only when subsample_freq is above 0, which the tuning grid sets to 1.
Histogram-based split finding and multi-core useThe most plausible source of the speed measured here.

GOSS and EFB are still worth knowing, because they matter as data gets larger or sparser. The research paper is LightGBM (NeurIPS 2017), and a more accessible walkthrough is What makes LightGBM lightning fast?

How many fits fit in an hour?

Back-of-envelope: 3,600 seconds divided by each model's single-fit time, ignoring any tuning overhead.

Plain scikit-learn Gradient Boosting was by far the slowest, while XGBoost and LightGBM were both much faster, with a much smaller gap between the two. That gap depends on hardware and dataset size, so read it from your own numbers rather than assuming a fixed ratio. For a wristband that has to be retrained regularly as pilot data arrives, a model that fits in seconds instead of minutes is the difference between retraining weekly and retraining only when someone has time.

Switching GOSS on

GOSS trains each stage on a sample of the rows, so on a dataset this small there is no dramatic speed-up to expect, and accuracy can shift slightly. Its benefit grows with dataset size.

Beyond boosting: Voting

The ensemble overview listed a fourth family, Voting. It combines the predictions of several already-trained models using a simple rule, with no meta-model learning how to combine them. There are two flavours:

  • Hard voting. Each model casts one vote for a class, and the class with the most votes wins.
  • Soft voting. Each model outputs class probabilities. They are averaged (or weighted-averaged) across models, and the class with the highest average wins.

Soft voting usually edges out hard voting, since it uses each model's confidence, not just its final answer: a model that is 51% sure and a model that is 99% sure both count as "one vote" under hard voting, but soft voting lets the more confident model pull harder.

The probabilities are illustrative, chosen to show when the two rules disagree. Two classes are used for simplicity: "Stays" and "Leaves".

Isn't this just Bagging?

Bagging "trains many models independently and lets them vote", which is the same voting mechanism. The real difference is what varies between the models.

BaggingVoting
Model typeThe same algorithm, repeated (many Decision Trees)Different algorithms (a Decision Tree, a Random Forest, a Logistic Regression)
Training dataDifferent bootstrap samples of the dataTypically the same data for every model
What creates diversityRandom sampling of rows (and features, for Random Forest)Genuinely different modelling assumptions

A Random Forest is, technically, hard voting across many Decision Trees. "Voting" here is the more general case: mixing fundamentally different kinds of models.

Beyond boosting: Stacking

Stacking trains several different, independently chosen models (not just trees: a Logistic Regression, an SVM and a Random Forest, say, all at once) on the same data. Then it trains one more small meta-model on top, whose job is to learn how to best combine their predictions.

Beyond boosting: Cascading

Cascading chains several models one after another. Each model's job is to confidently filter out the "easy" cases, passing only the harder, more uncertain ones down to the next model in the chain.

In a fraud-detection pipeline, for example, the first model quickly clears the overwhelming majority of clearly genuine transactions. The second looks only at what is left, the harder cases, and tries to find likely-fraudulent ones. This can continue through several stages, each trained on a progressively smaller, harder subset of the data. If uncertainty remains after the last model, a human reviewer makes the final call.

Illustrative fraud-detection pipeline

Why not just use one strong model?

Cascading is especially valuable when the cost of a wrong answer is high: fraud detection, cancer diagnosis and similar domains. There, a single confident-but-wrong model is far more dangerous than a slower, staged pipeline that reserves genuine uncertainty for a human to review.

The ensemble families side by side

FamilyHow the models are builtHow they are combined
BaggingThe same algorithm on different bootstrap samples, independentlyVote or average
BoostingOne after another, each correcting the errors of the ones before itWeighted sum of stages
VotingDifferent, already-trained algorithms, typically on the same dataSimple rule: majority (hard) or average probability (soft)

Summary

XGBoost

XGBoost keeps stage-by-stage boosting but optimises an explicitly regularised objective: a penalty γ per leaf and λ on leaf weights, using a second-order (gradient and Hessian) approximation of the loss. It also finds splits faster, through parallel split evaluation and approximate, quantile-based threshold search.

XGBoost overfitting controls

The familiar controls (max_depth, subsample, n_estimators, learning_rate) are extended with colsample_bytree, min_child_weight, reg_lambda and gamma.

LightGBM

LightGBM speeds things up through histogram-based split finding and leaf-wise growth, plus GOSS, which reduces the rows considered at each split, and EFB, which reduces the features by bundling mutually exclusive ones. GOSS is opt-in and EFB only helps with sparse features, so neither was doing the work in the dense 8-channel demo.

The benchmark

In a controlled single-fit benchmark, plain scikit-learn GBDT was by far the slowest (291.3 s), while XGBoost (4.6 s) and LightGBM (2.9 s) were both much faster, with a much smaller gap between the two.

Voting

Voting combines predictions from different, already-trained algorithms, by majority (hard) or by averaging predicted probabilities (soft). Unlike Bagging, which repeats the same algorithm on resampled data, its diversity comes from mixing genuinely different models.

Stacking

Stacking trains a meta-model to combine several different model types' predictions. It is powerful, but expensive to build and maintain, which is why it isn't always the right choice.

Cascading

Cascading chains specialised models, each filtering out confidently resolved cases and passing harder ones forward, ending in human review if needed. It shines where misclassification is costly, like fraud detection.
