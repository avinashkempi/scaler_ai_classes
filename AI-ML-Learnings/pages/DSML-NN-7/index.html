01/ 06

From Sequential to custom modules

Where a single chain of layers stops being enough, and what writing your own forward() buys you.

Where nn.Sequential breaks down

The baseline model is one input → one output, strictly sequential: each layer's output is the next layer's only input, nothing else. That's fine until the requirements change. Say Healthyfi.me wants a second prediction alongside the fitness class — a continuous score — computed at the same time. Or two feature groups, body-metrics and performance-metrics, that each need their own processing before combining. Could nn.Sequential handle that?

No. Sequential is a single chain — each layer's output feeds directly into the next layer's input, nothing else. It can't branch, merge, or handle more than one input or output. The moment an architecture needs any of that, Sequential is the wrong tool.

PyTorch's answer is to write your own nn.Module subclass with a custom forward() method — one flexible building block that can express any architecture, branching included. It isn't a specialized escape hatch for unusual cases; it's the general-purpose way of describing a model, and Sequential is really just a convenience wrapper around the simplest possible case of it.

__init__() just creates and registers the layers as attributes, so PyTorch knows to track their parameters — it doesn't run the model. forward() is what actually defines execution order.

Worth double-checking

It's easy to assume layers run in the order they're listed inside __init__(). They don't — __init__() is just object creation. Execution order is whatever forward() says, line by line, and nothing else.

Two inputs in, two outputs out, two independent processing paths in between — forward() just describes the graph directly. This is the entire "Functional API" story in PyTorch: there's no second API to learn, only a more expressive way to use the one you already have.

In practice

This pattern shows up constantly in production: a recommendation model combining user features and item features through separate towers, or a model predicting both a category and a price from the same input. Branching architectures are the norm once you're past toy problems.

From logits to probabilities, at inference time

The model was trained to output raw logits, not probabilities — a deliberate choice, since nn.CrossEntropyLoss needs logits. To get human-readable probabilities for display, softmax is applied separately, only at inference time, never inside the model itself.

No. Softmax preserves order, so argmax(logits) and argmax(softmax(logits)) always agree. It was only needed to see interpretable probability values, not to pick the class.

Hold onto that idea — softmax, only at inference, never inside the model. The next section is about what happens if you forget it.

03/ 06

The double-softmax bug

A prediction, an experiment, and a genuine "aha" about why loss functions document what they expect as input.

Predict before you read on

The model currently ends in raw logits, feeding nn.CrossEntropyLoss. Softmax is the function that turns logits into probabilities — and probabilities feel like the more "complete," proper thing to hand a loss function. What happens if one more layer is added — nn.Softmax(dim=1) — right at the end, so the model outputs probabilities directly?

  • "It should do nothing — softmax is just normalization."
  • "It should help — the loss function gets cleaner, already-normalized values to work with."

Both feel intuitive. Neither is right.

python

Same architecture as the baseline, with one addition — nn.Softmax(dim=1) — and training visibly suffers: the flawed model's loss falls far more slowly than the baseline's over the same number of epochs, and its final validation accuracy lands well below it.

Why: CrossEntropyLoss already does this internally

nn.CrossEntropyLoss is not just a loss function — it internally combines two steps, LogSoftmax then NLLLoss. It already expects raw logits and applies softmax itself, on the inside:

raw logitsmodel output
→
LogSoftmaxinside CrossEntropyLoss
→
NLLLossinside CrossEntropyLoss
→
loss valueone scalar

Add a Softmax layer to the model, and the loss function applies softmax to values that are already softmax output — squashed once, then squashed again. Softmax is not idempotent: applying it twice compresses the output distribution further, flattening the differences between classes and, with them, the gradient signal the optimizer relies on. This is the same underlying pattern as the vanishing-gradient idea from Part 1: a transformation that pushes values into a range where derivatives go small, slowing learning down rather than speeding it up.

Takeaway

Any time a loss function's documentation says it "expects raw logits" or "combines an activation internally," adding that activation yourself in the model is a bug, not extra safety. Always check what a loss function expects before deciding whether the output layer needs an activation at all.

Monitoring & controlling training

A fixed-length loop that prints nothing is rarely what a real project wants. Stopping early, saving the best version seen so far, and logging progress durably don't need a special framework mechanism — they're a few lines of logic, placed exactly where they're needed.

Basic logging can be as simple as Part 1's if epoch % 50 == 0: print(...) — periodic visibility into training progress, without flooding the output by printing every single epoch. Two patterns matter more in almost every real project: stopping early once the model stops improving, and saving the best version of the model as training goes — both written directly into the loop.

Two more common training-control patterns, briefly:

  • Logging to a file — open("log.csv", "a"), a row written per epoch, so the record survives past the notebook session.
  • Adjusting the learning rate during training — PyTorch's torch.optim.lr_scheduler module (StepLR, ReduceLROnPlateau), covered properly in a later module.

In practice

In a real training job, saving checkpoints isn't optional. A crashed job — GPU pre-emption, spot-instance eviction, an out-of-memory error hours in — with no checkpoint means starting from scratch. This one torch.save line is often the difference between losing 10 minutes and losing a day.

06/ 06

Recap — the whole two-part journey

  • nn.Sequential builds a straight chain; a custom nn.Module with its own forward() can express any architecture, branching included.
  • Evaluating and predicting are just model.eval() + torch.no_grad() + a forward pass — worth writing as a small reusable function.
  • Logits vs. probabilities isn't cosmetic — CrossEntropyLoss already applies softmax internally, and adding it again quietly breaks training.
  • Stopping early, saving the best model, and logging progress don't need a special mechanism — just a few lines of logic, placed exactly where they're needed in the loop.
  • TensorBoard is a place to send the same numbers already being tracked, using add_scalar().
