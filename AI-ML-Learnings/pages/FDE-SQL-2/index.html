🔑 Keys, Relationships, Data Types & CAST

This reinforces what Class 2 covered on the Zomato dataset: how a schema describes data, how primary, unique and foreign keys keep it honest, how relationships and composite keys connect tables, which data type belongs in which column, and how CAST fixes a value that arrived in the wrong type. Work through each section, try the simulators, and keep the recap table at the end for reference.

1

Recap — What Is a Schema? 🗺️

A new analyst joins the team tomorrow and is handed the customers and orders tables, full of data, and nothing else. Within five minutes she will ask: what do the columns mean, what type of value is in each one, and how do the two tables connect. That description of the data has a name: the schema.

📚
The Library Analogy: The books are the data. The floor plan and the catalogue system are the schema. You cannot find a book if you do not understand how the shelves are organised, and you cannot write a good query if you do not understand the schema. The books change every day. The floor plan almost never does.

Our real Zomato data only has customers and orders. To practise keys and relationships safely without touching real data, Class 2 builds a second schema, zomato_practice, containing restaurants, dishes, fssai_licences, placed_orders and order_items. The real tables stayed read-only all class, and the practice database is dropped at the end.

One-line aside: In MySQL, schema and database mean the same thing. CREATE SCHEMA and CREATE DATABASE do the same job, which is why Workbench's left panel is called "Schemas."
🏢 MySQL vs BigQuery: schema

BigQuery calls a database a dataset and addresses tables as project.dataset.table. It also uses "schema" for the list of columns and types of one table (the Schema tab on a table's page). MySQL database = BigQuery dataset.

Right now, nothing stops two customers from having the same ID, or an order from pointing to a customer who does not exist. The rules that stop that are called keys. But first: why is the data in two tables at all?

Why Data Lives in Multiple Tables 🧩

Imagine Zomato kept a single sheet, where every order row also carried the customer's name, phone and city:

C063 has placed 13 orders, so her name, phone and city would be typed 13 times. Now she moves from Pune to Mumbai. You must change 13 rows, and if you miss one, the database says the same person lives in two cities.

The one-sheet design breaks in four ways

ProblemWhat goes wrongZomato example
RepetitionThe same fact is stored again and againC063's phone number is stored 13 times
Update problemChange one copy, miss another, and the data disagrees with itselfShe moves city, and one row still says Pune
Insert problemA fact cannot be stored until something else exists15 of our 200 customers have never ordered. With one sheet they would have no row at all
Delete problemRemoving one fact destroys anotherDelete a customer's only order and the customer disappears

The fix is to store each fact once, in its own table, and link the tables with a key (the proper name for this idea is normalisation).

📱
The Contacts Analogy: You save a friend's number once in Contacts, and every chat and call points to that contact. You never retype the number into every message. Our two tables work the same way: customers is the Contacts list, and every row in orders just points to a contact.
One row in customers, and the many rows in orders that point to it

See the link in the real data (read-only):

📄 C063's record and all her orders
USE zomato;


SELECT customer_id, first_name, last_name, city
FROM customers
WHERE customer_id = 'C063';


SELECT order_id, customer_id, order_date, order_value

🗣️ Result: One row: C063 | Anjali | Patel | Pune. Thirteen order rows, every one carrying C063 — her name and city are never repeated inside the orders table itself.
🧠 A habit for your whole career

Every time you see the same column name in two tables, ask: is this a link? Wherever there is a link, there is a question that needs both tables, such as "show me all orders placed by Prime customers in Bangalore."

One more problem remains: nothing yet stops someone typing C999 into an order, or adding C063 twice to customers. The rules that guard the link are called keys.

3

Primary, Unique and Foreign Keys 🪪

Nothing stops a duplicate customer row, or an order pointing to a customer who does not exist, unless the database is told to enforce it. A constraint is a rule attached to a table that the database enforces on its own: NOT NULL, PRIMARY KEY, UNIQUE and FOREIGN KEY are all constraints. The three that guard identity and links are called keys.

To practise safely, Class 2 builds the part of Zomato it is missing: restaurants and the dishes they serve, in zomato_practice. Here is the map of the practice tables built across this class:

The practice schema built one table at a time: restaurants → dishes → fssai_licences → placed_orders → order_items

🔴 Primary Key — the row's identity

🪪
The Aadhaar Analogy: One Aadhaar number per person. No one else has the same number. Every resident has one, so it is never blank. Any office can find you instantly with it. A primary key is the Aadhaar number of a row. Your name cannot do that job: the customers table has 14 different customers called Priya Mehta.

Rules of a primary key: unique (no two rows share the value), not null (never blank), at most one per table, and stable (the value should never change, since other tables point to it). Zomato: customer_id in customers, order_id in orders.

📄 Building restaurants with a primary key
USE zomato_practice;


CREATE TABLE restaurants (
    restaurant_id    INT           NOT NULL,
    restaurant_name  VARCHAR(100)  NOT NULL,
    city             VARCHAR(50),
    contact_email    VARCHAR(100),
    PRIMARY KEY (restaurant_id)
);
🗣️ Reads as: "restaurant_id uniquely identifies every row, and it can never be blank."

Try to break the rules — a duplicate id, and a missing id:

🐛 Two attempts that MySQL refuses
INSERT INTO restaurants (restaurant_id, restaurant_name, city)
VALUES (101, 'Copy Cat Cafe', 'Pune');  -- duplicate id


INSERT INTO restaurants (restaurant_id, restaurant_name, city)
VALUES (NULL, 'Ghost Kitchen', 'Delhi');  -- no id at all
🗣️ Result: Error 1062 (Duplicate entry '101' for key 'restaurants.PRIMARY'), then Error 1048 (Column 'restaurant_id' cannot be null). Nobody had to remember to check — the database refused both rows itself.

🟣 Unique Key — no clones allowed

📧
The Passport Analogy: A passport number is also one per person, but you do not use it to run your whole life, and not everyone has one. Two restaurants should never share a contact email, but email is not the row's identity — restaurant_id already does that job. For a column that must not repeat but is not the main identifier, use a unique key.
📄 Adding a unique key, then checking it
ALTER TABLE restaurants ADD UNIQUE (contact_email);
DESC restaurants;
🗣️ In DESC output: the Key column shows PRI for restaurant_id and UNI for contact_email.

Break the unique rule, then confirm NULL is still allowed:

AttemptResult

Insert a restaurant with contact_email = NULL (a second one)Accepted — a unique key can hold multiple NULLs, because NULL means "unknown," and two unknowns are not considered the same value
Remember: a primary key can never be NULL. A unique key can.

🔵 Foreign Key — the bridge between tables

📱
Back to Contacts: A chat does not copy a friend's whole identity — it stores a link to the contact, and your phone will not let you start a chat with a contact that does not exist. A foreign key is a column in one table that must match the primary key of another table. In Zomato, customer_id in orders points to customer_id in customers. The table holding the primary key is the parent; the table holding the foreign key is the child.
📄 A dish belongs to one restaurant
CREATE TABLE dishes (
    dish_id        INT            NOT NULL,
    restaurant_id  INT            NOT NULL,
    dish_name      VARCHAR(100)   NOT NULL,
    price          DECIMAL(8,2)   NOT NULL,
    PRIMARY KEY (dish_id),
    FOREIGN KEY (restaurant_id)
        REFERENCES restaurants (restaurant_id)
);

Testing both directions:

AttemptResult
Insert a dish with restaurant_id = 999 (does not exist)Error 1452: Cannot add a child row — the FK constraint fails
Delete a restaurant that still has dishes pointing to itError 1451: Cannot delete a parent row — the FK constraint fails

The foreign key protects in both directions: you cannot create a child with no parent (an orphan), and you cannot remove a parent that still has children. A parent with zero children is fine — 15 of our 200 customers have never placed an order.

The three keys side by side

⭐ Primary key = who you are. Foreign key = who you belong to. Unique key = no clones allowed.
⚠️ Two common mistakes

1. Incompatible types: a foreign key INT cannot point to a primary key VARCHAR(10) — MySQL refuses with Error 3780. Use the same type (and for text, the same character set). Copy the parent column's definition from DESC.

2. Wrong build order: the parent table must exist before the child. A parent cannot be dropped while a child still points to it (Error 3730) — drop children first.

🏢 MySQL vs BigQuery: keys

BigQuery lets you declare primary and foreign keys, but they are marked NOT ENFORCED — labels that help the optimizer and document the design, but BigQuery will still store a duplicate id or an orphan row. There is no UNIQUE constraint at all in BigQuery.

Candidate Keys — Which Column Deserves the Job? 🏆

Look at the customers table: customer_id, first_name, last_name, phone, email, city. Which column, or combination, could identify a customer?

🪪
Aadhaar and PAN: each is unique to you, and every resident is expected to have one. Each is a candidate for "the ID I use everywhere." You pick one for official use — that becomes your primary key. The rest are still unique, so they become unique keys.

A candidate key is any column that could be the primary key: unique and never blank, by rule. Testing against the real data (read-only):

📄 Looking for Priya Mehta
USE zomato;


SELECT customer_id, first_name, last_name, city
FROM customers
WHERE first_name = 'Priya' AND last_name = 'Mehta'
ORDER BY customer_id;
🗣️ Result: 14 rows — 14 different customers named Priya Mehta, across Mumbai, Pune, Delhi and Bangalore. One of them, C104, is stored as "PRIYA" in capitals, and MySQL's default comparison still matched it (ignores case).
ColumnUnique in our data?Ever blank?Verdict
customer_idYesNo✅ Candidate — chosen as the primary key
first_name + last_nameNo — 14 Priya MehtasNo❌ Not a candidate
emailNo — several share a blank emailYes — some NULL, some blank text❌ Not a candidate
phoneYes — 200 different numbers todayNo❌ Not a candidate — unique by coincidence, not by rule
⚠️ Why "unique today" is not enough

phone is unique in our data today, but nothing in the design forces it to stay that way — people change numbers, share numbers, old numbers get reassigned. A candidate key must be unique and never blank by rule, not because the data happens to look that way this month. The best primary key is meaningless, short and never changes — exactly what customer_id is.

The pre-class data-quality check on email found: 24 NULL, 5 empty text, and 2 spaces-only values. That is exactly why a UNIQUE rule on email would be refused on the real table — several customers share the same blank email.

Relationships, Composite Keys & the Junction Table 🔗

Answer "one" or "many" for each pair: one customer and their orders; one restaurant and its FSSAI food licence; one order and the dishes in it. The third pair is the odd one out — both sides are "many": an order has many dishes, and a dish appears in many orders. There are three kinds of relationship.

1️⃣ One-to-Many — the most common relationship

One row on the "one" side matches many rows on the "many" side. One customer has many orders, but every order has exactly one customer. You build it by putting the foreign key on the "many" side — exactly as we did for dishes and restaurants: one restaurant, many dishes. A "one" row may have zero "many" rows: 15 customers have never ordered.

One customer, many orders — the foreign key lives on the orders (many) side

2️⃣ One-to-One — rare, but real

🪪
A person and their PAN card: one person, one card, and each card belongs to one person. In Zomato, a restaurant has at most one FSSAI food licence, and each licence belongs to one restaurant. You build it with a foreign key that is also UNIQUE, so the "many" side cannot repeat.
📄 A licence belongs to exactly one restaurant
CREATE TABLE fssai_licences (
    licence_no     VARCHAR(14)  NOT NULL,
    restaurant_id  INT          NOT NULL,
    valid_till     DATE,
    PRIMARY KEY (licence_no),
    UNIQUE (restaurant_id),
    FOREIGN KEY (restaurant_id)
        REFERENCES restaurants (restaurant_id)
);
🗣️ Testing it: inserting a second licence for restaurant 101 fails with Error 1062 — the UNIQUE rule on the foreign key is what turns one-to-many into one-to-one. Our practice data gives licences to two of the five restaurants.
A foreign key that is also UNIQUE: one restaurant, at most one licence

3️⃣ Many-to-Many — the one that needs a trick

An order has many dishes, and a dish appears in many orders. Put dish_id in the order, and each order can hold only one dish. Put order_id in the dish, and each dish can appear in only one order. Neither works. Every many-to-many relationship needs a third table in the middle, called a junction table (also called a bridge or link table).

🧾
The itemised bill: one line per dish, each line saying which order it belongs to and how many were ordered. That bill is the junction table.

Composite key — when one column is not enough

🎬
The Cinema Seat Analogy: "Seat 7" is not unique — every row has a seat 7. "Row D" is not unique either. But Row D, Seat 7 together point to exactly one seat. A composite key is a primary key made of two or more columns that are unique only together.
📄 The junction table: order_items
CREATE TABLE order_items (
    order_id  INT  NOT NULL,
    dish_id   INT  NOT NULL,
    quantity  INT  NOT NULL,
    PRIMARY KEY (order_id, dish_id)
);
🗣️ Reads as: order_id repeats (one order has several lines), dish_id repeats (one dish is on many bills), but the pair must be unique. Inserting (1, 1, 5) again — the exact same order_id + dish_id pair — fails with Error 1062: "Duplicate entry '1-1' for key 'order_items.PRIMARY'." To order more of the same dish, update the quantity; don't add a second row.
⚠️ Careful with composite keys

A composite key is one key made of several columns, not several separate keys. PRIMARY KEY (order_id, dish_id) does not make order_id unique and does not make dish_id unique — it makes the combination unique.

Connecting the junction table to both parents (foreign keys to placed_orders and dishes) means an order line for a non-existent order, like order_id = 99, is rejected with Error 1452. Later, when joins are introduced, this table is exactly what lets us answer "which dishes were in order 1?"

placed_orders and dishes connect through order_items — a junction table with a composite primary key

🏢 MySQL vs BigQuery: relationships

The three relationship types are the same everywhere. A composite key in BigQuery is also information-only: PRIMARY KEY (order_id, dish_id) NOT ENFORCED — nothing stops a duplicate pair. Because BigQuery is built for large scans, teams often copy repeated values into one wide table, or nest repeated data using ARRAY and STRUCT, instead of building many small tables.

String Data Types: CHAR, VARCHAR, TEXT 🔤

Text can hold anything — a name, a price, a date, a rating. So why does every column carry a type at all? If order_value were stored as text, you cannot add or average it, and '45.5' sorts after '320.50' because text is compared character by character. The type is what makes math, sorting and validation possible.

TypeWhat it holdsSize ruleUse it forZomato column
CHAR(n)Fixed-length textAlways reserves n charactersShort fixed codesis_prime is CHAR(1): 'Y' or 'N'
VARCHAR(n)Text up to n charactersUses only what it needsNames, cities, ids, emailscity is VARCHAR(50)
TEXTLong free textUp to ~64 KBReviews, descriptionsnone yet — a review_text column would be TEXT
📝
The Paper Form Analogy: CHAR(2) is two printed boxes for a state code — always two boxes, even if you only write one letter. VARCHAR(50) is a single line with a maximum length — you write what you need, up to 50 characters. TEXT is the blank "Comments" page at the back — no tight limit, but you would not use a whole page for a two-letter code.
📌 Three points worth remembering
  • The number in VARCHAR(n) is a limit, not a reservation. Choose a limit comfortably above the longest real value.
  • A phone number or licence number is made of digits, but we never add or average them — they are labels, stored as text, which also keeps the leading + and any leading zeros. phone is VARCHAR(20).
  • The ID rule: IDs are labels, so we never do math on them. Coded ids like C063 and ORD0001 must be VARCHAR. Simple counters like practice dish_id 1, 2, 3 can be INT.
⚠️ Data that does not fit gets refused, not chopped

Inserting 'Zomato Gold Plus' (16 characters) into a VARCHAR(10) column gives Error 1406: "Data too long for column." By default MySQL refuses data that does not fit instead of quietly truncating it — which is why a limit that is too small is a real bug: valid customers get rejected.

🏢 MySQL vs BigQuery: strings

BigQuery has a single text type, STRING, with no length. CHAR, VARCHAR and TEXT all become STRING.

Numeric Data Types: INT, DECIMAL, FLOAT 🔢

Add 0.1 and 0.2 on a calculator and you get 0.3. Watch what happens when the same addition is done two different ways in MySQL:

📄 Exact addition vs floating-point addition
SELECT 0.1 + 0.2                AS decimal_sum,
       0.1e0 + 0.2e0            AS double_sum,
       (0.1 + 0.2 = 0.3)        AS decimal_equals_03,
       (0.1e0 + 0.2e0 = 0.3e0)  AS double_equals_03;
🗣️ Result: decimal_sum = 0.3, double_sum = 0.30000000000000004, decimal_equals_03 = 1 (true), double_equals_03 = 0 (false). The e0 forces floating point. Computers store floating point numbers in binary, and 0.1 has no exact binary form — the error is tiny, but a million tiny errors become a visible rupee.
FamilyTypesExact?Use forZomato column
Whole numbersTINYINT INT BIGINTYesCounts, ratings, flagsrating, delivery_time_mins are INT
Exact decimalsDECIMAL(p,s)YesMoney, anything that must be exactorder_value is DECIMAL(10,2)
Approximate decimalsFLOAT DOUBLENo, tiny errorsMeasurements, coordinatesnone — deliberately

Whole number ranges: TINYINT holds -128 to 127 (used for a 1/0 flag), INT holds about ±2.1 billion, BIGINT reaches about 9.2 quintillion. A 10-digit phone number is larger than the biggest INT, so storing it as a number (which we do not, since it's an ID) would need BIGINT. Use the smallest type that is always big enough.

DECIMAL(p, s): p is the total digits, s is how many come after the decimal point. DECIMAL(10,2) means 10 digits total, 2 after the point — largest value 99,999,999.99, which is why order_value can hold 441.42.

🪙
Coins vs a kitchen scale: DECIMAL counts every paisa exactly, like counting coins. FLOAT and DOUBLE are like a kitchen scale — accurate enough for tomatoes, not good enough for rupees.
⭐ The money rule: store money as DECIMAL, never as FLOAT or DOUBLE. (Some systems store money as a whole number of paise in a BIGINT — also exact, also valid. The unsafe choice is the approximate one.)
⚠️ Two common mistakes

Storing money as INT: MySQL rounds the paise away on insert — 340.50 becomes 341, 340.49 becomes 340. The paise are silently lost.

Storing money as FLOAT/DOUBLE: totals look right at first, then drift by a paisa, and two reports start disagreeing.

🏢 MySQL vs BigQuery: numbers

BigQuery has one whole-number type, INT64, replacing TINYINT/INT/BIGINT. DECIMAL becomes NUMERIC (38 digits, 9 after the point; BIGNUMERIC is larger). FLOAT/DOUBLE become FLOAT64 — same approximation problem, so use NUMERIC for money.

Date and Time Types: DATE, TIME, DATETIME, TIMESTAMP 📅

Your manager asks: which hour of the day gets the most Zomato orders? Our orders.order_date column is a DATE — it stores the day and nothing else. There is no hour anywhere in the table, so the question cannot be answered. The type you choose today decides which questions you can answer tomorrow.

TypeWhat it storesLooks likeUse for
DATEJust the day2025-04-01Birthdays, signup day, order day
TIMEJust a time or duration18:30:00Opening hours, durations
DATETIMEDay and time, no time zone2025-04-01 18:30:00A fixed clock reading
TIMESTAMPDay and time, stored in UTC, shown in viewer's time zone2025-04-01 18:30:00Audit columns: created_at, updated_at

In our schema, signup_date and order_date are DATE. A real delivery app would store order time as DATETIME or TIMESTAMP.

DATETIME vs TIMESTAMP — the one that surprises people

DATETIME stores exactly what you typed. TIMESTAMP converts to UTC when stored and converts back to the session's time zone when shown:

Session time zoneplaced_dt (DATETIME)placed_ts (TIMESTAMP)
+05:30 (India)2025-04-01 18:30:002025-04-01 18:30:00
+00:00 (UTC)2025-04-01 18:30:002025-04-01 13:00:00

Same row, same moment. Someone in India reads 6:30 PM. Someone on a UTC connection reads the same moment as 1:00 PM. TIMESTAMP adjusts to the viewer; DATETIME shows identical text to everyone. Use TIMESTAMP for "the exact moment this row was created," and DATETIME or DATE when the clock reading itself is the fact.

DATETIME never changes; TIMESTAMP recalculates for the viewer's time zone
Two limits to remember: DATE and DATETIME cover years 1000–9999. TIMESTAMP only covers 1970–January 2038.
🏢 MySQL vs BigQuery: dates and times

DATE, TIME and DATETIME exist with the same meaning. BigQuery's TIMESTAMP is a moment in UTC with microsecond precision, displayed in UTC by default. Time zones are usually applied inside functions rather than a MySQL-style SET time_zone.

       column_name             AS child_column,
       referenced_table_name   AS parent_table,
       referenced_column_name  AS parent_column

WHERE table_schema = 'zomato'
  AND referenced_table_name IS NOT NULL;
🗣️ Result: one row — orders.customer_id points to customers.customer_id. The child table orders points to the parent table customers.

CAST — Fixing a Value in the Wrong Type 🧮

A restaurant partner sends a file. Prices arrive as text: '320.50', '120.00', '45.5'. Sort them highest to lowest, and the cheapest item comes out on top. Why?

📄 Text comparison vs numeric comparison
SELECT '45.5' > '320.50'    AS text_says_bigger,
       CAST('45.5' AS DECIMAL(8,2))
         > CAST('320.50' AS DECIMAL(8,2))  AS number_says_bigger;
🗣️ Result: text_says_bigger = 1 (true), number_says_bigger = 0 (false). As text, '45.5' is "bigger" because text compares character by character, and '4' comes after '3'. As numbers, 45.5 is smaller, which is what was actually meant. That conversion is called CAST.
Text sorting vs numeric sorting — same values, different order
🥤
Pouring water into a different glass: CAST(expression AS type) converts a value from one type to another. Same water, a different shape of glass, and the glass decides what you can do with it. Pour text into a number glass and you can add it up. If the new glass is narrower, something is lost — pour 290.82 into a whole-number glass and you get 291. CAST changes the value in your result only. It never changes the stored column.
Target typeConverts toExampleResult
SIGNEDA whole numberCAST('42' AS SIGNED)42
DECIMAL(p,s)An exact decimalCAST('45.5' AS DECIMAL(8,2))45.50
CHARTextCAST(441.42 AS CHAR)'441.42'
DATEA dateCAST('2025-04-01' AS DATE)2025-04-01
DATETIMEA date and timeCAST('2025-04-01' AS DATETIME)2025-04-01 00:00:00

The rounding rule — numbers round, text reads left to right

ExpressionResultWhy
CAST(290.82 AS SIGNED)291A decimal number is rounded to the nearest whole number
CAST('290.82' AS SIGNED)290 (with a warning)Text is read left to right up to the first non-digit character — .82 is ignored, not rounded
⚠️ Careful with the type names

CAST(x AS INT), INTEGER, VARCHAR, STRING and NUMBER are not valid in MySQL. MySQL uses SIGNED for whole numbers and CHAR for text. Writing the BigQuery/PostgreSQL name in MySQL gives Error 1064. This is one of the most common mistakes — and AI assistants make it constantly.

Implicit vs Explicit Conversion ⚡

What does '5' + 3 give — an error, '53', or 8?

📄 MySQL converting types on its own
SELECT '5' + 3        AS a,
       '5' + '3'      AS b,
       '3 apples' + 2 AS c,
       1 = '1'        AS d,
       'abc' = 0        AS e;
🗣️ Result: a=8, b=8, c=5, d=1, e=1. MySQL quietly converted text to numbers. That is implicit conversion — automatic and invisible. CAST is explicit conversion — you wrote it and can see it. Text that does not start with a digit becomes 0, which is why 'abc' = 0 is true.

Now the dangerous version, on real data: customer_id values look like 'C001', 'C002'. What happens when text is compared against a number?

📄 Comparing text with a number — read-only
USE zomato;


SELECT COUNT(*) FROM customers WHERE customer_id = 0;
SELECT COUNT(*) FROM customers WHERE customer_id = 'C063';
🗣️ Result: the first query returns 200 — every single customer "matches"! MySQL converts every 'C001' into a number to compare it, and text that does not start with a digit becomes 0, so all 200 rows match. No error, a completely wrong answer. The second query correctly returns 1. Always compare like with like.
Implicit conversionExplicit conversion

RiskWrong results with no errorLow, if you check the result

🏢 MySQL vs BigQuery: implicit conversion

BigQuery refuses to guess. '5' + 3 stops with "No matching signature for operator +," and customer_id = 0 stops with a similar error. Annoying sometimes, but a wrong type shows up immediately instead of as a wrong number in a dashboard.

⭐ Be explicit. Write the CAST, so the query says what you mean and runs the same way everywhere.

When CAST Shows Up in Real Work 🛠️

In real projects, CAST is almost never about showing off — it is a repair tool. Four situations come up again and again:

SituationWhat goes wrongThe fix
1. Numbers stored as text that you need to sort, SUM or AVG'45.5' sorts after '320.50'; MySQL silently uses floating point when adding text, so totals can driftCAST(price_text AS DECIMAL(8,2))
2. Text dates that you need to filter as datesText is compared character by character, so it does not behave like a dateCAST(ordered_on AS DATE)
3. A date and time that you need as a day onlyThe time part gets in the way when grouping orders per dayCAST(placed_at AS DATE)
4. Joining a number to textA number cannot be glued into a sentence in every databaseCONCAT('Rs ', CAST(order_value AS CHAR))

Case 1 in action — adding '0.1' + '0.2' + '0.3' as text gives 0.6000000000000001 (drifted via implicit float conversion); casting each to DECIMAL first gives exactly 0.60.

Case 2 note — CAST(... AS DATE) expects year-month-day order, e.g. 2025-04-01. A date written the Indian way, 25/12/2024, gives NULL and needs a different function (STR_TO_DATE).

Case 4 note — MySQL turns a number into text automatically inside CONCAT, but BigQuery stops with an error until you write CAST(order_value AS STRING) explicitly.

That "no error, wrong answer" pattern is worth understanding completely. What does MySQL actually do when a conversion cannot work?

When a Conversion Fails 💥

'abc' is not a number. Should the database stop with an error, return NULL, or return something else?

ExpressionResultWarning?
CAST('abc' AS SIGNED)0Yes, code 1292
CAST('12abc' AS SIGNED)12Yes — reads the leading 12, ignores the rest
CAST('45.50' AS SIGNED)45Yes — reads leading 45, ignores .50
CAST('2025-13-45' AS DATE)NULLYes — there is no month 13
A failed CAST in a SELECT never stops the query — it returns 0, a partial number, or NULL, with a warning

In MySQL, a failed conversion inside a SELECT is not an error. You get a result (zero, a partial number, or NULL) plus a warning — easy to miss unless SHOW WARNINGS; is run immediately after. For example, casting a phone number like +91-7968364412 to a whole number would give just 91, the leading digits before the first non-digit character. That is one more reason we store phone numbers as text.

⚠️ MySQL is strict in exactly one place

When you try to store a bad value (INSERT or UPDATE), the default is an error and nothing is stored: 'abc' into an INT column gives Error 1366; '12abc' gives Error 1265.

SELECT with a bad conversionINSERT/UPDATE with a bad value
MySQL (default)Warning, with 0/NULL/partial resultError, nothing stored
BigQuery CASTError, query stopsError
BigQuery SAFE_CASTReturns NULL, no errorNot applicable
🏢 MySQL vs BigQuery: failed conversions

CAST('abc' AS INT64) stops with an error in BigQuery. SAFE_CAST('abc' AS INT64) returns NULL — very useful for cleaning messy files, but it hides the problem, so count the NULLs afterward.

⭐ The golden rules for CAST:
1. Say the type you want — don't let the database guess.
2. After a CAST, look for surprises: a column of zeros, NULLs, or fewer rows than expected.
3. If a value should never be converted at all (phone numbers, ids, licence numbers), fix the column type instead of casting it.

AI Segment — Data Types and CAST 🤖

✈️
The Co-Pilot Analogy: The co-pilot (AI) helps with calculations and checklists. The pilot (you) is always in charge. AI is very good at SQL syntax, and very bad at knowing your database and your business meaning.

Trap 1: the right idea, the wrong dialect

Prompt: "Write a SQL query to show the first 5 orders of customer C063 with the order value as a whole number." A typical AI answer, correct in BigQuery/PostgreSQL but wrong in MySQL:

🐛 Fails in MySQL with Error 1064
SELECT order_id, CAST(order_value AS INT) AS order_value_int
FROM orders
WHERE customer_id = 'C063'
ORDER BY order_id
LIMIT 5;
🗣️ The catch: MySQL has no INT target for CAST. The AI did not know which database was being used — in MySQL the correct target is SIGNED.

Trap 2: correct syntax, ambiguous business meaning

With full context given (MySQL 8.0 + exact column types), the AI correctly writes CAST(order_value AS SIGNED). But look at the result on real C063 orders:

order_idorder_valuewhole_value
ORD0033294.57295
ORD0152201.65202

The catch: CAST rounds. "Whole number" could mean rounded (295), or the rupees with paise cut off (294). The AI silently picked one without asking. Syntax correctness is not the same as business correctness — always check a few rows yourself.

Trap 3: a table design that looks fine at a glance

Prompt: "Create a MySQL payments table for Zomato, linked to orders." A typical AI answer, reviewed but never run:

🐛 Would fail with Error 3780 if run
CREATE TABLE payments (
    payment_id  INT PRIMARY KEY,
    order_id    INT,
    amount      FLOAT,
    paid_at     DATETIME,
    FOREIGN KEY (order_id) REFERENCES orders (order_id)
);

📌 Checklist before using AI-written SQL about types
  • Did I say "MySQL 8.0" (or "BigQuery") in the prompt?
  • Are all type names valid in my database? (SIGNED/CHAR in MySQL, INT64/STRING in BigQuery)
  • Is every money column DECIMAL or NUMERIC, never FLOAT?
  • Does every foreign key column match its parent's exact type?
  • After any CAST, did I check for zeros, NULLs and rounded values?
⭐ AI knows SQL. It does not know your database, your column types, or what your numbers mean. You do.
