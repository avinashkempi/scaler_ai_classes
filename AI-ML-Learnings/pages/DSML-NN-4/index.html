4 signals → 5 units → 4 units → 3 tracks — the exact funnel built in Act 3
    1 Foundations, fast

    Two ideas worth having solid

    Before generalizing from two rounds to any number of rounds, two results from last session are worth confirming — not re-deriving, just confirming.

    A sigmoid neuron is logistic regression

    A single neuron computes z = w·x + b and passes it through an activation function. Swap in sigmoid, and the neuron becomes functionally identical to logistic regression — same functional form, same output range. Swap in a step function instead, and it becomes a Perceptron.

    Softmax's clean gradient: dZ = P − Y

    For a softmax output layer trained with cross-entropy loss, the gradient at the final round collapses to one clean expression: the predicted probabilities minus the true one-hot labels, dZ = P − Y. It's the starting point every backward pass in this lecture builds from — you'll see it again, generalized, in Act 4.

    Two more worth a gut-check: why a hidden round needs a non-linear activation at all, and what actually causes vanishing gradients. Both were covered in full last session — if either feels shaky, that's worth revisiting before Act 1.
    2 Act 1

    The panel's decision space

    A classification round doesn't just compute scores — it carves up the space of possible inputs. Wherever the predicted class changes, that's a decision boundary. Moving the weights moves those boundaries.

    3 Act 2

    Naming an N-round funnel

    Two rounds by hand was manageable: W¹, b¹, W², b². That notation doesn't scale to ten rounds. Here's the generalized version.

    For a network with L rounds total (not counting the raw input), label them 1, 2, … L, where round L is the final panel:

    SymbolMeaning
    A[0] = Xthe raw signals — there's no "round 0," just the input
    W[l]weight matrix connecting round l−1's output to round l
    b[l]bias vector for round l
    Z[l] = A[l−1]W[l] + b[l]round l's raw scores
    A[l] = g[l](Z[l])round l's activation output, using whichever activation g[l] that round uses

    If round l−1 has nl−1 units and round l has nl units: W[l] has shape (nl−1, nl), and b[l] has shape (1, nl).

    4 Act 3

    Running an N-round funnel, for real

    A real 3-round funnel: 4 raw signals → a pre-screening round of 5 units (ReLU) → a second round of 4 units (ReLU) → a final panel of 3 tracks (softmax).

    Forward pass — one loop, any number of rounds

    def forward_propagation(X, params, num_layers):
    A = X
    cache = {"A0": A}
    for l in range(1, num_layers + 1):
        Z = A.dot(params[f"W{l}"]) + params[f"b{l}"]
        A = softmax(Z) if l == num_layers else relu(Z)
        cache[f"Z{l}"], cache[f"A{l}"] = Z, A
    return A, cache

    layer_sizes is the only thing that changes to make this funnel bigger or deeper — [4, 5, 4, 3] becomes [4, 8, 8, 8, 3] by editing one line, and the loop above already handles it for any number of rounds. That's the entire payoff of Act 2's notation: it's what makes this a loop instead of a hand-typed block of code per round.

    A network that only runs forward is frozen — it never improves. Adding the backward pass (the same general formula formalized in Act 4) closes the loop:

    Backward pass

    def backward_propagation(params, cache, Y, num_layers):
    grads = {}
    dZ = (cache[f"A{num_layers}"] - Y) / Y.shape[0]   # dZ[L] = A[L] − Y
    for l in range(num_layers, 0, -1):
        grads[f"dW{l}"] = cache[f"A{l-1}"].T @ dZ
        grads[f"db{l}"] = np.sum(dZ, axis=0, keepdims=True)
        if l > 1:
            dZ = (dZ @ params[f"W{l}"].T) * relu_deriv(cache[f"Z{l-1}"])
    return grads

    Common misconception backward_propagation doesn't need to know every round's activation function in general — it only calls relu_deriv here because every hidden round in this funnel uses ReLU. Swap one round's activation and only that one derivative call changes, not the whole function.
    5 WOW moment

    The loss went down the whole time

    If training loss is steadily decreasing, every single epoch — is the model definitely getting better?

    The setup: a deliberate mismatch — only 30 training candidates, but a panel with 200 hidden units. Far more capacity than 30 points need.

    Train loss vs. validation loss, over 2,800 epochs
    Curve shape approximates the run as described (exact per-epoch figures aren't given in the source); the labeled points are the values stated directly.

    The answer is (B). Train loss falls the entire run, from about 3.9 down to roughly 0.003. Validation loss falls too — at first. It bottoms out near 0.14 around epoch 200, then climbs steadily back past 0.28 by epoch 2800, even as train loss keeps dropping the whole time.

    Past that turning point, the model isn't learning the underlying pattern anymore — it's memorizing the 30 training candidates, including their noise. This is overfitting, and it's the single most common failure mode you'll debug on the job.

    Debugging scenario A teammate reports 99% training accuracy and 61% validation accuracy. The order of operations: confirm it's genuinely overfitting — not a data leak or a bug in how the validation set was built — then reduce model capacity or add regularization (dropout, weight decay), then get more training data if possible, then switch to early stopping based on validation loss, not training loss.
    Common misconception "Just train for longer" — this demo directly disproves it. Longer training here makes the metric that actually matters, validation loss, worse, not better.
    6 Act 4

    Backprop through N rounds, in matrix form

    Last session, feedback was summed neuron by neuron. That's correct, but it doesn't scale to code for an arbitrary number of rounds. Here's the same idea, written once, for an entire round at a time.

    At the final round L (softmax + cross-entropy):

    dZ[L] = A[L] − Y

    For every earlier round l — click each part of the formula below:

    dZ[l] = ( dZ[l+1] W[l+1]ᵀ ) ⊙ g′[l](Z[l])
    Click a highlighted part of the equation above.

    From dZ[l], the same pattern as always:

    dW[l] = (A[l−1])ᵀ dZ[l]     db[l] = Σ dZ[l]

    This one formula, applied repeatedly, is the multi-path summing rule from last session — written in matrix form, the sum over every downstream path a unit feeds into happens automatically inside the matrix multiplication. Nothing new is being claimed here; it's the same idea, industrial-strength.

    7 Debugging habits

    Proving a backward pass is correct

    Whenever you hand-derive a backward pass — exactly what Act 4 just did — there's a standard way to catch a sign error or a transposed matrix before it wastes hours of confusing training runs.

    numerical gradient ≈ ( J(w+ε) − J(w−ε) ) / 2ε

    Nudge one weight by a tiny amount, see how much the loss actually changes, and compare that to what the formula predicts. Run on the exact 3-round funnel from Act 3:

    W[i, j] = orig + eps;  loss_plus  = loss_fn(forward(X, params, L)[0], Y)
W[i, j] = orig - eps;  loss_minus = loss_fn(forward(X, params, L)[0], Y)
numerical  = (loss_plus - loss_minus) / (2 * eps)
analytical = grads[f"dW{l}"][i, j]

    The numerical and analytical columns should match to about 8–10 decimal places — anything larger than roughly 1e-5 signals a real bug in the backward derivation, not floating-point noise.

    Why nudge the weight both up and down?
    A one-sided nudge (only +ε) has first-order error in ε. The centered version — nudging both up and down and averaging — cancels that error term, giving a far more accurate estimate for the same computational cost.
    Why not just use gradient checking as the training method?
    It requires one full forward pass per parameter, per check — completely impractical at scale. It's a correctness check for a hand-derived backward pass, not a training algorithm.
    Worth knowing: production deep learning frameworks compute gradients automatically (automatic differentiation) and don't need this check for standard layers. Gradient checking earns its keep specifically when you hand-derive a backward pass yourself, exactly as above.

    Debug this shape mismatch

    X is shape (32, 10). W1 is shape (10, 16). W2 is shape (16, 1). Computing A1 = relu(X @ W1), then A2 = A1 @ W2.T throws a shape error.

    A1 is (32, 16); W2 is (16, 1), so W2.T is (1, 16) — (32,16) @ (1,16) doesn't align. The fix: A1 @ W2, no transpose, giving (32, 1).

    8 Capstone

    When a model overfits

    Three different types of fix, and what each one actually changes:

    DATA-SIDE

    More data

    Get more training data, or augment what you already have.

    CAPACITY-SIDE

    Shrink capacity

    Shrink the network, or add dropout / weight decay to penalize complexity.

    TRAINING-SIDE

    Early stopping

    Stop at the validation-loss minimum, not when training loss stops falling — exactly the turning point from the WOW moment.

    Where this goes next: dropout (randomly zeroing out some activations during training, so no single unit can be relied on too heavily) and weight decay (penalizing large weights directly in the loss) are both simple, standard additions once "why does my model overfit" is second nature.
