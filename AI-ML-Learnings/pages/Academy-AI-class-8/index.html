Section 2 · 14 minWorkflow 1: Day-Trip Buddy, an agent with no tools yet

We build an assistant that helps you decide what to do in a city tomorrow. It will end up checking real weather. For now it has nothing but a model.

Step 1 - Open your n8n Cloud workspace and create a new workflow. Name it Day-Trip Buddy.

Step 2 - Click Add first step and search for Chat Trigger. On the canvas it appears as "When chat message received". This is the front door: every message you type arrives here.

Step 3 - Click the plus after the trigger and add an AI Agent node.

Step 4 - Under the agent you will see a slot called Chat Model. Click its plus and choose Groq Chat Model. Create a new credential and paste your Groq key from Class 1.

ImportantThe Groq node's default model is an old one, llama3-8b-8192. Open the Model list and pick openai/gpt-oss-120b, the same model as in Class 7. If you would rather use the OpenAI Chat Model node pointed at Groq, as in Class 6, switch off the option called Use Responses API, because it is on by default.

Step 5 - Open the AI Agent node, go to Options, add System Message, and paste this.

You are Day-Trip Buddy, a friendly assistant that helps people decide what to do in a city tomorrow.
Use find_city to get a city's coordinates, then get_weather to check the forecast, and wikipedia for things to see.
Never guess a forecast. If a tool fails twice in a row, tell the user the service is unavailable and stop.

Step 6 - Open the chat panel on the canvas and send: Hi, what can you do?

Step 7 - Now send: Should I carry an umbrella in Jaipur tomorrow?

Ask LearnersWhat did it do: admit it cannot check, or guess a forecast?

Either answer is the point. The model has no way to look anything up. Everything that follows fixes that.

Note for InstructorThe system message names tools that do not exist yet. That is deliberate: the same message is used for the whole build, so nobody has to edit it later. If the model mentions it has no weather tool, that is correct.
Doubt by Learner"Where is the loop? I do not see any loop on the canvas."

It is inside the node. The AI Agent node runs think, act, observe for you, and repeats until the model has an answer or hits Max Iterations. You will meet that limit in Section 5.

Section 3 · 20 minGive it tools

A tool is a function plus a description. In n8n that means a node plus the words you write about it. The model never sees the node's settings. It sees two things only: the node's name and its description.

Use the visualizer below. Switch tools on and off, ask a question, and see which questions the agent can still answer.

A tool with no setup

Step 1 - Under the agent, click the plus on Tool and add Wikipedia. It needs no credentials.

Step 2 - Ask: Tell me one famous place to visit in Jaipur.

A tool you configure: find_city

The weather service we use is Open-Meteo. It needs no key. But its forecast works from latitude and longitude, not from city names, so we need a second tool that turns a city into coordinates.

Step 3 - Click the plus on Tool again and add HTTP Request Tool. Rename the node to find_city. Select it and press F2, or double-click the name.

Step 4 - Set Description to manual and write this.

Look up a city by name. Returns its latitude and longitude.

Step 5 - Set the URL.

https://geocoding-api.open-meteo.com/v1/search?count=1

Step 6 - Switch on Send Query Parameters, choose Using Fields Below, and add one parameter. Name: name. For the value, switch the field to Expression and type this.

{{ $fromAI('city', 'The name of the city, for example Jaipur', 'string') }}
Important$fromAI is how a tool asks the model to fill in a value. The first word, city, is the label. The sentence is what the model reads to know what to put there. It works only on tools connected to an agent. The editor can also generate this for you from a button on the field, but the button's wording changes between versions, so we type the expression.

The second tool: get_weather

Step 7 - Add another HTTP Request Tool. Rename it get_weather. Description:

Get the daily weather forecast for a place from its latitude and longitude. Returns the highest and lowest temperature in Celsius and the chance of rain for the next two days.

Step 8 - URL:

https://api.open-meteo.com/v1/forecast?daily=temperature_2m_max,temperature_2m_min,precipitation_probability_max&forecast_days=2&timezone=auto

Step 9 - Switch on Send Query Parameters, Using Fields Below, and add two parameters. Name latitude with this value:

{{ $fromAI('latitude', 'Latitude of the place, from find_city', 'number') }}

And name longitude with this value:

{{ $fromAI('longitude', 'Longitude of the place, from find_city', 'number') }}
DisclaimerOpen-Meteo is free for non-commercial use, up to 10,000 calls a day, and asks for attribution under a CC BY 4.0 licence. That is fine for a class. A product you sell would need a paid plan.

Step 10 - Ask again: Should I carry an umbrella in Jaipur tomorrow? Then open the Logs view, or switch on Return Intermediate Steps in the agent's options, and read the calls in order.

Ask LearnersWhich tool did it call first, and why could it not start with get_weather?

Because the forecast tool needs coordinates and only find_city can produce them. Nobody wrote "first this, then that". The model worked out the order from the two descriptions.

Doubt by Learner"Why two tools? Why not one tool that takes a city?"

Because the weather service wants coordinates. Splitting the job into small tools with clear descriptions lets the model chain them, and each tool stays easy to test on its own.

Doubt by Learner (Optional)"What stops it from making up a forecast anyway?"

Nothing absolute. The system message says never to guess and the tool gives it real data, which makes guessing unnecessary. It is a strong nudge, not a guarantee. That is why Section 5 adds guards that do not depend on the model behaving.

Note for InstructorIf a learner's run fails at the Groq model with a tool error, first check they chose openai/gpt-oss-120b. Groq lists tool use as supported for it but not parallel tool calls, and an occasional malformed tool call is a known issue with some models. Re-running the message almost always works.

Section 4 · 10 minGive it memory

First, watch the problem. Open a fresh chat and send these two messages, one after the other.

My name is Aarav.

What is my name?
Ask LearnersDid it know? Why not?

It did not, and this does not depend on the model. Each message starts a new run. Nothing carries the first one into the second.

Step 1 - Under the agent, click the plus on Memory and add Simple Memory. Leave the defaults: the session ID comes from the Chat Trigger, and the Context Window Length is 5.

Step 2 - Start a fresh chat and send the same two messages.

This time it knows. Then clear the chat to start a new session and ask the name again. It is gone, because a new session is a new memory.

What memory really is

Remember the message list from Class 7. Memory is that list, kept between messages. Before each run, n8n takes the last few exchanges for this session and puts them in front of the new message. The model does not remember anything. It is re-reading the recent past every time.

Use the visualizer below. Slide the window length and the chat length, and see which messages the model can still read.

ImportantSimple Memory lives inside n8n's own memory. It does not survive a restart of n8n, and the docs say it is not for queue mode. It is right for learning and small tests. A product that must remember customers needs memory stored in a database.
Doubt by Learner"Why not just send the entire chat every time?"

Cost and limits. Every message you re-send is billed in tokens and counts against Groq's tokens-per-minute limit. A window is a trade: more memory, more cost.

Section 5 · 12 minBreak it on purpose, then fix it

Agents fail in predictable ways. We will cause two of them on purpose. Each time the rhythm is the same: break it, apply one fix, show it working.

Failure 1: a broken tool

Step 1 - In get_weather, change temperature_2m_max in the URL to temperature_2m_maxx. One extra letter, a typo.

Step 2 - Ask: Should I carry an umbrella in Jaipur tomorrow? Then open the Logs view and read what get_weather returned.

You will see a short, vague message from the tool, along the lines of "Bad request - please check your parameters". The agent cannot tell what is wrong, because the message does not say. It may try again, or give up and apologise. Either way, the bug is ours.

Ask LearnersWhose bug is this, the model's or ours?

Ours. When an agent misbehaves, look at the tool's output in the logs before touching the prompt.

Step 3 - Fix it: change the URL back to temperature_2m_max. Ask again. It works.

Note for InstructorThe weather service rejects an unknown variable name with a client error, and n8n passes only a generic bad-request message back to the agent. That is why the typo is a reliable failure: it breaks the tool, not the model. Confirm the exact message in your dry run. If a learner sees different words, the lesson is unchanged.

Failure 2: a runaway loop

Step 4 - Open the AI Agent node, go to Options, add Max Iterations, and set it to 2.

Step 5 - Ask the umbrella question again.

It stops with an error that reads "Max iterations (2) reached. The agent could not complete the task within the allowed number of iterations." The task needs three rounds: find the city, get the forecast, write the answer. We gave it two.

Step 6 - Fix it: set Max Iterations to 6. Ask again. It works.

The default is 10. A limit matters because every round is a model call. An agent stuck in a loop spends your tokens and your Groq request allowance until something stops it.

ImportantThis is the same step limit as Class 7. There you set it in code. Here it is one box in the node. The guard lives outside the model, so it works whatever the model does.

Failure 3: a blip

Not every failure is a bug or a loop. Sometimes a service is busy for a moment and works a second later.

Step 7 - Open the get_weather node, go to its Settings tab, switch on Retry On Fail, and set Max Tries to 3 with a wait of 1000 milliseconds between tries.

Now a short outage is absorbed by the node and the agent never sees it. A real bug still fails after three tries, so retry does not hide it forever.

Section 6 · 22 minWorkflow 2: an agent that acts, with a human gate

Workflow 1 only reads. Workflow 2 changes something in the world: it sends a message to a customer. That is where control matters.

Back in Class 6 you built a ticket pipeline with an IF node. Every path was drawn. Use the visualizer below and compare it with an agent on the same task, including a ticket nobody planned for.

Load the support desk

Step 1 - Import support_desk_agent.json. In n8n, open the workflow menu and choose Import from file.

Step 2 - Reconnect credentials. The Groq Chat Model needs your Groq credential. The send_reply tool needs your Telegram bot credential, and its Chat ID field needs your own chat ID from Class 6.

Note for InstructorImported workflows name the credentials they need but never contain the keys. This is the Class 6 export skill used in the other direction. Learners will see a credential warning on two nodes. Connecting them is part of the step.

What the agent can do

Three tools, all small.

lookup_order is a Code tool that finds an order by its number. The code is plain JavaScript, and the model's input arrives in a variable called query.

const orders = {
  "1001": "Order 1001: delivered on 5 Nov.",
  "1002": "Order 1002: delayed. The new delivery date is 18 Nov.",
  "1003": "Order 1003: cancelled. A refund was issued."
};
const id = String(query).replace(/[^0-9]/g, "");
return orders[id] || "No order found with number " + id;

refund_policy is another Code tool that returns one fixed sentence about refunds.

send_reply is the Telegram tool. We fixed its Chat ID ourselves, so the model cannot choose who to message. The model only writes the text, through the same $fromAI idea you used in Section 3.

ImportantNotice what we did with the Chat ID. The things that must never change are set by you. The things that should be decided by the model are left to it. That split is a safety decision, not a convenience.

Run it with nobody watching

Step 3 - Ask: A customer says: where is my order 1002? Find it and message the customer.

Your Telegram buzzes. The agent looked up the order and sent a message, and nobody approved it.

Ask LearnersThe agent misreads the order number as 1003 and tells a customer a wrong refund was issued. What would have stopped it?

Only a human. That is what we add next.

Add the gate

Step 4 - Open the AI Agent node and go to its Tools. Select send_reply and open Human review. Choose Telegram as the approval channel, pick your credential and Chat ID, and set the message to this.

The agent wants to send this reply to the customer:

{{ $tool.parameters.text }}
Important$tool.parameters holds what the model filled in for the tool. Our send_reply field is called text, so .text shows exactly the message. Without .text the approver sees a blob instead of the reply.
ImportantThe system message already tells the agent that every send needs approval, and that it must not retry if the request is denied. n8n's docs recommend writing the review setup into the system prompt, so the agent is not surprised by it.

Step 5 - Run the same question again. Telegram now shows the proposed message with Approve and Decline buttons, and nothing has been sent yet.

Step 6 - Tap Approve. A page opens in your browser to record your answer, and the message goes to your chat.

Step 7 - Run it once more and tap Decline. Nothing is sent. The agent is told the request was rejected and told to stop.

ImportantThe buttons are links to your n8n's public address. That is why this section needs n8n Cloud. A local n8n address cannot be opened from Telegram.

Use the visualizer below. Step through one request twice, once approved and once declined.

Note for InstructorThe Approve and Decline links are meant to be opened by a person. If you test them with a script or a link-preview tool, the page will not record the answer. Open them in a normal browser. Also, the labels in the Human review panel come from the docs. If a learner cannot find the panel, import support_desk_agent_with_approval.json and look at the extra node called Ask for approval, which sits between send_reply and the agent.
Doubt by Learner"Can the approver change the message before it goes?"

Not in this setup. The approver can only approve or decline. To change the message, decline it and ask the agent again.

Doubt by Learner (Optional)"Should every tool have a gate?"

No. Reading an order is harmless, so it runs freely. Gate the actions that cannot be undone: sending, deleting, paying. Too many gates and nobody will read them.

Section 8 · 5 minWrap-up and what is next

You started today with a model in a chat box. You end with two agents.

What you now know. The AI Agent node is the loop from Class 7 in one box. The model chooses, the node runs. A tool is a node plus a description, and the description is the model's only manual. Memory is the recent message list re-sent each time. Guards belong outside the model: Max Iterations for loops, Retry On Fail for blips, and a human gate for actions that cannot be undone.

What you built. A chat agent that checks real weather and remembers you. A support agent that can act, and cannot act without your tap.

Ask LearnersIn one line: which of your own tasks would you hand to an agent, and which action would you never let it take without asking you?

Next class the agent leaves the canvas. You meet OpenClaw, an agent that runs on your own machine and does real work there. The questions you practised today, what can it touch and who approves it, matter even more.
