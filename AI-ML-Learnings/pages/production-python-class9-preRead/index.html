Make It Fast: Concurrency and Async

Class 8 made the Workbench small and bounded: it measures, it streams, and it caps the model. Class 9 asks a different question: most of a big run is spent waiting. Can the waiting overlap, without losing a case, mixing up an answer, or breaking the rules of Class 8? You will tell waiting from computing, use threads, a process pool and asyncio, keep every answer under its own case, and pace the calls so that a provider never has to say “too many requests”. Read this before class, then arrive with your tools ready.

2. The big idea: name the wait

If a cook is waiting for the oven, a second cook can chop onions in the meantime, and dinner is ready sooner. If the cook is chopping, a second cook helps only when there is a second chopping board. Most of the Workbench’s time is oven time: a source pull, a model call. Class 9 makes you find out which kind of slow you have before you add anything.

5. Name the wait: waiting or computing?

A job is I/O-bound when most of its time goes to waiting for something outside the program: a network reply, a disk read. It is CPU-bound when most of its time goes to computing. More waiting at once makes an I/O-bound job faster. Only more cores make a CPU-bound job faster.

Standard Python has a lock, the GIL, that lets only one thread run Python code at a time. A thread that is waiting lets the lock go, so another thread can run. A thread that is computing keeps it. That one fact explains most of the class.

Five waits at once: the shape of an asyncio program
import asyncio

async def pull(name):
    await asyncio.sleep(0.2)     # a wait, standing in for a network call
    return name

async def main():
    return await asyncio.gather(*(pull(n) for n in "abcde"))

# five waits of 0.2 s, one after another:  1.00 s
# the same five with gather:               0.20 s

The measurements from class, on a machine with 2 cores:

ToolGood forWhat we measured
ThreadsWaiting: source pulls, model callsEight waits of 0.2 s: 1.60 s one by one, 0.40 s on four threads. Computing: 1.73 s against 1.63 s, no gain
asyncioMany waits, one threadFive waits: 1.00 s one after another, 0.20 s with gather
Process poolHeavy computing, large per-item work100 rounds per note: slower (0.007 s against 0.043 s). 100,000 rounds: 6.861 s against 3.515 s
A guess the measurement proves wrong Many people expect three threads to speed up reading the three source files. On local files, three threads took 0.31 seconds and so did one by one: parsing rows is computing, and the threads take turns. Only when each source waits (0.30, 0.40 and 0.25 seconds, simulated) did three threads help: 1.32 seconds became 0.59. Measure before you add a pool.

6. Several at once, without losing track

Running things together has one standing danger: answers come back in the order they finish, not the order they were asked. Every tool in this class keeps the answer with its key (the case_id or the source name), so it can never be paired with the wrong one. A failure, a timeout or a cancellation is an answer too, and it is kept under its key like any other.

A semaphore is not a rate limit A semaphore limits how many calls are in flight. A provider’s rate limit counts how many calls start each second. The two are linked by one line of arithmetic: calls in flight is about starts per second times seconds per call. Eight in flight at 0.04 seconds per call starts about 200 calls a second. Keep that number in mind for Section 7.

7. Plan, run, check

In live mode every flagged case with a note is one model call. Class 8 put gates in front of the call: skip short notes, reuse cached answers, stop at the call cap. If all those decisions were made inside the calls, running together would let two calls race for the last place under the cap, and the answer would change from run to run. So Class 9 splits the work in three, and the first and last parts are plain Python.

1. PlanOne case at a time, in case order: skip, cached, cap. Nothing waits
→
2. RunOnly the cases that need a call: at most 8 in flight, at most 80 starts per second
→
3. CheckAnswer n belongs to request n, and nothing is missing or doubled

The result you will see in class: the same 5,000-row run, with the same 200 calls and the same cost, goes from about 9.5 seconds to about 3.4 seconds, and the reports are byte-for-byte the same as the one-by-one run.
