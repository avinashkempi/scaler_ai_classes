Section 1 · 4 minWhere we are: you wrote this in Python already

Three classes ago you built a pipeline. Something comes in, a model processes it, something goes out. You wrote it in Python, in four files.

Today you build the same shape without writing code, and you add the parts your app never had: it runs on its own, and it sends the result somewhere.

Importantn8n is not a different kind of AI. The node that calls the model is making the same API call you made in Class 1, with the same three roles and the same key. What n8n gives you is everything around that call: a trigger, branching, connections to other services, and a picture of what happened.
Ask LearnersYour summariser only runs when you run it. Name one thing you do manually every week that could run on its own.
Note for InstructorTake two answers and keep them. The best one usually becomes somebody's Section 9 build.

Section 2 · 8 minThe canvas: triggers, nodes, connections

Three ideas, and then you can read any workflow you ever meet.

Idea What it is
Trigger What starts the workflow. A form, a schedule, an incoming message, or you pressing a button
Node One step. Call a model, send an email, add a row, make a decision
Connection The line between two nodes. Data flows left to right along it

That is the whole mental model. Everything else is which node you picked.

How data moves

Every node hands the next node a list of items, and each item is JSON. Class 2 taught you to ask a model for JSON; this is where that pays off, because the next node can reach into it by field name.

A node does its job once per item. Hand it five tickets and it runs five times, which is a thing people find surprising the first time.

ImportantWhen something does not work, the question is almost always "what did this node actually receive". Not what you think it received. n8n shows you, and Section 7 is about reading it.

Importing a workflow, which you will want twice today

Two ways in, and both are worth knowing because one of them rescues you mid-class.

Section 4 · 12 minThe node types you need, and how credentials work

You will meet hundreds of nodes. They are all one of five things.

Kind What it does Examples
Trigger Starts the workflow Form, Schedule, Webhook, Manual
AI Calls a model OpenAI Chat Model and the other chat model nodes
Action Does something in another service Gmail, Google Sheets, Telegram
Logic Decides or reshapes IF, Switch, Edit Fields
HTTP Request Calls any API that has no dedicated node The escape hatch
ImportantHTTP Request is the one to remember. If a service has no n8n node but has an API, you can still use it. That single node is the difference between "n8n cannot do that" and "n8n can do anything with an API".

Credentials: connect once, reuse everywhere

Any node that touches an outside service needs credentials. You create them once and every workflow can use them. There are two kinds and they cost very different amounts of your time.

Kind What you do Time
API key or token Paste a key you already have Under a minute
OAuth Sign in to the service and approve access A few minutes, more on a local install
ImportantThis is where a local install differs from n8n Cloud, and it is the one exception worth knowing. Google nodes such as Gmail and Sheets use OAuth, and on a self-hosted n8n you have to register your own application with Google to get a client ID and secret first. On n8n Cloud that is handled for you. It is not hard, it is just a detour, so do it before class rather than during it.
Note for InstructorAdvanced learner extension: ask why a self-hosted install cannot borrow n8n's OAuth app. The answer is that the redirect has to come back to your machine, and that is a useful thirty seconds on how OAuth actually works.

The AI node, and the swappable brain again

The chat model node needs a credential too, and here is the Class 1 callback: you can point an OpenAI-type credential at a different provider by changing the base URL, exactly as you did in first_call.py.

Field What to put
API key Your Groq key from Class 1
Base URL https://api.groq.com/openai/v1
Model openai/gpt-oss-120b
ImportantSame key, same base URL, same model name as the code you wrote in Class 1. The brain is swappable here too, and for the same reason: the interface is the same.

Telegram, because it is the fastest credential in the class

1
In Telegram, message @BotFather and send /newbot. Give it a name and a username.
2
BotFather replies with a token. That token is the credential.
3
Message your new bot once, so it is allowed to message you back. Then get your chat ID, which BotFather's helper bots or the Telegram API will give you.
Note for InstructorDo this live, on screen. It takes two minutes and it is the cheapest possible demonstration of an API-token credential, in contrast to the OAuth one.

Section 5 · 20 minLive build: support ticket triage

Note for Instructor20 minutes, built live with the room following. This replaces the old form-to-email build, which worked but was too small to feel like real work. Build it in the order below and do not skip ahead to the second branch until the first one runs.

What you are building: a ticket arrives, the model reads it and decides how urgent it is and what it is about, and then urgent and routine tickets go to different places.

Form  ->  AI classifies  ->  IF urgent?  ->  yes: Telegram alert
                                         ->  no:  Gmail draft reply

Step 1 to Step 3: the trigger and the input

1
Add a Form Trigger. Give it three fields: customer email, subject, and the message body.
2
Open the form URL n8n gives you and submit one realistic ticket. Use something messy, not tidy. For example: Ordered 3 weeks ago, nothing arrived, nobody is answering my emails and I need this before Friday or I want my money back.
3
Look at what the trigger produced. It is JSON, with your three fields in it. That JSON is what the next node receives.

Step 4 and Step 5: the AI node

4
Add the chat model node and set up the Groq credential from Section 4.
5
Give it this system prompt. It should look familiar, because it is Class 2's structured output lesson.
You triage incoming customer support tickets.

Return only JSON with exactly these keys:
{
  "category": "delivery | billing | product_fault | other",
  "urgency": "high | normal",
  "sentiment": "angry | neutral | happy",
  "summary": "one sentence, under 20 words",
  "suggested_reply": "a polite reply, under 80 words, no promises about refunds"
}

Mark urgency high only if the customer mentions a deadline, a legal threat,
or says they have already been ignored.

Return only the JSON object. No explanation, no code fences.
ImportantThat last line is the one from Class 2, and it matters more here than it did in a chat window, because the next node is going to try to read these fields by name. A friendly sentence before the JSON breaks the whole workflow.

Step 6 to Step 8: branching and the two actions

6
Add an IF node. Condition: the urgency field equals high. Section 6 covers how to reference that field.
7
On the true branch, add a Telegram node using the bot credential from Section 4. Send the summary and the customer's email.
8
On the false branch, add a Gmail node and create a draft reply using the suggested_reply field.
Note for InstructorIf Gmail OAuth is not working for some of the room, have them put a second Telegram node on the false branch with a different message. The lesson is the branch, not the mail provider. Say that out loud so nobody feels they have missed something.
Ask LearnersSubmit an angry ticket with a deadline in it, then a calm one asking about a delivery date. Did they go down different branches?
ImportantYou have just built something a real support team would recognise. Not a toy: a triage step that reads unstructured text, makes a judgement, and routes accordingly. The only thing missing for production is error handling, which is Class 8.

Section 6 · 12 minExpressions: the prompt template with variables

Note for Instructor12 minutes, and this is the section Classes 2 and 3 both pointed at. Say so: template prompting was deferred twice because it needs real variable injection to be worth teaching, and this is it.

So far every node used fixed text. Expressions are how a node uses the data flowing into it.

The syntax

An expression is wrapped in double curly braces and reads from $json, which is the item coming in.

Expression What it gives you
{{ $json.urgency }} The urgency field from the previous node
{{ $json.customer_email }} The email the customer typed into the form
{{ $json.summary.toUpperCase() }} The summary, shouted. It is JavaScript inside the braces
{{ $('Form Trigger').item.json.subject }} A field from a specific earlier node, not just the previous one

That last row is the one people need and do not know to look for. Once you are three nodes deep, the thing you want is often not from the node immediately behind you.

The template, finally

Here is prompt templating with variables, which is what you were promised.

A customer wrote in about an order. Write a reply.

Their name: {{ $json.customer_name }}
Their order number: {{ $json.order_id }}
What they said: {{ $json.message }}
How urgent we judged it: {{ $json.urgency }}

Match the tone to the urgency. Do not promise a refund.

The prompt is written once. The values change on every run. That is the difference between a prompt you paste and a prompt that is part of a system.

Note for InstructorLive demo, 4 minutes. Rather than typing an expression, drag a field from the input panel on the left of the node into a text box. n8n writes the expression for you and shows you the resolved value underneath as you build it. Teach the drag first and the syntax second; people who learn to drag stop fearing expressions.
ImportantThe resolved preview is the whole trick. You can see what the expression evaluates to before you run anything, so a typo in a field name is obvious immediately rather than three runs later.
Doubt by LearnerIs this the same as the few-shot examples from Class 2?

No, and they combine well. Few-shot is examples of the output you want, written into the prompt. This is injecting live data into a prompt. A production prompt usually has both: fixed rules, fixed examples, and variable slots for whatever just came in.

Section 7 · 11 minReading a run, and breaking it on purpose

Note for Instructor11 minutes. This is the strongest teaching section in the class and it was in the original for good reason. Keep it.

When a workflow misbehaves, you do not guess. Every node keeps what went in and what came out.

The loop

1
Run the workflow and look at the canvas. Nodes that ran are marked, and the one that failed is marked differently.
2
Click the failing node. You get two panels: input on the left, output on the right.
3
Read the input. The question is always the same: is this what you expected this node to receive?
4
If yes, the node's own settings are wrong. If no, the problem is upstream and you move one node to the left and repeat.
ImportantThat is the entire debugging method and it works on every workflow you will ever open, including somebody else's. Most workflow problems are a field name that does not exist, and the input panel shows you that in two seconds.

Break it on purpose

Note for InstructorDo all three of these live. They are engineered failures, so they reproduce in every batch, which is the module's rule about never depending on a model misbehaving.
1
Change a field name in an expression to something that does not exist. Run it. The expression resolves to nothing and the downstream node either fails or sends an empty message. Point out that it did not crash, it just quietly sent nothing, which is worse.
2
Remove the "Return only the JSON object" line from the AI prompt and run it again. The model adds a friendly sentence, the output stops being valid JSON, and the IF node cannot find the urgency field. This is Class 2's lesson arriving as a broken workflow.
3
Submit a ticket with an empty message body. Watch what the model does with nothing to classify.
Ask LearnersWhich of those three would be hardest to notice in production? Most rooms say the first, and they are right.

Section 8 · 7 minExport, import, and sharing your work

A workflow is a JSON file. Knowing that is what lets you back it up, share it, move it between machines, and put it in version control.

Exporting

1
Open the workflow menu, the three dots at the top right of the canvas.
2
Choose Download. You get a .json file containing every node, its settings, and how they are connected.
3
Open that file in a text editor and look at it. You will recognise your own node names and your prompt text sitting in it.
ImportantYour credentials are not in that file. n8n exports a reference to a credential, not the key itself. That is what makes it safe to share a workflow, and it is also why importing someone else's workflow means reconnecting your own accounts before it runs.

Importing

1
From a file: the same three-dot menu, then Import from File.
2
From the clipboard: copy the JSON and paste it onto the canvas. This is the fastest way to share one in a classroom or a chat.
3
Reconnect credentials. Any node that needs an account will show that it needs one.

Why this matters beyond backups

Note for InstructorMake this point properly, it connects to Class 4.

In Class 4 you learned that the instructions are yours and the platform's box is temporary. The same applies here. A workflow you can export is a workflow you own. You can diff two versions, you can keep it in a repository, and you can move it to a different n8n without rebuilding it by hand.

Ask LearnersExport today's workflow now and keep the file. You will want it next class.

Section 10 · 4 minWrap-up and what is next

What you can do now

You can read any n8n workflow as triggers, nodes and connections, and say what data is moving along each line.

You can connect a model to a workflow using the same key and the same base URL as your Python code.

You can inject live data into a prompt with expressions, which is the template prompting that Classes 2 and 3 deferred to today.

You can debug by reading what a node actually received rather than guessing.

And you can export a workflow as JSON, which means you own it.

What is still missing

Today's workflow has no error handling. If Telegram is down, the run fails and nobody finds out. If the model returns something unexpected, the branch does the wrong thing silently. Real automations need retries, fallbacks and a way to tell somebody when they break.

Next class

Class 7 is agents. Today you decided the path: you wrote the IF node, you chose what happens when urgency is high. An agent is what you get when the model makes that choice instead, picking its own tools and its own sequence. Everything you built today still applies, and the question becomes what happens when nobody wrote the branch in advance.

Fast-changing facts: verify before each batch

Note for Instructorn8n ships frequently and menu labels move. Check these the week before you teach and correct them in place.
  • That the install video still matches the current n8n version, and that the Drive link is shared so anyone with it can open
  • The three-dot menu labels for Download and Import from File
  • Whether the chat model node still accepts a custom base URL, and that the Groq model name is current
  • That Telegram's BotFather flow is unchanged
  • Your own exported triage workflow, re-imported into a fresh n8n, to confirm it still loads
