🗄️ Key Data Types & SQL Basics

What this covers: Before we can ask the database smart questions, we need to understand how data is organised inside it. This guide covers what holds a database together (keys), what kinds of data it stores (types), and how to write our very first real SQL queries on Zomato data!

1

Opening Hook — What Makes Data Trustworthy? 🤔

Imagine you work at Zomato. You open the orders table and you see this:

order_idcustomer_nameorder_valuecity
ORD001Ravi Kumar450Bangalore
ORD001Ravi Kumar450Bangalore
ORD002Priya Sharmanullnull

ORD003Ravi kumar720delhi

What problems do you see here? ORD001 is duplicated! ORD003 appears twice with different capitalisation! Some values are missing!

Imagine your manager asks: "How many orders did we receive today?" You say 5. But the real answer is 3! You just LIED to your manager — not on purpose, but because the data itself was broken. This is the nightmare every data analyst fears. And this is EXACTLY why databases have rules called constraints — and the most important constraints are built around keys.

🏥
The Hospital Horror Story: A hospital database had duplicate patient records. Doctor A updated blood type for "Ravi Kumar" — but there were TWO Ravi Kumars in the system. The wrong patient's record got updated. This is not a data problem. This is a life-or-death problem. Keys prevent this from ever happening by making sure every row is uniquely identifiable. No duplicates. Ever.

⭐ A database without keys is like a city without house addresses. You cannot find anything, you cannot trust anything. Keys are the address system of your data.
🏢 Real World: Why keys matter every single day
  • Banking (HDFC, SBI): Every account has a unique account number. Without it, your deposit could go to the wrong account.
  • Zomato / Swiggy: Every order has a unique order_id. Without it, two identical orders for "Butter Chicken" from the same customer look like duplicates.
  • Government (Aadhaar): The entire Aadhaar system is a 12-digit primary key assigned to every Indian citizen — to eliminate duplicate beneficiaries in welfare schemes.
  • E-commerce: Every product has a unique SKU (Stock Keeping Unit). Without it, the same T-shirt in red and blue looks like the same item — and stock counts go wrong.

Types of Keys — The ID Cards of Your Data 🪪

🔴 Primary Key — The Aadhaar Card of a Table

🪪
The Aadhaar Analogy: Every Indian citizen has ONE unique Aadhaar number. No two people share the same number. Nobody has two Aadhaar cards. And you CANNOT exist in the system without one. That is exactly what a Primary Key does for a row in a database table.

Three unbreakable rules of a Primary Key:
1️⃣ Unique — no two rows can have the same Primary Key value.
2️⃣ Never NULL — every row MUST have a Primary Key. No blank IDs allowed!
3️⃣ One per table — a table can have only ONE primary key.

In the Zomato orders table, order_id is the Primary Key — ORD001, ORD002, ORD003 — each one is unique, each one always exists. 🎯

The Foreign Key in orders.customer_id is a bridge to customers.customer_id (Primary Key)

🟣 Unique Key — The "No Clones Allowed" Rule

📧
The Email Analogy: Think about signing up on any website. You cannot use an email address that someone else already has. But — unlike Aadhaar — you CAN theoretically not provide an email (it can be NULL if the field is optional). Also, one person could have a personal email AND a work email registered in different columns. That is the Unique Key: values must be unique, but a NULL is sometimes allowed, and a table can have more than one unique key.
Primary Key 🔑Unique Key 🔐
Duplicates allowed?❌ Never❌ Never
NULL allowed?❌ Never✅ Sometimes (one NULL)
How many per table?Only ONECan have MANY
Zomato exampleorder_idcustomer_email

🔵 Foreign Key — The Bridge Between Tables

🌉
The Bridge Analogy: Imagine two islands. Island 1 is the orders table. Island 2 is the customers table. Every order has a customer_id field on it. That field is a bridge connecting each order to a specific customer on the other island. The bridge ONLY works if the customer_id on the order actually exists on the customers island. If someone tries to place an order for a customer ID that doesn't exist — the database BLOCKS it. No ghost customers allowed! 👻🚫

The Foreign Key needs to match a Primary Key on the other table because you cannot deliver food to a ghost address. The FK ensures every order is linked to a REAL, existing customer. This is called Referential Integrity — a fancy phrase that just means "your bridges must connect to real places!" 🌉

The FK bridge only works if the destination (PK) actually exists — ghost customers are blocked!
🧠 Analyst Brain: wherever there is a Foreign Key, there is a JOIN question waiting!

Every time you see a column like customer_id in the orders table, your analyst brain should light up and say: "There is more customer information in another table — I can connect these!"

That connection is called a JOIN and it is the most powerful tool in SQL. JOINs are covered in the next module — but it all starts with understanding Foreign Keys here. 🔗

🏢 Real World: Keys in industry
  • Zomato: order_id (PK in orders), restaurant_id (FK linking orders to restaurants), rider_id (FK linking to delivery partners).
  • Banking: account_number is PK. Every transaction row has it as FK. This is how your bank statement knows WHICH account each debit belongs to.
  • Netflix: user_id (PK in users table), used as FK in every "watch history" row. This is how Netflix knows YOUR watch history and not someone else's.
  • Hospitals: patient_id (PK). Every prescription, test result, and appointment row links back to it via FK. This is what prevents the medical record nightmare we described earlier!

Candidate Key & Composite Key — The Interview Favourites 🎤

Before the database picks a Primary Key, it first looks for ALL columns that COULD be a primary key — any column (or group of columns) where every value is unique and never NULL. These candidates are called Candidate Keys.

🏆 Candidate Key — "I could be the Primary Key!"

🏆
The Job Interview Analogy: Imagine a company has three people applying to be the "Company Representative" — the one person who officially speaks for the company. All three are qualified. All three are unique individuals. But the company can only pick ONE official rep. The people who applied are the Candidate Keys. The one who gets the job becomes the Primary Key. The others are still unique — they just weren't chosen as the main one.

In a customers table: customer_id is unique, email is unique, and phone_number is unique. All three are Candidate Keys — any of them COULD be the Primary Key. The database designer picks one. The rest become Unique Keys.

ColumnUnique?Never NULL?Candidate Key?Chosen as?
customer_id✅✅✅ YesPRIMARY KEY
email✅✅✅ YesUNIQUE KEY
phone_number✅✅✅ YesUNIQUE KEY
city❌✅❌ NoRegular column

🧱 Composite Key — "Two columns working as one team!"

🎭
The Theatre Ticket Analogy: A theatre ticket has a Row number and a Seat number. Row 5 alone is not unique — there are many seats in Row 5. Seat 12 alone is not unique — many rows have a Seat 12. But Row 5, Seat 12 together? That is ONE specific seat in the entire theatre. No duplicate! That combination is the Composite Key — two (or more) columns that together form a unique identity, even though neither is unique on its own.

Zomato example: in a table called restaurant_menu, a restaurant can have a "Butter Chicken" item. Another restaurant can ALSO have a "Butter Chicken" item. So item_name alone is not unique. But one restaurant cannot list Butter Chicken twice — so the combination of restaurant_id + item_name is unique. That is a Composite Key!

Neither column is unique alone — but together they form a unique Composite Key!

🎤 Interview tip: how to answer "What is a Candidate Key?"

"A Candidate Key is any column or combination of columns that satisfies the conditions to be a Primary Key — it must be unique and never NULL. The database designer chooses one candidate to be the actual Primary Key. The rest become Unique Keys."

That one sentence answer will impress any interviewer. 💪

SQL Data Types — The "What Kind of Thing Is This?" Question 📦

Every column in every table has a data type. It decides what you can store and what you can do with it. When you build a house, every room has a purpose — bedroom, kitchen, bathroom. You would not cook in the bathroom! Similarly, every column in a database is designed to hold ONE type of data. That type is called the Data Type.

🗂️
The Filing Cabinet Analogy: Imagine a filing cabinet with four types of drawers:
🔢 Number drawer — only numbers go in here (INT, DECIMAL). You can do maths on them!
🔤 Text drawer — names, descriptions, addresses (VARCHAR, TEXT). You can search and read them!
📅 Date drawer — dates and times (DATE, DATETIME). You can calculate days between dates!
✅ Yes/No drawer — only TRUE or FALSE (BOOLEAN). Perfect for flags like "is this customer a Prime member?"

If you try to put a name in the number drawer, the cabinet REFUSES. "That doesn't belong here!" That is data type enforcement. 🚫📝

🔢 Category 1 — Numeric Types

TypeWhat it storesExampleZomato use
INTWhole numbers only — no decimals1, 42, 10000rating (1,2,3,4,5), delivery_time_mins
BIGINTVery large whole numbers9,000,000,000total_orders_ever across platform
DECIMALNumbers with decimal points (precise)499.99, 23.5order_value, discount_amount
FLOATNumbers with decimals (approximate)3.14159...GPS coordinates, probability scores
⚠️ Use DECIMAL for money — NEVER FLOAT!

FLOAT is approximate. Computers store it as binary fractions, which can cause tiny rounding errors. For example, 0.1 + 0.2 in FLOAT gives 0.30000000000000004 — not 0.3!

For bank balances, order values, or any money column: always use DECIMAL. Your finance team will thank you! 💸

🔤 Category 2 — Text (String) Types

TypeWhat it storesMax lengthZomato use
CHAR(n)Fixed-length text — always n characters255Status codes with fixed length: 'Y'/'N'
VARCHAR(n)Variable-length text — up to n characters65,535customer_name, city, coupon_code
TEXTVery long text — no fixed limitHugeRestaurant descriptions, review text
👕
CHAR vs VARCHAR — T-shirt sizes:
CHAR(10) is like a box that is ALWAYS exactly 10 cm wide, even if you only put a 2 cm item inside. The empty space is filled with invisible padding. Wastes space but predictable.
VARCHAR(10) is like a stretchy bag — it shrinks to fit whatever you put in, up to a maximum of 10 cm. Efficient! Most columns you will use are VARCHAR. 🛍️

📅 Category 3 — Date and Time Types

TypeWhat it storesFormatZomato use

TIMETime only — no dateHH:MM:SSRestaurant opening hours
DATETIMEDate AND time togetherYYYY-MM-DD HH:MM:SSorder_timestamp — exact moment of order
TIMESTAMPDate and time (timezone aware)YYYY-MM-DD HH:MM:SS UTCServer logs, audit trails
📅
DATE vs DATETIME: Think of it this way — if someone asks "when is your birthday?", you say "15th August" — that is a DATE. If someone asks "when exactly did the order come in?", you say "15th August at 7:43:22 PM" — that is a DATETIME. Use DATE when you only care about the day. Use DATETIME when the exact second matters (like delivery tracking).

✅ Category 4 — Boolean Type

TypeWhat it storesValuesZomato use
BOOLEANTrue or False only — nothing else!TRUE / FALSE (or 1 / 0)is_prime — is this a Prime customer? is_vegetarian on menu items
💡
The Light Switch: A BOOLEAN is exactly like a light switch. It is either ON (TRUE, 1) or OFF (FALSE, 0). There is no "maybe" or "sort of on". Perfect for yes/no questions: Is the customer subscribed? Is the item available? Is the payment verified? 💡
⚠️ Wrong data type = broken calculations!

Imagine storing order_value as VARCHAR (text) instead of DECIMAL (number). Then you try: SELECT SUM(order_value) FROM orders — the database either throws an error or gives you 0. You cannot do SUM on text!

It is like trying to add the word "five hundred" to the word "three hundred" using a calculator. The calculator says: "I can't! I need actual numbers!" 🧮🚫

Data type issues are one of the most common bugs in beginner SQL. Always check column types before writing calculations!

🏢 Real World: Data types matter enormously in industry
  • Banking: Account balances use DECIMAL(15,2) — up to 15 digits, always exactly 2 decimal places. Using FLOAT here would cause paisa-level errors across millions of transactions. Actual money would be lost!
  • Zomato ETAs: The "Order arrives in 32 minutes" uses DATETIME arithmetic — subtracting the current DATETIME from the estimated arrival DATETIME gives a number of minutes. Only works if the column is actually stored as DATETIME.
  • Aadhaar database: The 12-digit Aadhaar number is stored as CHAR(12) — always exactly 12 characters, never more, never less.
  • Netflix: is_adult_content is a BOOLEAN column on every title. That one bit of data (TRUE/FALSE) controls whether the content is visible to child profiles.

SELECT — "I'll Have This, This, and This Please" 🍽️

The most fundamental SQL statement — it tells the database WHAT to show you. The most basic question you can ask a database: "What is in this table?"

🍽️
The Restaurant Order Analogy: Imagine you walk into a restaurant. The waiter (the database) has a full menu with 50 items (the table with all columns). You don't order everything — you say "I'll have the soup, the pasta, and the juice please." That is a SELECT statement. You are telling the waiter exactly what to bring from the menu. If you say "bring me everything", that is SELECT * — the all-you-can-eat buffet! 🍜🍝🍹
📄 Query 6.1 — SELECT * (the buffet)
SELECT  *
FROM    zomato.orders;
🗣️ Reads as: "Show me EVERYTHING from the orders table — all columns, all rows." (The all-you-can-eat buffet — everything comes!)
⚠️ SELECT * — use it carefully in the real world!

In BigQuery, the orders table might have 10 million rows and 20 columns. SELECT * fetches ALL of that — costing time, memory, and money (BigQuery charges by data scanned).

For learning and exploration: perfectly fine! For production reports: always specify only the columns you need. Think of it as ordering the FULL buffet when you are only hungry enough for a salad. 🥗

📄 Query 6.2 — SELECT specific columns (order from the menu)
SELECT  order_id,
        order_status,
        order_value,
        payment_method
FROM    zomato.orders;
🗣️ Reads as: "Show me only order ID, status, value, and payment method — nothing else from the orders table." (Just the soup, pasta, and juice — not the whole menu!)
SQL execution: FROM (open table) → SELECT (pick columns) → RESULT (show you)
🎮 SIMULATOR — Build Your SELECT!
Check the columns you want in your SELECT. See only those columns appear in the result! (10 rows from zomato.orders)
Check some columns and press RUN! 👆
🏢 Real World: SELECT in industry
  • Every analyst everywhere: 100% of SQL written in the world starts with SELECT. It is the foundation of every report, dashboard, and data export ever created.
  • Zomato operations team: "SELECT order_id, customer_id, order_status FROM orders" runs thousands of times per minute to power the live order-tracking dashboard.
  • BigQuery cost saving: Selecting 3 specific columns instead of SELECT * on a 1 TB table can save 95% of the query cost. A good analyst saves the company real money by being specific!

SELECT brings back every row. But often you only want to see the UNIQUE values in a column — for example, which cities does Zomato operate in? Not a list of all orders (with Delhi appearing a thousand times), but just the unique city names. That is what DISTINCT is for. ➡️

7

DISTINCT — The Duplicate Eraser 🧹

DISTINCT returns only unique values — removing all duplicates from the result. For example: how many unique cities do Zomato customers come from? Without DISTINCT, the cities column repeats for every single order. With DISTINCT — one unique list!

📮
The Stamp Collection Analogy: Imagine you have a pile of 500 postcards from around India. Many cards show the same city — 80 cards say "Mumbai", 60 say "Delhi", 45 say "Bangalore". If someone asks "which cities have postcards?", you don't hand them all 500 cards! You look through the pile and keep ONE card from each city. That is DISTINCT — it gives you the unique list, once each, no repeats. 📮
📄 Query 7.1 — without DISTINCT (duplicates everywhere!)
SELECT  city
FROM   zomato.customers;
🗣️ What you see: "Bangalore, Delhi, Mumbai, Bangalore, Bangalore, Delhi, Mumbai, Mumbai..." — every customer's city, repeated thousands of times. 😵
📄 Query 7.2 — with DISTINCT (clean unique list!)
SELECT  DISTINCT  city
FROM    zomato.customers;
🗣️ Reads as: "Show me each city ONCE — no repetitions." Result: Bangalore, Delhi, Mumbai, Pune, Chennai — done! ✅
📄 Query 7.3 — DISTINCT on two columns (unique combinations)
SELECT  DISTINCT  city,
                  payment_method
FROM    zomato.orders;
🗣️ Reads as: "Show each unique combination of city + payment method. Delhi-UPI, Delhi-Debit Card, Mumbai-UPI etc. — each combination once."
DISTINCT erases all duplicate values — one clean unique list remains
🎮 SIMULATOR — Watch Duplicates Disappear!
Toggle DISTINCT on/off. Watch the city column go from a messy repeated list to a clean unique one!
Press a button! 👆
🏢 Real World: DISTINCT in industry
  • Marketing: "SELECT DISTINCT customer_id FROM orders" gives the count of unique customers who ever ordered — very different from total order count!
  • Product teams: "SELECT DISTINCT device_type FROM app_sessions" quickly tells you: are users on iOS, Android, Web, or something else? Essential for deciding which platform to fix first.
  • Operations: "SELECT DISTINCT city FROM restaurants" instantly shows which cities Zomato is active in — no duplicates, clean list for reporting.

We can now pick any columns we want, and remove duplicates. But the results come in a random order. Analysts need results sorted in a meaningful way — highest sales first, newest orders first, alphabetical cities. That is ORDER BY. ➡️

8

ORDER BY — Sorting the Stack 📚

Two directions: ASC means Ascending — small to big, A to Z. DESC means Descending — big to small, Z to A. ASC is the default, but in analysis, DESC is almost always what you want — highest value first, latest date first. Always be explicit!

📝
The Exam Papers Analogy: After a test, the teacher has 40 exam papers in a random pile. She wants to sort them. She could sort highest to lowest score (DESC — to find the toppers first) or lowest to highest score (ASC — to find the students who need extra help). ORDER BY is that sorting action — you choose the column to sort by, and the direction. 📝
📄 Query 8.1 — ORDER BY DESC (highest first)
SELECT  order_id,
        order_value,
        order_status
FROM    zomato.orders
ORDER BY  order_value  DESC;
🗣️ Reads as: "Show all orders, sorted from highest order value to lowest." (Find the big spenders first! 💰)
📄 Query 8.2 — ORDER BY ASC on text (alphabetical)
SELECT  DISTINCT  city
FROM    zomato.customers
ORDER BY  city  ASC;
🗣️ Reads as: "Unique cities, sorted A to Z." Result: Bangalore, Chennai, Delhi, Mumbai, Pune — alphabetical!
📄 Query 8.3 — ORDER BY multiple columns
SELECT  order_id,
        city,
        order_value
FROM    zomato.orders
ORDER BY  city  ASC,
          order_value  DESC;
🗣️ Reads as: "Sort by city A to Z first. Within each city, sort by order value highest to lowest. So we see Bangalore's biggest orders first, then Chennai's biggest, and so on."
ASC: small to big · DESC: big to small — both work on numbers AND text!
🏢 Real World: ORDER BY in industry
  • Sales reports: Every "Top 10 products this week" list is just a query with ORDER BY revenue DESC LIMIT 10. That leaderboard on your company dashboard was written in 10 seconds!
  • Customer support: Tickets sorted by ORDER BY created_at ASC means oldest unresolved ticket first — so nothing gets forgotten.
  • Fraud detection: Suspicious transactions sorted by ORDER BY amount DESC — the biggest unusual transactions investigated first.

Sorting is powerful — but imagine sorting 10 million rows and then trying to look at all of them. Nobody can read 10 million rows! We need a way to say "just give me the first 10 rows" or "show me rows 21 to 30". That is LIMIT and OFFSET. ➡️

9

LIMIT & OFFSET — The Cookie Jar Rules 🍪

🍪
The Cookie Jar Analogy:
LIMIT = "You can have 5 cookies." — LIMIT 5 gives you exactly 5 rows. No more!
OFFSET = "Skip the first 10 cookies (they're for your brother) and then take 5." — OFFSET 10 LIMIT 5 skips the first 10 and starts counting from row 11.

Together, LIMIT and OFFSET are how websites show you Page 1, Page 2, Page 3... of results. When you scroll to the next page of Google results — that is OFFSET in action! 📖
📄 Query 9.1 — LIMIT (only 5 cookies!)
SELECT  order_id,
        order_value,
        order_status
FROM    zomato.orders
ORDER BY  order_value  DESC
LIMIT   5;
🗣️ Reads as: "Show me the 5 highest-value orders." (Top 5 big spenders!)
📄 Query 9.2 — LIMIT + OFFSET (skip, then take)
SELECT  order_id,
        order_value,
        order_status
FROM    zomato.orders
ORDER BY  order_value  DESC
LIMIT   5
OFFSET  5;
🗣️ Reads as: "Skip the first 5 rows (that was Page 1), then give me the next 5 rows (this is Page 2)."
LIMIT 5 = first 5 · LIMIT 5 OFFSET 5 = next 5 · This is how every "next page" button works!
🎮 SIMULATOR — Cookie Jar!
Drag the sliders to set LIMIT and OFFSET. Watch exactly which rows come through!
LIMIT: 3
OFFSET: 0
📌 LIMIT is your best friend when exploring a new table

Never run SELECT * FROM big_table on an unknown table in production — it could return millions of rows and crash your session!

Always start with SELECT * FROM table LIMIT 10 to safely peek at the data structure first. This is professional habit #1.

🏢 Real World: LIMIT and OFFSET in industry
  • Every website with pagination: Page 1 = LIMIT 20 OFFSET 0. Page 2 = LIMIT 20 OFFSET 20. Page 3 = LIMIT 20 OFFSET 40. The "next page" button literally runs a new query with a higher OFFSET each time!
  • Mobile apps (infinite scroll): Load 10 more posts = LIMIT 10 OFFSET (current_position). Instagram's feed loads in batches using exactly this technique.
  • Data exploration: Analysts always start with LIMIT 100 to understand a new dataset quickly without burning expensive compute on millions of rows.

We can now fetch, deduplicate, sort, and page through data. Now let us make the database do maths for us — calculating new values directly inside the query! ➡️

10

Inline Calculations — The Built-In Calculator 🧮

Perform arithmetic on column values directly in SELECT — the database calculates for every row automatically. When a manager asks "What is the final amount the customer actually paid, after the discount?", the table stores order_value and discount_amount separately. The subtraction can be done inside the SELECT itself!

🧮
The Magic Spreadsheet Analogy: Imagine in Excel, Column A is order_value and Column B is discount_amount. You can add a Column C with the formula =A2-B2 and it calculates the final amount for every row automatically. SQL does the exact same thing — but for millions of rows at once, and without needing a separate column in the actual table. The calculation lives only in your SELECT query. The original table is untouched. ✨
📄 Query 10.1 — Inline calculation: final amount paid
SELECT  order_id,
        order_value,
        discount_amount,
        order_value - discount_amount   AS  final_amount
FROM    zomato.orders
LIMIT   10;
🗣️ Reads as: "For each order, calculate order value minus discount — label that column 'final_amount'." The database calculates this for every single row automatically!
📄 Query 10.2 — Inline calculation: discount percentage
SELECT  order_id,
        order_value,
        discount_amount,
        (discount_amount / order_value) * 100   AS  discount_pct
FROM    zomato.orders
WHERE   discount_amount > 0
LIMIT   10;
🗣️ Reads as: "Calculate what percentage of the order value was discounted — for orders where a discount was actually applied."
📄 Query 10.3 — All four operators (for reference)
SELECT  order_id,
        order_value + 50              AS  value_plus_delivery,
        order_value - discount_amount  AS  final_amount,
        order_value * 1.18            AS  value_with_gst,
        order_value / 2              AS  half_value
FROM    zomato.orders
LIMIT   5;
🗣️ Reads as: "Calculate four different things for each order — adding delivery, subtracting discount, adding 18% GST, and halving the value. All in one query!"
OperatorWhat it doesExample
+Additionorder_value + 50 (add delivery fee)
-Subtractionorder_value - discount_amount (final price)
*Multiplicationorder_value * 1.18 (add GST)
/Divisiondiscount_amount / order_value (discount ratio)
⚠️ Division by zero — the silent killer!

If order_value is ever 0 (a fully free order), then discount_amount / order_value causes a division by zero error. Always add a filter: WHERE order_value > 0 before dividing!

Think of it like dividing 10 chocolates among 0 children — the universe breaks! 🍫❌

🏢 Real World: Inline calculations in industry
  • Finance teams: revenue - cost AS profit — every P&L report in the world is calculated this way in SQL.
  • E-commerce: selling_price * quantity AS line_total — the "subtotal" on every invoice is an inline calculation.
  • Zomato: order_value * 0.20 AS platform_commission — Zomato takes 20% from restaurants. Calculated instantly for millions of orders with one query.
  • GST compliance: base_amount * 1.18 AS amount_with_gst — tax-inclusive price calculated for every item in every invoice, using SQL.

Our calculations are creating new columns on the fly. But they have ugly default names like (discount_amount / order_value) * 100. Let us give them clean, human-readable names using Aliases. ➡️

11

Alias (AS) — The Nickname Machine 🏷️

AS gives a column or table a temporary, readable name in the output — without changing anything in the actual database. Without an alias, a calculated column in the result has the column header (discount_amount / order_value) * 100 — technically accurate but looks terrible in a report. AS fixes that.

🏷️
The Nickname Analogy: Your friend's full name might be "Raghavendra Subramaniam Krishnamurthy" — which is beautiful but hard to say quickly in conversation! So everyone calls him "Raghu". That nickname is an Alias. It is used just in THIS conversation (this query). His official name in the government records is unchanged. SQL Aliases work exactly the same way — the column gets a friendly name in the result, but the actual table column is untouched. 🏷️
📄 Query 11.1 — AS alias on a calculation
SELECT  order_id,
        order_value                              AS  original_price,
        discount_amount                          AS  discount,
        order_value - discount_amount            AS  final_amount,
        (discount_amount / order_value) * 100   AS  discount_pct
FROM    zomato.orders
WHERE   discount_amount > 0
LIMIT   10;
🗣️ Reads as: "Show a clean pricing breakdown — rename order_value as 'original_price', the subtracted column as 'final_amount', and the percentage calculation as 'discount_pct'."
📄 Query 11.2 — AS alias with spaces in name
SELECT  order_id,
        order_value    AS  `Order Value (₹)`,
        order_status   AS  `Delivery Status`
FROM    zomato.orders
LIMIT   5;
🗣️ Reads as: "Show order value labelled as 'Order Value (₹)' and status labelled as 'Delivery Status' — using backticks because the alias has spaces." (In BigQuery, you can also use double quotes for aliases with spaces.)
⚠️ AS does NOT change your data — ever!

The alias only exists in the output of this query. The actual column in the table is still called order_value. If you run a separate query tomorrow, it will still be order_value.

Aliases are like wearing a name tag at a conference. Your name tag says "Raghu" for today's event. Your passport still says "Raghavendra Subramaniam Krishnamurthy". The tag is temporary. The passport is permanent. 🪪

📌 Alias rules — four things to remember
  • 🏷️ column_name AS alias_name — the AS keyword is between them.
  • ✂️ AS is actually optional: order_value original_price also works. But always include AS for readability!
  • 🔤 Single-word aliases: no quotes needed. AS final_amount
  • 📝 Multi-word aliases: use backticks (MySQL/BigQuery) or double quotes: AS "Final Amount"
🏢 Real World: Aliases in industry
  • Business dashboards: Every Tableau or Power BI report that shows "Revenue", "Profit Margin", "Customer Count" is using SQL aliases to rename calculated columns into business-friendly terms.
  • Data exports: When an analyst emails a CSV report to the CEO, clean column headers come from AS aliases — not raw database column names like ord_val_ttl_excl_disc!
  • Table aliases (preview): FROM zomato.orders AS o — when we get to JOINs, table aliases make queries shorter. This is just the warm-up!

You now have a full toolkit for writing real SQL. Before we practice — let us see how AI can help write queries from plain English, and how to spot when it makes mistakes. ➡️

AI Segment — Your SQL Co-Pilot 🤖✈️

✈️
The Co-Pilot Analogy: In a cockpit, the pilot (you!) makes all the decisions — the route, the landing, the safety calls. The co-pilot (AI) helps with calculations, checklists, and reading instruments. The co-pilot is incredibly useful — but the pilot is ALWAYS in charge. If the co-pilot makes a mistake and the pilot blindly follows — that is how planes crash. AI-generated SQL needs a human pilot to review it every time. ✈️

🗺️ The workflow: English → SQL using AI

  • Step 1 — Write your business question in plain English.
  • Step 2 — Tell the AI your table name and column names.
  • Step 3 — Ask it to write the SQL.
  • Step 4 — READ the query before running it. Does the logic make sense?
  • Step 5 — Run it. Check the results against your expectation.

Step 1 — the English prompt to paste into AI

📋 Paste this into Claude or ChatGPT
I have a BigQuery table called zomato.orders with these columns:
order_id (VARCHAR), customer_id (VARCHAR), order_value (DECIMAL),
discount_amount (DECIMAL), order_status (VARCHAR),
payment_method (VARCHAR), rating (INT), order_date (DATE).


Write a SQL query to:

displaying order_id, order_value, discount_amount,
and a calculated column for the final amount after discount.
Label the calculated column as final_amount.
Sort by order_value from highest to lowest.
🗣️ What we are teaching: Be specific with AI. Give it your table name, column names, and exact requirements. Vague prompts get vague (and wrong) SQL.

Step 2 — what good AI output should look like

✅ What the AI should generate (correct version)
SELECT  order_id,
        order_value,
        discount_amount,
        order_value - discount_amount   AS  final_amount
FROM    zomato.orders
ORDER BY  order_value  DESC
LIMIT   10;
🗣️ This is correct! Matches all our requirements. Well done AI! — but we still READ it before trusting it.

Step 3 — a buggy version AI sometimes produces

Can you spot the three mistakes before reading the answer below? 🕵️

🐛 Buggy AI output — 3 bugs hiding here!
SELECT  order_id,
        order_value,
        discount_amount,
        order_value - discount_amount   AS  final amount,
FROM    orders
ORDER BY  final_amount  DESC
LIMIT   '10';
🗣️ Challenge: There are THREE bugs. Can your class spot them before we reveal?
🎯 The three bugs — revealed!

🐛 Bug 1: AS final amount — the alias has a space but no backticks or quotes. SQL will think "amount" is a separate keyword and throw an error. Should be AS final_amount or AS `final amount`.

🐛 Bug 2: FROM orders — missing the dataset prefix. In BigQuery it must be FROM zomato.orders. AI sometimes forgets the schema prefix!

🐛 Bug 3: LIMIT '10' — LIMIT takes a number, not a string. Quotes around 10 will cause an error. Should be LIMIT 10.

Also: ORDER BY final_amount — sorting by the alias final_amount may or may not work depending on the SQL dialect. To be safe, sort by the original expression or use ORDER BY position number.
