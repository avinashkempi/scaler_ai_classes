Overview

What SageMaker is mostly used for

The previous stage built the platform: a private VPC with no way in from the internet, a role scoped to one bucket, a VPC-only SageMaker domain, and a space an editor connects to. It also got the data ready — a leaky column dropped, four files written to S3 in the exact format the built-in XGBoost algorithm expects.

This stage does the part SageMaker is mostly used for on real teams. A training job trains the model on a machine that exists only for a few minutes. Then the same trained model is served three different ways, each with a different bill and a different trade-off.

MODE 01

Real-time endpoint

Answers one order at a time, in milliseconds. Bills every hour it exists.

MODE 02

Serverless endpoint

Same answers, no machine running all day. Bills only for time spent on requests.

MODE 03

Batch transform

Scores a whole file at once, when nobody is waiting on the answer.

All three are started from Python files using the SageMaker Python SDK; the console is where the work is watched, not where it is driven.

Infrastructure

Bringing the platform back

At the end of the previous stage, everything that bills by the hour was deliberately stopped or deleted. The bucket, the role, the domain, the VPC and its security groups stayed in place — they cost nothing idle. What's gone has to come back before any of this can run.

Removed last timeHourly costComes back via
NAT gateway + public IP~$0.045/hrRestore script
Six interface endpoints~$0.12/hr combinedRestore script
Each private route to the internet—Repointed by the restore script
The running space$0.115/hrStarted manually

Teams don't rebuild this by hand. The pieces that come and go are written down as code, so bringing them back is one command with the same result every time. Two small scripts handle it: one that only reads and reports status, and one that creates whatever is missing.

The restore sequence

1

Check what's missing

A read-only script inspects the VPC, route tables, NAT gateway and all six interface endpoints, printing OK, MISSING, or NOT-YET for each.

2

Create the NAT gateway

A new regional NAT gateway is created and the script waits until it reports available — typically two to three minutes.

3

Repoint the private routes

Each private route table's outbound route, which still points at the deleted NAT gateway as a dead "blackhole," gets repointed at the new one.

4

Recreate the interface endpoints

All six interface endpoints are created in a loop and come back pending before settling into available a minute or two later.

5

Verify from inside the space

Once the space itself is running, a script inside it independently confirms every AWS service it needs resolves to a private 10.0.x.x address, and that outbound internet access through the NAT still works.

The blackhole route

A private route table's internet route, left pointing at a NAT gateway that no longer exists, is marked by AWS as a blackhole. Traffic sent there is silently dropped — no error, nothing in the logs. A new NAT gateway doesn't fix this automatically; the route has to be explicitly repointed at it, which is exactly what the restore script's third step does.

Once every line reads OK, a final check runs from inside the space itself: it asks for the role's identity through STS, lists training jobs through the SageMaker API, lists the bucket through S3, and resolves each service's hostname to confirm it lands on a private 10.0.x.x address rather than routing out to the public internet. A last call to a public package index confirms the NAT gateway itself is working. Only once every one of those checks passes does training begin.

Training

A training job from code

A training job is one request to SageMaker. It specifies which algorithm to run, which S3 prefixes to read, what machine to rent, and where in S3 to put the result. SageMaker starts the machine, downloads the data onto it, runs the container, uploads the trained model, and deletes the machine. Billing covers only the seconds in between.

One request in, one model file out

The SageMaker Python SDK sends that request from code. Its training module provides a trainer class; its core module provides the building blocks — a lookup for the address of AWS's ready-made containers, and small config objects describing compute, data channels and output location.

What each setting controls

IMAGE

Container lookup

Retrieves the address of AWS's XGBoost 1.7-1 container for the target region.

ROLE

Execution identity

The training job runs as the same role the space runs as — which is why it can read the bucket.

COMPUTE

The machine

ml.m5.large with 5GB of disk, plenty for 8,400 training rows.

HYPERPARAMETERS

XGBoost settings

binary:logistic outputs a probability; AUC is tracked as the model trains.

CHANNELS

Named data inputs

A train channel and an optional validation channel, each one name paired with an S3 prefix.

Reading the result

The row counts match exactly what the data-prep stage wrote, confirming the format was read correctly. The final validation AUC of 0.708 lines up closely with the 0.706 quick-check score from the previous stage — two different tools agreeing is a good sign nothing broke in between. The training AUC (0.850) is noticeably higher than the validation AUC, meaning the model fits rows it already saw better than new ones. That gap is normal; the validation number is the one to trust.

Training jobs are permanent

Training jobs can never be deleted or renamed. Every job stays listed, with its full settings and logs, for as long as the account exists — which is why job names are typically built from a base name plus a timestamp rather than reused.

Checkpoint — testing overfitting with one changed line

Copy the training script, change only max_depth from 4 to 8, and run it again. Before comparing results, predict which number moves more: train AUC or validation AUC. A deeper tree usually raises the training score more than the validation score — watching that happen with one changed line is a clear, direct picture of overfitting. It's also a demonstration of why this work lives in code: a console form would have meant refilling every field from scratch.

Serving

Three objects behind every endpoint

Serving a model in SageMaker always involves three separate objects, created in a fixed order. Understanding the split clarifies a lot of otherwise-confusing SageMaker behavior.

ObjectWhat it holdsBills?
ModelWhich container image to run, and which model.tar.gz to loadNo
Endpoint configurationWhich model, on which machine type, how many machinesNo
EndpointThe actual running machines and the HTTPS addressYes, every hour

The split exists so one thing can change at a time. Moving to a bigger machine means creating a new configuration and pointing the endpoint at it — SageMaker starts the new machines before stopping the old ones, so callers never see a gap.

Serving · Mode 1

A real-time endpoint

A real-time endpoint keeps a machine running continuously and answers requests over HTTPS in milliseconds. The same XGBoost container used for training also serves, since the built-in algorithm does both.

Unlike a typical web service, an endpoint's HTTPS address can't be called with a plain request — every call has to be signed with AWS credentials, so only something with IAM permission to invoke it can use it. A public-facing product would put something in between (an API gateway or a small service of its own) to hold those credentials.

What the endpoint silently accepts

Three malformed requests were sent to test the endpoint's behavior. Only two of them failed loudly.

Result: rejected (400 error). One feature too many triggers a clear client error from the container. This is the safe kind of failure — loud, and visible the first time it happens.

Result: silently accepted, wrong answer. With price left out, the row has 17 values instead of 18. The endpoint accepted it and answered anyway — every remaining value shifted one column to the left, so the discount was read as the price, delivery days as the discount, and so on. The prediction changed from 0.279 to 0.069, a confident "safe" verdict for entirely the wrong reason, with nothing anywhere reporting an error.

Result: rejected (415 error). A raw category string where a number belongs fails to parse as CSV and the container reports it clearly.

The dangerous failure mode

The missing-column case is the one that matters. This happens in real systems when the code that builds requests drifts away from the code that built the training data — someone adds a column to one and not the other. The usual fixes: build both from the same shared function, or put a small check in front of the endpoint that counts columns before forwarding the request. SageMaker will not catch this for you.

Serving · Mode 2

A serverless endpoint

A real-time endpoint keeps a machine running all day. For a model getting only a few hundred requests daily, that means paying for 24 hours of machine to do a few minutes of actual work. A serverless endpoint has no standing machine — SageMaker starts one when a request arrives and stops it after a period of inactivity. Billing covers only the time spent actually handling requests.

The setup reuses the same trained model with a different endpoint configuration: a memory size and a concurrency limit, in place of a specific machine type.

An SDK bug encountered along the way

Building the serverless configuration through the high-level SDK class failed before the request even reached AWS, with a parameter validation error: the installed SDK version spelled the memory field with a lowercase "b" (MemorySizeInMb) where the API expects MemorySizeInMB. Nothing about the calling code was wrong — it was a bug in that SDK version. The practical fix: drop down to boto3, the lower-level AWS library the SageMaker SDK itself is built on, for that one call. Boto3 takes the API's field names exactly as AWS documents them, sidestepping the bug entirely.

The cold start

The real catch with serverless hosting is the first request after a quiet spell. The model has to be loaded onto a freshly started machine before it can answer — this is a cold start. A test run immediately after creating the endpoint will look deceptively fast, since the endpoint is still warm from creation. Measuring it properly means waiting until it has actually sat idle, the way real traffic would arrive.

Serving · Mode 3

Batch transform

Often nobody needs an answer immediately. A shop wanting a return-risk score for every order placed yesterday, to plan warehouse staffing, doesn't need an endpoint at all. A batch transform job starts a machine, loads the model, scores every row in an S3 prefix, writes the scores to another prefix, and stops.

Two settings matter here: splitting the input file into lines so it's sent to the model incrementally rather than as one enormous request, and reassembling the output in the same line order so each score lines back up with its original row.

MetricValue

The AUC of 0.726 on rows the model never saw during training sits close to the 0.708 validation score, meaning the model behaves on new data roughly the way training predicted it would. Two completely different serving paths — real-time and batch — producing identical scores for the same rows is exactly what should happen, since both load the same model.tar.gz file.

Decision Framework

Choosing between the three

Neither endpoint type is correct in general, and batch isn't always the cheap default either. The right choice follows from the shape of the traffic and the cost of making someone wait.

Real-time endpoint

You pay for every hour the machine exists, whether or not it receives any traffic. Use it when traffic is steady, or when every single request must come back fast with no exceptions.

15–380mstypical latency
~$84/moif left running
Steady trafficbest fit

Worked examples

  • A "chance of return" badge on every product page — needs an answer in the time it takes a page to render. A real-time endpoint is the only option that fits; an 11-second serverless cold start is not acceptable mid-page-load.
  • A nightly email to the warehouse with tomorrow's likely returns — nobody is waiting live. Batch transform scores the whole file, bills only while it runs, and needs no standing endpoint at all.
  • An internal tool a support agent opens roughly twenty times a day — genuinely ambiguous. Low, bursty traffic favors serverless on cost, but an occasional 11-second wait might annoy an agent mid-call. There's no single right answer here; the point is being able to argue it either way from the actual traffic pattern and the cost of waiting.

Cleanup

Tearing it all down

Four kinds of thing from this stage bill by the hour: the two SageMaker endpoints, the space, the NAT gateway, and the interface endpoints. The SageMaker endpoints come down first, since they cost the most and nothing else depends on them.

1

Delete both endpoints

The real-time and serverless endpoints are deleted first via code, followed by their endpoint configurations and the shared model object.

2

Verify in the console

The Endpoints list in the console is checked by eye — a script that failed partway through would have printed an error that's easy to miss.

3

Stop the space

Stopping the space halts its own billing, but does not delete endpoints, buckets, or anything else created from inside it. Each thing has to be removed where it actually lives.

4

Delete the interface endpoints

Every interface-type VPC endpoint is removed, leaving only the free S3 gateway endpoint in place.

5

Delete the NAT gateway

Its auto-assigned public IP lingers briefly in Elastic IPs before releasing itself.

Left behindOngoing costTo fully remove it
The space, stoppedA few cents/month for its 5GB diskDelete the space in Studio
Domain and user profileNothingDelete spaces, then profile, then domain
VPC, subnets, security groups, S3 endpointNothingAfter the domain is gone, delete S3 endpoint, then the VPC
The IAM roleNothingDelete in IAM after the domain is gone
The bucket~1MB storageEmpty it, then delete it
Training and batch jobsNothingCannot be deleted — permanent record

A domain can't be deleted while it still has user profiles; a user profile can't be deleted while it still has spaces; a VPC can't be deleted while anything is still inside it. The order above respects those dependencies.

Summary

What this stage actually accomplished

A training job asked for a machine, a container, and two named data channels, and returned one model.tar.gz. Serving it required three objects — a model, a configuration, and an endpoint — and only the endpoint itself bills. Real-time endpoints answer in milliseconds and bill all day. Serverless endpoints bill only for actual work but took 11 seconds to wake from idle. Batch transform needed no endpoint at all when nobody was waiting on the answer. The same underlying model file produced identical predictions through all three.

Everything ran from Python files against a private platform, and the platform's costly parts came back with one script and went away again at the end. That is the shape of real infrastructure work: the platform is written down as code, and the model work is code that can be reviewed and rerun.

The recurring theme

The quiet failures were the real lessons. A role that could see a file but not read it would have failed a training job only after already billing for it. The endpoint silently shifted every value in a row with a missing column and returned a confident wrong answer. A route pointed at a deleted NAT gateway turned into a blackhole that dropped traffic without a word. The SDK itself had a bug that only a drop down to boto3 worked around. None of these raised a clear error at the moment it actually mattered — catching every one of them came down to actually reading the numbers and the logs, not trusting that something would shout if it went wrong.
