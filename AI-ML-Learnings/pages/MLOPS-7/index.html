01 / OVERVIEW

Why Docker exists

A model that behaves perfectly on your laptop can still misbehave on a teammate's machine, or on a server months later. Docker is the tool the industry uses to close that gap.

In simple words, Docker is a tool that packages an application together with everything it needs to run, so that it runs the same way on any computer.

"Everything it needs" means more than the code. It means the libraries the code imports, the exact versions of those libraries, the language runtime such as Python itself, and the settings the application expects. Docker puts all of it into one package — easy to share, and started with one command.

That package is called an image, and the package while it is running is called a container. So you'll often hear Docker described as a way to "run an application in a container." Hold onto that simple picture for now — an image is the package, and a container is that package running — the vocabulary chapter ahead fills in the rest, once you've seen why Docker became the industry default in the first place.

02 / FOUNDATIONS

Containers vs. virtual machines

Virtual machines are older than Docker and also give an application its own environment. So why did Docker become so popular?

The answer is in how an operating system is built. It has two main layers. The kernel is the part that talks to the hardware — it hands out CPU time, memory, and disk to programs. The applications layer sits on top of the kernel, holding the programs, files, and tools that make an operating system recognizable.

Docker and virtual machines are both virtualization tools. The difference is which of these two layers each one packages.

Your computer
Applications layer
Operating system kernel
Hardware: CPU, memory, disk
A Docker container
Applications layer, in the image
host kernel, shared
Hardware
A virtual machine
Applications layer
its own kernel
hypervisor, then hardware
Docker packages only the applications layer and uses the host's kernel. A virtual machine packages the kernel too, and boots it like a separate computer.

That one difference explains three practical ones:

Docker containerVirtual machine
SizeUsually tens to hundreds of MBUsually several GB
Start timeAbout a secondOften a minute or more — it boots a kernel
Runs on any hostNeeds a matching kernel, so Linux images need LinuxAny operating system runs on any host

Almost every image you'll use is built for Linux, which Windows and macOS don't have a kernel for. Docker Desktop solves this quietly: it runs one small, lightweight Linux virtual machine in the background, and every container uses its kernel. So on a Mac or Windows laptop you're really running two tools at once — a virtual machine underneath, and containers on top. On a Linux server there's no virtual machine at all.

Docker Desktop itself gives you three things: Docker Engine, the background service that does the actual work; the Docker command line, the docker command that sends every request to the engine; and a graphical window where you can see and control the same things with buttons instead of commands.

You can check the installation is working with two commands. The first confirms the command line can talk to the engine:

shell
$ docker version --format 'client {{.Client.Version}}, engine {{.Server.Version}} on {{.Server.Os}}/{{.Server.Arch}}'
client 29.6.2, engine 29.6.2 on linux/arm64

Notice it says linux, even on a Mac — that's the small Linux virtual machine at work. The second check is Docker's version of hello world: it asks Docker to fetch a tiny ready-made program from the internet and run it.

shell
$ docker run hello-world
Unable to find image 'hello-world:latest' locally
latest: Pulling from library/hello-world
58dee6a49ef1: Pull complete
Digest: sha256:5e23090353324d887c48ad5e5c56d294eab81588df9605b07d1afe895f9cc8f8
Status: Downloaded newer image for hello-world:latest
Hello from Docker!
This message shows that your installation appears to be working correctly.

To generate this message, Docker took the following steps:
 1. The Docker client contacted the Docker daemon.
 2. The Docker daemon pulled the "hello-world" image from Docker Hub.
 3. The Docker daemon created a new container from that image which runs the
    executable that produces the output you are currently reading.
 4. The Docker daemon streamed that output to the Docker client, which sent it
    to your terminal.

Read the four numbered steps. Your docker command passed the request to the engine. The engine didn't have the hello-world program yet, so it downloaded it from Docker Hub — that's the "Unable to find" line. Then it started the program and streamed what it printed back to your terminal.

You can prove the shared-kernel idea directly. uname -sm prints the kernel's name and chip — run it on the laptop, then inside a container:

shell
$ echo "my laptop:          $(uname -sm)"
my laptop:          Darwin arm64
$ echo "inside a container: $(docker run --rm nginx:1.27 uname -sm)"
inside a container: Linux aarch64
WHAT JUST HAPPENEDThe laptop is macOS, whose kernel is called Darwin, on an arm64 chip. The container reports Linux on the same chip (which Linux calls aarch64). The container brought no kernel of its own — it used the Linux kernel of Docker Desktop's small virtual machine.
03 / FOUNDATIONS

The Docker vocabulary

Five words carry almost the entire subject: image, container, registry, repository, and tag. Get these solid and everything else is just commands.

Images and containers

An image is the package

Think of a zip file or a Java .jar, with much more inside. Besides your code, it holds the Linux files the application needs, the runtime such as Python, installed libraries, folders, environment variables, and the command that starts the application. You build it once, and it never changes after that.

A container is a running copy

When you run an image, Docker starts the application inside it, in its prepared environment. That running thing is a container. It lives exactly as long as the program inside it runs, and it keeps a small writable space of its own for anything it creates.

One image, read-only
start command: uvicorn
app/ and model/
scikit-learn 1.9.1 and friends
Python 3.12
Debian Linux files
container 1, running its own small writable layer on top
container 2, running its own small writable layer on top
container 3, running its own small writable layer on top
docker run starts a new container from the image each time. Running three copies of a service to handle more traffic needs only one image.

Two commands show the difference on a real machine. docker images lists the images you have; docker ps -a lists containers, including stopped ones. Running the hello-world example from the last chapter left exactly one of each:

shell
$ docker images hello-world
IMAGE                ID             DISK USAGE   CONTENT SIZE
hello-world:latest   5e2309035332       22.6kB         10.3kB

$ docker ps -a --filter ancestor=hello-world
container gifted_jackson   Exited (0) Less than a second ago

One image, one container — already exited, because the hello-world program ends the moment it finishes printing. The container still exists after it stops, though; a later chapter shows what to do with stopped containers.

Registries: where images live

Containers come from images. But where do images come from? Mostly from a registry — a storage service built specially for images, playing the same part for images that GitHub plays for code. The biggest one is Docker Hub, at hub.docker.com, and it's also the default: ask for an image without saying where it lives, and Docker looks there. No account is needed to browse it or download public images.

Look for the Docker Official Image badge. Official images — python, nginx, postgres, redis — are published by a dedicated Docker team together with the people who make each tool, and reviewed for security and good practice. Companies can also publish as verified publishers. Everything else is published by individuals and ranges from excellent to abandoned, so prefer an official image whenever one exists.

REGISTRY VS. REPOSITORYA registry is the whole storage service, such as Docker Hub or Amazon ECR. A repository is one application's space inside it, holding every tag (every version) of that one image. So nginx is a repository on the Docker Hub registry, and 1.27, 1.26-alpine, and latest are tags inside it.

Docker Hub is public — anyone can pull the images you'll use in this read. A company doesn't want its own application images public, so it keeps them in a private registry instead. Every large cloud has one:

Amazon ECR Google Artifact Registry Azure Container Registry Docker Hub (private repos) self-hosted — Nexus, GitHub

Tags: versions of an image

Software changes, so images have versions too — and a version is called a tag, written after the image name with a colon:

# image name : tag
nginx:1.27          nginx web server, version 1.27
python:3.12          Python 3.12
python:3.12-slim      Python 3.12, a trimmed-down variant
postgres:16          PostgreSQL 16

One tag is special. latest is what Docker uses when you give none — docker pull nginx really means docker pull nginx:latest. It sounds like a promise, "the newest version." It isn't. It's only a name, like any other tag, pointing at whichever image the publisher last gave that name. Try the simulation below: a teammate rebuilds and pushes under the same latest tag, and see where the name ends up pointing.

SIMULATE: WHO DOES pump-health:latest POINT AT?
latest
32bf3ac2e7b1
pump-health:0.1.0
pushed in March
515421c1106a
pump-health:dev
pushed in June
Right now, latest points at the March build — the one you tested.

It changes under you

The nginx:latest you pull today and the one you pull next month can be different programs, with nothing in your command different.

Two machines can disagree

A teammate who pulled latest in March and a server that pulled it in June are running different versions under the same name.

You can't roll back

If a release breaks and everything used latest, there's no name left for "the version that worked yesterday."

RULE OF THUMBlatest is fine for trying something out on a laptop. Anywhere it matters — and above all on a server — always choose a specific tag, such as nginx:1.27, so the same command always gives you the same thing.
04 / PRACTICE

Running containers, hands‑on

The example here is nginx, a small web server — a good first target because it shows a page in the browser, so you can see immediately whether a container really worked.

Pull, then run

docker pull downloads an image without running it. Choosing a specific version keeps things predictable:

shell
$ docker pull nginx:1.27
1.27: Pulling from library/nginx
06cdcf65323d: Pull complete
34ef2a75627f: Pull complete
Digest: sha256:6784fb0834aa7dbbe12e3d7471e69c290df3e6ba810dc38b34ae33d3c1c05f7d
Status: Downloaded newer image for nginx:1.27

$ docker images nginx
IMAGE        ID             DISK USAGE   CONTENT SIZE
nginx:1.27   6784fb0834aa        284MB           72MB

You never said "Docker Hub" — it's the default. The download arrived in layers, the lines ending Pull complete; an image is a stack of layers, which matters a great deal once you're building your own (see the case study ahead). Leave the tag out, and Docker quietly falls back to latest:

shell
$ docker pull nginx
Using default tag: latest
latest: Pulling from library/nginx
Status: Downloaded newer image for nginx:latest

$ docker images nginx
IMAGE          ID             DISK USAGE   CONTENT SIZE
nginx:1.27     6784fb0834aa        284MB           72MB
nginx:latest   abe47724e466        260MB         64.6MB

Two separate images, two different image IDs — exactly the latest-isn't-a-promise lesson from the last chapter, now visible on disk. docker run starts a container from an image. Typed plainly, it blocks your terminal with nginx's own startup log until you press Ctrl+C — which also stops the container. Add -d, for detached, to run it in the background instead:

shell
$ docker run -d nginx:1.27
4fe3186e720cf27d90b7bdde7a11fca97158ff2ccac9052d7028131b599d12ca

$ docker ps --filter ancestor=nginx:1.27
CONTAINER ID   IMAGE        STATUS        PORTS     NAMES
4fe3186e720c   nginx:1.27   Up 1 second   80/tcp    gracious_lederberg

The terminal is free again. docker ps lists running containers; you didn't give a name, so Docker made one up from two random words. A background container still writes logs — docker logs shows them — and you don't have to pull an image before running it. If docker run can't find one locally, it pulls it first, which means two different versions of nginx can start side by side with no conflict at all:

shell
$ docker run -d nginx:1.26-alpine
Unable to find image 'nginx:1.26-alpine' locally
1.26-alpine: Pulling from library/nginx
Status: Downloaded newer image for nginx:1.26-alpine

$ docker ps --filter ancestor=nginx:1.27 --filter ancestor=nginx:1.26-alpine
IMAGE               STATUS         NAMES
nginx:1.26-alpine   Up 1 second    awesome_galois
nginx:1.27          Up 9 seconds   gracious_lederberg

Port binding

Two nginx containers are running — can you open them in a browser? Not yet. A container lives inside Docker's own private network, closed to your laptop by default. Every application listens on a numbered port (nginx uses 80, PostgreSQL 5432, Redis 6379), but that port only exists inside the container until you bind it.

no -p, nothing reaches it
browser / curl
localhost:80
Docker's network
closed by default
-p 9090:80 host:container
browser / curl
localhost:9090
nginx container
listens on port 80
A binding is set only when a container is created. The host port comes first, the container port second.
shell
$ curl -sS http://localhost:80
curl: (7) Failed to connect to localhost port 80: Couldn't connect to server

$ docker stop $(docker ps -q --filter ancestor=nginx:1.27)
$ docker run -d -p 9090:80 nginx:1.27
PORTS
0.0.0.0:9090->80/tcp, [::]:9090->80/tcp

$ curl -s http://localhost:9090 | grep '<title>'
<title>Welcome to nginx!</title>

The ports column now reads 0.0.0.0:9090->80/tcp: port 9090 on the laptop leads to port 80 in the container. If you ever forget which port you bound, docker ps tells you. In practice, people usually bind the same number on both sides — -p 5432:5432 for PostgreSQL — unless it's already busy on the laptop. Two containers can't bind the same host port at once, but they can reuse the same container-side port, since each has its own.

Starting, stopping, and naming

Every docker run creates a new container; it never reuses an old one. So docker ps -a — running and stopped — usually shows more than docker ps alone:

shell
$ docker ps -a --filter ancestor=nginx:1.27 --filter ancestor=nginx:1.26-alpine
IMAGE               STATUS                     PORTS               NAMES
nginx:1.27          Up 8 seconds               0.0.0.0:9090->80/tcp   goofy_kalam
nginx:1.26-alpine   Up 10 seconds              80/tcp                 awesome_galois
nginx:1.27          Exited (0) 8 seconds ago                          gracious_lederberg

Three containers: one bound and running, one running unbound, and the very first one — stopped in the port-binding step above — still sitting there, exited. A stopped container restarts with docker start, keeping the same ID, no new container created. And rather than typing or looking up IDs, give a container a name of your own with --name when you create it:

shell
$ docker run -d --name web-app -p 9091:80 nginx:1.27
4af9b203b0ee64f69a93bef16ed301f6983910f0c52533003d7dd2d11646cadc

$ docker logs web-app | tail -1
2026/09/25 08:40:57 [notice] 1#1: start worker process 38

Now docker logs web-app, docker stop web-app, and docker start web-app all work with a name you can remember. Names must be unique per container.

05 / CASE STUDY

Writing a Dockerfile for a model service

Everything so far used images other people built. Now you package your own — a small pump-health model — as one image that runs anywhere.

The problem

A water utility runs hundreds of pumps that push water through its pipes. When one fails without warning, the pipe it feeds can lose pressure or burst, a neighbourhood goes without water, and an emergency crew is sent out at night. Most failures give warning signs days in advance — a bearing runs hot, the pump starts to shake, or its motor draws more current than it should.

The utility already records five readings from every pump, once a day:

ReadingWhat it measuresUnit
bearing_temp_cHow hot the pump's bearing runs°C
vibration_mm_sHow much the pump shakesmm/s
discharge_pressure_barThe pressure the pump pushes water out atbar
motor_current_aHow much current the motor drawsA
hours_since_serviceRunning hours since the last maintenancehours

With a small number of crews and a lot of pumps, the question every day is simple: will this pump fail within the next seven days, and should a crew inspect it? A model answers it — it takes the five readings and returns the probability of failure within a week. Failures are rare, about 6% of pumps in any given week, so the model doesn't decide at 50%. A wasted inspection costs one crew visit; a missed failure costs a burst main. So the service flags a pump once its probability reaches 0.3.

Meet the service

The model is served by a small FastAPI application with two endpoints: GET /health, which confirms the service is ready and running the same scikit-learn version the model was saved with, and POST /predict, which takes one pump's five readings and returns a failure probability, an inspect flag, the threshold used, and the model version. Training data is generated from a fixed random seed, so the project needs no download and behaves identically on every machine.

Choosing a base image

The first step — "install Python" — isn't something you do yourself in a Dockerfile. You start from an existing image that already has it, called the base image, and nearly every Dockerfile begins with one. For a Python service that's one of the official python images, and the question is which tag: python:3.12 comes in several variants with very different footprints.

python:3.12
418 MB
3.12-slim
45.7 MB
3.12-alpine
19.2 MB
Downloaded (content) size of each variant. The plain image is built on Debian and includes compilers and tooling; slim is the same Debian with those removed; alpine is built on a much smaller Linux distribution entirely.

Size isn't the whole story. Each variant answers two questions differently — does it have a C compiler, and which C library does it use?

VariantC compilerC library
python:3.12yes — gccglibc (Debian)
python:3.12-slimnoglibc (Debian)
python:3.12-alpinenomusl

Only the plain image has a compiler — most of what slim saves. The C library matters more: both Debian variants use glibc, the library almost every Linux server uses. Alpine uses musl, a different one. Compiled Python libraries such as numpy and scikit-learn ship ready-made packages ("wheels") for each C library they support; when there's no wheel for yours, pip falls back to downloading the source and trying to compile it. Installing the service's exact scikit-learn version shows the difference directly:

shell
--- slim:
installed scikit-learn 1.9.1
--- alpine:
  Downloading scikit_learn-1.9.1.tar.gz (7.8 MB)
  ../meson.build:1:0: ERROR: Unknown compiler(s): [['cc'], ['gcc'], ['clang']]
WHERE ALPINE HURTS MACHINE LEARNINGOn slim, pip found a matching wheel and finished in seconds. On alpine, no wheel existed for this package and chip, so pip tried to compile from source — and alpine has no compiler. numpy and SciPy do publish alpine wheels, which is exactly why this depends on the specific package and version, and why it catches people out.

So for Python and machine learning, start from slim. Reach for the plain image only when a package genuinely needs compiling, and for alpine only when every dependency ships an alpine wheel. The pump service's base image is python:3.12-slim.

The Dockerfile, line by line

A Dockerfile writes down, as instructions, exactly what you'd otherwise do by hand on a fresh machine: install Python, copy in the dependency list and install it, copy in the code and model, then set the start command. Click any line for what it does.

1# Dockerfile — the pump health service, with its model inside.
2# docker build -t pump-health:0.1.0 .
3# docker run -d --name pump-api -p 9000:8000 pump-health:0.1.0
 
4# An exact base, never python:latest. slim is Debian without compilers.
5FROM python:3.12-slim
 
6# Every path below is relative to /app inside the image.
7WORKDIR /app
 
8# Dependencies before code — an edit to app/ won't reinstall scikit-learn.
9COPY requirements.txt .
10RUN pip install --no-cache-dir -r requirements.txt
 
11# Code and model last, because they change most often.
12COPY train.py .
13COPY app/ app/
14COPY model/ model/
 
15# Documents the port. Publishes nothing — docker run -p does that.
16EXPOSE 8000
 
17# 0.0.0.0, not the default 127.0.0.1, or nothing outside can connect.
18CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
step 1 / 9

Start from the base image

python:3.12-slim already has Python installed. An exact tag — never python:latest — because reproducible builds depend on it.

RUN vs. CMDRUN happens once, while the image is built, and its result is saved inside the image — that's why the libraries are already installed when a container starts. CMD never runs during the build at all; it's only the command every container starts with.

What the build leaves out

When you build, Docker sends the whole project folder to the builder, and only files from it can be copied into the image. A file named .dockerignore lists what to leave out — it works like .gitignore:

# .dockerignore
.git
.venv
__pycache__
*.pyc
.env
scratch
.DS_Store

.git and .venv are large and useless inside an image. .env is where local secrets live. An image is often shared with many people, so nothing secret can be allowed inside it — this file is what makes sure of that. Later in this chapter you'll see exactly what happens without one.

Fast rebuilds through caching

You'll rebuild often while developing. Docker keeps each step's result as a layer and reuses it on the next build when nothing that step reads has changed — but once one step changes, every step after it runs again. That's exactly why the Dockerfile installs libraries before copying code. A one-line edit to the service code proves it:

shell
$ docker build -t pump-health:dev .
#5 [1/7] FROM docker.io/library/python:3.12-slim
#6 [2/7] WORKDIR /app                                    CACHED
#7 [3/7] COPY requirements.txt .                         CACHED
#8 [4/7] RUN pip install --no-cache-dir -r requirements.txt  CACHED
#9 [5/7] COPY train.py .                                 CACHED
#10 [6/7] COPY app/ app/
#11 [7/7] COPY model/ model/
real  0m0.606s
first build
14.6s
cached rebuild
0.6s

Everything up to and including pip install says CACHED. Only the code copy and the step after it ran again. If the Dockerfile copied all the code before installing, a single changed comment would reinstall every library, every time — the full 14-second build, instead of well under a second. Copy what changes rarely first, and what changes often last.

The secrets that slip through anyway

The pump Dockerfile copies named files and folders. Many Dockerfiles you'll meet are shorter, and copy the whole project folder in one line — COPY . . — where .dockerignore is the only thing standing between your secrets and the image. To see what that means: a made-up API token in a local .env file, and a one-line Dockerfile that copies everything, built two ways.

WITHOUT .dockerignore — inside /app

  • .env PLANT_API_TOKEN=…
  • .git full project history
  • .gitignore
  • Dockerfile
  • README.md
  • app
  • model
  • requirements.txt
  • scratch

WITH .dockerignore — inside /app

  • .dockerignore
  • .gitignore
  • Dockerfile
  • README.md
  • app
  • model
  • requirements.txt
  • train.py
NOTHING WARNS YOUThe build succeeds either way, and git status stays clean the whole time — Git and Docker keep completely separate lists. .gitignore keeps a file out of Git; it does nothing for an image. Deleting a secret in a later Dockerfile step doesn't help either, since every earlier layer is still inside the image and layers can be opened. Two habits follow: write .dockerignore before the first COPY . ., and better still, copy only what the image needs, by name — then a new local file can never reach an image by accident.

The most common mistake

One line matters more than it looks: --host 0.0.0.0. Leave it out, and uvicorn listens on 127.0.0.1 — "only this machine" — and inside a container, that machine is the container. Anything typed after the image name in docker run replaces its CMD, which makes the mistake easy to reproduce on purpose:

shell
$ docker run -d -p 9001:8000 pump-health:0.1.0 uvicorn app.main:app --port 8000
$ curl -sS http://localhost:9001/health
curl: (56) Recv failure: Connection reset by peer
$ docker logs pump-loopback | tail -1
INFO:     Uvicorn running on http://127.0.0.1:8000 (Press CTRL+C to quit)
READ THE SYMPTOMEverything looks healthy — the container is up, the port is bound, the log says uvicorn is running. Yet every request from the laptop is refused. The clue is in the log line itself: traffic from a bound port arrives at the container from outside, and a server listening only on 127.0.0.1 never sees it. If a bound port refuses connections, check which address the server is actually listening on first.
06 / SHIPPING

Tagging and sharing your image

A version people can talk about, a way back to the exact code, and a path from your laptop to any other machine that can run Docker.

Tag by version, and by commit

The image already carries 0.1.0, a version number people can talk about. Teams usually add a second tag — the Git commit the image was built from — so any problem leads straight back to the exact code. One image can carry many tags at once:

shell
$ docker tag pump-health:0.1.0 pump-health:$(git rev-parse --short HEAD)
$ docker images pump-health --format 'table {{.Tag}}\t{{.ID}}'
TAG        IMAGE ID
0.1.0      32bf3ac2e7b1
e0d1d47    32bf3ac2e7b1

0.1.0 and the commit tag e0d1d47 share one image ID — two names for the same image. Now watch the danger from the vocabulary chapter play out for real. Give this image the latest tag, the way many teams do on every build — then simulate a teammate tagging a different build as latest later on:

shell
$ docker tag pump-health:0.1.0 pump-health:latest
latest points at 32bf3ac2e7b1, the same as 0.1.0

## later, a teammate tags a different build:
$ docker tag pump-health:dev pump-health:latest
latest points at 515421c1106a, now the dev build
NO WARNING AT ALLSame name, different image. Anyone who now runs docker run pump-health with no tag gets the dev build, and nothing in their command tells them so — exactly the kind of change that makes a server behave differently overnight. Deploy by an exact tag or commit, and remove latest once you're done with it: docker rmi pump-health:latest deletes only that name. The image itself stays, since another tag still points at it.

Push to a registry, and pull it back

To use the image on another machine, push it to a registry, then pull it there. Here that means a small local registry running as its own container — it works exactly like Docker Hub. The image's name decides where it goes, so it's renamed with the registry's address on the front before pushing:

shell
$ docker run -d --name class-registry -p 5050:5000 registry:2
$ docker tag pump-health:0.1.0 localhost:5050/pump-health:0.1.0
$ docker push localhost:5050/pump-health:0.1.0
The push refers to repository [localhost:5050/pump-health]
afc3e62b43fc: Pushed
c84bebac337e: Pushed
0.1.0: digest: sha256:32bf3ac2e7b121143502dfc1a4d762c05ff2c5dd6ef7c5b51a89f1043e2ec343

The push sends the image one layer at a time. The registry now holds a pump-health repository with one tag, and the last line gives a digest — a content fingerprint. A tag can later move to a different image, as you just saw; a digest always means exactly these bytes. A teammate needs only the name to pull it back and run it, the way another machine would:

shell
$ docker pull localhost:5050/pump-health@sha256:32bf3ac2e7b1...
$ docker run -d -p 9004:8000 localhost:5050/pump-health@sha256:32bf3ac2e7b1...
$ curl -s http://localhost:9004/health
{"status":"ok","model_version":"20260924-102606","trained_with_sklearn":"1.9.1","running_sklearn":"1.9.1"}

The same service, started from the registry's copy — no clone, no Python install, no pip install. That's the handover promised back in the first chapter.

The same thing on Docker Hub

For Docker Hub, only the name changes. Log in once, tag the image under a Docker Hub username, and push:

docker login
export DOCKERHUB_USER=your-docker-hub-user-name
docker tag pump-health:0.1.0-amd64 "$DOCKERHUB_USER/pump-health:0.1.0"
docker push "$DOCKERHUB_USER/pump-health:0.1.0"

A new Docker Hub repository is public unless you make it private. Most cloud servers use x86 chips (amd64); an image built on Apple silicon is built for arm64 and won't run on them. --platform builds for the server's chip instead:

shell
built on this laptop for linux/arm64
$ docker build -q --platform linux/amd64 -t pump-health:0.1.0-amd64 .
built with --platform for linux/amd64
A TIDY WORKSPACEContainers and images pile up fast during development. docker system prune removes every stopped container and unused image at once — a wide net, worth using with care on a laptop other projects share.
07 / THE BIGGER PICTURE

Docker in the machine-learning lifecycle

Every building block from this read fits together into one path — the same image travelling from a laptop to production. Step through it below.

Your laptop

You write the service and its Dockerfile. Anything it depends on — a database, say — runs as a container pulled from Docker Hub, so nothing gets installed by hand.

Nobody in that chain installs Python or scikit-learn on a server, and nobody follows a document of steps. The image carries all of it, from the laptop all the way to production.

08 / RECAP

Key takeaways

The whole read, condensed to what's worth remembering.

01

Docker packages an application with everything it needs

Code, libraries, runtime, and settings — so it runs the same on every machine. In development that replaces long per-machine installs with one command per service; in deployment it replaces a document of steps with a package the server simply runs.

02

A container is not a virtual machine

A virtual machine brings its own kernel. A container brings only the applications layer and shares the host's kernel, so it's smaller and starts in about a second. On macOS and Windows, Docker Desktop supplies the small Linux virtual machine underneath.

03

An image is the package; a container is it running

One image can start many containers. Images come from registries — Docker Hub is the public default, and companies keep their own in private registries such as Amazon ECR. A registry holds repositories, and a repository holds the tags of one image. Choose a specific tag; never rely on latest.

04

The everyday commands

docker pull, docker images, docker run with -d, -p host:container and --name, then docker ps / docker ps -a, docker logs, docker stop and docker start.

05

A Dockerfile is the recipe for your own image

FROM a base image — for Python, slim. Then WORKDIR, COPY the requirements, RUN pip install, COPY the code and model, and finish with CMD. Install libraries before copying code so rebuilds stay fast. Bind the server to 0.0.0.0. Keep secrets out with .dockerignore.

06

Share an image deliberately

Tag it with a version and a commit, push it to a registry, and pull it by tag or digest wherever it needs to run — built for that machine's chip.
