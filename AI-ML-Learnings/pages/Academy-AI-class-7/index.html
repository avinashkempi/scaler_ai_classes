Section 1 · 4 minFrom advisor to contractor

In Class 6 you built a workflow. You drew every step yourself. You wrote the IF node, you chose what happens when the message is urgent. The path was yours.

Today the model chooses the path.

Until now, every AI tool in this module has worked the same way. You type, it answers, and you decide what to do with the answer. That is an advisor. A good one, but you still do all the work.

An agent is a contractor. You describe the outcome. It works out the steps, picks up the tools it needs, does the work, checks the result, and keeps going until it is done or stuck.

ImportantThe difference is not how smart the model is. The same model can sit inside a chatbot or inside an agent. The difference is the system built around it: tools to act with, and a loop that lets it keep going.

Here is the whole class in one demo, before we explain any of it.

Section 2 · 8 minChatbot or agent: the four differences

Think about the last time you asked an AI a question. One message in, one answer out, and then it stopped and waited for you. That is a chatbot turn. It is reactive.

Now give an AI this instead: "Find three free online events this week about coding, check each one's date, and put them in a table." A chatbot answers from memory, and the dates will be stale. An agent goes and looks.

There are four differences, and they are worth knowing by heart.

The four differences

Chatbot Agent
Scope One turn: you ask, it answers A whole task, which may take many steps
Tools None. It can only produce text Can search, read files, call services, change things
Memory Only the current conversation Also tracks what it has done and what happened
Who decides You decide every next step It decides its own next step

The last row is the one that matters. In Class 6 you were the one deciding the path. In an agent, the model is.

Three ingredients

Every agent has the same three ingredients, and you will see each one in the code later.

Tools are its hands. Without them it can only talk.

Memory is its notebook. During a task, the agent keeps a running list of what was asked, what it did and what came back. That list is just a list of messages. We will print it in Section 6, so you see there is nothing hidden.

The loop is its decision-making. It looks at the situation, picks an action, does it, reads the result, and decides again. That is Section 3.

Use the visualizer below. Pick a task and compare what each one produces.

Doubt by Learner"So is an agent just a chatbot with a loop?"

Close enough to be a useful way to think about it. The model is the same kind of model. What changes is that it is allowed to call tools and to keep going until it decides it is finished. That small change is what makes agents powerful, and it is also what makes them risky, which is why half of today is about limits.

Doubt by Learner"Is ChatGPT or Claude an agent?"

The app can be either. When it just answers, it is a chatbot turn. When it searches, runs code or uses your files on its own over several steps, that mode is an agent. Many products are both, depending on what you ask for.

Section 3 · 9 minThe loop every agent runs

There is no magic inside an agent. There is a loop with three beats.

Think: look at the goal and what you know so far, and decide what to do next. Act: do it, by calling a tool. Observe: read what came back.

Then go round again. Think, act, observe, until the goal is met or the agent is stuck. This pattern has a name, ReAct, short for reason and act. It comes from a 2022 research paper and it is still the shape of almost every agent you will meet.

If you have ever used a thermostat, you have met the idea. It senses the temperature, compares it with the target, turns the heating on or off, and senses again.

Walk the loop once

Our class agent works in a small shop. It has one tool that looks up a price. Here is the question from Section 1.

"Is the bag cheaper than Rs 1,500, and what would two caps cost?"

Round 1. Think: I need the bag price. Act: look up the bag. Observe: Rs 1,299.

Round 2. Think: I still need the cap price. Act: look up the cap. Observe: Rs 299.

Round 3. Think: I have both numbers. 1,299 is under 1,500, and two caps are 2 times 299, which is 598. Nothing more to look up. Stop and answer.

Three rounds, two tool calls, one answer, and you wrote none of the steps.

Use the visualizer below. Step through the loop and watch the message list on the right grow. That list is the agent's entire memory of the task.

ImportantThe agent stops when the model decides it has enough to answer. Nothing in the loop forces that. Hold that thought, because in Section 7 we make it fail.

Where loops go wrong

Three things go wrong again and again, and each one maps to one beat of the loop.

It never stops. The observation keeps saying "not done yet" and the agent keeps trying.

It believes a wrong observation. The tool returns something misleading, and the agent builds an answer on it with full confidence.

It stops too early. It decides "close enough" and answers without finishing the job.

We will cause the first two on purpose in Section 7.

Doubt by Learner"Does the agent really think, or is that just a word?"

The model writes out reasoning before it picks an action, and that is what we call thinking. Whether that is the same as human thinking is a separate debate. For building agents, what matters is that the reasoning is visible and that it drives the next action.

Section 5 · 7 minTools, and the standard plug called MCP

In the demo the agent used tools. Now we open one up.

A tool is two things: a function that does something, and a description that tells the model what it is for. The model reads the description. It never sees the code.

How a tool call really happens

The model cannot run anything. It can only write text.

When it wants to use a tool, it writes a request: the tool's name and the inputs, such as get_price with item set to shoes. The code around the model, which we call the runtime, sees that request, runs the real function, and puts the result back into the conversation as a new message. Then the model reads it.

So three parties are involved. The model decides. The runtime acts. The tool does the work.

ImportantBecause the model only ever sees the name and the description, the description is the entire manual for that tool. A vague or wrong description gives you a wrong agent. We prove that in Section 7.

MCP: one plug for every tool

Writing a custom connection from every agent to every app does not scale. If there are 5 agents and 10 apps, that is 50 separate connections.

MCP, the Model Context Protocol, is a standard way to describe and call tools. An app exposes its tools once in the MCP format, and any agent that speaks MCP can use them. 5 agents and 10 apps become 15 pieces of work instead of 50. Think of it like a USB-C port: one shape that many devices agree on.

MCP began at Anthropic. In December 2025 it was donated to the Agentic AI Foundation, which the Linux Foundation hosts, so that no single company controls it. Today many agents and many apps support it.

Use the visualizer below. Drag the sliders and watch how the number of connections changes.

Doubt by Learner"Do I need MCP to build an agent?"

Not today. The agent you build in Section 6 uses a plain Python function as its tool. MCP matters when you want to plug in something someone else already built, such as a calendar, a file store or a code host, without writing the connection yourself.

Doubt by Learner (Optional)"Is a tool the same as an API?"

A tool usually wraps an API. The API is the service. The tool is the small function with a description that lets the model use it.

Step 4 - Give the agent a tool and a brain

This is the whole agent. Read it before you run it.

from langchain.agents import create_agent
from langchain.tools import tool
from langchain_groq import ChatGroq

PRICES = {"shoes": 799, "bag": 1299, "cap": 299}
BUSY = False   # we flip this in Section 7

@tool
def get_price(item: str) -> str:
    """Look up the price of one item, in rupees (INR), by its name."""
    if BUSY:
        return "Service busy. Please try again."
    if item.lower() in PRICES:
        return f"{item}: {PRICES[item.lower()]}"
    return f"No item called {item}"

model = ChatGroq(model="openai/gpt-oss-120b", temperature=0)

agent = create_agent(
    model,
    tools=[get_price],
    system_prompt="You are a shop assistant. Use the tool for prices. Never guess a price.",
)

Here is what each part does.

PRICES is a tiny pretend shop. In a real product this would be a database or a web service.

The line starting with @tool turns an ordinary function into a tool. The sentence inside the triple quotes is the description. That sentence is what the model reads. The function name and the argument name are part of it too.

ChatGroq is the model, the same one from Class 1 served by Groq. Temperature zero keeps it steady.

create_agent snaps the three ingredients together: the model, the list of tools, and the instruction. The loop from Section 3 is built in.

Step 5 - Add a helper that shows every step

Normally an agent hides its steps and returns an answer. This helper prints each message as the loop produces it, so you can watch.

from langgraph.errors import GraphRecursionError

def ask(question, limit=12):
    message = {"messages": [{"role": "user", "content": question}]}
    try:
        for step in agent.stream(message, config={"recursion_limit": limit}, stream_mode="values"):
            step["messages"][-1].pretty_print()
    except GraphRecursionError:
        print(f"\nSTOPPED: the agent hit its limit of {limit} steps.")

Two things to notice. The stream prints the newest message after every step. And limit is a hard cap on how many steps the loop may take. Every model call and every tool run counts as one step, so a limit of 12 allows about six attempts. We use it in Section 7.

Step 6 - Run it, and read the message list

ask("How much are the shoes?")

You should see four messages in order: your question, then a message from the model containing a tool call, then the tool's result, then the model's final answer.

That list of four is the entire memory of this task. The tool call is the act. The tool message is the observe. The model reading it and answering is the next think.

Section 7 · 14 minBreak it on purpose, then fix it

Agents fail in a small number of ways, and you will meet all of them in real work. Today we cause two of them deliberately. The rule is the same each time: break it, see it, apply one fix, see it working.

ImportantBoth failures are caused by the tool, not by the model making a mistake. That is on purpose. It means they appear on every model, in every batch, so you can rely on seeing them.

Failure 1: it never stops

Flip the tool into a broken state. It will now always say it is busy.

BUSY = True
ask("How much are the shoes?")

Two outcomes are both fine. Either the agent keeps retrying until the step limit stops it, or it gives up politely after a few tries and tells you the service is down. Watch which one you get.

ImportantNotice that ask() passes a limit of 12 here. We set it only to protect your free quota. The library's own default is far higher: in the version we tested, create_agent sets a limit of 9,999 steps, which in practice means no limit at all. So if you forget to set one, a stuck agent can keep calling the model about five thousand times.
Ask LearnersType what happened on your screen: did it stop by itself, or did the limit stop it?

Learners will report different things on the same code. That is the lesson. When an agent stops is the model's decision, and the model can decide wrongly. A stop you can count on has to live in your code, not in a hope.

Note for InstructorIf the model gives up after two attempts on every learner's screen, say so and move to the fix anyway. The point stands: nothing guaranteed it. Then ask what would happen if the tool had said "try again" a hundred times, and run the next cell to show the cap in action.

Fix 1: a hard step limit

Run it again with a lower limit. This is a guarantee, not a request.

ask("How much are the shoes?", limit=6)

A limit of 6 allows about three attempts. If the agent is still going, the code cuts it off, prints STOPPED, and your program carries on. Without a cap, an agent in this state can keep calling a paid service until your credits run out.

Fix 2: tell it when to give up

A limit protects you. An instruction can make the agent behave better inside the limit. Rebuild the agent with one extra sentence.

agent = create_agent(
    model,
    tools=[get_price],
    system_prompt=(
        "You are a shop assistant. Use the tool for prices. Never guess a price. "
        "If the tool fails twice in a row, stop and tell the user it is unavailable."
    ),
)
ask("How much are the shoes?", limit=6)

It will usually stop and explain. Note the word usually. The instruction improves behaviour. The limit guarantees it. You want both.

Now put the tool back to normal.

BUSY = False
Ask LearnersWhich of the two fixes would you keep if you could only keep one, and why?

The limit. A prompt asks, and the limit enforces.

Failure 2: it believes a wrong description

This time the tool works perfectly. We change only its description. In the Step 4 cell, change the sentence inside the triple quotes from "in rupees (INR)" to "in US dollars", then run that whole cell again. Then ask:

ask("How much are the shoes?")

The tool returns 799, with no unit. The description says dollars. The agent has no other source of truth, so it will report the shoes as 799 dollars, with full confidence.

Ask LearnersWho made the mistake, the model or the tool author?

The tool author. The model did exactly what the description told it to do. The description is the agent's entire understanding of the tool, so a wrong description produces a wrong agent, however good the model is.

Fix: make the truth travel with the result

Two changes. Restore the description to say rupees. And have the tool put the unit in its own result, so the observation carries the truth instead of relying on the description. In the Step 4 cell, change the line that returns the price to:

        return f"{item}: Rs {PRICES[item.lower()]}"

Run the cell again and ask the same question. The answer now says rupees, and it would even if someone later wrote a careless description, because the result states the unit itself.

ImportantThe pattern from both failures is the same. Do not rely on the model to be careful. Put the guarantee in code: a step limit, a clear description, results that carry their own meaning.
Doubt by Learner"Would a better model not make these mistakes?"

A better model recovers more often, and some will notice a unit mismatch and say so. It still has no way to verify what the tool really does. The tool and the limits are your job, whatever model you use.

Doubt by Learner (Optional)"What about the third failure, stopping too early?"

It is the mirror image of never stopping: the agent decides it is done before it is. The fix is a clear success condition in the instruction, such as "only answer once you have a price for every item asked about". Try it as an extension by asking for three items at once.

Section 8 · 6 minChatbot or agent? Tool or no tool?

Two quick rounds to sharpen your judgement. Answer in the chat before the instructor reveals each one.

Round 1: chatbot or agent?

Decide for each: chatbot, agent, or neither.

  1. "Explain how photosynthesis works."
  2. "Every morning, check my college portal for new notices and message me the important ones."
  3. "Fix the spelling mistakes in this paragraph."
  4. "Read my twenty unread emails and draft replies for the ones that need one."
  5. The keyboard suggesting the next word as you type.

Answers.

  1. Chatbot. One question, one answer, no tools and no steps.
  2. Agent. It acts on its own over time, uses a tool to read the portal, and decides which notices matter.
  3. Chatbot. It is one task done in one pass, with nothing to look up or do.
  4. Agent. It reads many items, decides for each one what to do and writes the drafts.
  5. Neither. It predicts the next word from context. It does not pick tools or loop.

The question to ask each time: does it use tools, take several steps, and decide the order itself?

Doubt by Learner"Number 3 feels like it could be an agent. It is doing work."

Doing work is not the test. Fixing spelling is one pass over text you gave it. An agent goes and gets information or takes actions in several steps, and chooses those steps itself.

Round 2: tool or no tool?

Use the agent you built. For each message, predict whether it will call get_price, then run it.

ask("Hi, who are you?")
ask("What is the capital of France?")
ask("Which is cheaper, the shoes or the cap?")
ask("How much is a laptop?")
Ask LearnersBefore running each one, type: tool or no tool?

Most likely you will see no tool for the first two, because the agent can answer them itself. Two lookups for the third. And a tool call for the fourth, which comes back empty, so the agent tells you the shop has no laptop.

The agent decides when it needs a tool. That decision, made by the model on every turn, is the heart of what makes it an agent.

Note for InstructorIf the model surprises anyone, for example by answering the capital of France through the tool, use it as the discussion rather than an error. The point is that the decision belongs to the model, and learners should be able to read the message list to see what it decided.

Section 9 · 9 minDesign an agent on paper

Now design one yourself, without code. A good agent starts as a one-page plan. If you cannot fill in this page, you are not ready to build.

The one-page spec

Line Question Our shop agent
Goal What outcome does it deliver? Answer questions about item prices
Tools What can it use? get_price
Stop condition How does it know it is done? It has the price for every item asked about
Step limit The most it may do 6 steps
Needs approval Which actions need a human first? None, because it only reads
If it fails What does it do when a tool breaks? Tell the user and stop

The last three lines are the ones beginners leave out. They are also the ones from Section 7.

Section 10 · 4 minWrap-up and what is next

You started today with a model that answers. You end with a system that decides.

What you now know. An agent is a model, plus tools, plus a loop. The loop is think, act, observe. The model decides and the runtime acts. A tool is a function plus a description, and the description is the model's only manual. Agents fail in predictable ways, and the guarantees belong in your code.

What you built. A working agent, its full message list, and two deliberate failures with their fixes.
