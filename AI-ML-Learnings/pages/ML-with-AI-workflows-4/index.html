Linear regression 3: building a model you can actually trust

A good R² is not enough to put a model in front of a customer. This is the story of how one data scientist learns to scale features fairly, judge a model's fit honestly, and check the five assumptions that decide whether a linear regression can be trusted at all.

Before we begin: a scenario

Why any of this matters

Meet Kabir

Kabir is a data scientist at Fleetline, a last-mile delivery startup. The app promises customers an estimated delivery time the moment they place an order, and Kabir has been asked to build the model behind that estimate. It takes in details available right when an order is placed — the distance the courier has to travel, the package weight, a traffic congestion index for the route, the courier's average speed on past deliveries, and a few other signals — and outputs a predicted number of minutes until the order arrives.

This sounds like a plain linear regression problem, and it is. But this number gets shown directly to customers on their screens, over and over, thousands of times a day. If the model is quietly unreliable in some situations, customers notice fast, and so does the support team fielding complaints. Before Kabir's manager will let this model anywhere near the live app, she wants to know not just how accurate it looks on paper, but why it can actually be trusted.

Every idea in this post shows up because Kabir ran into a question he had to answer before his model could be trusted with a real customer's delivery estimate.

Setting the stage: preparing today's data

A realistic, imperfect delivery dataset

Fleetline's real order database isn't something we can work with directly, so we simulate a dataset that mirrors what Kabir actually works with: the same features, the same rough relationships, and — importantly — the same kind of imperfections a real dataset has. Real delivery data is noisy, a few features overlap in what they measure, the spread of errors isn't perfectly tidy, and every now and then something genuinely unusual happens, like an order getting caught in a flash flood. That messiness is built in on purpose, because learning to spot these issues is the whole point of this material.

One flash-flood order is also planted in the training data as a genuine outlier.

Why did we scale the features before training?

Putting every feature on the same footing

Every feature was scaled into the same 0-to-1 range before training, using min-max scaling:

$$x_{scaled} = \dfrac{x - x_{min}}{x_{max} - x_{min}}$$
  • x — the original value of a feature for one data point
  • x_min, x_max — the smallest and largest values that feature takes across the training set
  • x_scaled — the rescaled value, always between 0 and 1
🔊

The intuition. Route distance runs from a few hundred to over twenty thousand meters; traffic congestion sits on a simple 0-to-1 scale. Left unscaled, an optimizer ends up taking much larger steps for the feature with the larger raw values — not because it's more important, but purely because of the size of its numbers. It's a bit like judging how much two people have to say based on how loudly they happen to be speaking, rather than the substance of what they're saying. Scaling removes that unfair advantage.

Quiz 1
A delivery-time dataset has route distance recorded in meters (typically in the thousands) and a traffic congestion index recorded on a 0-to-1 scale. If a linear regression model is trained on this data without any scaling, what is the most likely consequence?
Linear regression doesn't understand units on its own. When one feature's raw values are far larger than another's, the optimization process and the resulting coefficients get skewed by that difference in scale — not by which feature is truly more predictive. Scaling puts every feature on the same footing.

The trouble with R²

"If we add a few more columns, would the model get better?"

Kabir shows his manager the first model's R² value. She's pleased, and asks a natural follow-up: if we add a few more columns from the order data — even ones we're not sure matter — would the model get better? Kabir tries it, adding a feature that is essentially random and unrelated to delivery time, just to test the idea. To his surprise, the R² score goes up anyway. That doesn't feel right — and it isn't.

$$R^2 = 1 - \dfrac{SS_{res}}{SS_{tot}}$$
  • SS_res — sum of squared residuals, Σ(y_i − ŷ_i)²
  • SS_tot — total sum of squares, Σ(y_i − ȳ)², where ȳ is the mean of all actual values

R² tells us what fraction of the variation in the target the model manages to explain. The trouble is that adding any extra feature, even a useless one, can never make SS_res larger — at worst the model assigns it a coefficient of zero. In practice, with real data, the model usually finds at least a tiny, coincidental pattern to latch onto, so R² creeps up even though nothing meaningful was added.

🎟️

Think of it like a raffle where you're allowed to keep buying more tickets for free. Buying an extra ticket can never lower your odds of winning, so of course you'd keep buying more — whether or not it reflects skill. R² behaves the same way with features: it can only go up or stay flat as you add more, whether or not those features carry real information.

Adjusted R²

A metric that charges rent for every feature

Adjusted R² fixes the raffle problem by charging the model a small penalty for every feature it adds, so a feature only helps the score if it earns its place.

$$Adj.\,R^2 = 1 - \left[\dfrac{(1 - R^2)(n - 1)}{n - d - 1}\right]$$
  • R² — the regular R² value
  • n — number of data points used to fit the model
  • d — number of predictor features in the model (not counting the intercept)

As d grows, the denominator n − d − 1 shrinks, making the penalty larger. If a new feature doesn't meaningfully reduce SS_res, the penalty outweighs the tiny gain in R², and Adjusted R² actually goes down — a warning that the feature isn't pulling its weight.

🏅

Sports-roster analogy. Imagine a team's efficiency rating that accounts for squad size. Just having more players on the roster shouldn't automatically make a team look better on paper — a good rating should only rise if the extra players actually contribute to winning, and fall if they're just taking up space. Adjusted R² plays that same role for a regression model's feature set.

View: computing R² and Adjusted R² on Fleetline's test data 
y_hat = lr.predict(X_test)
Adj_R = 1 - ((1 - lr.score(X_test, y_test)) * (len(y_test) - 1)
             / (len(y_test) - X_test.shape[1] - 1))
print("R-squared:", lr.score(X_test, y_test))
print("Adjusted R-squared:", Adj_R)
Output
R-squared: 0.7622307584318843
Adjusted R-squared: 0.7608344625501923

Earning trust: the five-assumption checklist

A good score isn't the same as a trustworthy model

Kabir now has a model with a respectable Adjusted R² and a detailed summary table. He brings this to his manager, expecting a green light. Instead she asks a harder question: "Before we let this model print an estimated delivery time on a customer's screen, how do we know it's actually reliable — and not just lucky on this one batch of data?"

Linear regression makes several assumptions about the data it's trained on, and the model is only as trustworthy as those assumptions are true. Kabir decides to run his model through a trust checklist — five assumptions, one at a time.

The five assumptions, one at a time

Each accordion below expands into the full check

1Linearity⌄

Linear regression assumes the relationship between each feature and the target is a straight-line relationship: a fixed increase in a feature produces roughly the same fixed change in the prediction, no matter where you are on that feature's range.

For Kabir, this means the model assumes each extra kilometer of route distance adds roughly the same number of minutes to a delivery, whether the route is 2 km or 20. If routes through the crowded city center take disproportionately longer per kilometer than routes on open highway, a plain linear model will systematically get those cases wrong.

🏃

Imagine judging how tired someone is after a run purely by distance covered, assuming tiredness increases at a constant rate per kilometer. That might hold for the first few kilometers, but a marathon runner at kilometer 40 is often far more exhausted, relative to distance, than at kilometer 4. A straight line drawn through the whole race would miss that curve.

Quiz 2
Which of the following situations would violate the linearity assumption of linear regression?
A relationship that stays flat for a while and then bends sharply upward past a threshold is a curved relationship, not a straight line. A plain linear model forced onto this pattern will underpredict past the threshold and overpredict before it.
2No multicollinearity between features⌄

Multicollinearity happens when two or more features carry almost the same information. Route distance and estimated fuel cost are a good example here: Fleetline's ops team calculates estimated fuel cost as roughly a fixed rate multiplied by distance, so it moves in near lock-step with distance itself.

When two features tell the model almost the exact same story, it has no reliable way to decide how much credit each deserves. Small changes in the data can cause coefficients to swing wildly between the two, even though the combined prediction barely changes — making individual coefficients untrustworthy even when overall predictions still look fine.

⚖️

Like two witnesses in a courtroom who saw the exact same thing and describe it identically. The second witness adds no new confidence — they're just repeating the first. But splitting credit between them would be arbitrary and unstable, because there was never really two independent sources of information.

Measuring it: the Variance Inflation Factor (VIF)

$$VIF_j = \dfrac{1}{1 - R_j^2}$$
  • VIF_j — variance inflation factor for feature j
  • R_j² — R² from regressing feature j against every other feature

A common rule of thumb: a VIF above 5 — and especially above 10 — signals serious multicollinearity for that feature.

Since estimated fuel cost is computed directly from distance, the two are highly correlated. Regressing either against the rest of the dataset — including the other — yields a very high R², pushing both VIF values well above common caution thresholds like 5 or 10.

3Errors are normally distributed⌄

Every prediction has an error, or residual, attached to it:

$$e_i = y_i - \hat{y}_i$$

Linear regression assumes these errors, taken across the whole dataset, roughly follow a normal (bell-curve) distribution centered around zero: most predictions close to correct, with a few a bit too high and a few a bit too low, symmetrically. If errors are heavily skewed or dominated by a handful of extreme values, several statistical guarantees behind linear regression start to break down — including how much we can trust the p-values in the summary table.

Why outliers matter

The one delivery caught in a flash flood, delayed far outside anything else in the data, behaves like one unusually loud voice in an otherwise calm room: it can pull the model's fitted line toward itself, distorting predictions for every other, far more typical delivery, just to accommodate one unusual case.

Checking it: the Shapiro-Wilk test

The Shapiro-Wilk test produces a statistic W measuring how closely a set of values resembles a normal distribution. W ranges up to 1 — the closer to 1, the more normal the errors look.

View: computing the Shapiro-Wilk statistic 
from scipy import stats
res = stats.shapiro(errors)
print("Shapiro-Wilk statistic (W):", res.statistic)
Output
Shapiro-Wilk statistic (W): 0.9723562152221223

A histogram of residuals that looks roughly bell-shaped, together with a Shapiro-Wilk statistic close to 1, is a reasonable sanity check that the errors are close to normally distributed — one more box checked.

Quiz 4
One delivery was delayed by a sudden flash flood that shut down the only bridge on its route, producing a delay far outside the pattern followed by every other delivery. What is the most likely effect of this single data point on the model's error distribution?
A single extreme outlier can have an outsized effect on a linear regression fit, since the model minimizes squared error and a very large individual error contributes a disproportionately large penalty — distorting both the fitted coefficients and the shape of the error distribution.
4Constant error spread (no heteroskedasticity)⌄

Beyond looking normal, we also want the spread of errors to stay roughly constant across the full range of predictions — a property called homoskedasticity. Its opposite, heteroskedasticity, is when the error spread grows or shrinks depending on the predicted value.

📣

Picture pointing a megaphone at a crowd. If the cone stays the same width all the way to the back, that's constant spread — homoskedasticity. If the cone widens dramatically the further back you go, so people far away hear something far noisier than people close by, that's heteroskedasticity: the "noise" depends on how far away they are.

For Kabir, this means checking whether predictions are equally reliable for short, nearby deliveries and long, cross-city ones — or whether errors balloon specifically for deliveries predicted to take a long time.

Visual check

The residual-vs-predicted plot shows a reasonably consistent spread across the range of predictions, without a strong funnel or megaphone pattern — visually supporting homoskedasticity.

The Goldfeld-Quandt test

This test removes a chunk of observations from the middle of the dataset (ranked by a chosen variable), then compares the error spread of the remaining low group against the remaining high group. Similar spread in both groups supports homoskedasticity.

  • A p-value above a chosen significance level (commonly 0.05) means no strong evidence against homoskedasticity
  • A p-value below that threshold would suggest heteroskedasticity is present
View: running the Goldfeld-Quandt test 
import statsmodels.stats.api as sms
gq_test = sms.het_goldfeldquandt(sm_model.resid, sm_model.model.exog)
gq_f_statistic, gq_p_value = gq_test[0], gq_test[1]
Output
F statistic: 0.8642168016770395
p-value: 0.9967420600452369

Since the p-value (0.9967) is far greater than the 0.05 significance level, we fail to reject the null hypothesis of homoskedasticity — there's no strong statistical evidence of heteroskedasticity here.

If heteroskedasticity is found, common fixes include applying a transformation to the target (log, square-root, or Box-Cox) or removing outliers driving the uneven spread.

Quiz 5
In a scatter plot of residuals against predicted values, the spread of residuals visibly fans out, like a megaphone, as predicted values increase. What does this indicate?
A residual-vs-predicted plot that widens as predictions increase is the classic visual signature of heteroskedasticity — non-constant error spread — distinct from multicollinearity (checked with VIF), autocorrelation (checked via sequential patterns), or R², which has no fixed relationship with residual spread.
5No autocorrelation between errors⌄

The last assumption is that one data point's error shouldn't help predict the next data point's error. If errors are correlated in sequence, the model is systematically missing some structure in the data — usually tied to order or time.

This matters most when data has a natural sequence, such as orders placed over the course of a day. If the model tends to underpredict delivery time for several orders in a row during the dinner rush, then overpredict for several in a row during a quiet mid-afternoon lull, that's autocorrelation: the errors aren't random and independent, they're tracking something the model hasn't captured — a time-of-day traffic pattern.

🌦️

Similar to weather forecasting: if a forecaster's error yesterday tells you something about the direction of their error today — say, they've been consistently underestimating temperature all week — that's a sign their model is missing a pattern, rather than making independent, random mistakes each day.

The story resolves

What finally earns the model its place on the live app

Kabir works through his trust checklist: the relationship between his features and delivery time looks reasonably linear, his VIF values are all comfortably low after dropping the redundant fuel-cost feature, his residuals look close to normal aside from the one flash-flood outlier documented separately, his Goldfeld-Quandt test doesn't raise a red flag on constant error spread, and after grouping his data by time of day, he doesn't find strong autocorrelation either.

He brings this checklist — not just a single accuracy number — back to his manager. That's what finally earns the model a place on the live app: not a high R² alone, but a model whose behavior Kabir can explain, defend, and monitor.

🧭 The foundational assumption underneath all five
Each data point, (x⁽ⁱ⁾, y⁽ⁱ⁾), is drawn as a random, representative sample — rather than being selected in some biased way.
