Console Orientation, Regions & the $0 Billing Alarm

⏱ 14 min

Before creating a single resource, set a tripwire that emails you the moment real spend appears. Every section from here builds on top of this being done first, always.

🛠 Instructor Does

Walk the room through the console's three fixed landmarks: the region selector (top right — most services are region-scoped, meaning a resource created in Mumbai is invisible from N. Virginia's view), the search bar (the fastest way to reach any service by name instead of hunting menus), and the account name menu (top right, next to region — this is where Billing lives). Today's resources go in one consistent region, chosen once, and stuck with throughout.

Why a billing alarm has to exist before anything else

Nothing about the free tier stops a misconfigured resource from silently billing real money once a cap is crossed — there's no gentle warning banner the way Render's dashboard shows one. A billing alarm is the only thing standing between "oops" and "found out three weeks later." AWS actually offers two different tools for this, and it's worth knowing both exist.

ToolWhat it actually doesThe gotcha
AWS BudgetsLets you set a literal near-zero dollar threshold (e.g. "alert me the moment actual spend crosses $1") and emails you when it's crossed. The more direct match for "a $0 alert."Found under Billing and Cost Management — no region-switching needed, it's account-wide.
CloudWatch billing alarmThe older, more commonly tutorialized route — a CloudWatch alarm watching the account's EstimatedCharges metric.The metric is only ever published in us-east-1 (N. Virginia) — an alarm created in any other region will sit there silently and never fire, no matter what actually gets spent.

Setting Up a Near-Zero Spend Alert (the AWS Budgets route)

The path, in order: open the account menu in the top right and go into Billing and Cost Management. Before anything else, open Billing preferences and check "Receive Billing Alerts" (some accounts also show a separate Free Tier usage alert checkbox — check that one too) and save — either kind of billing alarm silently does nothing until this box is checked. From there, go into Budgets and create a budget: pick a Zero spend budget template if one's offered, or a Cost budget with a $1 monthly threshold otherwise. Set the alert threshold at 100% of actual spend and point it at your own email. Creating the budget still isn't the last step — AWS sends a confirmation email, and nothing actually arrives later without clicking through to confirm that subscription.

The classic gotcha, worth knowing on purpose: plenty of older tutorials instead walk through the CloudWatch-alarm route — and that alarm has to be created with the region selector set to US East (N. Virginia) / us-east-1, even if every resource today lives in Mumbai or anywhere else. This is a genuinely common trip-up, and one worth double-checking against AWS's current documentation, since it has shifted emphasis toward Budgets over the years.

IAM Hands-On — Creating a Scoped, Non-Root User

⏱ 14 min

Class 22 explained least privilege. Today Nikhil actually clicks through creating the user who'll do every remaining step today — never root again after this section.

Worth saying before Step 1: the root user (the identity created at signup) can do literally anything, including deleting the whole account. AWS's own guidance is to stop using it for daily work immediately after setup. Everything from here — S3, Elastic Beanstalk, EC2 — should be done signed in as the IAM user created below, not root.

Creating the Deploy User

From the console search bar, IAM → Users → Create user, named something identifiable like nikhil-deploy. Checking "Provide user access to the AWS Management Console", choosing "I want to create an IAM user," and setting a custom password (unchecking "require password reset" keeps things fast for a live class) sets up console access. On the permissions screen, "Attach policies directly" and, for today's scope, attaching AmazonS3FullAccess, AWSElasticBeanstalkFullAccess, and AmazonEC2FullAccess covers everything the session needs. After Create user, the confirmation screen shows an IAM sign-in link in the shape https://[account-id-or-alias].signin.aws.amazon.com/console — that link, not the root email, is how every remaining step gets done from here on. The actual checkpoint that proves it worked: signing out of root, signing back in through that IAM link with the new username and password, and confirming the console loads.

Worth saying out loud, honestly: the three managed policies above are broad — AmazonS3FullAccess grants access to every bucket in the account, not just today's demo bucket. That's a deliberate classroom trade-off for speed, not real least privilege. A production setup would instead write a custom JSON policy scoped to exact actions on exact resource ARNs — SIM 2 below is exactly that exercise, without touching the real console.

S3 Hands-On — Bucket, Upload & the Public-Access Trap

⏱ 14 min

Object storage as a building block, hands-on — and the one real behavior change that catches almost everyone who last touched S3 more than a couple of years ago.

Creating a Bucket and Uploading a File

Signed in as nikhil-deploy, the console search bar leads to S3 → Create bucket. Bucket names are globally unique across all of AWS, so something specific works best — blurbbot-demo-yourname-2026, for instance — in the same region every other resource today uses. Every Block Public Access setting stays checked on; that's the correct default and it stays that way for the bucket as a whole. After Create bucket, opening it and running Upload → Add files with any small test file completes the upload. Clicking the uploaded object's name and copying its Object URL into a new browser tab produces Access Denied — not a mistake, just Block Public Access doing exactly its job.

Not the old 2018 behavior — worth stating explicitly: S3 now blocks all public access by default on every new bucket, account-wide. Older tutorials that show one checkbox toggle to "make public" are describing pre-2023 defaults. Getting one object public today genuinely requires two separate steps, on purpose — AWS added the friction after a long string of real-world leaked-bucket incidents.

Making Exactly One Object Public (Not the Whole Bucket)

Getting one object public — and only that object — takes two deliberate steps. First, inside the bucket's Permissions tab, the Block public access (bucket settings) panel needs Edit → unchecking only "Block public access to buckets and objects granted through new public bucket or access point policies," saved and confirmed by typing confirm. Second, back in Permissions, the Bucket policy section needs a policy granting s3:GetObject to * — scoped to that one object's ARN specifically, never to arn:aws:s3:::bucket-name/*, which would expose everything in the bucket instead of just one file. Saving that and reopening the same Object URL should now resolve instead of returning Access Denied.

Security callout — worth real weight, not a footnote: a bucket policy scoped to /* instead of one specific object key is the single most common way real S3 leaks happen — member lists, invoice PDFs, backup dumps, all reachable by anyone with the URL. Scope every public grant to the exact object it needs to cover, never the whole bucket, especially once real customer data like the chain's member records is involved.

Meet Blurb Bot — The One App Both Paths Deploy

⏱ 8 min

One form field, one AI call, one page. Small enough to write live, small enough to deploy twice, and it closes a loop that's been open since Class 17.

🎙 Instructor Says

"Remember shelf-talker.html from Class 17 — the one that only ever worked by double-clicking it on Nikhil's own laptop? Blurb Bot is its real successor: type a book title, get back a one-line shelf-talker blurb generated live by an actual LLM call, on a page anyone can reach — not just whoever's standing at Nikhil's desk. Same idea from Class 17, finally running on real infrastructure with a real address."

Which LLM, and why: Blurb Bot calls Groq's API — the same reliable free choice this series settled on back in Class 16, after Gemini's free tier proved too rate-limit-prone for a live class. Groq's API is OpenAI-compatible (same request shape, different base URL) and its free tier needs no card on file for the API itself — a real, currently-available free tier with per-model request-per-minute and token-per-minute caps, not a time-limited trial. Model used below: llama-3.1-8b-instant — fast, currently listed as a production model, and more than enough for a one-line blurb.

app.py — the whole backend

from flask import Flask, render_template, request
import os
from openai import OpenAI

app = Flask(__name__)
client = OpenAI(
    api_key=os.environ.get("GROQ_API_KEY"),
    base_url="https://api.groq.com/openai/v1"
)

@app.route("/", methods=["GET", "POST"])
def index():
    blurb = None
    title = ""
    if request.method == "POST":
        title = request.form.get("title", "").strip()
        if title:
            resp = client.chat.completions.create(
                model="llama-3.1-8b-instant",
                messages=[
                    {"role": "system", "content": "Write one punchy one-line bookshop shelf-talker blurb for the given title. Under 20 words. No surrounding quotes."},
                    {"role": "user", "content": title}
                ],
                max_tokens=60
            )
            blurb = resp.choices[0].message.content.strip()
    return render_template("index.html", blurb=blurb, title=title)

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=8000)

Path A — Elastic Beanstalk (Beginner Path)

⏱ 20 min

Hand AWS the code; it provisions and manages the EC2 machine, load balancer, and health checks underneath. Fewer decisions, one command to go live.

Before Step 1 — Confirm the EB CLI Is Installed

Check · Python installed?Run python3 --version (Mac) or python --version (Windows). The EB CLI installs via pip, so Python has to already be there — install from python.org first if it's missing.
Install, on MacRun python3 -m pip install --upgrade --user awsebcli in Terminal. If eb isn't recognized afterward, the pip user-install path isn't on PATH yet — the terminal output tells you exactly which folder to add.
Install, on WindowsOpen a fresh Command Prompt or PowerShell and run pip install awsebcli --upgrade --user. If eb --version fails afterward, add the Python Scripts folder shown in the install output to your system PATH and reopen the terminal.
Confirm either OSRun eb --version — a version string back means it's ready.

Deploying Blurb Bot via Elastic Beanstalk

From inside the Blurb Bot project folder — app.py, requirements.txt, templates/ — running eb init starts things off: pick a region, an application name like blurb-bot, and the Python platform matching the local version. When it asks for credentials, those are the access key of nikhil-deploy from §2 (generated under that IAM user's Security credentials tab if it doesn't have one yet) — never the root account's keys. Running eb create blurb-bot-env provisions an EC2 instance, a load balancer, and health monitoring underneath — genuinely several minutes, not instant. The first real checkpoint is eb status reading Health: Green. From there, eb setenv GROQ_API_KEY=your_actual_key_here sets the Groq key without ever touching a file, and eb open opens the live EB URL directly in a browser — typing a book title into Blurb Bot and getting a real blurb back is the checkpoint that closes the loop.

Worth flagging honestly: modern Elastic Beanstalk Python platforms (Amazon Linux 2023) generally expect a Procfile in the project root (one line: web: gunicorn app:app) to know how to start the app — older platform generations auto-detected an application.py file instead. Which platform generation is current, and which file EB expects, is worth confirming against AWS's docs before relying on it — this is one of the more actively-changing corners of AWS.
Checkpoint recap: three green checkpoints, in order — eb create finishes without error, eb status reads Health: Green, and eb open loads a page that actually returns a blurb. Any red between those is worth pausing on before moving to Path B.
§ 5

Path B — EC2 + EC2 Instance Connect (Intermediate Path)

⏱ 20 min

The same app, the manual way — full control over the machine, and a browser-based connection with no local SSH key setup at all.

Instance-type honesty check, before Step 1: the classic "750 free EC2 hours a month, 12 months" claim applies only to accounts created before July 15, 2025 (see the Setup section above). Which free-tier terms today's demo account is actually on determines which instance size is genuinely free-tier-eligible — t2.micro or t3.micro on the classic tier, or a small size covered by remaining credit on a newer account. Worth re-checking the current list at aws.amazon.com/free rather than assuming.

Launching, Connecting, and Running Blurb Bot on EC2

The manual path starts at EC2 → Launch instance: name it (blurb-bot-ec2, say), choose the Amazon Linux AMI, and pick t3.micro or t2.micro, whichever the account's free tier actually covers. For the key pair, "Proceed without a key pair" is the right choice — EC2 Instance Connect needs no local SSH key at all. Under Network settings → Edit, SSH (port 22) opens from My IP, and a second custom TCP rule opens port 8000 — Blurb Bot's port — from Anywhere (0.0.0.0/0), which is what makes the live URL actually reachable from outside. After Launch instance, the status needs to read Running and 2/2 checks passed before continuing. Selecting the instance and going Connect → EC2 Instance Connect → Connect opens a browser-based terminal directly — no local .pem file, no ssh command typed anywhere. Inside that terminal: sudo yum install -y python3-pip git, then cloning the Blurb Bot repo, cd into it, and pip3 install -r requirements.txt --user. Setting export GROQ_API_KEY=your_actual_key_here and running python3 app.py starts the app — and that terminal has to stay open, since closing it stops the app. The checkpoint: copying the instance's Public IPv4 address from the EC2 console and opening http://that-address:8000 should return a real blurb end to end.

Kept deliberately minimal, on purpose: Flask's own built-in server (app.run(...)) is doing the serving here, not gunicorn behind nginx — that stack is real-world best practice, but it's more moving parts than a live two-hour class needs to get one working public URL. Worth naming out loud as a scope call, not an oversight.
Opening 0.0.0.0/0 on a custom port is a classroom trade-off, said honestly: it's the fastest way to get a demo-reliable public URL live in one session. A real deployment would restrict that rule far more tightly (a specific IP range, or better, behind a load balancer) — worth naming out loud as a shortcut being taken for demo reliability, not a recommended production pattern.

⏱ 12 min

Both paths just deployed the exact same app. The choice between them was never about capability — it's about how much of the machine underneath you actually want to manage yourself.

§ 7

Cleanup & Free-Tier Monitoring — Avoiding the Surprise Bill

⏱ 12 min

This is the section that keeps today free, literally. Treat it with the same weight as the deploy itself — an unattended resource is how a free class becomes a real bill.

Tearing Down Everything Built Today

Cleanup, in order: on EC2, selecting blurb-bot-ec2 and choosing Instance state → Terminate instance — terminate, not just stop, since a stopped instance can still hold billable storage attached to it. For Elastic Beanstalk, either eb terminate blurb-bot-env from the CLI, or in the console, environment → Environment actions → Terminate environment. That's not the end of it, though: Elastic Beanstalk auto-creates its own S3 bucket to hold uploaded application versions and logs, and terminating the environment does not delete that bucket — it needs to be found (named something like elasticbeanstalk-[region]-[account-id]) and removed manually. The demo bucket from §3 needs the same treatment, emptied first if it holds more than one object. Only after all of that is the Billing dashboard (or the Budget from §1) worth rechecking — and the next day, not immediately, since billing data has a reporting delay and "$0 right now" isn't proof yet.

Worth saying with real weight: "terminated the environment" and "done" are not the same sentence. The single most common real AWS surprise-bill story is exactly this shape — an environment or instance gets torn down, but a bucket, an Elastic IP, or a log group it created along the way keeps quietly running. Five extra minutes checking S3 and EC2 directly is the actual difference between a free class and a bill nobody expected.

Key Takeaways

1. The billing alarm comes first, always — before the first resource, not after. A $1 Budget alert or a correctly-regioned CloudWatch alarm is the only real safety net a free-tier class has.

2. Root is for setup, not for daily work. The very first real action on a new AWS account should be creating a scoped IAM user and never touching root again.

3. S3 defaults to private now, on purpose. Public access takes two deliberate steps — and should be scoped to one object, never a whole bucket, especially once real data is involved.

4. Elastic Beanstalk and EC2 deployed the identical app today — the difference was never capability. It's how much of the machine underneath you want to manage yourself.

5. "Terminated" and "cleaned up" are not the same word. Check what an environment or instance quietly created along the way before calling cleanup done.
