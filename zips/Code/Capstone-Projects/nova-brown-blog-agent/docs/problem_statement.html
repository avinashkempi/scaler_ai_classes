Build a multi-agent system that researches and writes technical blogs

Two cooperating AI agents: one that does the research and one that writes, reviews and edits, turning a one-page brief into a cited, on-style article draft.

Target role
AI Engineer, Forward Deployed Engineer (FDE), Applied ML Engineer
Level
Intermediate to advanced. You should be comfortable with Python, async code and calling LLM APIs.
Time
1 to 2 weeks as a portfolio project. 60 to 90 minutes as a system design interview discussion.
Stack
Python, uv, LangGraph, FastMCP (Model Context Protocol), Gemini models, Perplexity or Tavily search, Firecrawl scraping, Opik for tracing and evals
Author
Shivank Agarwal

The situation

You are an AI engineer at a fast-growing ed-tech company. The content team publishes technical lessons and blog posts every week on topics like RAG, tool calling and AI agents. Each 3,000-word article takes a senior engineer two to three working days:

  • Day 1, research. Reading docs, papers, GitHub repos and conference talks, and keeping track of which source said what.
  • Day 2, drafting. Writing the article in the company's voice, with diagrams and code.
  • Day 3, editing. Checking the draft against the brief and the style guide, then fixing tone, structure and terminology.

The head of content wants to cut this to a few hours of human review per article without losing quality. Engineers should only have to write a one-page brief (the article guideline) and then review a solid, cited draft.

Think of how a newsroom works. A researcher collects and checks sources and hands a file to the writer. The writer drafts the story. An editor marks it up with a blue pencil, and the writer revises until the editor has no more comments. Your job is to build that newsroom with two AI agents.

What you will build

A system of two specialised agents that work through files on disk:

  1. Nova, the research agent, reads article_guideline.md, gathers and filters sources, and writes research.md.
  2. Brown, the writing agent, reads the guideline and the research, writes the article, reviews it against the guideline and the style profiles, edits it, and saves article.md.

Both agents must be exposed as MCP servers, so they can be driven from a terminal client you build, from Claude Desktop or Cursor, or from one combined endpoint that runs the full research-to-article flow.

Input: the article guideline

A Markdown brief written by a human. It describes the topic, the outline, the audience and the sources the author already wants used. Here is part of a real guideline from the project's sample data:

nova-research-agent/data/research_function_calling/article_guideline.md

Functional requirements

R1. Research agent (Nova)

Turns a guideline into a research file.

  1. Extract every reference in the guideline and sort it into GitHub links, YouTube links, other web links and local files (.py, .ipynb, .md).
  2. Ingest each kind in parallel: summarise GitHub repos, transcribe YouTube videos, scrape and clean web pages, copy local files.
  3. Run a research loop for 3 rounds. In each round, find the gaps between the guideline and what has been collected so far, generate new search queries, and run them on a web search API.
  4. Score every search result for trust, authority and relevance, and keep only the good ones.
  5. Pick up to 5 of the kept sources that deserve a full scrape, and scrape them.
  6. Combine everything into one research.md, organised into sections with collapsible blocks.
  7. If a step completely fails (for example 0 of 7 URLs scraped), stop the workflow and ask the user how to continue. Do not write an article on empty research.

R2. Writing agent (Brown)

Turns a guideline plus research into a finished article, and edits articles on request.

  1. Load the guideline, the research, a set of reusable writing profiles (author persona, article rules, structure, mechanics, terminology, tonality) and a few example articles for style.
  2. Detect diagram requests in the guideline (for example "Generate mermaid diagram") and generate them in parallel before writing.
  3. Write a first draft that follows the outline and stays anchored in the research.
  4. Review the draft against the guideline and every profile, producing specific, located comments. Then edit the article to address them.
  5. Repeat review and edit up to a configurable number of rounds (3 by default), and stop early if the reviewer has nothing to say. Save every version.
  6. Support two editing modes driven by human feedback: edit the whole article, or edit only a selected range of lines.

R3. Integration and access

Makes the agents usable from anywhere.

  1. Expose Nova and Brown as separate MCP servers with tools, prompts and resources, over both stdio and HTTP.
  2. Ship an interactive terminal client that lists tools, loads prompts and lets an LLM call the tools.
  3. Ship one composed MCP server that mounts both agents and adds a single end-to-end prompt: research, then write, on the same folder.

Non-functional requirements

  • Configurable. Models, thinking levels, number of review rounds and file paths live in YAML or environment settings, not in code.
  • Reliable. LLM calls retry on transient errors. Scraping runs with a concurrency limit and timeouts. Failures are reported clearly.
  • Testable offline. The test suite runs with a fake model and makes no paid API calls.
  • Observable. Every workflow run can be traced end to end, including each LLM call.
  • Measurable. Article quality is scored with LLM-as-judge metrics against a small evaluation dataset.
  • Cost-aware. Use a fast, cheap model for most steps and a stronger model only where it pays off.

Constraints

  • Python with uv. Each component is its own uv project with its own virtual environment.
  • LLMs: Gemini models through LangChain (google_genai) and the Google GenAI SDK. Keep the model choice behind a config so it can be swapped later.
  • Search: Perplexity by default, Tavily as an alternative provider. Scraping: Firecrawl.
  • The agents talk only through files and MCP. No shared database is needed for the local version.

A good solution keeps a human in charge: the agents produce a researched draft, and a person decides what gets published. Design for "excellent first draft in hours", not "publish without reading".

Deliverables

  1. Source code for Nova (server and client), Brown (workflows and server) and the integration layer.
  2. A README that gets a new engineer from clone to first article in under 15 minutes.
  3. At least one sample folder with a guideline, the research Nova produced and the article Brown wrote, including the intermediate drafts.
  4. A passing offline test suite.
  5. A short evaluation report: which metrics you used, scores for two model configurations, and what you would change.

Suggested milestones

  1. Brown on fixed research. Load a guideline and a hand-written research.md, write one draft with a single LLM call, save it.
  2. Profiles and the review loop. Add the writing profiles, a reviewer with structured output, the edit step and the early stop.
  3. Diagrams. Add a tool-calling step that finds diagram requests and generates Mermaid diagrams in parallel.
  4. Nova tools. Build the extraction, scraping, GitHub, YouTube and web search tools, and the file layout under a hidden .nova folder.
  5. Nova as an agent. Expose the tools over MCP, write the workflow prompt, and drive it from a terminal client.
  6. Integration. Expose Brown over MCP, then compose both servers behind one endpoint with an end-to-end prompt.
  7. Quality. Fake-model tests, Opik tracing, an evaluation dataset and two LLM-judge metrics.

What the interviewer will probe

  • Why two agents and not one? Why is Brown a fixed workflow while Nova is driven by an LLM following a prompt?
  • How do you stop the writer from making things up that are not in the research?
  • How do you know the review loop makes the article better and not just different?
  • Scraped web pages are untrusted input. What stops a page from injecting instructions into your agents?
  • What does one article cost, and where would you cut cost first?
  • How would you scale this to 100 articles a day, and swap Gemini for another provider?

Stretch goals

  • A human approval step between research and writing, where the author can drop or add sources.
  • Publish the final article to a CMS (for example a Notion or WordPress draft) through another MCP server.
  • Model-provider switch: run Brown on OpenAI or Groq by changing only the config.
  • Deploy Nova as a container (Docker, then AWS or Cloud Run) with Postgres to store research runs.
  • Cache scraped pages and search results so re-running research on a similar topic is cheaper.
