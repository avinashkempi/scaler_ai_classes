The one idea behind this module

An LLM cannot run code, read your database, or do exact maths reliably. With tool calling, the LLM can ask your program to run a function, then use the result in its answer.

1. Askquestion + tool menu
→
2. LLM decidesanswer, or "call tool X with Y"
→
3. Your coderuns the function
→
4. Send resultrole = tool
→
5. LLM answersusing the result
Important

The LLM never runs your function. It only asks. Your Python code runs it and reports back.

Setup: the site's Help page. Open the folder 1_GIVE_FIRST_Starter_Code.

How tool calling really works

Analogy: a restaurant waiter (the LLM) and the kitchen (your code). The waiter cannot cook. He reads the menu (your tool list), writes an order slip with a table number (tool_call_id), and when the dish comes back he serves it with a smile (the final answer).

Everything happens through one growing list of messages. For "What is the square root of 144?" it grows like this:

What the messages list looks like (ids are examples)
# after step 1 (the LLM asked for a tool)
[{"role": "user", "content": "What is the square root of 144?"},
 {"role": "assistant", "content": None,
  "tool_calls": [{"id": "call_abc123", "type": "function",
                  "function": {"name": "square_root", "arguments": "{\"number\": 144}"}}]}]

# after step 3 (our code ran the tool and appended the result)
 ...,
 {"role": "tool", "tool_call_id": "call_abc123", "content": "12.0"}]

# step 4: we send the whole list again; the LLM now replies with normal text
"The square root of 144 is 12."

Note that arguments is a JSON string, not a dict. That is why we need json.loads.

            },
        },

]

This is a JSON Schema: it says the tool takes one argument named number, of type number, and it is required. The description fields are the most important part. The LLM reads them to decide when to use the tool.

TODO 2 — Run the requested tool and add its result to messages

Solution for TODO 2
fn_name = tool_call.function.name
fn_args = json.loads(tool_call.function.arguments)  # e.g. {"number": 144}
result = tool_map[fn_name](**fn_args)
print(f"   [tool] {fn_name}({fn_args}) -> {result}")
messages.append({
    "role": "tool",
    "tool_call_id": tool_call.id,  # tells the LLM which request this result belongs to
    "content": str(result),
})

Three moves: read the name, turn the JSON string into a dict, call the real function with **fn_args (which means square_root(number=144)). Then append a message with role: "tool" and the same tool_call_id, so the LLM knows which request this answers. The API rejects a tool result without a matching id.

TODO 3 — Call the LLM a second time with the updated messages and return its text

Solution for TODO 3

    model=MODEL,
    messages=messages,
    tools=tools,
    reasoning_effort="none",
)
return final_response.choices[0].message.content

The second call sends the full history (question, tool request, tool result). Now the LLM has the number it needs and writes a sentence.

Example output (the [tool] lines are exact; the AI's wording will vary)
Q: What is the square root of 144?
   [tool] square_root({'number': 144}) -> 12.0
A: The square root of 144 is 12.

Q: What is the capital of France?
A: The capital of France is Paris.

Q: Can you calculate the square root of 2025 for me?
   [tool] square_root({'number': 2025}) -> 45.0
A: The square root of 2025 is 45.
Why reasoning_effort="none"?

We use OpenAI's gpt-6-luna, a fast, low-cost model. In the Chat Completions API, OpenAI only allows tool calling with this model when reasoning_effort="none" (no long internal "thinking" before answering). It also makes the replies faster.

"""
Exercise 3.1 — Tool Calling from Scratch (plain OpenAI SDK, no frameworks)
Created by Shivank Agarwal

LLMs are good with words but can be wrong with exact maths.
"Tool calling" lets the LLM ask OUR Python code to do a job, then use the result.

The flow (remember these 4 steps):
  1. We send the question + a description of our tools (a JSON "menu")
  2. The LLM replies either with a normal answer OR with "please call tool X with arguments Y"
  3. Our code runs the Python function and sends the result back (role = "tool")
  4. The LLM writes the final answer using that result

Run it:
    python 1_tool_calling_from_scratch.py
"""

import json
import math

from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()  # reads OPENAI_API_KEY from the .env file

client = OpenAI()
MODEL = "gpt-6-luna"

# ----------------------------------------------------------------------------
# 1) The real Python function (the "tool")
# ----------------------------------------------------------------------------
def square_root(number: float) -> float:
    if number < 0:
        raise ValueError("Cannot compute square root of a negative number.")
    return math.sqrt(number)


# Maps the tool NAME the LLM will use -> the Python function we run
tool_map = {"square_root": square_root}

# ----------------------------------------------------------------------------
# 2) The tool "menu" we show the LLM (JSON Schema)
#    The LLM never sees our Python code. It only sees this name, description and parameters.
# ----------------------------------------------------------------------------
# ----- TODO 1 (solved): Describe the square_root tool in OpenAI's JSON tool format -----
tools = [
    {
        "type": "function",
        "function": {
            "name": "square_root",
            "description": "Calculate the square root of a non-negative number.",
            "parameters": {
                "type": "object",
                "properties": {
                    "number": {
                        "type": "number",
                        "description": "The non-negative number to take the square root of.",
                    }
                },
                "required": ["number"],
            },
        },
    }
]


def chat_with_tools(user_message: str) -> str:
    messages = [{"role": "user", "content": user_message}]

    # Step 1: ask the LLM, and tell it which tools exist.
    # reasoning_effort="none" is required for tool calling with this model in the Chat Completions API.
    response = client.chat.completions.create(
        model=MODEL,
        messages=messages,
        tools=tools,
        reasoning_effort="none",
    )
    message = response.choices[0].message
    messages.append(message)  # keep the assistant's reply (including its tool requests) in the history

    # Step 2: did the LLM ask for a tool?
    if not message.tool_calls:
        return message.content  # no tool needed, e.g. "What is the capital of France?"

    # Step 3: run every tool the LLM asked for and send the results back
    for tool_call in message.tool_calls:
        # ----- TODO 2 (solved): Run the requested tool and add its result to messages -----
        fn_name = tool_call.function.name
        fn_args = json.loads(tool_call.function.arguments)  # e.g. {"number": 144}
        result = tool_map[fn_name](**fn_args)
        print(f"   [tool] {fn_name}({fn_args}) -> {result}")
        messages.append({
            "role": "tool",
            "tool_call_id": tool_call.id,  # tells the LLM which request this result belongs to
            "content": str(result),
        })

    # Step 4: ask again; now the LLM can see the tool results and write the final answer
    # ----- TODO 3 (solved): Call the LLM a second time with the updated messages and return its text -----
    final_response = client.chat.completions.create(
        model=MODEL,
        messages=messages,
        tools=tools,
        reasoning_effort="none",
    )
    return final_response.choices[0].message.content


if __name__ == "__main__":
    questions = [
        "What is the square root of 144?",
        "What is the capital of France?",               # no tool needed
        "Can you calculate the square root of 2025 for me?",
    ]
    for q in questions:
        print(f"\nQ: {q}")
        print(f"A: {chat_with_tools(q)}")

"""
Exercise 3.2 — The same Tool Calling, with LangChain
Created by Shivank Agarwal

Same 4 steps as Exercise 3.1, but LangChain removes the boring parts:
  * @tool builds the JSON "menu" for us from the function name, type hints and docstring
  * llm.bind_tools([...]) attaches the menu to every call
  * response.tool_calls gives the requests already parsed into Python dicts

Run it:
    python 2_tool_calling_with_langchain.py
"""

import math

from dotenv import load_dotenv
from langchain_core.messages import HumanMessage, ToolMessage
from langchain_core.tools import tool
from langchain_openai import ChatOpenAI

load_dotenv()


# ----- TODO 1 (solved): Turn square_root into a LangChain tool -----
@tool
def square_root(number: float) -> float:
    """Calculate the square root of a non-negative number."""
    if number < 0:
        raise ValueError("Cannot compute square root of a negative number.")
    return math.sqrt(number)


tools = [square_root]
tool_map = {t.name: t for t in tools}  # "square_root" -> the tool object

llm = ChatOpenAI(model="gpt-6-luna", reasoning_effort="none")
llm_with_tools = llm.bind_tools(tools)  # the LLM now knows the tool exists


def chat_with_tools(user_message: str) -> str:
    messages = [HumanMessage(content=user_message)]

    response = llm_with_tools.invoke(messages)  # Step 1: ask
    messages.append(response)

    if not response.tool_calls:  # Step 2: no tool needed
        # .text = the answer as plain text. (With tools bound, LangChain talks to OpenAI's newer
        # "Responses API", where .content is a list of blocks; .text joins them for us.)
        return response.text

    # ----- TODO 2 (solved): Run every requested tool and add a ToolMessage with its result -----
    for tc in response.tool_calls:  # Step 3: run the tools
        result = tool_map[tc["name"]].invoke(tc["args"])
        print(f"   [tool] {tc['name']}({tc['args']}) -> {result}")
        messages.append(ToolMessage(content=str(result), tool_call_id=tc["id"]))

    return llm_with_tools.invoke(messages).text  # Step 4: final answer (.text = plain text)


if __name__ == "__main__":
    # Peek at the JSON "menu" that @tool generated for us
    print("Tool name       :", square_root.name)
    print("Tool description:", square_root.description)
    print("Tool arguments  :", square_root.args)

    questions = [
        "Is 15241383937 the square of 123456?",  # a trap: 123456 squared is 15241383936
        "What is the capital of France?",
        "Can you calculate the square root of 2025 for me?",
    ]
    for q in questions:
        print(f"\nQ: {q}")
        print(f"A: {chat_with_tools(q)}")

"""
Exercise 3.3 — An LLM that can use FOUR tools (warehouse assistant)
Created by Shivank Agarwal

Same pattern as 3.2, but now the LLM must CHOOSE the right tool from a menu of four,
and fill in the arguments (SKU id, lead time) from the user's plain-English question.

Run it:
    python 3_inventory_tools_demo.py
"""

from dotenv import load_dotenv
from langchain_core.messages import HumanMessage, ToolMessage
from langchain_core.tools import tool
from langchain_openai import ChatOpenAI

load_dotenv()

# ----------------------------------------------------------------------------
# A tiny "database" (a Python dict) of warehouse items. SKU = Stock Keeping Unit = product id.
# reorder_point = when stock falls to this level or below, we should order more.
# ----------------------------------------------------------------------------
INVENTORY = {
    "SKU-001": {"name": "Industrial Valve", "stock": 120, "reorder_point": 50,  "unit_cost": 7000},
    "SKU-002": {"name": "Hydraulic Pump",   "stock": 18,  "reorder_point": 25,  "unit_cost": 35000},
    "SKU-003": {"name": "Conveyor Belt",    "stock": 5,   "reorder_point": 10,  "unit_cost": 17500},
    "SKU-004": {"name": "Safety Helmet",    "stock": 300, "reorder_point": 100, "unit_cost": 1000},
    "SKU-005": {"name": "Pressure Gauge",   "stock": 42,  "reorder_point": 40,  "unit_cost": 4500},
}

# How many units of each item we use per day (on average)
DAILY_DEMAND = {"SKU-001": 8, "SKU-002": 3, "SKU-003": 2, "SKU-004": 15, "SKU-005": 6}


# ----------------------------------------------------------------------------
# Tools. The docstring is what the LLM reads to decide WHICH tool to use, so it must be clear.
# ----------------------------------------------------------------------------
@tool
def get_stock_level(sku: str) -> str:
    """Return current stock level and reorder point for a given SKU."""
    sku = sku.upper()
    item = INVENTORY.get(sku)
    if not item:
        return f"SKU {sku} not found."
    status = "LOW" if item["stock"] <= item["reorder_point"] else "OK"
    return f"{item['name']} ({sku}): stock={item['stock']}, reorder_point={item['reorder_point']}, status={status}"


@tool
def calculate_reorder_quantity(sku: str, lead_time_days: int = 7) -> str:
    """Calculate recommended reorder quantity for a SKU given supplier lead time in days."""
    sku = sku.upper()
    item = INVENTORY.get(sku)
    if not item:
        return f"SKU {sku} not found."
    daily = DAILY_DEMAND.get(sku, 1)
    # Simple rule of thumb:
    #   demand during delivery wait  = daily demand x lead time
    #   safety buffer                = the same amount again (in case of delays / spikes)
    #   order                        = (wait demand + buffer) - what we already have
    lead_time_demand = daily * lead_time_days
    safety_buffer = lead_time_demand
    reorder_qty = max(lead_time_demand + safety_buffer - item["stock"], 0)
    total_cost = reorder_qty * item["unit_cost"]
    return (
        f"{item['name']} ({sku}): recommend ordering {reorder_qty} units "
        f"(lead_time_demand={lead_time_demand}, safety_buffer={safety_buffer}, "
        f"lead_time={lead_time_days}d, estimated_cost=Rs {total_cost:,})"
    )


@tool
def days_until_stockout(sku: str) -> str:
    """Estimate how many days until a SKU runs out of stock at current demand rate."""
    sku = sku.upper()
    item = INVENTORY.get(sku)
    if not item:
        return f"SKU {sku} not found."
    daily = DAILY_DEMAND.get(sku, 1)
    days = item["stock"] / daily
    return f"{item['name']} ({sku}): {days:.1f} days until stockout (stock={item['stock']}, daily_demand={daily})"


# ----- TODO 1 (solved): Write a 4th tool that lists every SKU at or below its reorder point -----
@tool
def list_low_stock_items() -> str:
    """List all SKUs that are at or below their reorder point and need restocking."""
    low = [
        f"{sku} ({item['name']}): stock={item['stock']}, reorder_point={item['reorder_point']}"
        for sku, item in INVENTORY.items()
        if item["stock"] <= item["reorder_point"]
    ]
    if not low:
        return "All items are adequately stocked."
    return f"Items needing reorder ({len(low)} total): " + "; ".join(low)


# ----- TODO 2 (solved): Put all four tools in a list, build tool_map, and bind the tools to the LLM -----
tools = [get_stock_level, calculate_reorder_quantity, days_until_stockout, list_low_stock_items]
tool_map = {t.name: t for t in tools}

llm = ChatOpenAI(model="gpt-6-luna", reasoning_effort="none")
llm_with_tools = llm.bind_tools(tools)


def chat_with_tools(user_message: str) -> str:
    """Same 4-step loop as Exercise 3.2."""
    messages = [HumanMessage(content=user_message)]
    response = llm_with_tools.invoke(messages)
    messages.append(response)

    if not response.tool_calls:
        return response.text  # .text = the answer as plain text

    for tc in response.tool_calls:
        result = tool_map[tc["name"]].invoke(tc["args"])
        print(f"   [tool] {tc['name']}({tc['args']}) -> {result}")
        messages.append(ToolMessage(content=str(result), tool_call_id=tc["id"]))

    return llm_with_tools.invoke(messages).text


if __name__ == "__main__":
    questions = [
        "What is the current stock level for SKU-003?",

    ]
    for q in questions:
        print(f"\nQ: {q}")

Think about it

  1. In 3.3, how did the LLM know that "my supplier takes 10 days" should become lead_time_days=10?
  2. What would happen if two tools had the same description, for example "Get info about a SKU"?
  3. Why do we send tool_call_id back with every tool result?
  4. Our 3.1–3.3 code calls the LLM at most twice. Think of a question that would need two tools one after the other. What would break?
  5. Is it safe to let an LLM call any function? Give one tool you would never expose without a human check.
Show the answers
1. How did "my supplier takes 10 days" become lead_time_days=10?

The tool menu says calculate_reorder_quantity takes lead_time_days: int and its description mentions "supplier lead time in days". The LLM matches the phrase to the parameter and fills it in. Clear parameter names and descriptions make this reliable.

2. Two tools with the same description?

The LLM cannot tell them apart, so it picks one more or less at random, or calls both. Every tool needs a description that says exactly when to use it.

3. Why send tool_call_id?

The LLM can ask for several tools at once. The id links each result to the request it answers, like a table number on a restaurant order slip. The API rejects results without a matching id.

4. A question needing two tools in a row?

Example: "Look up SKU-005, then calculate its reorder point" (the second tool needs the first tool's output). Our code calls tools once and then forces a final answer, so the second step never happens. The fix is a loop: keep calling the LLM until it stops asking for tools. You build exactly that in Module 4, Step 06.

5. Is it safe to expose any function?

No. Read-only tools (look up stock) are low risk. Tools that change the world (place a purchase order, send money, delete records, send emails) should need a human "approve" step, and should check their inputs, because the LLM can misunderstand or be tricked by text it reads.
